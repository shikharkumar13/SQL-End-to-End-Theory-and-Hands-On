Yesterday ended with a hint: cloud warehouses are fast because they read less, only the columns a query needs. That idea is the whole of today. A query is slow when the database has to read too much to answer it. On Day 3 you met indexes on the tiny practice tables, where they couldn't make any visible difference, and we promised to come back with a much bigger table. Today you'll build one with over a million rows, count exactly how many rows MySQL reads, and learn the tool that shows you its plan before you wait for it: EXPLAIN.

Before you start. Today uses a new practice database, perf_lab, created in section 1 from the shop's website data. It takes about 160 MB of disk space and around 10 seconds to build. Your other databases aren't changed. Some outputs show times in milliseconds: yours will be different, because they depend on your computer. The row counts will be the same.

1Why queries get slow

Imagine finding one customer's file in an office. If the files are in a pile, you check every folder until you find it. If they're in a cabinet sorted by name, you open the right drawer and pull it out. Same office, same files, very different amount of work. Databases are the same: the time a query takes depends mostly on how much data the database has to read to answer it.

Our shop's tables are too small to feel this. Even the biggest, web_events, has 53,024 rows, which MySQL reads in a blink. So let's make a practice table that's 20 times bigger: 20 copies of the website events, each copy moved 92 days further back in time and given its own customer numbers, as if the shop had five years of tracking for a much larger customer base:

Build 1: a table with a million rows
DROP DATABASE IF EXISTS perf_lab;
CREATE DATABASE perf_lab;
USE perf_lab;

CREATE TABLE events (
    event_id    BIGINT AUTO_INCREMENT PRIMARY KEY,
    session_id  VARCHAR(20) NOT NULL,
    customer_id INT,
    event_time  DATETIME    NOT NULL,
    event_type  VARCHAR(30) NOT NULL,
    product_id  INT,
    device      VARCHAR(20)
);

INSERT INTO events (session_id, customer_id, event_time, event_type, product_id, device)
WITH RECURSIVE copies AS (                  -- 0, 1, 2 ... 19 (Day 16)
    SELECT 0 AS n UNION ALL SELECT n + 1 FROM copies WHERE n < 19
)
SELECT CONCAT(w.session_id, '-', c.n),
       w.customer_id + c.n * 3100,          -- each copy gets its own customers
       w.event_time - INTERVAL c.n * 92 DAY,
       w.event_type,
       w.product_id,
       LOWER(TRIM(w.device))
FROM online_store_full.web_events w
CROSS JOIN copies c;                        -- every event, 20 times (Day 7)
SQL
SELECT COUNT(*)                    AS events,
       MIN(event_time)             AS first_event,
       MAX(event_time)             AS last_event,
       COUNT(DISTINCT customer_id) AS customers
FROM events;
Result
+---------+---------------------+---------------------+-----------+
| events  | first_event         | last_event          | customers |
+---------+---------------------+---------------------+-----------+
| 1060480 | 2019-12-19 00:00:02 | 2024-12-31 23:55:57 |     49020 |
+---------+---------------------+---------------------+-----------+

Just over a million rows, five years, about 49,000 logged-in customers. It's a practice table, made from real patterns, and big enough for the differences to show. Right now, its only index is the primary key.

2Reading the plan: EXPLAIN

Before MySQL runs a query, its optimizer decides how: which table to read first, whether to use an index, how to sort. That decision is called the query plan. Put EXPLAIN in front of any query, and MySQL shows you the plan without running the query. Let's find every event for customer 181:

SQL
EXPLAIN
SELECT event_time, event_type
FROM events
WHERE customer_id = 181;
Result
+----+-------------+--------+------------+------+---------------+------+---------+------+---------+----------+-------------+
| id | select_type | table  | partitions | type | possible_keys | key  | key_len | ref  | rows    | filtered | Extra       |
+----+-------------+--------+------------+------+---------------+------+---------+------+---------+----------+-------------+
|  1 | SIMPLE      | events | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 1060480 |    10.00 | Using where |
+----+-------------+--------+------------+------+---------------+------+---------+------+---------+----------+-------------+

Wide, but you only need four columns:

ColumnWhat it tells youHere
typeHow the table is read. From worst to best: ALL (every row), index (every entry of an index), range (a slice of an index), ref (all rows matching one value), eq_ref and const (exactly one row)ALL: a full table scan
keyThe index it chose, if anyNULL: no index
rowsHow many rows it expects to read. An estimate, not an exact countabout a million
ExtraExtra work, good or bad: Using where, Using index, Using filesort, Using temporaryUsing where: filter each row as it's read

The plan says: read every row, and keep the ones for customer 181. To see what actually happens, MySQL keeps counters of how many rows it has read in your session. FLUSH STATUS sets them back to zero, then you run the query, then you look:

SQL
FLUSH STATUS;

SELECT COUNT(*) AS events_for_181
FROM events
WHERE customer_id = 181;

SHOW SESSION STATUS
WHERE Variable_name IN ('Handler_read_key', 'Handler_read_next', 'Handler_read_rnd_next');
Result
+----------------+
| events_for_181 |
+----------------+
|             45 |
+----------------+
+-----------------------+---------+
| Variable_name         | Value   |
+-----------------------+---------+
| Handler_read_key      | 1       |
| Handler_read_next     | 0       |
| Handler_read_rnd_next | 1060481 |
+-----------------------+---------+

Handler_read_rnd_next counts rows read one after another in a full scan: 1,060,481, to find 45 events. (Every row, plus one last read that finds the end of the table.) Over 99.99% of that work was wasted. And EXPLAIN ANALYZE runs the query and shows the plan with real timings:

SQL
EXPLAIN ANALYZE
SELECT event_time, event_type
FROM events
WHERE customer_id = 181;
Result
-> Filter: (`events`.customer_id = 181)  (cost=106048 rows=106048) (actual time=21.3..253 rows=45 loops=1)
    -> Table scan on events  (cost=106048 rows=1.06e+6) (actual time=0.159..202 rows=1.06e+6 loops=1)

Read it from the innermost line outward: a table scan read about a million rows (rows=1.06e+6), and then a filter kept 45. actual time is in milliseconds (the second number is when the step finished): a few hundred milliseconds, on the computer that built this page. That sounds fast, but it's for one customer. A dashboard that looks up thousands of customers, on a table a hundred times bigger, can't work like this. (FLUSH STATUS needs the RELOAD privilege, or the narrower FLUSH_STATUS privilege that MySQL 8 added. If you're logged in as root on your own computer, you have it.)

3How an index works

Day 3 compared an index to the index at the back of a textbook. Here's what it really is inside. Think of an old paper dictionary. You don't read it from the first page. You open it somewhere near the middle, see you're at "M", flip back towards "H", then to "He", and in three or four jumps you're on the right page. You can do that because the words are sorted, and each page tells you which words it covers.

A MySQL index is a sorted structure called a B-tree, built the same way. The top page (the root) says which range of values lives in which page below it. Those pages point further down, until the bottom pages (the leaves) hold the values themselves, in order. Each page points to hundreds of pages below, so even a million rows need only three or four jumps from the root to the right leaf. And because the leaves are in order, "all the values from here to there" is just a walk along them.

Two kinds of index matter in MySQL's InnoDB engine:

  • The primary key is the table. InnoDB stores the rows themselves in a B-tree sorted by the primary key. That's why finding a row by ID is always fast (Day 3).
  • Every other index (a secondary index) stores its column's values in order, and next to each one, the row's primary key. Finding a row is two steps: look up the value in the secondary index, then use the primary key to fetch the rest of the row. Remember that second step, because it matters in sections 4 and 5.
The path to customer 181: root, branch, leafEach entry is customer_id | event_id (numbers made up for the picture)

Now give customer_id an index:

Build 2: an index on customer_id
CREATE INDEX idx_events_customer ON events (customer_id);

Building it took MySQL a moment, because it had to sort a million values. Now the same query:

SQL
EXPLAIN
SELECT event_time, event_type
FROM events
WHERE customer_id = 181;
Result
+----+-------------+--------+------------+------+---------------------+---------------------+---------+-------+------+----------+-------+
| id | select_type | table  | partitions | type | possible_keys       | key                 | key_len | ref   | rows | filtered | Extra |
+----+-------------+--------+------------+------+---------------------+---------------------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | events | NULL       | ref  | idx_events_customer | idx_events_customer | 5       | const |   45 |   100.00 | NULL  |
+----+-------------+--------+------------+------+---------------------+---------------------+---------+-------+------+----------+-------+

type is now ref (all the rows matching one value), key is our new index, and the estimate is 45 rows. Count what really happens:

SQL
FLUSH STATUS;

SELECT COUNT(*) AS events_for_181
FROM events
WHERE customer_id = 181;

SHOW SESSION STATUS
WHERE Variable_name IN ('Handler_read_key', 'Handler_read_next', 'Handler_read_rnd_next');
Result
+----------------+
| events_for_181 |
+----------------+
|             45 |
+----------------+
+-----------------------+-------+
| Variable_name         | Value |
+-----------------------+-------+
| Handler_read_key      | 1     |
| Handler_read_next     | 45    |
| Handler_read_rnd_next | 0     |
+-----------------------+-------+

One jump into the index (Handler_read_key), then 45 steps along it (Handler_read_next), and zero rows scanned. From 1,060,481 rows read to 46.

SQL
EXPLAIN ANALYZE
SELECT event_time, event_type
FROM events
WHERE customer_id = 181;
Result
-> Index lookup on events using idx_events_customer (customer_id=181)  (cost=5.25 rows=45) (actual time=0.0672..0.132 rows=45 loops=1)

An index lookup instead of a table scan, and the time drops from hundreds of milliseconds to a fraction of one millisecond: hundreds to thousands of times faster, depending on the run. On a table ten times bigger, the scan would take ten times longer. The lookup would barely change, because the tree would be only a little deeper.

4When an index can't help

Having an index doesn't mean MySQL can use it. There are three common reasons it can't, and you've met two of them already.

1. A function wrapped around the column

Day 12 warned against WHERE YEAR(order_date) = 2024 and promised the reason today. Add an index on event_time, then count the events on 20 November 2024 two ways:

Build 3: an index on event_time
CREATE INDEX idx_events_time ON events (event_time);
SQL
FLUSH STATUS;

SELECT COUNT(*) AS events_on_20_nov
FROM events
WHERE DATE(event_time) = '2024-11-20';           -- a function on the column

SHOW SESSION STATUS
WHERE Variable_name IN ('Handler_read_key', 'Handler_read_next', 'Handler_read_rnd_next');
Result
+------------------+
| events_on_20_nov |
+------------------+
|              779 |
+------------------+
+-----------------------+---------+
| Variable_name         | Value   |
+-----------------------+---------+
| Handler_read_key      | 1       |
| Handler_read_next     | 1060480 |
| Handler_read_rnd_next | 0       |
+-----------------------+---------+
SQL
FLUSH STATUS;

SELECT COUNT(*) AS events_on_20_nov
FROM events
WHERE event_time >= '2024-11-20' AND event_time < '2024-11-21';   -- the column left bare

SHOW SESSION STATUS
WHERE Variable_name IN ('Handler_read_key', 'Handler_read_next', 'Handler_read_rnd_next');
Result
+------------------+
| events_on_20_nov |
+------------------+
|              779 |
+------------------+
+-----------------------+-------+
| Variable_name         | Value |
+-----------------------+-------+
| Handler_read_key      | 1     |
| Handler_read_next     | 779   |
| Handler_read_rnd_next | 0     |
+-----------------------+-------+

Same answer, 779 events. But the first version read 1,060,480 index entries, and the second read 779. The index is sorted by event_time, not by DATE(event_time). MySQL can't know where "dates equal to 20 November" begin without calculating DATE() for every entry, so it walks the whole index. With the bare column and Day 12's half-open range, it jumps to the first 20 November entry and stops at the first 21 November one. A condition that can use an index like this is called sargable.

The same goes for a leading wildcard, like Day 17's LIKE '%fit%': an index sorted by the start of the text can't help find text that could begin anywhere. LIKE 'fit%' can use it.

2. Comparing different types

If a column is text and you compare it with a number, such as WHERE session_id = 123, MySQL has to convert every stored value to a number before comparing, which is a hidden function on the column, so an index on session_id couldn't be used. Compare like with like: WHERE session_id = '123'. (Day 11's lesson about types, in a new place.)

3. The index doesn't narrow things down enough

An index is great at finding a few rows. Ask it for most of the table, and it can be slower than not using it at all. Remember the second step from section 3: for each match, MySQL jumps from the index back to the table to fetch the row. A million jumps to scattered places is much more work than one straight read through the table. Let's see it. More than two-thirds of all events come from mobile:

Build 4: an index on device
CREATE INDEX idx_events_device ON events (device);
SQL
EXPLAIN ANALYZE
SELECT COUNT(event_time)
FROM events
WHERE device = 'mobile';
Result
-> Aggregate: count(`events`.event_time)  (cost=109905 rows=1) (actual time=2870..2870 rows=1 loops=1)
    -> Index lookup on events using idx_events_device (device='mobile')  (cost=56916 rows=529894) (actual time=0.974..2823 rows=730380 loops=1)
SQL
EXPLAIN ANALYZE
SELECT COUNT(event_time)
FROM events IGNORE INDEX (idx_events_device)     -- tell MySQL not to use it
WHERE device = 'mobile';
Result
-> Aggregate: count(`events`.event_time)  (cost=160114 rows=1) (actual time=490..490 rows=1 loops=1)
    -> Filter: (`events`.device = 'mobile')  (cost=107125 rows=529894) (actual time=0.105..446 rows=730380 loops=1)
        -> Table scan on events  (cost=107125 rows=1.06e+6) (actual time=0.102..287 rows=1.06e+6 loops=1)

MySQL chose the index, and it was several times slower than a plain table scan, which IGNORE INDEX forced for comparison. Two lessons. First, an index helps when it's selective: when each value matches a small share of the rows. customer_id is very selective. device, with three values, isn't. Second, the optimizer isn't perfect. Its decision is based on estimates (here, it expected just over half a million mobile rows, and there were 730,380), and estimates can be wrong. That's why you measure, and don't just trust a plan. A column with only a few different values is usually a poor choice for an index of its own.

5Composite and covering indexes

Real questions often filter on two columns: "customer 181's events in December". The single customer_id index finds the customer's 45 events, and then each one is checked for the date. An index on both columns can find exactly the right ones:

Build 5: a composite index
CREATE INDEX idx_events_customer_time ON events (customer_id, event_time);
SQL
FLUSH STATUS;

SELECT COUNT(*) AS december_events
FROM events IGNORE INDEX (idx_events_customer_time)   -- the old way: customer index only
WHERE customer_id = 181 AND event_time >= '2024-12-01';

SHOW SESSION STATUS
WHERE Variable_name IN ('Handler_read_key', 'Handler_read_next');
Result
+-----------------+
| december_events |
+-----------------+
|              25 |
+-----------------+
+-------------------+-------+
| Variable_name     | Value |
+-------------------+-------+
| Handler_read_key  | 1     |
| Handler_read_next | 45    |
+-------------------+-------+
SQL
FLUSH STATUS;

SELECT COUNT(*) AS december_events
FROM events                                           -- now MySQL can use the new index
WHERE customer_id = 181 AND event_time >= '2024-12-01';

SHOW SESSION STATUS
WHERE Variable_name IN ('Handler_read_key', 'Handler_read_next');
Result
+-----------------+
| december_events |
+-----------------+
|              25 |
+-----------------+
+-------------------+-------+
| Variable_name     | Value |
+-------------------+-------+
| Handler_read_key  | 1     |
| Handler_read_next | 25    |
+-------------------+-------+

45 entries read, then 25. A composite index is sorted by the first column, and within each value of it, by the second, like a phone book sorted by surname and then by first name. Inside customer 181's part of the index, the events are already in time order, so MySQL jumps straight to 1 December and reads only the 25 that match. On a customer with thousands of events, that difference is big.

The phone book also explains the most important rule, the leftmost prefix rule. A phone book sorted by surname, then first name, makes it easy to find "Sharma", and easy to find "Sharma, Priya". It's no help at all for finding everyone called "Priya", because Priyas are scattered across every surname. In the same way, an index on (customer_id, event_time) helps queries on customer_id, or on customer_id and event_time together, but not on event_time alone. (At best, MySQL can read the whole index from start to end, which EXPLAIN shows as type: index. MySQL 8 also has a "skip scan" for when the first column has only a few different values, but with tens of thousands of customers, it doesn't apply.) So the order of the columns matters: put the column you filter with = first, and the range (>=, BETWEEN) second.

Covering indexes: skipping the table altogether

Remember the second step, from the index back to the table to fetch the row? If every column the query needs is already in the index, MySQL can skip that step. Compare these two plans, which differ only in the column selected:

SQL
EXPLAIN
SELECT event_time
FROM events
WHERE customer_id = 181 AND event_time >= '2024-12-01';
Result
+----+-------------+--------+------------+-------+--------------------------------------------------------------+--------------------------+---------+------+------+----------+--------------------------+
| id | select_type | table  | partitions | type  | possible_keys                                                | key                      | key_len | ref  | rows | filtered | Extra                    |
+----+-------------+--------+------------+-------+--------------------------------------------------------------+--------------------------+---------+------+------+----------+--------------------------+
|  1 | SIMPLE      | events | NULL       | range | idx_events_customer,idx_events_time,idx_events_customer_time | idx_events_customer_time | 10      | NULL |   25 |   100.00 | Using where; Using index |
+----+-------------+--------+------------+-------+--------------------------------------------------------------+--------------------------+---------+------+------+----------+--------------------------+
SQL
EXPLAIN
SELECT event_type
FROM events
WHERE customer_id = 181 AND event_time >= '2024-12-01';
Result
+----+-------------+--------+------------+-------+--------------------------------------------------------------+--------------------------+---------+------+------+----------+-----------------------+
| id | select_type | table  | partitions | type  | possible_keys                                                | key                      | key_len | ref  | rows | filtered | Extra                 |
+----+-------------+--------+------------+-------+--------------------------------------------------------------+--------------------------+---------+------+------+----------+-----------------------+
|  1 | SIMPLE      | events | NULL       | range | idx_events_customer,idx_events_time,idx_events_customer_time | idx_events_customer_time | 10      | NULL |   25 |   100.00 | Using index condition |
+----+-------------+--------+------------+-------+--------------------------------------------------------------+--------------------------+---------+------+------+----------+-----------------------+

The first says Using index in Extra: everything it needs (customer_id, event_time) is in the composite index, so it never touches the table. That's called a covering index. The second uses the same index to find the same 25 entries, but Extra says Using index condition instead: event_type isn't in the index, so for each of the 25, MySQL makes the second step back to the table to fetch it. 25 extra trips is nothing. On a query matching 100,000 rows, it's 100,000 trips. This is one more reason for Day 5's habit of selecting only the columns you need: sometimes it's the difference between reading the index alone and reading the table too.

6Sorting, grouping and joins

ORDER BY with LIMIT

"Show the 5 most recent events" is a very common query. With an index on event_time, the rows are already sorted inside the index:

SQL
EXPLAIN
SELECT event_id, event_time, event_type
FROM events
ORDER BY event_time DESC
LIMIT 5;
Result
+----+-------------+--------+------------+-------+---------------+-----------------+---------+------+------+----------+---------------------+
| id | select_type | table  | partitions | type  | possible_keys | key             | key_len | ref  | rows | filtered | Extra               |
+----+-------------+--------+------------+-------+---------------+-----------------+---------+------+------+----------+---------------------+
|  1 | SIMPLE      | events | NULL       | index | NULL          | idx_events_time | 5       | NULL |    5 |   100.00 | Backward index scan |
+----+-------------+--------+------------+-------+---------------+-----------------+---------+------+------+----------+---------------------+
SQL
EXPLAIN
SELECT event_id, event_time, event_type
FROM events IGNORE INDEX (idx_events_time)
ORDER BY event_time DESC
LIMIT 5;
Result
+----+-------------+--------+------------+------+---------------+------+---------+------+---------+----------+----------------+
| id | select_type | table  | partitions | type | possible_keys | key  | key_len | ref  | rows    | filtered | Extra          |
+----+-------------+--------+------------+------+---------------+------+---------+------+---------+----------+----------------+
|  1 | SIMPLE      | events | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 1059789 |   100.00 | Using filesort |
+----+-------------+--------+------------+------+---------------+------+---------+------+---------+----------+----------------+

With the index, MySQL reads it from the end (Backward index scan) and stops after 5 rows. Without it, it has to read the whole table and sort a million rows (Using filesort) just to keep 5. Using filesort on a big table is a warning sign. (The name is old: it means "a sort done separately", and it doesn't always use a file.)

GROUP BY

SQL
EXPLAIN
SELECT event_type, COUNT(*)
FROM events
GROUP BY event_type;
Result
+----+-------------+--------+------------+------+---------------+------+---------+------+---------+----------+-----------------+
| id | select_type | table  | partitions | type | possible_keys | key  | key_len | ref  | rows    | filtered | Extra           |
+----+-------------+--------+------------+------+---------------+------+---------+------+---------+----------+-----------------+
|  1 | SIMPLE      | events | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 1059789 |   100.00 | Using temporary |
+----+-------------+--------+------------+------+---------------+------+---------+------+---------+----------+-----------------+

Using temporary: MySQL builds a temporary table to hold one row per group while it reads the whole table. With 5 event types, that's harmless. Grouping a big table by a column with millions of different values is where it becomes expensive. An index on the grouping column lets MySQL read the groups already sorted, without a temporary table. Try it in Try this, question 4.

Joins

For the last two plans, switch back to the shop's database. Here's a join between customers and their orders:

SQL
USE online_store_full;

EXPLAIN FORMAT=TREE
SELECT c.first_name, o.order_id
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE c.city = 'Pune';
Result
-> Nested loop inner join  (cost=732 rows=870)
    -> Filter: (c.city = 'Pune')  (cost=334 rows=310)
        -> Table scan on c  (cost=334 rows=3103)
    -> Covering index lookup on o using customer_id (customer_id=c.customer_id)  (cost=1 rows=2.8)

FORMAT=TREE shows the plan as steps, read from the innermost outward, like EXPLAIN ANALYZE without running the query. MySQL scans customers for the Pune customers, then, for each one, uses the index on orders.customer_id to find their orders. That index exists because it's a foreign key (Day 3). The plan even says Covering: the query needs only order_id from orders, and as the primary key, it's stored in every secondary index, so MySQL never visits the orders table at all. Without that index, every customer would mean a full scan of orders. That's the most important indexing rule for joins: index the columns you join on, which usually means the foreign keys.

And now Day 8's promise. Day 8 said that IN, EXISTS and a join often run the same way behind the scenes, so you should pick the clearest one. Here are the plans for "how many customers have a completed order?", written with IN and with EXISTS:

SQL
EXPLAIN FORMAT=TREE
SELECT COUNT(*) FROM customers c
WHERE c.customer_id IN (SELECT o.customer_id FROM orders o WHERE o.status = 'Completed');

EXPLAIN FORMAT=TREE
SELECT COUNT(*) FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o
              WHERE o.customer_id = c.customer_id AND o.status = 'Completed');
Result
-> Aggregate: count(0)  (cost=390692 rows=1)
    -> Nested loop inner join  (cost=195668 rows=1.95e+6)
        -> Index scan on c using PRIMARY  (cost=334 rows=3103)
        -> Single-row index lookup on <subquery2> using <auto_distinct_key> (customer_id=c.customer_id)  (cost=715..715 rows=1)
            -> Materialize with deduplication  (cost=714..714 rows=629)
                -> Filter: (o.`status` = 'Completed')  (cost=652 rows=629)
                    -> Table scan on o  (cost=652 rows=6285)

-> Aggregate: count(0)  (cost=390692 rows=1)
    -> Nested loop inner join  (cost=195668 rows=1.95e+6)
        -> Index scan on c using PRIMARY  (cost=334 rows=3103)
        -> Single-row index lookup on <subquery2> using <auto_distinct_key> (customer_id=c.customer_id)  (cost=715..715 rows=1)
            -> Materialize with deduplication  (cost=714..714 rows=629)
                -> Filter: (o.`status` = 'Completed')  (cost=652 rows=629)
                    -> Table scan on o  (cost=652 rows=6285)

Two different-looking queries, exactly the same plan. MySQL rewrote both into the same form (a semijoin: "keep each customer once if a match exists"). So for IN versus EXISTS, choose whichever reads better. A plain join would be planned differently, and it would also need COUNT(DISTINCT ...), because a customer with three orders would appear three times (Day 7). When you're unsure whether two versions differ in speed, don't guess: compare their plans.

7What indexes cost

If indexes are this good, why not index every column? Day 3 gave the short answer: they make writing slower and take space. Here's the space, measured:

SQL
USE perf_lab;
ANALYZE TABLE events;

SELECT ROUND(data_length  / 1024 / 1024) AS table_mb,
       ROUND(index_length / 1024 / 1024) AS other_indexes_mb
FROM information_schema.tables
WHERE table_schema = 'perf_lab' AND table_name = 'events';
Result
+-----------------+---------+----------+----------+
| Table           | Op      | Msg_type | Msg_text |
+-----------------+---------+----------+----------+
| perf_lab.events | analyze | status   | OK       |
+-----------------+---------+----------+----------+
+----------+------------------+
| table_mb | other_indexes_mb |
+----------+------------------+
|       72 |               91 |
+----------+------------------+

(ANALYZE TABLE refreshes MySQL's statistics about a table, including the sizes and the row estimates that EXPLAIN uses. data_length is the table itself, the primary key's tree, and index_length is all the other indexes.) Our four extra indexes together take more space than the table itself. And every one of them has to be updated whenever a row is inserted, changed or deleted. A table that receives thousands of new rows a second, like real website tracking, pays for every index on every write.

So the rule is: index for the queries you actually run. Index the columns you join on, filter on and sort by often, prefer one good composite index over several single ones, and remove indexes nobody uses. Our device index made a query slower, so it's a good candidate for removal:

Build 6: drop an index that doesn't earn its place
DROP INDEX idx_events_device ON events;

In real jobs, analysts often can't add indexes. The shop's live database belongs to the engineering team, and an index on a huge, busy table is a change they need to plan. What you can do: write sargable queries, select fewer columns, filter early, and if a query you run every day is slow, bring the EXPLAIN output to the team. "This runs a full scan on 50 million rows, and an index on (customer_id, event_time) would make it a lookup" is a request engineers take seriously. Many companies also give analysts a read replica, a copy of the database just for reading, so heavy queries can't slow down the shop. And in warehouses (Day 17), speed comes from different tricks: storing data by column, splitting big tables by date (called partitioning), and summary tables.

And a step-by-step routine for a query that's too slow:

  1. Run EXPLAIN. Look for type: ALL on a big table, a huge rows estimate, Using filesort or Using temporary on many rows.
  2. Find the step that reads too much. In a long query, EXPLAIN ANALYZE shows the actual rows and time of every step.
  3. Ask why it can't use an index. Is there no index, a function on the column, a type mismatch, a leading wildcard, or a column with too few distinct values?
  4. Fix the query first (make it sargable, select fewer columns, filter earlier), and only then ask whether an index is needed.
  5. Measure again. Count rows read, and compare plans. Don't trust a change that you haven't measured.

🎯 Interview corner

Performance questions separate people who write SQL from people who understand how it runs. You won't be expected to tune a database, but you will be expected to explain indexes and read a plan.

Concept questions

Q1What is an index, and how does it make queries faster?

A separate, sorted structure (in MySQL, a B-tree) that maps column values to the rows that contain them. Because it's sorted and organised as a shallow tree, MySQL can find a value in a few steps and read a range by walking along the leaves, instead of scanning every row in the table.

Q2What's the difference between a clustered and a secondary index?

In InnoDB, the clustered index is the table itself, stored sorted by the primary key, so a primary key lookup goes straight to the row. A secondary index stores the indexed column's values plus the primary key. A lookup finds the value, then uses the primary key to fetch the row, unless the index covers every column the query needs.

Q3Why might MySQL not use an index you created?

A function or calculation on the column (YEAR(col) = 2024), a type conversion (a text column compared with a number), a leading wildcard (LIKE '%x'), a composite index whose first column isn't used, or low selectivity, where the optimizer judges a full scan cheaper. Its estimates can also be wrong, which is why you measure.

Q4What does "sargable" mean?

A condition that can use an index to narrow the search: the column stands alone on one side of the comparison. order_date >= '2024-01-01' AND order_date < '2025-01-01' is sargable. YEAR(order_date) = 2024 isn't, because MySQL would have to calculate the function for every row.

Q5What is a composite index, and what is the leftmost prefix rule?

An index on several columns, sorted by the first, then the second within it, and so on. It can be used for searches on the first column, the first two, and so on, but not for later columns alone, like a phone book sorted by surname that can't find people by first name. Put equality columns first and range columns last.

Q6What is a covering index?

An index that contains every column a query needs, so MySQL answers from the index alone without visiting the table. EXPLAIN shows Using index. It's the fastest kind of lookup, and another reason to select only the columns you need.

Q7How do you read EXPLAIN? What are the warning signs?

Look at type (ALL is a full scan, and ref, range, eq_ref and const use an index), key (the index chosen), rows (estimated rows read) and Extra. Warning signs on big tables: type: ALL, huge rows, Using filesort, Using temporary. EXPLAIN ANALYZE runs the query and shows actual rows and times for each step.

Q8Why not index every column?

Each index takes disk space (here, four indexes were bigger than the table itself) and must be updated on every insert, update and delete, which slows writes. Indexes on low-selectivity columns may not even be used, or can make queries slower. Index for the queries you actually run, and remove unused indexes.

Q9Is EXISTS faster than IN?

Often neither: modern MySQL rewrites both into the same semijoin plan, as EXPLAIN shows, so choose the clearer one. The real difference is with NOT IN when the subquery can return NULL, which changes the result, not just the speed (Day 5). When it matters, compare the plans rather than relying on rules of thumb.

Practical questions

P1A dashboard runs this every minute and it's slow. What index would you suggest? SELECT order_id, order_date FROM orders WHERE customer_id = ? AND status = 'Completed' ORDER BY order_date DESC LIMIT 10

A composite index on (customer_id, status, order_date). The two equality columns go first, so MySQL jumps straight to one customer's completed orders, and order_date last, so those rows are already sorted and MySQL can read the newest 10 and stop, with no filesort. If you also added order_id it would be covering, but in InnoDB the primary key is stored in every secondary index anyway, so it's covered already. Then confirm with EXPLAIN: you're hoping for ref and no Using filesort.

P2Rewrite these conditions so they can use an index on the column: YEAR(order_date) = 2024, DATE(created_at) = '2024-11-20', price * 1.18 > 1000.

order_date >= '2024-01-01' AND order_date < '2025-01-01'. created_at >= '2024-11-20' AND created_at < '2024-11-21'. price > 1000 / 1.18. The pattern is always the same: move the calculation to the other side, so the column stands alone.

P3Read this plan and say what's wrong: type: ALL, key: NULL, rows: 48,000,000, Extra: Using where; Using filesort.

MySQL is reading all 48 million rows (no index used), filtering them, and then sorting the survivors separately. Next steps: check which column the WHERE uses and whether it's sargable, then look at whether an index on the filter column, with the sort column second, would let MySQL find the rows and read them already in order. And ask whether the query needs every column it selects.

Quick recap

  • A query's speed depends mostly on how much the database has to read. A full table scan read 1,060,481 rows to find 45 events. With an index, it read 46.
  • EXPLAIN shows the plan. Watch type (ALL is a full scan), key, rows and Extra. EXPLAIN ANALYZE runs the query and shows real rows and times. Session counters (Handler_read_%) count rows actually read.
  • An index is a sorted B-tree. The primary key is the table itself, and secondary indexes point back to it.
  • Indexes can't help with a function on the column, a type mismatch or a leading wildcard, and they can hurt when a value matches a large share of the table.
  • Composite indexes follow the leftmost prefix rule: equality columns first, the range last. Covering indexes answer from the index alone (Using index).
  • Indexes help ORDER BY ... LIMIT avoid Using filesort, and joins use the indexes on foreign keys. IN and EXISTS often get the same plan.
  • Indexes cost space and slow down writes: index for the queries you actually run. Fix the query first, then measure.
