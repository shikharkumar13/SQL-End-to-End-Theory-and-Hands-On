1What DDL does

DDL stands for Data Definition Language. These are the commands that build and change the structure of a database: the database itself, its tables, the columns in each table, and the rules on those columns.

Think of building a house. First you build the walls, the rooms and the cupboards. Only then do you move the furniture in. DDL builds the house. DML (Day 4) moves the furniture in. DQL (Day 5 onwards) is walking around the house and looking at what is where.

DDL has four main commands. Going back to our shop from Day 2:

CommandWhat it doesIn the shop
CREATEMakes a new database, table or indexPut up a new shelf
ALTERChanges a table that already existsAdd a new section to a shelf, or change its label
DROPDeletes a table or database completelyTake the shelf away, with everything on it
TRUNCATERemoves every row but keeps the empty tableClear everything off the shelf, keep the shelf

Today you will use all four, in that order. Most of the time goes into CREATE, because that is where you decide what each table looks like and which rules it follows.

Where to type. Open the tool you picked on Day 2: an online MySQL site, or MySQL Workbench on your own computer. Every code box below has a Copy button. Paste the code, run it, and compare what you see with the result shown under it.

2Create the database

Picture MySQL as a big office building. Each database is one office inside it, and the tables are the cupboards inside that office. Before you can put up any cupboards, you need an office of your own.

Create the database and step into it
CREATE DATABASE online_store;
USE online_store;
  • CREATE DATABASE online_store; makes a new, empty database called online_store.
  • USE online_store; is like walking into that office and closing the door. From now on, every table you create lands in online_store. You only need to run USE once each time you open a new session.

To check that it worked, ask MySQL to list every database it has:

SQL
SHOW DATABASES;
Result
+--------------------+
| Database           |
+--------------------+
| information_schema |
| mysql              |
| online_store       |
| performance_schema |
| sys                |
+--------------------+

There it is. The other four are MySQL's own system databases. MySQL uses them to keep track of users and settings, details about every table, and how the server is performing. Look, but don't change anything in them.

Not sure which database you are inside right now? Ask:

SQL
SELECT DATABASE();
Result
online_store

Running it twice

If you run CREATE DATABASE online_store; a second time, MySQL refuses, because the office already exists:

MySQL says
ERROR 1007 (HY000): Can't create database 'online_store'; database exists

If you want a command that is safe to run again and again, add IF NOT EXISTS. When the database is already there, MySQL skips the step and leaves only a small warning instead of an error:

SQL
CREATE DATABASE IF NOT EXISTS online_store;

Using an online MySQL site? Many of them already give you a database and don't let you create a new one. If CREATE DATABASE or USE gives you an error there, skip those two lines and go straight to creating tables. Everything else in this lesson works the same.

3Your first table: categories

Every table is made with CREATE TABLE. The general shape is always the same: a name for the table, then a list of columns inside brackets. Each column gets a name, a data type, and any rules it must follow.

The shape of every CREATE TABLE
CREATE TABLE table_name (
    column_name   data_type   rules,
    column_name   data_type   rules,
    ...
);

A good way to think about this is a paper form, like a bank account opening form. Each column is one box on the form. The data type says what kind of answer goes in the box: a number, some text, a date. The rules are the small print under the box: "required", or "must not match anyone else's".

We start with the simplest table, categories. On Day 2 you saw a short version of it. Here is the full version, with two extra rules:

Create the categories table
CREATE TABLE categories (
    category_id   INT          AUTO_INCREMENT,
    category_name VARCHAR(50)  NOT NULL UNIQUE,
    PRIMARY KEY (category_id)
);

Read it one piece at a time:

PieceWhat it means
category_id INTA column for whole numbers, holding the category's ID.
AUTO_INCREMENTMySQL fills in the ID for you: 1, then 2, then 3, and so on. You never type it yourself.
category_name VARCHAR(50)A text column, up to 50 characters.
NOT NULLEvery category must have a name. A blank one is refused.
UNIQUENo two categories can have the same name. You can't have "Books" twice. By default MySQL ignores capital letters here, so "books" counts as the same name too.
PRIMARY KEY (category_id)category_id is the column that identifies each row (Day 1). It can never be empty and can never repeat.

Notice the commas. Each column line ends with a comma, except the very last line before the closing bracket. A missing or extra comma is the most common reason a CREATE TABLE fails, so check those first when you see an error.

Look at what you built

DESCRIBE shows the columns of a table and the rules on each one:

SQL
DESCRIBE categories;
Result
+---------------+-------------+------+-----+---------+----------------+
| Field         | Type        | Null | Key | Default | Extra          |
+---------------+-------------+------+-----+---------+----------------+
| category_id   | int         | NO   | PRI | NULL    | auto_increment |
| category_name | varchar(50) | NO   | UNI | NULL    |                |
+---------------+-------------+------+-----+---------+----------------+
Column in the outputWhat it tells you
FieldThe column name
TypeThe data type
NullNO means the column can't be left empty
KeyPRI is a primary key, UNI is unique, MUL is a column with an ordinary index where the same value can appear many times. Foreign key columns show up as MUL (you'll see this soon)
DefaultThe value used when you don't give one
ExtraAnything else, like auto_increment

You can also write DESC categories; for short. Both do the same thing.

Two ways to write a primary key. You can put it on the column's own line, like category_id INT AUTO_INCREMENT PRIMARY KEY,, or on a separate line at the bottom like we did. Both give exactly the same table. We use the bottom line in this series because it is easy to spot, and because it is the only way to write a key made of two columns (you'll see this in the Interview corner).

4Constraints: the rules that protect your data

The rules you just used, like NOT NULL and UNIQUE, have a name: constraints. A constraint is a rule that the database checks every single time a row is added or changed.

Think of a security guard standing at the door of each table. Every new row has to show its papers. Is the name filled in? Is this email already taken? Is the price a sensible number? If any rule fails, the guard turns the row away and nothing is saved. Nobody has to remember to check by hand, because the guard never takes a day off.

These are the constraints you will use all the time:

ConstraintThe ruleEveryday example
PRIMARY KEYIdentifies each row. Never empty, never repeated.Your Aadhaar number
FOREIGN KEYMust match a key in the table it points to, usually another table's primary keyA library card number that must exist in the members list
NOT NULLThe column must have a valueA "required" box on a form
UNIQUENo two rows can have the same valueTwo people can't sign up with the same email
DEFAULTFills in a value when none is givenA form where "Country" is already filled in as India
CHECKThe value must pass a test"Age must be 18 or above"
AUTO_INCREMENTMySQL picks the next number for youThe token machine at a bank

AUTO_INCREMENT is not a rule in the strict sense, it is a helper. But you will always see it next to the others, so it belongs in this list.

The customers table

Now let's turn the Day 2 plan for customers into SQL. Look at how each line of the plan becomes a line of code:

Create the customers table
CREATE TABLE customers (
    customer_id INT          AUTO_INCREMENT,
    first_name  VARCHAR(50)  NOT NULL,
    last_name   VARCHAR(50)  NOT NULL,
    email       VARCHAR(100) NOT NULL UNIQUE,
    city        VARCHAR(50),
    country     VARCHAR(50),
    signup_date DATE         NOT NULL,
    PRIMARY KEY (customer_id)
);
ColumnDay 2 plan saidSo we wrote
customer_idUnique number for each customerAUTO_INCREMENT and PRIMARY KEY
first_name, last_nameEvery customer has a nameNOT NULL
emailMust be different for every customerNOT NULL UNIQUE
cityCan be NULLNo rule at all, so it is optional
countryCountryOptional too
signup_dateThe day they joinedDATE NOT NULL

This is the real job of constraints. The shop's business rules ("every customer needs an email, and no two can share one") get written into the table itself. Remember Noah Brown from Day 2, the customer with no city? He can be stored only because we left city optional. If we had written city VARCHAR(50) NOT NULL, the guard would have turned him away.

AUTO_INCREMENT: the token machine

At a bank or a clinic, you pull a token from a machine: 41, then the next person gets 42, then 43. Nobody chooses their own number, and two people never get the same one. AUTO_INCREMENT works the same way for IDs.

Like a token machine, it never goes backwards (the one exception is emptying a table with TRUNCATE, in section 11). If token 42 leaves without being served, the next person still gets 43, not 42. In the same way, if a row is deleted, its number is never handed out again. Some failed inserts use up a number too, for example one turned away for a duplicate value. So gaps like 1, 2, 4 are normal. They are not a bug. This is also why you should never use the biggest ID to count rows. Count the rows instead (Day 6).

DEFAULT: the box that is already filled in

When you order something online, its status starts as "Order placed" before you do anything. Nobody types that in. A DEFAULT does the same job. If a new row comes in without a value for that column, MySQL uses the default. You'll see two of them in the next section:

  • A new product's stock_quantity starts at 0.
  • A new order's status starts as 'Pending'.

CHECK: a test the value must pass

A CHECK lets you write your own rule. A price below zero makes no sense, and nobody buys zero of something. So we will add CHECK (price >= 0) to products and CHECK (quantity > 0) to order lines.

Version warning. MySQL only started obeying CHECK rules in version 8.0.16. Older versions accept the line without complaint and then ignore it, so bad data slips through silently. This is why Day 2 asked you to run SELECT VERSION();. If yours is older, everything else in this lesson still works.

5Foreign keys: linking the tables

Now the most important rule in a relational database: the foreign key. This is what turns five separate tables into one connected database.

Think of a library. You can only borrow a book if your card number is in the members list. The librarian checks the list every time. A foreign key is that librarian. When an order says "customer 7", MySQL checks that customer 7 really exists in customers. If not, the order is refused. An order for a customer who doesn't exist is an order nobody can explain, and the foreign key makes sure it can never happen. This guarantee has a name: referential integrity.

Build order matters

A foreign key points to another table, so that table has to exist first. You can't build the roof before the walls. Here is the order for our five tables:

  1. 1Point to nothingcategories, customers

    No foreign keys, so they can go first. You have already built these two.

  2. 2Point to step 1products, orders

    products points to categories. orders points to customers.

  3. 3Point to step 2order_items

    Points to both orders and products, so it goes last.

Here is what happens if you get the order wrong. Say you try to create products before categories exists:

MySQL says
ERROR 1824 (HY000): Failed to open the referenced table 'categories'

MySQL is saying "you told me to point at categories, but I can't find it". The fix is simple: create categories first, then try again.

The products table

Create the products table
CREATE TABLE products (
    product_id     INT           AUTO_INCREMENT,
    product_name   VARCHAR(100)  NOT NULL,
    category_id    INT,
    price          DECIMAL(10,2) NOT NULL,
    stock_quantity INT           NOT NULL DEFAULT 0,
    PRIMARY KEY (product_id),
    FOREIGN KEY (category_id) REFERENCES categories(category_id),
    CHECK (price >= 0)
);

The new pieces:

  • FOREIGN KEY (category_id) REFERENCES categories(category_id) reads as: "the category_id in this table must match a category_id in the categories table".
  • category_id INT has no NOT NULL. That means a product can exist without a category for now, for example a new item that hasn't been sorted yet. A NULL here is allowed, but a category number that doesn't exist is not.
  • price DECIMAL(10,2) NOT NULL: money goes in DECIMAL, as you learned on Day 2.
  • stock_quantity ... DEFAULT 0: a new product starts with zero stock unless you say otherwise.
  • CHECK (price >= 0): no negative prices.

The orders table

Create the orders table
CREATE TABLE orders (
    order_id    INT          AUTO_INCREMENT,
    customer_id INT          NOT NULL,
    order_date  DATE         NOT NULL,
    status      VARCHAR(20)  NOT NULL DEFAULT 'Pending',
    PRIMARY KEY (order_id),
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

Here customer_id has two rules at once. NOT NULL means every order must belong to someone. The foreign key means that someone must be a real customer. Compare this with products.category_id above, which was allowed to be empty. A product without a category is fine for a while. An order without a customer is not.

status starts as 'Pending' by default, just like a new order on a shopping app.

The order_items table

Last comes the bridge table from Day 2. Each row is one line on a bill, so it points to two tables: the order it belongs to, and the product that was bought.

Create the order_items table
CREATE TABLE order_items (
    order_item_id INT           AUTO_INCREMENT,
    order_id      INT           NOT NULL,
    product_id    INT           NOT NULL,
    quantity      INT           NOT NULL,
    unit_price    DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (order_item_id),
    FOREIGN KEY (order_id)   REFERENCES orders(order_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id),
    CHECK (quantity > 0)
);

A table can have as many foreign keys as it needs. This one has two. And that's it: all five tables now exist and are linked, exactly like the diagram on Day 2.

Going deeper: what happens to orders if a customer is deleted?

Say Aarav has three orders, and someone tries to delete Aarav from customers. His orders would now point to a customer who doesn't exist. MySQL has to decide what to do, and you choose when you write the foreign key, by adding ON DELETE:

OptionWhat happensLike this in real life
RESTRICTThe delete is refused while orders still point to AaravA library won't close your membership while you still have books out
CASCADEAarav is deleted, and all his orders are deleted with himDeleting a WhatsApp group deletes all its messages too
SET NULLAarav is deleted, and his orders stay, with customer_id set to NULLAn employee leaves, their old files stay, with the "owner" box left blank

This is how you would write one of them. Don't run it, it is only here to show the shape:

SQL
FOREIGN KEY (customer_id) REFERENCES customers(customer_id) ON DELETE CASCADE

If you write no ON DELETE at all, MySQL uses NO ACTION, which in MySQL behaves exactly like RESTRICT: the delete is refused. That is what online_store uses. Sales history is the most valuable data a shop has, so it should never disappear by accident because someone deleted a customer. SET NULL would not work for us anyway. orders.customer_id is NOT NULL, and MySQL refuses to create a SET NULL rule on a column that can't hold NULL.

6When a rule is broken

So far the guard has had nothing to do, because the tables are empty. Let's see what happens when bad data tries to get in. You will learn INSERT properly tomorrow. For now, just read each attempt and the message MySQL sends back.

Read these, don't run them. Day 4 expects your five tables to be completely fresh. Even a failed insert can quietly use up an AUTO_INCREMENT number, and then your IDs won't match the lessons. If you have already run something, don't worry. Section 7 shows how to reset everything in one step.

Imagine the tables already hold a few rows: Aarav is saved as a customer with the email aarav.sharma@email.com, and category 1 is Electronics.

1. Two customers with the same email. Someone else signs up with Aarav's address:

Read only: don't run
INSERT INTO customers (first_name, last_name, email, city, country, signup_date)
VALUES ('Riya', 'Mehta', 'aarav.sharma@email.com', 'Pune', 'India', '2023-02-01');
MySQL says
ERROR 1062 (23000): Duplicate entry 'aarav.sharma@email.com' for key 'customers.email'

2. A customer with no first name.

Read only: don't run
INSERT INTO customers (first_name, last_name, email, signup_date)
VALUES (NULL, 'Mehta', 'riya.mehta@email.com', '2023-02-01');
MySQL says
ERROR 1048 (23000): Column 'first_name' cannot be null

3. A product with a negative price.

Read only: don't run
INSERT INTO products (product_name, category_id, price)
VALUES ('Wireless Mouse', 1, -799);
MySQL says
ERROR 3819 (HY000): Check constraint 'products_chk_1' is violated.

4. A product in a category that doesn't exist. There is no category 99:

Read only: don't run
INSERT INTO products (product_name, category_id, price)
VALUES ('Wireless Mouse', 99, 799);
MySQL says
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`online_store`.`products`, CONSTRAINT `products_ibfk_1` FOREIGN KEY (`category_id`) REFERENCES `categories` (`category_id`))

Every one of these rows was turned away, and nothing was saved. That is exactly what we want.

How to read a MySQL error

Error messages look scary at first, but they all follow the same pattern. Take this one:

MySQL says
ERROR 1048 (23000): Column 'first_name' cannot be null
  • 1048 is MySQL's number for this kind of error. If you don't understand a message, search for "MySQL error 1048" and you'll find plenty of help.
  • (23000) is a standard code called SQLSTATE, which most SQL databases share. 23000 means "a rule was broken". You can mostly ignore it.
  • The message names the column or the rule that failed. Read this part first.

You will see the same handful of errors again and again. Here are the ones from today:

ErrorWhat it means in plain English
1062That value already exists in a UNIQUE or primary key column
1048You gave NULL to a NOT NULL column
1364You left out a NOT NULL column that has no default
3819A CHECK rule failed
1452The foreign key points to a row that doesn't exist
1824The table the foreign key points to doesn't exist yet
1050A table with that name already exists
3730You can't drop this table, another table points to it (section 11)

Notice the names in the messages, like products_chk_1 and products_ibfk_1. We never named our rules, so MySQL named them for us: table name, then chk for a check rule or ibfk for a foreign key, then a number. You'll see these names again in section 8.

7The full build script

If you followed along, you already have all five tables. Here is everything in one block, in the right order. This is the same as the schema.sql file in the series' GitHub repository. Running it from top to bottom builds the whole online_store structure from nothing.

schema.sql: the whole structure in one go
CREATE DATABASE online_store;
USE online_store;

-- 1. Categories (no dependencies)
CREATE TABLE categories (
    category_id   INT          AUTO_INCREMENT,
    category_name VARCHAR(50)  NOT NULL UNIQUE,
    PRIMARY KEY (category_id)
);

-- 2. Customers (no dependencies)
CREATE TABLE customers (
    customer_id INT          AUTO_INCREMENT,
    first_name  VARCHAR(50)  NOT NULL,
    last_name   VARCHAR(50)  NOT NULL,
    email       VARCHAR(100) NOT NULL UNIQUE,
    city        VARCHAR(50),
    country     VARCHAR(50),
    signup_date DATE         NOT NULL,
    PRIMARY KEY (customer_id)
);

-- 3. Products (depends on categories)
CREATE TABLE products (
    product_id     INT           AUTO_INCREMENT,
    product_name   VARCHAR(100)  NOT NULL,
    category_id    INT,
    price          DECIMAL(10,2) NOT NULL,
    stock_quantity INT           NOT NULL DEFAULT 0,
    PRIMARY KEY (product_id),
    FOREIGN KEY (category_id) REFERENCES categories(category_id),
    CHECK (price >= 0)
);

-- 4. Orders (depends on customers)
CREATE TABLE orders (
    order_id    INT          AUTO_INCREMENT,
    customer_id INT          NOT NULL,
    order_date  DATE         NOT NULL,
    status      VARCHAR(20)  NOT NULL DEFAULT 'Pending',
    PRIMARY KEY (order_id),
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

-- 5. Order items (depends on orders AND products)
CREATE TABLE order_items (
    order_item_id INT           AUTO_INCREMENT,
    order_id      INT           NOT NULL,
    product_id    INT           NOT NULL,
    quantity      INT           NOT NULL,
    unit_price    DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (order_item_id),
    FOREIGN KEY (order_id)   REFERENCES orders(order_id),
    FOREIGN KEY (product_id) REFERENCES products(product_id),
    CHECK (quantity > 0)
);

Lines that start with -- are comments. MySQL skips them. They are notes for the humans who read the script later, and that human is often you, three months from now.

Keeping your structure in a script file is a habit worth building from day one. A script is like a recipe: if the dish goes wrong, you don't fix it bite by bite, you cook it again from the recipe. At work, teams keep these files so anyone can rebuild the same database on a new machine.

Starting over

Made a mistake, or ran one of the error examples from section 6? Remove the whole database and run the script again:

Reset: delete everything, then rerun the script above
DROP DATABASE IF EXISTS online_store;

Only on your own practice database. DROP DATABASE deletes every table and every row inside it, with no undo. It's fine today because our tables are empty. On a real company database, never run it.

MySQL usually lists them in alphabetical order, not in the order you made them. Now look inside the bridge table:

SQL
DESCRIBE order_items;
Result
+---------------+---------------+------+-----+---------+----------------+
| Field         | Type          | Null | Key | Default | Extra          |
+---------------+---------------+------+-----+---------+----------------+

There are the two foreign keys, marked MUL. That stands for "multiple": the same order_id can appear on many rows, which makes sense, because one order can have many lines.

DESCRIBE doesn't show everything, though. It hides the CHECK rules and which table each foreign key points to. To see the full picture, ask MySQL for the exact statement it saved:

SQL
SHOW CREATE TABLE products;
Result
CREATE TABLE `products` (
  `product_id` int NOT NULL AUTO_INCREMENT,
  `product_name` varchar(100) NOT NULL,
  `category_id` int DEFAULT NULL,
  `price` decimal(10,2) NOT NULL,
  `stock_quantity` int NOT NULL DEFAULT '0',
  PRIMARY KEY (`product_id`),
  KEY `category_id` (`category_id`),
  CONSTRAINT `products_ibfk_1` FOREIGN KEY (`category_id`) REFERENCES `categories` (`category_id`),
  CONSTRAINT `products_chk_1` CHECK ((`price` >= 0))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci

This is your own table, written back to you in MySQL's words. A few things to notice:

  • The names MySQL gave your rules: products_ibfk_1 for the foreign key and products_chk_1 for the check.
  • A line you never wrote: KEY `category_id`. MySQL added an index on the foreign key column by itself. More on that in the next section.
  • ENGINE=InnoDB. The engine is the part of MySQL that actually stores the data. InnoDB is the default, and it is the engine that enforces foreign keys and supports transactions. You don't need to do anything, just know why your links work.
  • The backticks ` around names are MySQL's way of quoting names. You don't need to type them yourself.

Your checklist, all of which should now be true:

  • SHOW TABLES lists five tables.
  • Every table has one column marked PRI in DESCRIBE.
  • The foreign key columns (products.category_id, orders.customer_id, order_items.order_id and order_items.product_id) are marked MUL.
  • customers.email and categories.category_name are marked UNI.

9Indexes: finding rows fast

Open a thick textbook and try to find every page that mentions "normalization". You could read all 600 pages. Or you could turn to the index at the back, which lists the topic with its page numbers, and go straight there.

A database index works the same way. It is a sorted list that tells MySQL exactly where to find rows with a certain value. Without one, a question like "find customer 7" on a table with a million rows means checking every row, one by one. This is called a full table scan. With an index, MySQL jumps straight to the right row.

Some indexes are made for you

You haven't created a single index today, but you already have several. MySQL builds one automatically for every:

  • Primary key (in InnoDB the whole table is stored sorted by its primary key, so finding a row by ID is always fast),
  • UNIQUE column (same reason), and
  • Foreign key column (so it can check links quickly). This is the KEY `category_id` line you spotted above.

You can see the indexes on any table. The real output has many columns, so only the useful two are shown here:

SQL
SHOW INDEX FROM orders;
Result (only Key_name and Column_name shown)
Key_name      Column_name
PRIMARY       order_id
customer_id   customer_id

Making your own

For any other column you search or sort by a lot, you add the index yourself. Analysts filter orders by date all the time ("orders in March"), so order_date is a natural choice:

Create an index on order_date
CREATE INDEX idx_orders_order_date ON orders (order_date);
SQL
SHOW INDEX FROM orders;
Result (only Key_name and Column_name shown)
Key_name               Column_name
PRIMARY                order_id
customer_id            customer_id
idx_orders_order_date  order_date

The name is up to you. A common habit is idx_, then the table, then the column, so anyone can tell what it is from the name alone.

Indexes are not free, though:

Reading gets faster

  • Filtering on that column is much quicker
  • Sorting by it is quicker too
  • The gain grows as the table grows

Writing gets a bit slower

  • Every insert, update or delete must also update the index
  • Each index takes up extra space on disk
  • Too many indexes slow down a busy table

A simple rule: index the columns you often filter, join or sort by, and leave the rest alone. On a tiny table like ours, you won't notice any speed difference at all. Indexes only start to matter with many thousands of rows, which is why we come back to them on Day 18 with a much bigger table.

To keep your database exactly the same as the plan, remove the index you just made:

SQL
DROP INDEX idx_orders_order_date ON orders;

10ALTER: changing a table later

Plans change. A family adds a room to their house without knocking the whole house down. ALTER TABLE does the same for a table: it changes the structure while keeping the table, and any data already in it.

Let's try it on a real request. The shop owner says: "We want to store customers' phone numbers." Follow along. We will undo every change at the end, so your table ends up just as it was.

Step 1. Add a column. AFTER email puts the new column right after email. Without it, the new column goes at the end.

SQL
ALTER TABLE customers ADD COLUMN phone VARCHAR(20) AFTER email;
DESCRIBE customers;
Result
+-------------+--------------+------+-----+---------+----------------+
| Field       | Type         | Null | Key | Default | Extra          |
+-------------+--------------+------+-----+---------+----------------+
| customer_id | int          | NO   | PRI | NULL    | auto_increment |
| first_name  | varchar(50)  | NO   |     | NULL    |                |
| last_name   | varchar(50)  | NO   |     | NULL    |                |
| email       | varchar(100) | NO   | UNI | NULL    |                |

| city        | varchar(50)  | YES  |     | NULL    |                |
| country     | varchar(50)  | YES  |     | NULL    |                |
| signup_date | date         | NO   |     | NULL    |                |
+-------------+--------------+------+-----+---------+----------------+

Remember from Day 2: a phone number goes in VARCHAR, not INT, because it can start with + or 0 and you never do maths on it.

Step 2. Change the column's type. 20 characters is more than we need. MODIFY COLUMN gives the column a new definition:

SQL
ALTER TABLE customers MODIFY COLUMN phone VARCHAR(15);

Step 3. Rename it. The team prefers a clearer name:

SQL
ALTER TABLE customers RENAME COLUMN phone TO phone_number;

Step 4. Add a rule. No two customers should share a phone number. This time we give the rule our own name, instead of letting MySQL pick one:

SQL
ALTER TABLE customers ADD CONSTRAINT uq_customers_phone UNIQUE (phone_number);

Step 5. Remove it. The owner changes their mind. DROP COLUMN removes the column, its data, and the rule on it:

SQL
ALTER TABLE customers DROP COLUMN phone_number;

Run DESCRIBE customers; once more, and you'll see the same seven columns you started with.

ALTER cheat sheet

You want toWrite

This is where naming your own rules pays off. To remove a rule, you need its name. uq_customers_phone is easy to remember. customers_chk_3 means looking it up first with SHOW CREATE TABLE. A common habit is a short prefix: uq_ for unique, fk_ for foreign key, chk_ for check, idx_ for an index.

Careful when the table already has data. Changing an empty table is easy. Changing a full one is riskier. Say a column called name holds the text 'Aarav Sharma Jaipur' and you try to shrink it to VARCHAR(5). With MySQL's default (strict) settings, it stops you, because the data won't fit:

MySQL says
ERROR 1265 (01000): Data truncated for column 'name' at row 1

That error is protecting you. On a big table, an ALTER can also take a long time and slow the table down while it runs. At work, structure changes are usually planned and checked by the team first.

11DROP and TRUNCATE: removing things

The last two DDL commands remove things. Think of a shelf in the shop once more:

  • DROP takes the shelf away completely, with everything on it.
  • TRUNCATE sweeps everything off the shelf, but leaves the empty shelf standing.
  • DELETE, which is DML and comes tomorrow, takes items off one by one, and you choose which ones.
The commands (don't run these on your tables)
DROP TABLE order_items;              -- table and all its rows, gone
DROP TABLE IF EXISTS order_items;    -- same, but no error if it isn't there
TRUNCATE TABLE order_items;          -- all rows gone, empty table stays
DROP DATABASE online_store;          -- the whole database, gone

The guard is still on duty

Foreign keys protect you here too. Try to drop categories while products still points to it:

Safe to run: it fails, so nothing changes
DROP TABLE categories;
MySQL says
ERROR 3730 (HY000): Cannot drop table 'categories' referenced by a foreign key constraint 'products_ibfk_1' on table 'products'.

And TRUNCATE is blocked for the same reason:

Safe to run: it fails, so nothing changes
TRUNCATE TABLE categories;
MySQL says
ERROR 1701 (42000): Cannot truncate a table referenced in a foreign key constraint (`online_store`.`products`, CONSTRAINT `products_ibfk_1`)

So tables come down in the reverse of the order they went up. You built from the bottom to the roof. Now you take the roof off first: order_items, then orders and products, then customers and categories.

DROP vs TRUNCATE vs DELETE

This is one of the most asked SQL interview questions, so it is worth learning as a table:

A simple way to choose: TRUNCATE when you want an empty table quickly, DELETE when you want to control which rows go, and DROP only when you never want the table again.

Going deeper: why DDL has no undo button

On Day 2 you met transactions: a way to group changes and then save them (COMMIT) or undo them (ROLLBACK). That works for DML. It doesn't work for DDL in MySQL. Every DDL command saves itself the moment it runs. This is called an implicit commit.

Here it is in action on a small throwaway table:

SQL
CREATE TABLE notes (id INT PRIMARY KEY);

START TRANSACTION;
DROP TABLE notes;
ROLLBACK;

SHOW TABLES LIKE 'notes';
Result
(no rows)

The ROLLBACK did nothing. The table is gone. It is like sending a WhatsApp message with no "delete for everyone" option.

So before any DROP or TRUNCATE, build three small habits:

  • Run SELECT DATABASE(); to check which database you are in.
  • Use IF EXISTS in scripts, so a missing table doesn't stop the script halfway.
  • Keep your build script (section 7), so you can always rebuild the structure. The data is another matter, which is why real companies take regular backups.

As an analyst, you will rarely drop or truncate tables at work. Your access is often read-only, for good reason. But you will build and remove your own practice and scratch tables all the time, and interviewers love to ask about these three commands.

🎯 Interview corner

DDL questions are common in the first round of analyst interviews, especially the difference between DROP, TRUNCATE and DELETE. Try to answer each one out loud before you open the answer.

Concept questions

Q1What is DDL? Name its main commands.

DDL (Data Definition Language) is the set of SQL commands that create and change the structure of a database, not the data inside it. The main commands are CREATE (new database, table or index), ALTER (change an existing table), DROP (delete a table or database) and TRUNCATE (remove all rows but keep the table). Some people also list RENAME and COMMENT.

Q2What is the difference between DROP, TRUNCATE and DELETE?

DROP removes the whole table, structure and data. TRUNCATE removes all rows but keeps the empty table, and resets AUTO_INCREMENT. DELETE removes only the rows you choose with WHERE (or all rows without it), and goes row by row. DROP and TRUNCATE are DDL, are very fast, and can't be rolled back in MySQL. DELETE is DML, is slower on big tables, and can be rolled back inside a transaction.

Q3What is a constraint? Name the common ones.

A constraint is a rule on a column or table that the database checks every time data is added or changed, so bad data can't get in. The common ones are PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE, DEFAULT and CHECK. Example: CHECK (price >= 0) stops a negative price from ever being saved.

Q4What is the difference between a PRIMARY KEY and a UNIQUE constraint?

Both stop duplicate values. But a table can have only one primary key, and it can never be NULL. A table can have many UNIQUE columns, and in MySQL a UNIQUE column can hold NULL, even several NULLs, because one unknown value is not treated as equal to another. Example: customer_id is the primary key, while email is UNIQUE.

Q5What is a foreign key? Can a foreign key be NULL?

A foreign key is a column whose values must match the primary key (or another unique column) of the table it points to. That is usually another table, but it can be the same table, like an employee's manager. It keeps links valid, which is called referential integrity. For example, orders.customer_id must be a real customer_id. Yes, it can be NULL unless you add NOT NULL. A NULL simply means "not linked to anything yet". In our shop, products.category_id can be NULL, but orders.customer_id can't.

Q6Explain ON DELETE CASCADE, SET NULL and RESTRICT.

They decide what happens to child rows when the parent row they point to is deleted. RESTRICT refuses the delete while children exist. If you write nothing, MySQL uses NO ACTION, which in MySQL works the same as RESTRICT. CASCADE deletes the children too. SET NULL keeps the children but sets their foreign key to NULL, which only works if that column allows NULL. For sales data, RESTRICT is the safe choice, so history is never wiped by accident.

Q7Why does the order of creating and dropping tables matter?

A foreign key can only point to a table that already exists, so parent tables must be created before child tables. In our shop: categories and customers first, then products and orders, then order_items. Dropping goes in reverse, because MySQL won't drop a table that another table still points to.

Q8Can you roll back a DROP TABLE or TRUNCATE in MySQL?

No. In MySQL, DDL commands cause an implicit commit: they save themselves the moment they run, and they also save any open transaction before them. So ROLLBACK can't bring the table back. Only a backup can. DELETE is different, because it is DML and can be rolled back inside a transaction. (Some other databases, like PostgreSQL, do allow DDL inside a transaction, which is a nice point to add if you know it.)

Q9What is an index? What are the pros and cons?

An index is a sorted lookup structure on one or more columns that lets the database find rows without scanning the whole table, like the index at the back of a book. Pro: much faster filtering, joining and sorting on that column. Cons: inserts, updates and deletes get a little slower, because the index must be updated too, and it takes extra space. In MySQL, primary keys, UNIQUE columns and foreign key columns get an index automatically.

Q10A table's IDs go 1, 2, 4, 5. Is that a bug?

No. AUTO_INCREMENT never reuses a number. Gaps appear when a row is deleted, when some inserts fail (a duplicate value, for example), or when a transaction is rolled back after a number was handed out. IDs are labels, not a count. To count rows, use COUNT(*), never the largest ID.

Q11What is a composite primary key? When would you use one?

A primary key made of two or more columns together. Each column on its own can repeat, but the combination can't. Example: in an order lines table, the pair (order_id, product_id) could be the key, because the same product shouldn't appear twice in one order. You write it as PRIMARY KEY (order_id, product_id). We use a single order_item_id in online_store instead, which is simpler to point to from other tables.

Practical questions

P1Write a CREATE TABLE for employees: an auto ID, a required name, a unique required email, a required department, a salary that must be above zero, a required hire date, and a manager who is also an employee.
SQL
CREATE TABLE employees (
    employee_id INT           AUTO_INCREMENT,
    full_name   VARCHAR(100)  NOT NULL,
    email       VARCHAR(100)  NOT NULL UNIQUE,
    department  VARCHAR(50)   NOT NULL,
    salary      DECIMAL(10,2) NOT NULL,
    hire_date   DATE          NOT NULL,
    manager_id  INT,
    PRIMARY KEY (employee_id),
    FOREIGN KEY (manager_id) REFERENCES employees(employee_id),
    CHECK (salary > 0)
);

The interesting part is manager_id. It points to the same table, which is called a self-referencing foreign key. A manager is just another employee. It must allow NULL, because the person at the top has no manager. You will query a table like this with a self join on Day 7, and a real employees table arrives on Day 10.

P2Write ALTER statements for products: add a brand column after product_name, make product_name allow 150 characters, rename stock_quantity to stock_qty, and add a discount_pct column that must be between 0 and 90.
SQL
ALTER TABLE products ADD COLUMN brand VARCHAR(50) AFTER product_name;
ALTER TABLE products MODIFY COLUMN product_name VARCHAR(150) NOT NULL;
ALTER TABLE products RENAME COLUMN stock_quantity TO stock_qty;
ALTER TABLE products ADD COLUMN discount_pct DECIMAL(5,2) DEFAULT 0;
ALTER TABLE products ADD CONSTRAINT chk_products_discount CHECK (discount_pct BETWEEN 0 AND 90);

The trap is in the second line. MODIFY COLUMN replaces the whole column definition. If you write only MODIFY COLUMN product_name VARCHAR(150), the NOT NULL rule is quietly lost. Always repeat every rule you want to keep.

If you try this on your own online_store, undo it afterwards so the table matches the plan again:

SQL
ALTER TABLE products DROP CHECK chk_products_discount;
ALTER TABLE products DROP COLUMN discount_pct;
ALTER TABLE products RENAME COLUMN stock_qty TO stock_quantity;
ALTER TABLE products MODIFY COLUMN product_name VARCHAR(100) NOT NULL;
ALTER TABLE products DROP COLUMN brand;
P3A teammate runs DROP TABLE customers; and gets error 3730. Why? How would you remove all five tables?

orders has a foreign key pointing to customers, so MySQL won't drop customers while it is still in use. You have two ways out:

  • Drop the tables in reverse build order: order_items, then orders and products, then customers and categories.
  • Or drop the whole database at once with DROP DATABASE online_store;, which removes everything inside it.

A good answer also says: "Before doing either, I'd check that I'm in the right database, and that a backup exists, because neither can be undone."

Quick recap

  • DDL builds and changes structure. Its main commands are CREATE, ALTER, DROP and TRUNCATE.
  • CREATE DATABASE makes the database, and USE steps inside it. CREATE TABLE lists each column with a data type and its rules.
  • Constraints are rules the database checks on every row: PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE, DEFAULT, CHECK. AUTO_INCREMENT fills in IDs, and gaps in IDs are normal.
  • Foreign keys keep links valid. Parent tables are created first, and dropped last.
  • Check your work with SHOW TABLES, DESCRIBE and SHOW CREATE TABLE. Read errors by their number and message.
  • Indexes make searching faster and writing a bit slower. Primary keys, UNIQUE columns and foreign keys get one automatically.
  • ALTER TABLE adds, changes, renames or removes columns and rules. Name your own rules so they are easy to remove.
  • DROP removes the table, TRUNCATE empties it, DELETE (Day 4) removes chosen rows. DDL can't be rolled back in MySQL.
