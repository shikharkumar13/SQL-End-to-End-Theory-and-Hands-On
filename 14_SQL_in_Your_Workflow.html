1Where SQL fits in an analyst's day

Think of a huge warehouse and a small shop counter. When a customer asks for one item, nobody carries the whole warehouse to the counter and searches there. You find the item in the warehouse, pack it, and bring only that box to the counter. The database is the warehouse. SQL is how you pick and pack. Python, Excel or a dashboard is the counter, where the result is shown to people.

A typical piece of analysis goes through the same stages every time:

  1. Question. "Is Facebook advertising worth what we pay for it?"
  2. Query. SQL pulls, joins, filters and summarises the data inside the database, where it's fast and close to the source.
  3. Shape and show. A tool like Python turns the small result into charts, pivots, statistics or a model, and combines it with data that isn't in the database (a spreadsheet, a file from another team).
  4. Share. A chart, a table, a short message with a recommendation (Day 13, section 7).
  5. Save. The query is kept, so it can be run again next month, by you or someone else (section 8).

The tools you'll meet around SQL:

ToolWhat analysts use it for
MySQL Workbench, DBeaver, DataGripWriting and testing SQL, exploring tables
Python (pandas, Jupyter notebooks)Analysis, charts, statistics, machine learning, automating reports
BI tools (Power BI, Tableau, Looker Studio)Dashboards. They send SQL to the database behind the scenes, and many let you write your own.
Excel, Google SheetsQuick checks, and sharing small results with people who don't write SQL

This article uses Python, because it's the most common partner for SQL in data jobs, and everything you learn carries over to the other tools.

2Connecting Python to MySQL

Three packages work together:

  • pandas holds the results as tables (called DataFrames).
  • PyMySQL is the driver: the piece that actually speaks MySQL's language over the network.
  • SQLAlchemy manages the connection. Think of it as a universal travel adapter: your code plugs into SQLAlchemy, and SQLAlchemy plugs into whichever database you use, through the right driver. Switching to PostgreSQL later means changing one line.

Keep the password out of your code

The first rule of connecting: never type your password into your code. Code gets shared, emailed and uploaded to GitHub, and a password in it goes along. Instead, store it in an environment variable, a named value your computer keeps for programs to read:

Terminal (run once per session)
# Mac or Linux
export MYSQL_USER="root"
export MYSQL_PASSWORD="your-password-here"

# Windows PowerShell
$env:MYSQL_USER = "root"
$env:MYSQL_PASSWORD = "your-password-here"

(A popular alternative is a file called .env read by the python-dotenv package. If you use one, add .env to your .gitignore so it never reaches GitHub.)

Create the engine

In SQLAlchemy, the object that knows how to reach your database is called an engine:

Python
import os
from urllib.parse import quote_plus

import pandas as pd
from sqlalchemy import create_engine, text

user = os.environ["MYSQL_USER"]
password = quote_plus(os.environ["MYSQL_PASSWORD"])   # makes characters like @ safe

engine = create_engine(
    f"mysql+pymysql://{user}:{password}@localhost:3306/online_store_full?charset=utf8mb4"
)

The long string is a connection URL, and every part has a job:

PartMeaning
mysql+pymysql://The database (MySQL) and the driver (PyMySQL)
user:passwordWho you are
@localhost:3306Where the server is: this computer, on MySQL's usual port, 3306
/online_store_fullWhich database to use, like USE
?charset=utf8mb4Send text as utf8mb4, so names like "Zoë" and the ₹ sign arrive intact (remember Day 10's garbled characters)

Why quote_plus? Because @, :, / and # have special meanings inside a URL. Here's what happens with a password like my@secret that isn't made safe:

Python
bad_engine = create_engine("mysql+pymysql://analyst:my@secret@localhost:3306/online_store_full")
with bad_engine.connect() as conn:
    conn.execute(text("SELECT 1"))
Python says
Traceback (most recent call last):
  ...
sqlalchemy.exc.OperationalError: (pymysql.err.OperationalError) (2003, "Can't connect to MySQL server on 'secret@localhost' ([Errno -2] Name or service not known)")

The URL was split at the first @, so the driver went looking for a server called secret@localhost. The error says "can't connect", and nothing mentions the password, which is why this one wastes so much time. quote_plus turns the special characters into codes that URLs understand:

Python
print(quote_plus("my@secret#1"))
Output
my%40secret%231

Now test the real connection. with ... as conn opens a connection and closes it again automatically at the end of the block:

Python
with engine.connect() as conn:
    result = conn.execute(text("SELECT CURRENT_USER() AS who, DATABASE() AS db, VERSION() AS version"))
    print(result.fetchall())
Output
[('analyst@localhost', 'online_store_full', '8.0.46-0ubuntu0.24.04.4')]

Connected. (Yours will show your own user name and version.) If it fails, the error usually tells you which part of the URL is wrong:

ErrorUsual cause
1045 Access denied for user ... (using password: YES)Wrong user name or password
2003 Can't connect to MySQL server on 'localhost'MySQL isn't running, or the host or port is wrong (or an unescaped @, as above)
1049 Unknown databaseDatabase name misspelled. (If your user isn't allowed to see it, you get 1044 Access denied ... to database instead.)
No module named 'pymysql'The driver isn't installed: pip install pymysql
A message asking for the cryptography packageSome MySQL 8 login methods need it: pip install cryptography

3Running queries from pandas

pd.read_sql(query, engine) sends a query to MySQL and returns the result as a DataFrame. Let's bring in the monthly revenue from Day 12. Here's the first attempt, and the first surprise:

Python
monthly = pd.read_sql(
    "SELECT DATE_FORMAT(order_date, '%Y-%m-01') AS month_start, SUM(line_total) AS revenue "
    "FROM clean_sales GROUP BY month_start",
    engine,
)
Python says
Traceback (most recent call last):
  ...
ValueError: unsupported format character 'Y' (0x59) at index 33

The SQL is perfectly fine. It ran on Day 12. The problem is PyMySQL: it uses %s to mark places where values will be filled in, so when it sees %Y, it gets confused. The same thing happens with LIKE '%test%'. The fix, and a good habit for every query, is to wrap the SQL in SQLAlchemy's text(), which handles the % signs for you. Triple quotes let the query run over several lines, laid out exactly as you'd write it in Workbench:

Python
monthly_sql = text("""
    SELECT DATE_FORMAT(order_date, '%Y-%m-01') AS month_start,
           COUNT(DISTINCT order_id)            AS orders,
           SUM(line_total)                     AS revenue
    FROM clean_sales
    GROUP BY month_start
    ORDER BY month_start
""")

monthly = pd.read_sql(monthly_sql, engine)
print(monthly.head(3))
print(monthly.dtypes)
Output
  month_start  orders    revenue
0  2023-01-01     126  256113.23
1  2023-02-01     102  205904.70
2  2023-03-01     130  286742.70
month_start        str
orders           int64
revenue        float64
dtype: object

It worked. Always check the types after loading (dtypes), because they decide what you can do next. orders is a whole number, and revenue is a decimal number (pandas turns MySQL's DECIMAL into float64). But month_start is text, not a date. That's not a pandas problem: Day 12 warned that DATE_FORMAT returns text. (pandas 3 shows text as str. Older versions say object.) Ask pandas to turn it into a real date as it loads:

Python
monthly = pd.read_sql(monthly_sql, engine, parse_dates=["month_start"])
print(monthly.dtypes)
print(len(monthly), "months, total revenue:", round(monthly["revenue"].sum()))
Output
month_start    datetime64[us]
orders                  int64
revenue               float64
dtype: object
24 months, total revenue: 13172860

Now month_start is a real date, so sorting, filtering and charts will treat it as one. (Older pandas versions show datetime64[ns]. Same idea.) And the total is ₹1,31,72,860, exactly Day 11's clean revenue. Checking that the total survived the trip into Python is the same habit as Day 4's checks after loading a file.

Passing values into a query, safely

Often a query needs a value from your Python code: a date, a status, a customer ID. The tempting way is to paste it into the SQL with an f-string. Here's why you shouldn't:

Python
def count_orders(status):
    # DON'T do this: the value is pasted straight into the SQL text
    sql = f"SELECT COUNT(*) AS orders FROM clean_orders WHERE status = '{status}'"
    return pd.read_sql(text(sql), engine)

print(count_orders("Pending"))
print(count_orders("Pending' OR '1'='1"))
Output
   orders
0      40
   orders
0    6144

The first call is fine: 40 pending orders. In the second, the "status" contains a quote mark, and becomes part of the SQL itself: WHERE status = 'Pending' OR '1'='1'. Since '1'='1' is always true, the query returned every order. If that value came from a web form and the query was a DELETE, the damage would be real. This is called SQL injection, and it's one of the most common security bugs in the world.

The safe way is a parameter: write a named placeholder like :status in the SQL, and pass the value separately. The value is never mixed into the SQL text, so it can't change what the query does:

Python
def count_orders(status):
    sql = text("SELECT COUNT(*) AS orders FROM clean_orders WHERE status = :status")
    return pd.read_sql(sql, engine, params={"status": status})

print(count_orders("Pending"))
print(count_orders("Pending' OR '1'='1"))
Output
   orders
0      40
   orders
0       0

Now the strange input is treated as what it is: a status nobody has, so 0 orders. Parameters have a second benefit: values with quote marks, like the name D'Souza from Day 11, just work, with no special handling. Use parameters every time a value comes from outside the SQL.

4SQL for the heavy lifting, pandas for the rest

pandas can filter, join and group too, so why not pull the raw table into Python and do everything there? Compare two ways to get to the same answer:

Python
every_line = pd.read_sql(text("SELECT order_date, line_total FROM clean_sales"), engine)

print("Raw lines:      ", every_line.shape, "total", round(every_line["line_total"].sum()))
print("Monthly summary:", monthly.shape, "total", round(monthly["revenue"].sum()))
Output
Raw lines:       (9508, 2) total 13172860
Monthly summary: (24, 3) total 13172860

(shape is (rows, columns).) Same total, but the first way carried all 9,508 order lines across the network and into your computer's memory to answer a question whose answer has 24 rows. On our data that takes a moment. On a real table with 100 million rows, it can take hours or crash your laptop, while the database would summarise it in seconds. Databases are built for exactly this work. So the rule is: move the question to the data, not the data to the question.

The dynamic pivot

Day 8 built a pivot with one SUM(CASE ...) per column, and noted its weakness: you have to type every column yourself, so if a new category appears, the query has to change. pandas solves this. Let SQL do the heavy part (summarise to one row per month and category), then let pandas turn the categories into columns:

Python
by_category = pd.read_sql(text("""
    SELECT DATE_FORMAT(order_date, '%Y-%m-01') AS month_start,
           category_name,
           SUM(line_total)                     AS revenue
    FROM clean_sales
    WHERE order_date >= '2024-07-01'
    GROUP BY month_start, category_name
"""), engine)

wide = by_category.pivot_table(index="month_start", columns="category_name",
                               values="revenue", aggfunc="sum", fill_value=0)
print(wide.round().astype(int))

The quick way, and its problem

DataFrame.to_sql() writes a DataFrame into a table. With if_exists="replace", pandas creates the table for you:

Python
spend.to_sql("marketing_spend_quick", engine, if_exists="replace", index=False)
SQL
DESCRIBE marketing_spend_quick;
DROP TABLE marketing_spend_quick;   -- we'll build a better one
Result
+---------+--------+------+-----+---------+-------+
| Field   | Type   | Null | Key | Default | Extra |
+---------+--------+------+-----+---------+-------+
| month   | text   | YES  |     | NULL    |       |
| channel | text   | YES  |     | NULL    |       |
| spend   | bigint | YES  |     | NULL    |       |
+---------+--------+------+-----+---------+-------+

It worked, but look at what pandas chose: TEXT for both text columns, a huge BIGINT for money, every column allowed to be NULL, and no primary key. pandas can only guess from the data, and it guesses loosely. Nothing stops the same month being loaded twice, or spend being left empty. Everything Day 3 taught about good table design is missing. (index=False stops pandas adding its row numbers as an extra column.)

The proper way: design the table in SQL, then append

Create the table yourself, with the right types and a primary key, exactly as on Day 3. One month and one channel can only have one spend figure, so those two columns together are the key:

Build 1: the marketing_spend table
DROP TABLE IF EXISTS marketing_spend;

CREATE TABLE marketing_spend (
    month_start DATE          NOT NULL,
    channel     VARCHAR(30)   NOT NULL,
    spend       DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (month_start, channel)
);

Then tidy the DataFrame to match, and append it to the table you made:

Python
spend["month_start"] = pd.to_datetime(spend["month"] + "-01")   # '2023-01' becomes 1 Jan 2023
spend = spend[["month_start", "channel", "spend"]]                 # same columns as the table

rows = spend.to_sql("marketing_spend", engine, if_exists="append", index=False)
print(rows, "rows loaded")
Output
60 rows loaded

The file's month column was text like '2023-01'. Adding '-01' and converting with pd.to_datetime gives a real date, the first of the month: Day 11's text-to-date lesson, in Python. Now Day 4's two checks, in SQL:

SQL
SELECT COUNT(*)                AS rows_loaded,
       SUM(spend)              AS total_spend,
       MIN(month_start)        AS first_month,
       MAX(month_start)        AS last_month,
       COUNT(DISTINCT channel) AS channels
FROM marketing_spend;
Result
+-------------+-------------+-------------+------------+----------+
| rows_loaded | total_spend | first_month | last_month | channels |
+-------------+-------------+-------------+------------+----------+
|          60 |  1040000.00 | 2023-01-01  | 2023-12-01 |        5 |
+-------------+-------------+-------------+------------+----------+

60 rows and ₹10,40,000, the same as the file. Now see the primary key earn its place. What happens if someone runs the loading code a second time by mistake?

Python

Python says
Traceback (most recent call last):
  ...
pandas.errors.DatabaseError: Execution failed on sql 'INSERT INTO marketing_spend (month_start, channel, spend) VALUES (:month_start, :channel, :spend)': (pymysql.err.IntegrityError) (1062, "Duplicate entry '2023-01-01-Google Ads' for key 'marketing_spend.PRIMARY'")

Error 1062, the duplicate key error, and nothing was loaded twice. Without the primary key, the second run would have quietly doubled every number. When a monthly file needs reloading, the usual approach is to delete that month's rows first and then append, or to use Day 4's ON DUPLICATE KEY UPDATE.

The payoff: is each channel worth it?

Now the spreadsheet can meet the database. For each paid channel: how much did it cost to win one new customer in 2023 (spend ÷ new customers), and how does that compare with the profit those customers brought in their first year (Day 13, section 6)?

SQL
WITH new_customers AS (
    SELECT c.acquisition_channel AS channel,
           COUNT(*)              AS new_customers
    FROM customer_summary s
    JOIN clean_customers c ON c.customer_id = s.customer_id
    WHERE s.first_order_date >= '2023-01-01' AND s.first_order_date < '2024-01-01'
    GROUP BY c.acquisition_channel
),
first_year AS (                 -- Day 13: profit in each customer's first 12 months
    SELECT s.customer_id,
           SUM(cs.line_total - cs.line_cost) AS gross_profit
    FROM customer_summary s
    JOIN clean_sales cs ON cs.customer_id = s.customer_id
                       AND cs.order_date  < s.first_order_date + INTERVAL 12 MONTH
    WHERE s.first_order_date >= '2023-01-01' AND s.first_order_date < '2024-01-01'
    GROUP BY s.customer_id
),
profit_by_channel AS (
    SELECT c.acquisition_channel AS channel,
           AVG(f.gross_profit)   AS profit_12m
    FROM first_year f
    JOIN clean_customers c ON c.customer_id = f.customer_id
    GROUP BY c.acquisition_channel
),
spend_by_channel AS (
    SELECT channel, SUM(spend) AS spend_2023
    FROM marketing_spend
    GROUP BY channel
)
SELECT sp.channel,
       sp.spend_2023,
       n.new_customers,
       ROUND(sp.spend_2023 / n.new_customers)                AS cost_per_customer,
       ROUND(p.profit_12m)                                    AS profit_12m,
       ROUND(p.profit_12m - sp.spend_2023 / n.new_customers) AS profit_after_cost
FROM spend_by_channel sp
JOIN new_customers n     ON n.channel = sp.channel
JOIN profit_by_channel p ON p.channel = sp.channel
ORDER BY profit_after_cost DESC;
Result
+------------+------------+---------------+-------------------+------------+-------------------+
| channel    | spend_2023 | new_customers | cost_per_customer | profit_12m | profit_after_cost |
+------------+------------+---------------+-------------------+------------+-------------------+
| Email      |   30500.00 |            50 |               610 |       2921 |              2311 |
| Referral   |   61500.00 |           123 |               500 |       2552 |              2052 |
| Google Ads |  305500.00 |           204 |              1498 |       2756 |              1259 |
| Instagram  |  391500.00 |           206 |              1900 |       2622 |               722 |
| Facebook   |  251000.00 |            93 |              2699 |       2406 |              -293 |
+------------+------------+---------------+-------------------+------------+-------------------+

Four CTEs, each doing one job, all things you've built before. And a clear answer: email and referrals win customers cheaply. Google Ads is solidly profitable, and Instagram less so. Facebook costs about ₹2,700 to win a customer who brings in about ₹2,400 of profit in their first year: it loses money in year one. That's the kind of finding that changes a marketing budget.

Before anyone acts on this, say what it rests on. The channel is whatever the customer chose at sign-up, which isn't the full story of what persuaded them. "First-year profit" leaves out delivery and staff costs. Some customers keep buying after year one, so Facebook may still pay off later. And email has only 50 new customers behind its number (Day 13's small-group warning). Good analysts state the limits next to the result.

6Reading error messages

Everyone's queries break, every day. The difference between a beginner and an experienced analyst isn't fewer errors. It's how quickly they read them. MySQL's messages are short, but they're precise once you know how to read them:

SQL
SELECT order_id, order_status
FROM orders;
MySQL says
ERROR 1054 (42S22): Unknown column 'order_status' in 'field list'
  • 1054 is MySQL's own error number. Searching "MySQL error 1054" always finds help.
  • 42S22 is the SQLSTATE, a five-character code from the SQL standard. Other databases use the same codes, so programs can handle errors the same way everywhere.
  • The message names the problem and where it is: an unknown column, 'order_status', in the 'field list' (MySQL's name for the list of columns after SELECT). Other places you'll see are 'where clause', 'on clause' and 'order clause'.

The ones you'll see most

1064, the syntax error. The most common error of all, and the vaguest:

SQL
SELECT order_id,
FROM orders;
MySQL says
ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'FROM orders'

The key is the word near. MySQL shows the text starting from the point where it got confused. The real mistake is almost always just before that text. Here, MySQL read order_id, and expected another column, but found FROM. The mistake is the extra comma before it.

1052, the ambiguous column. Two joined tables have a column with the same name, and MySQL won't guess which you mean (Day 7):

SQL
SELECT order_id, quantity
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id;
MySQL says
ERROR 1052 (23000): Column 'order_id' in field list is ambiguous

The fix is to name the table: o.order_id. 1055, the GROUP BY rule (you met it on Days 10 and 11): every column in SELECT must be grouped or inside an aggregate:

SQL
SELECT customer_id, order_date, COUNT(*)
FROM orders
GROUP BY customer_id;
MySQL says
ERROR 1055 (42000): Expression #2 of SELECT list is not in GROUP BY clause and contains nonaggregated column 'online_store_full.orders.order_date' which is not functionally dependent on columns in GROUP BY clause; this is incompatible with sql_mode=only_full_group_by

A customer has many order dates, so which one should MySQL show? Either add order_date to GROUP BY, or summarise it, for example MAX(order_date). The rest of the common ones, with the exact messages MySQL gives:

Warnings: errors that only whisper

Sometimes MySQL accepts something odd, gives you an answer, and only leaves a warning. Workbench shows warnings in the output panel. In the command line, you ask with SHOW WARNINGS:

SQL
SELECT CAST('12abc' AS UNSIGNED) AS number;
SHOW WARNINGS;

MySQL quietly turned '12abc' into 12. No error, just a warning. If you're converting a whole column (Day 11), check the warnings, or count the values that don't look like numbers before converting.

The dangerous ones have no message at all

An error message is a gift: it stops you and tells you something is wrong. The mistakes that hurt are the ones that run without complaint. Here's a missing comma:

SQL
SELECT order_id status, order_date
FROM orders
ORDER BY order_id
LIMIT 3;
Result
+--------+---------------------+
| status | order_date          |
+--------+---------------------+
|      1 | 2023-01-01 01:08:40 |
|      2 | 2023-01-01 14:54:47 |
|      3 | 2023-01-01 19:25:44 |
+--------+---------------------+

Without the comma, MySQL reads order_id status as "order_id, renamed to status" (an alias without AS, Day 5). So the column called "status" is full of order IDs, and there's no error. You've met the others in this series:

  • A join that multiplies rows and inflates totals (Day 7)
  • NOT IN with a NULL in the list, returning nothing (Day 5)
  • BETWEEN on a DATETIME, losing the last day (Day 12)
  • LIMIT without ORDER BY, giving different rows each time (Day 5)
  • Numbers or dates stored as text, sorting in dictionary order (Day 11)
  • An unfinished period that looks like a crash (Day 12)

The defence against all of them is the same: check your result against something you already know, such as a row count, a total, or one customer you can verify by hand.

How to debug a long query

  1. Read the whole message, including the number and the "near" text. Look just before the "near" point.
  2. Run it in pieces. With CTEs, run each one alone: SELECT * FROM first_cte LIMIT 10. Find the first step that's wrong.
  3. Comment lines out with -- until the error goes away. The last line you removed is the culprit.
  4. Count at every step. Did the join keep the number of rows you expected? (Day 11: count before and after.)
  5. Search for the error number with "MySQL". You won't be the first person to meet it.

7One language, many dialects

Day 2 compared SQL dialects to English in India, the UK and the US: the same language, with different accents. In a data job, you'll probably meet some of these:

  • PostgreSQL: free and very popular with tech companies and data teams.
  • SQL Server: Microsoft's database, common in large companies.
  • SQLite: a tiny database that lives in a single file. It's built into Python and into most phones.
  • Cloud warehouses such as BigQuery, Snowflake and Redshift, each with its own dialect.

The good news: SELECT, joins, GROUP BY, CASE, CTEs and window functions work almost the same everywhere. Everything you've learned carries over. The bad news: a few small differences give different answers without any error. The examples below ran on a real PostgreSQL 16 server, next to MySQL.

Dividing whole numbers, and capital letters

SQL
SELECT 7 / 2           AS division,
       'Apple' = 'apple' AS same_text;
MySQL result
+----------+-----------+
| division | same_text |
+----------+-----------+
|   3.5000 |         1 |
+----------+-----------+
PostgreSQL
SELECT 7 / 2           AS division,
       'Apple' = 'apple' AS same_text;
PostgreSQL result
 division | same_text 
----------+-----------
        3 | f
(1 row)

Same query, two different answers. PostgreSQL divides a whole number by a whole number and gives a whole number: 7 / 2 is 3, and the remainder is thrown away. It also cares about capitals (Days 5 and 10 mentioned this), so 'Apple' = 'apple' is false (f). The division one is the dangerous one for analysts:

PostgreSQL
SELECT 2 / 3         AS share,
       2 * 100 / 3   AS pct,
       2 * 100.0 / 3 AS pct_decimal;
PostgreSQL result
 share | pct |     pct_decimal     
-------+-----+---------------------
     0 |  66 | 66.6666666666666667
(1 row)

A share of two counts comes out as 0, and a percentage loses its decimals. Many of this series' percentages were written like SUM(...) * 100 / COUNT(*), which works in MySQL but would be cut down to whole numbers in PostgreSQL. The fix is to make one number a decimal: 100.0 instead of 100, or CAST(x AS NUMERIC).

Joining text, and NULLs

SQL
SELECT 'a' || 'b'             AS pipes,
       CONCAT('a', NULL, 'b') AS concat_with_null;
MySQL result
+-------+------------------+
| pipes | concat_with_null |
+-------+------------------+
|     0 | NULL             |
+-------+------------------+
PostgreSQL
SELECT 'a' || 'b'             AS pipes,
       CONCAT('a', NULL, 'b') AS concat_with_null;
PostgreSQL result
 pipes | concat_with_null 
-------+------------------
 ab    | ab
(1 row)

In PostgreSQL (and SQLite and Oracle), || joins text. In MySQL, || means OR by default, so 'a' || 'b' becomes a true-or-false test on two words, and gives 0. (MySQL adds a warning that this use of || is deprecated.) And CONCAT treats NULL differently: MySQL returns NULL (Day 11 used that fact), while PostgreSQL skips the NULL and returns ab.

Day 6's shortcut, and strict types

On Day 6 you learned SUM(status = 'Cancelled') and were told it's MySQL-only. Here's what PostgreSQL says:

PostgreSQL
WITH o(status) AS (VALUES ('Completed'), ('Cancelled'), ('Completed'))
SELECT SUM(status = 'Completed') FROM o;
PostgreSQL says
ERROR:  function sum(boolean) does not exist
LINE 2: SELECT SUM(status = 'Completed') FROM o;
               ^
HINT:  No function matches the given name and argument types. You might need to add explicit type casts.

In PostgreSQL, a comparison gives a real true or false, not 1 or 0, and you can't add those up. Day 8's CASE version works everywhere, and PostgreSQL also has a neat FILTER clause:

PostgreSQL
WITH o(status) AS (VALUES ('Completed'), ('Cancelled'), ('Completed'))
SELECT SUM(CASE WHEN status = 'Completed' THEN 1 ELSE 0 END) AS with_case,
       COUNT(*) FILTER (WHERE status = 'Completed')          AS with_filter
FROM o;
PostgreSQL result
 with_case | with_filter 
-----------+-------------
         2 |           2
(1 row)

(VALUES makes a tiny table on the spot. It's handy for experiments.) PostgreSQL is also strict about types. MySQL turns 'abc' + 1 into 1 with a warning, like the '12abc' example in section 6. PostgreSQL refuses:

PostgreSQL
SELECT 'abc' + 1;
PostgreSQL says
ERROR:  invalid input syntax for type integer: "abc"
LINE 1: SELECT 'abc' + 1;
               ^

Strictness can feel annoying, but it's often protective: an error is better than a silently wrong number.

Habits that keep your SQL portable, so it moves between databases with the fewest surprises:

  • Use COALESCE rather than IFNULL, and CASE rather than MySQL's IF() or SUM(condition).

8Writing SQL others can use

A query you'll run once can look however you like. A query that goes into a report, gets reused next month, or gets handed to a colleague is different: other people (including you, in six months) need to understand it, trust it and change it. Here's the payoff query from section 5, written the way you'd save it:

channel_payback.sql
/*
  Channel payback: cost to win a customer vs. their first-year profit
  Question:  Is each paid marketing channel worth what we spend on it?
  Data:      marketing_spend (from the marketing team's 2023 file),
             customer_summary and clean_sales (Days 11 and 13)
  Decisions: "New customer" = first completed order in 2023.
             Channel = acquisition_channel recorded at sign-up.
             Profit = price minus cost price; delivery costs are not included.
  As of:     data up to 31 Dec 2024
*/
WITH new_customers AS (
    ...
)

The header comment answers the questions a reader will have before they ask: what this is for, where the data comes from, which decisions it makes, and what date it's true for. (/* ... */ is a comment that can run over several lines.) The other habits you've been using all along, now as a checklist:

  • One idea per line: one column per line, keywords in capitals, each JOIN on its own line with its ON condition.
  • CTE names that say what they hold (new_customers, first_year), not t1 and t2.
  • Comment the "why", not the "what". -- New Delhi counts as Delhi, agreed with the owner is useful. -- join to customers isn't.
  • Name your columns instead of SELECT * (Day 5), and give calculated columns clear aliases.
  • Save queries as .sql files, with names that say what they answer, and keep them in version control (Git), so changes are tracked and nothing is lost.
  • Put shared logic in views (Days 9 and 11), so everyone uses the same definitions instead of copying and slightly changing them.
  • Use parameters for values that change (dates, statuses), instead of editing the SQL by hand each month (section 3).

None of this changes what the query returns. It changes whether anyone can trust it, which in the end is the whole job.

🎯 Interview corner

Data roles rarely use SQL alone, so interviewers often ask how you work with it day to day: from Python, with errors, and across databases.

Concept questions

Q1How do you run SQL from Python?

Create a SQLAlchemy engine with a connection URL (database, driver, user, host, port, database name), with the password read from an environment variable rather than written in the code. Then use pd.read_sql(text(query), engine, params={...}) to get a DataFrame, and DataFrame.to_sql() to write one back. Wrap queries in text(), and check the column types after loading.

Q2What is SQL injection, and how do you prevent it?

When outside input is pasted into SQL text, a value containing quote marks can change the query itself, for example turning a filter into OR '1'='1' and returning or deleting every row. Prevent it with parameterised queries (placeholders like :status or %s, with the values passed separately), never with string formatting. Limiting database permissions adds a second layer of protection.

Q3When would you do work in SQL, and when in pandas?

Filter, join and aggregate in SQL, close to the data, so only a small result travels, especially on large tables. Use pandas for what SQL does poorly: charts, statistics and models, pivots with unknown columns, combining with files or APIs, and automation. Shared business logic belongs in the database (views) so every tool uses the same definition.

Q4What's the difference between a MySQL error number and an SQLSTATE?

The error number (like 1054) is MySQL's own, specific code. The SQLSTATE (like 42S22) is a five-character code from the SQL standard that other databases share, so programs can handle error types the same way across databases. Both appear in the message: ERROR 1054 (42S22): Unknown column ....

Q5How do you debug a long query that gives the wrong answer?

Break it into steps and check each one: run each CTE on its own, count rows after every join to spot multiplication, compare totals with a number you trust, and test one record you can verify by hand. For syntax errors, read the "near" text and look just before it.

Q6Name some differences between MySQL and PostgreSQL.

Integer division (7/2 is 3.5 in MySQL, 3 in PostgreSQL); text comparisons ignore capitals by default in MySQL but not in PostgreSQL (which has ILIKE); || joins text in PostgreSQL but means OR in MySQL; PostgreSQL has real booleans, so SUM(condition) fails (use CASE or FILTER); PostgreSQL has FULL OUTER JOIN; upserts use ON CONFLICT versus ON DUPLICATE KEY UPDATE; PostgreSQL is stricter about types; NULLs sort last in ascending order in PostgreSQL, first in MySQL.

Q7A percentage comes out as 0 in PostgreSQL but correct in MySQL. Why?

Integer division. In PostgreSQL (and SQL Server, SQLite), dividing one integer by another gives an integer, so 2/3 is 0. Make one side a decimal: 2 * 100.0 / 3, or CAST(x AS NUMERIC).

Q8What do the if_exists options of to_sql do?

"fail" (the default) raises an error if the table exists. "replace" drops the table and creates a new one with types pandas guesses: no primary key, loose types. "append" adds rows to the existing table. The safest pattern is to create the table yourself with proper types and keys, then append, so the database checks every row.

Quick recap

  • SQL does the heavy lifting inside the database. Python, BI tools or Excel shape and share the small result. Move the question to the data.
  • Connect with a SQLAlchemy engine and a connection URL: database and driver, user, password, host, port, database name and charset=utf8mb4. Keep the password in an environment variable, and wrap it in quote_plus.
  • pd.read_sql(text(query), engine). text() avoids the % trap. Check dtypes, and use parse_dates for dates.
  • Pass values with parameters (:name and params=), never by pasting them into the SQL. That's how SQL injection is prevented.
  • pandas is great for dynamic pivots and charts. Summarise in SQL first.
  • Load files by creating the table in SQL (types, keys), then to_sql(..., if_exists="append", index=False), and check the row count and total afterwards.
  • Read errors by their number and the "near" text. Check warnings. The worst mistakes give no error, so always check results against something you know.
  • Dialects differ in small ways that change answers: integer division, capitals, ||, CONCAT with NULL, booleans, NULL sorting. Write portable SQL, and test when you switch.
  • Save queries as commented .sql files in version control, with shared logic in views.
