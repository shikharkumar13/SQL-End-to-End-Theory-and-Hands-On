You passed Checkpoint 1. Everything so far ran on a tidy 70-row database you could check by eye. Real jobs don't look like that. On your first day, someone gives you access to a database you've never seen and says: "Have a look around, and tell me what you find." Today is that first day. You'll meet online_store_full, the shop's full records for 2023 and 2024, and learn the checklist analysts use in their first hour with any new data.

Today is mostly about looking, not fixing. You'll find a lot of problems, and write them down. Fixing them is Day 11.

1Meet online_store_full

The small online_store was like a practice exam: neat, short, every answer known. online_store_full is the real thing: the shop's records for two full years, exported from several different systems. The website and app wrote the orders, a payment company sent the payments, the warehouse logged the returns, HR keeps the staff list, and an analytics tool tracked clicks on the website. Each system had its own habits, and none of them was perfect.

It has ten tables. The first five are the ones you know, with a few extra columns. The other five are new:

TableOne row meansNew?
categoriesa product category (the same five)
productsa product. Now with a cost price, a launch date and an is_active flag
customersa sign-up. Now with phone number and how they found the shop
ordersan order. Now with the time as well as the date, the channel (web or app), any coupon, and the shipping fee
order_itemsa line on an order
employeesa member of staff, with their manager✓
paymentsa payment attempt. One order can have several.✓
returnsa returned order line✓
reviewsa rating and comment on a product✓
web_eventsone action on the website or app: a page view, add to cart, purchase and so on (October to December 2024 only)✓

That middle column is the most important idea of the day. Analysts call it the grain of a table: what exactly does one row stand for? Get it wrong and every count is wrong. Look at payments: one row is one attempt, not one order. If a card payment fails and the customer tries again with UPI, that's two rows for one order. Counting payment rows would overcount paid orders.

The data is messy on purpose. There are duplicate customers, inconsistent spellings, fake test orders, dates in the wrong format, and more. None of it was added to trick you. It's the same kind of mess every real company database has. Learning to spot it is one of the most valuable skills an analyst has.

2Load it

The whole database is one file, online_store_full.sql, in the series' GitHub repository. It's about 7 MB, so this is where you need MySQL on your own computer (Path B from Day 2). Online playgrounds can't handle a file this big.

In MySQL Workbench

  • Open File > Run SQL Script...
  • Pick online_store_full.sql and click Run.
  • Wait about a minute until it finishes.
  • Refresh the Schemas panel, and online_store_full appears.
Opening the file in the editor works too, but a 7 MB file makes the editor slow. Run SQL Script is quicker.

From the command line

  • Open a terminal in the folder with the file.
  • Run mysql -u root -p < online_store_full.sql
  • Type your password and wait.
  • The last thing it prints is a row count for every table.
It's the same way you can run complete_setup.sql, as shown in the series' README.

The file builds a new database. Your small online_store isn't touched, and every earlier lesson still works. From now on, switch between them with USE:

3Step 1: what's here, and how big is it?

Think of moving into a new house. Before you unpack anything, you walk through every room to see what's there. With a database, the walk-through starts with SHOW TABLES and the row counts you just saw.

There's also a faster way to see table sizes, without counting each table yourself. MySQL keeps notes about every database in a special built-in database called information_schema:

SQL
SELECT table_name, table_rows
FROM information_schema.tables
WHERE table_schema = 'online_store_full'
ORDER BY table_name;
Result
+-------------+------------+
| TABLE_NAME  | TABLE_ROWS |
+-------------+------------+
| categories  |          5 |
| customers   |       2980 |
| employees   |         30 |
| order_items |      10481 |
| orders      |       6086 |
| payments    |       6504 |
| products    |         61 |
| returns     |        556 |
| reviews     |       2117 |
| web_events  |      53024 |
+-------------+------------+

Compare it with the exact counts above. Several of these numbers are a little off (look at customers and orders), and when you run it yourself, you'll probably see different numbers again. That's not a bug. For InnoDB tables, table_rows is only an estimate, made from a quick sample, and MySQL refreshes it only from time to time. Your numbers may even differ from these. It's fine for "is this table about a thousand rows or about a million?", but whenever a number matters, use COUNT(*).

What is information_schema? It's MySQL's own catalogue of everything it stores: every database, table, column, key and index, in tables you can query like any other. You've already used SHOW TABLES and DESCRIBE. They get their answers from the same catalogue. Querying it directly lets you ask bigger questions, like "list every column in the whole database", in one go.

4Step 2: what's in each table?

Next, look at the columns. DESCRIBE works one table at a time. Here's the whole database at once, from information_schema.columns:

SQL
SELECT table_name,
       GROUP_CONCAT(CONCAT(column_name, ' ', column_type)
                    ORDER BY ordinal_position SEPARATOR ', ') AS columns_and_types
FROM information_schema.columns
WHERE table_schema = 'online_store_full'
  AND table_name IN ('customers', 'orders', 'web_events')
GROUP BY table_name;
Result
+------------+--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| TABLE_NAME | columns_and_types                                                                                                                                                                                      |
+------------+--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| customers  | customer_id int, first_name varchar(50), last_name varchar(50), email varchar(100), phone varchar(25), city varchar(50), country varchar(50), signup_date varchar(20), acquisition_channel varchar(30) |
| orders     | order_id int, customer_id int, order_date datetime, status varchar(20), channel varchar(10), coupon_code varchar(20), shipping_fee decimal(8,2)                                                        |
| web_events | event_id bigint, session_id varchar(20), customer_id int, event_time datetime, event_type varchar(30), product_id int, order_id int, device varchar(20), traffic_source varchar(30)                    |
+------------+--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+

(ordinal_position is each column's place in the table, so the columns come out in their real order.) Even this quick look raises questions an analyst should write down:

  • customers.signup_date is varchar(20), which is text, not a date. That's a red flag. You can't do date maths on text, and text dates can be in any format. Section 7 shows how bad it is.
  • orders.order_date is a datetime now, with a time. Remember Day 5's warning about BETWEEN on date-and-time columns.
  • web_events.customer_id exists, but is it linked to customers? Let's check.

5Step 3: how do the tables connect?

On Day 3 you created foreign keys. Now you can ask MySQL to list every one of them:

SQL
SELECT table_name,
       column_name,
       referenced_table_name,
       referenced_column_name
FROM information_schema.key_column_usage
WHERE table_schema = 'online_store_full'
  AND referenced_table_name IS NOT NULL
ORDER BY table_name, column_name;
Result
+-------------+---------------+-----------------------+------------------------+
| TABLE_NAME  | COLUMN_NAME   | REFERENCED_TABLE_NAME | REFERENCED_COLUMN_NAME |
+-------------+---------------+-----------------------+------------------------+
| employees   | manager_id    | employees             | employee_id            |
| order_items | order_id      | orders                | order_id               |
| order_items | product_id    | products              | product_id             |
| orders      | customer_id   | customers             | customer_id            |
| payments    | order_id      | orders                | order_id               |
| products    | category_id   | categories            | category_id            |
| returns     | order_item_id | order_items           | order_item_id          |
| returns     | processed_by  | employees             | employee_id            |
| reviews     | customer_id   | customers             | customer_id            |
| reviews     | product_id    | products              | product_id             |
+-------------+---------------+-----------------------+------------------------+

Ten links. Draw them, and you get a map of the database. Analysts call this an ER diagram (entity relationship diagram). Sketching one on paper is a great first-day habit.

Things: customers, products, categories, employeesEvents: orders, lines, payments, returns, reviewsweb_events: linked by ID only, no foreign keys

Two things stand out:

  • employees.manager_id points to employees itself, the self-referencing key from Day 3. And returns.processed_by tells you which employee handled each return.
  • web_events doesn't appear in the list at all. It holds customer, product and order IDs, but with no foreign keys. The tracking data comes from a separate analytics tool, so nothing checks that those IDs are real. Day 3 taught you that the guard only protects tables that have rules. Where there are no rules, expect problems (section 9 finds one).

7Step 5: profile the columns

Profiling means getting a quick summary of every important column: how many values are filled in, how many are different, the smallest and largest. It's like a doctor's check-up for data: a few quick measurements that show whether anything needs a closer look.

Every tool for this comes from Day 6. Here's a profile of customers:

SQL
SELECT COUNT(*)                AS customers,
       COUNT(city)             AS city_filled,
       SUM(city = '')          AS city_empty_text,
       SUM(city = 'N/A')       AS city_na,
       COUNT(DISTINCT city)    AS distinct_cities,
       COUNT(DISTINCT country) AS distinct_countries,
       MIN(signup_date)        AS min_signup,
       MAX(signup_date)        AS max_signup
FROM customers;
Result
+-----------+-------------+-----------------+---------+-----------------+--------------------+-------------+------------+
| customers | city_filled | city_empty_text | city_na | distinct_cities | distinct_countries | min_signup  | max_signup |
+-----------+-------------+-----------------+---------+-----------------+--------------------+-------------+------------+
|      3028 |        2937 |              32 |      14 |              44 |                 12 | 01-Aug-2023 | 31/10/2024 |
+-----------+-------------+-----------------+---------+-----------------+--------------------+-------------+------------+

Read it like a detective:

  • Missing cities come in three shapes. 91 are NULL (3,028 minus 2,937), 32 are empty text, and 14 are the text N/A. All three mean "we don't know", but only NULL is a real missing value. The other two are the fake NULLs you met on Day 4. A query looking for city IS NULL finds only 91 of the 137.
  • 12 countries sounds like a lot for a shop that's mostly in India. Section 8 checks why.
  • The earliest sign-up is "01-Aug-2023"? That can't be right, because there are orders from January 2023. Because signup_date is text, MIN compares it alphabetically, like words in a dictionary, and "01-Aug-..." comes before "2022-...". MIN and MAX on text dates are meaningless.

How many date formats are there? A CASE with REGEXP (Days 5 and 8) can sort the values by pattern:

SQL
SELECT CASE
           WHEN signup_date REGEXP '^[0-9]{4}-[0-9]{2}-[0-9]{2}$'    THEN 'YYYY-MM-DD'
           WHEN signup_date REGEXP '^[0-9]{2}/[0-9]{2}/[0-9]{4}$'    THEN 'DD/MM/YYYY'
           WHEN signup_date REGEXP '^[0-9]{2}-[A-Za-z]{3}-[0-9]{4}$' THEN 'DD-Mon-YYYY'
           ELSE 'something else'
       END AS date_format,
       COUNT(*) AS customers
FROM customers
GROUP BY date_format
ORDER BY customers DESC;
Result
+-------------+-----------+
| date_format | customers |
+-------------+-----------+
| YYYY-MM-DD  |      2428 |
| DD/MM/YYYY  |       460 |
| DD-Mon-YYYY |       140 |
+-------------+-----------+

(In a regular expression, {4} means "exactly 4 of the thing before", so [0-9]{4} is four digits.) Three formats, and luckily nothing else. Day 11 turns all three into proper DATE values with STR_TO_DATE.

SQL
SELECT MIN(quantity)    AS min_qty,
       MAX(quantity)    AS max_qty,
       SUM(quantity = 0) AS zero_qty_lines,
       MIN(unit_price)  AS min_price,
       MAX(unit_price)  AS max_price

Result
+---------+---------+----------------+-----------+-----------+

Four lines with a quantity of 0. Nobody buys zero of something. The table has no CHECK (quantity > 0) rule like our small shop did, so nothing stopped them. And a maximum of 10 is unusual for a shop where most people buy one or two of a thing. That's worth a look (section 9 explains it).

8Step 6: check the categories

For any column with a small set of allowed values (status, country, payment method), count each value. Messy spellings jump out straight away.

SQL
SELECT status, COUNT(*) AS orders
FROM orders
GROUP BY status
ORDER BY orders DESC;
Result
+------------+--------+
| status     | orders |
+------------+--------+
| Completed  |   5609 |
| cancelled  |    308 |
| Canceled   |     69 |
| Completed  |     60 |
| Pending    |     40 |
| Shipped    |     39 |
| COMPLETE   |     19 |
+------------+--------+

Something odd is going on. Completed appears twice, cancelled is in small letters, there's a Canceled with one L (the American spelling), and a COMPLETE. But even this list is hiding things. On Day 5 you learned that MySQL ignores capital letters when comparing text by default. GROUP BY does too, so completed and Completed were quietly put in the same group, and the group is shown under just one of the spellings. That's why the cancelled group appears as cancelled, in small letters, even though most of its rows say Cancelled.

To see the exact spellings, compare the text letter by letter with a binary collation, a setting that makes capitals count. The square brackets make spaces visible:

SQL
SELECT CONCAT('[', status, ']') COLLATE utf8mb4_0900_bin AS exact_status,
       COUNT(*) AS orders
FROM orders
GROUP BY exact_status
ORDER BY orders DESC;
Result
+--------------+--------+
| exact_status | orders |
+--------------+--------+
| [Completed]  |   4426 |
| [completed]  |   1183 |
| [Cancelled]  |    216 |
| [cancelled]  |     92 |
| [Canceled]   |     69 |
| [Completed ] |     60 |
| [Pending]    |     40 |
| [Shipped]    |     39 |
| [COMPLETE]   |     19 |
+--------------+--------+

Nine different spellings for what should be four statuses:

  • [Completed ] has a space at the end. That's why it formed its own group: MySQL ignores capitals, but it does not ignore trailing spaces. So WHERE status = 'Completed' misses those 60 orders.
  • completed and cancelled in small letters are 1,275 orders. Those happen to match = 'Completed' in MySQL. They wouldn't in PostgreSQL, which does care about capitals.
  • COMPLETE and Canceled are different words, so no comparison will ever catch them by accident.

Where did the small letters come from? One question tells you a lot:

SQL
SELECT channel,
       YEAR(order_date) AS yr,
       SUM(status COLLATE utf8mb4_0900_bin IN ('completed', 'cancelled')) AS lowercase_status,
       COUNT(*) AS orders
FROM orders
GROUP BY channel, yr
ORDER BY channel, yr;
Result
+---------+------+------------------+--------+
| channel | yr   | lowercase_status | orders |
+---------+------+------------------+--------+
| app     | 2023 |             1045 |   1047 |
| app     | 2024 |              230 |   1823 |
| web     | 2023 |                0 |   1475 |
| web     | 2024 |                0 |   1797 |
| web     | 2025 |                0 |      2 |
+---------+------+------------------+--------+

Only app orders, and only until early 2024. The likely story: the mobile app wrote statuses in small letters until an update fixed it. That's typical of real mess: it usually has a cause, and finding the cause tells you how far the problem goes and whether it's still happening.

Pick the right binary collation. MySQL 8 has two: utf8mb4_0900_bin, which we used, and an older one, utf8mb4_bin. Both make capitals count, but the older one ignores spaces at the end, so grouping with it would merge Completed back into Completed and hide the very problem you're looking for. Use utf8mb4_0900_bin.

9Step 7: duplicates, test data and orphans

Duplicate customers

Day 6's duplicate check, on emails:

SQL
SELECT COUNT(*) AS duplicated_emails
FROM (SELECT email
      FROM customers
      GROUP BY email
      HAVING COUNT(*) > 1) AS d;
Result
+-------------------+
| duplicated_emails |
+-------------------+
|                20 |
+-------------------+

20 emails belong to more than one account. And because MySQL ignores capitals, Shruti.joshi@gmail.com and shruti.joshi@gmail.com were already counted as the same email. But trailing spaces count, so tidy the email first and check again:

SQL
SELECT COUNT(*) AS duplicated_emails
FROM (SELECT LOWER(TRIM(email)) AS clean_email
      FROM customers
      GROUP BY clean_email
      HAVING COUNT(*) > 1) AS d;
Result
+-------------------+
| duplicated_emails |
+-------------------+
|                25 |
+-------------------+

25. Here's one of them:

SQL
SELECT customer_id, first_name, last_name, CONCAT('[', email, ']') AS email, signup_date
FROM customers
WHERE LOWER(TRIM(email)) = 'reyansh.kapoor@gmail.com';
Result
+-------------+------------+-----------+-----------------------------+-------------+
| customer_id | first_name | last_name | email                       | signup_date |
+-------------+------------+-----------+-----------------------------+-------------+
|        1247 | Reyansh    | Kapoor    | [reyansh.kapoor@gmail.com]  | 2023-03-11  |
|        3012 | Reyansh    | Kapoor    | [reyansh.kapoor@gmail.com ] | 2023-10-01  |
+-------------+------------+-----------+-----------------------------+-------------+

Same person, signed up twice, the second time with a space after the email. And both accounts have orders, so "orders per customer" and "repeat customers" are both wrong until you merge them. Note it down.

Test accounts

Developers and testers create fake accounts to check that the shop works. Those orders are real rows, but not real sales. A quick search:

SQL
SELECT c.customer_id, c.first_name, c.email, COUNT(o.order_id) AS orders,
       SUM(oi.quantity) AS units
FROM customers c

An orphan is a row that points to something that doesn't exist. Foreign keys make orphans impossible (unless someone switches the checks off while loading data), which is why section 5 matters: web_events has no foreign keys. Day 7's anti-join finds them:

11Why all this matters: two revenue numbers

Say the owner asks for total revenue over the two years, and you write the query you learned on Day 7. Here it is next to a more careful version, which reads the messy statuses properly and leaves out test orders and the two orders from the future:

SQL
SELECT ROUND(SUM(CASE WHEN o.status = 'Completed'
                      THEN oi.quantity * oi.unit_price END)) AS naive_revenue,
       ROUND(SUM(CASE WHEN LOWER(TRIM(o.status)) IN ('completed', 'complete')
                       AND c.email NOT LIKE '%test%'
                       AND o.order_date <= '2024-12-31 23:59:59'
                      THEN oi.quantity * oi.unit_price END)) AS careful_revenue
FROM orders o
JOIN order_items oi ON oi.order_id    = o.order_id
JOIN customers c    ON c.customer_id  = o.customer_id;
Result

| naive_revenue | careful_revenue |
+---------------+-----------------+
|      13101912 |        13188809 |
+---------------+-----------------+

The naive number is about ₹87,000 lower. It misses the 79 orders spelled Completed or COMPLETE, which is more than it wrongly includes from test accounts and future dates. Neither error would ever show up as a SQL error. The query runs, the number looks believable, and it's wrong.

And the careful version still isn't finished: it still counts the 15 double-submitted orders, and it ignores returns. That's the honest truth about real data: the SQL is usually the easy part. Knowing what the data really means is the job.

🎯 Interview corner

"You've been given a dataset you've never seen. What do you do first?" is one of the most common analyst interview questions. These answers give you a structure for it.

Concept questions

Q1You get access to a database you've never seen. What are your first steps?

Walk through it before answering anything. List the tables and their sizes. Understand each table's grain (what one row means). Map the keys and relationships, ideally with an ER diagram. Look at sample rows. Profile the important columns: NULLs, distinct values, min and max. Check category columns for inconsistent values, and look for duplicates, orphans, test data and out-of-range dates. Write the findings in an issues log, and ask the data owners about anything that needs a business decision.

Q2What is data profiling?

Summarising each column to understand its contents and quality: row count, how many values are filled in (and how many are NULL), the number of distinct values, min and max, the most common values, and the format of the values. It's done with simple aggregates like COUNT, COUNT(DISTINCT), MIN, MAX and GROUP BY, and it's the fastest way to find quality problems before they reach a report.

Q3What does "grain" mean, and why does it matter?

The grain is what one row of a table represents: one order, one order line, one payment attempt, one click. It decides what you can count and sum safely. If you think payments has one row per order but it really has one per attempt, you'll overcount paid orders and overstate the amount collected. Always confirm the grain before aggregating, and again after every join.

Q4What is information_schema? Give an example of using it.

A built-in database where MySQL describes everything it stores: databases, tables, columns, keys, indexes. You query it like normal tables. Examples: list all columns in a database from information_schema.columns, or all foreign keys from information_schema.key_column_usage. One catch: information_schema.tables.table_rows is only an estimate for InnoDB tables, so use COUNT(*) for exact numbers.

Q5Why might GROUP BY status hide inconsistent values in MySQL?

Because MySQL's default collation is case-insensitive, so 'completed' and 'Completed' count as equal and land in one group, shown under just one of the spellings. Trailing spaces, however, do count with the default MySQL 8 collation, so 'Completed ' forms a separate group. To see exact spellings, group by the value with a binary collation, for example GROUP BY status COLLATE utf8mb4_0900_bin. Avoid the older utf8mb4_bin for this: it ignores trailing spaces.

Q6What's the difference between NULL, an empty string and 'N/A'?

Only NULL is a real missing value. IS NULL finds it, and aggregates skip it. An empty string '' and the text 'N/A' are real values that mean missing, so IS NULL doesn't find them and COUNT(column) counts them as filled in. In profiling, check all three. In cleaning, usually turn the fake ones into NULL, for example with NULLIF.

Q7What is an orphan record, and how do you find one?

A row whose foreign-key-style column points to a row that doesn't exist, such as an order line for a deleted order. Foreign keys prevent them, so orphans appear where no foreign key exists, as with data copied between systems. Find them with an anti-join: LEFT JOIN parent ... WHERE parent.id IS NULL AND child.parent_id IS NOT NULL.

Q8Why should you exclude test data, and how do you find it?

Test accounts and orders are real rows but not real business, so they inflate revenue, order counts and units sold. Look for tell-tale emails and names ("test", "qa", "example.com"), odd quantities, internal domains and unusual prices. The best source is a list from the engineering team, because pattern searches never catch everything.

Practical questions

P1Write one query that profiles the city column: total rows, NULLs, empty strings, distinct values, and the most common value.
SQL
SELECT COUNT(*)                       AS total_rows,
       SUM(city IS NULL)              AS null_values,
       SUM(city = '')                 AS empty_strings,
       COUNT(DISTINCT city)           AS distinct_values,
       (SELECT city FROM customers
        WHERE city IS NOT NULL
        GROUP BY city ORDER BY COUNT(*) DESC LIMIT 1) AS most_common
FROM customers;
Result
+------------+-------------+---------------+-----------------+-------------+
| total_rows | null_values | empty_strings | distinct_values | most_common |
+------------+-------------+---------------+-----------------+-------------+
|       3028 |          91 |            32 |              44 | Mumbai      |
+------------+-------------+---------------+-----------------+-------------+

Aggregates for the counts, and a scalar subquery (Day 8) for the most common value. SUM(condition) counts the rows where the condition is true (Day 6).

P2Find customers whose email appears more than once, ignoring capital letters and extra spaces. Show every account involved.
SQL
WITH duplicated AS (
    SELECT LOWER(TRIM(email)) AS clean_email
    FROM customers
    GROUP BY clean_email
    HAVING COUNT(*) > 1
)
SELECT c.customer_id, c.first_name, c.last_name, c.email
FROM customers c
JOIN duplicated d ON d.clean_email = LOWER(TRIM(c.email))
ORDER BY d.clean_email, c.customer_id
LIMIT 6;

| customer_id | first_name | last_name | email                   |

P3How many order lines point to a product that doesn't exist? How many products have never appeared on an order?
SQL
SELECT
    (SELECT COUNT(*)
     FROM order_items oi
     LEFT JOIN products p ON p.product_id = oi.product_id
     WHERE p.product_id IS NULL)                AS orphan_lines,
    (SELECT COUNT(*)
     FROM products p
     WHERE NOT EXISTS (SELECT 1 FROM order_items oi
                       WHERE oi.product_id = p.product_id)) AS never_ordered_products;
Result
+--------------+------------------------+
| orphan_lines | never_ordered_products |
+--------------+------------------------+
|            0 |                      0 |
+--------------+------------------------+

No orphan lines, because order_items.product_id has a foreign key, so it's impossible. That's worth saying in an interview: "I checked, and the foreign key guarantees it." And every product, even the new Smart Fitness Band, has been ordered at least once. Checking both directions is the habit: children without parents, and parents without children.

Quick recap

  • online_store_full has 10 tables of real, messy records for 2023 and 2024. Load it once from online_store_full.sql, and switch with USE.
  • Know the grain of every table: one order, one line, one payment attempt, one click.
  • information_schema describes the whole database. Its table_rows is only an estimate, so use COUNT(*) for real numbers.
  • The first-hour checklist: tables and sizes, columns and types, keys and an ER diagram, sample rows, column profiles, category values, ranges and dates, duplicates, test data and orphans.
  • MySQL hides case differences in comparisons and GROUP BY. Use COLLATE utf8mb4_0900_bin to see exact spellings. Trailing spaces are not ignored.
  • Missing values hide as NULL, '' and 'N/A'. MIN and MAX on text dates are meaningless.
  • A believable number can still be wrong: naive revenue missed ₹87,000. Write every finding in a data issues log, and don't change the raw data in place.
