1What the harder rounds test

A first round checks that you can write correct SQL. Later rounds check whether you can be trusted with real work, where nobody tells you which pattern to use, and a query that runs isn't necessarily right. Here's what you're likely to meet, and where this series prepared you:

Day 15's five steps (clarify, name the grain, plan, build and look, test the edges) still apply to every one of these. Harder rounds add three habits on top:

  • Name the trade-off. "A window function is clearer here. A self join would also work, but it would count each pair twice." Showing that you chose is worth more than the choice itself.
  • Check the number against something you know. "The three years add up to 13.17 million, the same as the total, so nothing was lost or counted twice."
  • Say what you'd do next. An analysis rarely ends with a number. "This tells us where the drop is. Next, I'd check whether anything changed on the website that month."

2Practice: multi-step problems

Each of these needs three or four patterns in a row. Plan with named steps (Day 15), build one step at a time, and look out for the trap that's hidden in each.

1. Rebuild website visits from timestamps

The question: "Our tracking tool's session IDs can't be trusted. For logged-in customers, rebuild the visits yourself: a new visit starts when a customer has been inactive for more than 30 minutes. How many visits are there?"

Show the answer

This is called sessionisation, a classic. The plan has three steps: for each event, find the time of the customer's previous event (LAG, Day 9). Flag the event as the start of a new visit if there's no previous event, or the gap is over 30 minutes. Then a running total of the flags numbers the visits, the same trick as Day 16's gaps and islands.

SQL
WITH with_previous AS (
    SELECT customer_id, event_id, event_time, session_id,
           LAG(event_time) OVER (PARTITION BY customer_id ORDER BY event_time, event_id) AS previous_time
    FROM clean_web_events
    WHERE customer_id IS NOT NULL
), flagged AS (
    SELECT *,
           CASE WHEN previous_time IS NULL
                  OR event_time > previous_time + INTERVAL 30 MINUTE
                THEN 1 ELSE 0 END AS starts_visit
    FROM with_previous
), numbered AS (
    SELECT *,
           SUM(starts_visit) OVER (PARTITION BY customer_id ORDER BY event_time, event_id) AS visit_no
    FROM flagged
)
SELECT COUNT(*)                             AS events,
       COUNT(DISTINCT customer_id, visit_no) AS visits_rebuilt,
       COUNT(DISTINCT session_id)            AS session_ids
FROM numbered;
Result
+--------+----------------+-------------+
| events | visits_rebuilt | session_ids |
+--------+----------------+-------------+
|  17916 |           5534 |        5547 |
+--------+----------------+-------------+

The trap is in the ORDER BY: two events can share a timestamp, so event_id breaks the tie, and it must be the same order in both windows, or the running total and LAG disagree about which event came first (Day 9's tie-breaker). Then check your answer against something you know: the tracking tool's session IDs. 5,534 rebuilt visits against 5,547 session IDs is very close, so the rule works. And a good candidate asks about the 13 that differ:

SQL
WITH with_previous AS (
    SELECT customer_id, event_id, event_time, session_id,
           LAG(event_time) OVER (PARTITION BY customer_id ORDER BY event_time, event_id) AS previous_time
    FROM clean_web_events
    WHERE customer_id IS NOT NULL
), numbered AS (
    SELECT *,
           SUM(CASE WHEN previous_time IS NULL
                      OR event_time > previous_time + INTERVAL 30 MINUTE
                    THEN 1 ELSE 0 END)
               OVER (PARTITION BY customer_id ORDER BY event_time, event_id) AS visit_no
    FROM with_previous
)
SELECT session_ids_in_visit, COUNT(*) AS visits
FROM (SELECT customer_id, visit_no, COUNT(DISTINCT session_id) AS session_ids_in_visit
      FROM numbered
      GROUP BY customer_id, visit_no) v
GROUP BY session_ids_in_visit;
Result
+----------------------+--------+
| session_ids_in_visit | visits |
+----------------------+--------+
|                    1 |   5521 |
|                    2 |     13 |
+----------------------+--------+

13 of the rebuilt visits contain two session IDs: the tracking tool started a new session even though the customer came back within 30 minutes (some tools do this at midnight, or when a visitor arrives from a different advert). Neither answer is "wrong". They're two definitions, and the one-sentence answer says so: "5,534 visits by the 30-minute rule, 13 fewer than the tool's sessions, because the tool sometimes splits one visit in two."

2. Second orders within 30 days

The question: "What share of new customers placed a second order within 30 days of their first? Show it by the quarter of their first order."

Show the answer

Clarify first: "orders" means completed orders (clean_sales). The grain is one row per first-order quarter. The plan: number each customer's orders (ROW_NUMBER), put the first and second order dates side by side (a pivot with MAX(CASE ...), Day 8), flag who came back within 30 days, then group. There are two traps, and this question exists to see if you find them:

SQL
WITH orders AS (
    SELECT DISTINCT customer_id, order_id, order_date      -- one row per order, not per line
    FROM clean_sales
), ranked AS (
    SELECT customer_id, order_date,
           ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date, order_id) AS n
    FROM orders
), firsts AS (
    SELECT customer_id,
           MAX(CASE WHEN n = 1 THEN order_date END) AS first_order,
           MAX(CASE WHEN n = 2 THEN order_date END) AS second_order
    FROM ranked
    GROUP BY customer_id
), flags AS (
    SELECT first_order,
           first_order < '2024-11-25'                                AS had_30_days,  -- trap 2
           COALESCE(second_order < first_order + INTERVAL 30 DAY, 0) AS back_in_30      -- trap 1
    FROM firsts
)
SELECT CONCAT(YEAR(first_order), '-Q', QUARTER(first_order)) AS first_quarter,
       COUNT(*)                         AS new_customers,
       SUM(had_30_days)                 AS had_30_days,
       SUM(had_30_days AND back_in_30)  AS back_within_30,
       ROUND(100 * SUM(had_30_days AND back_in_30) / SUM(had_30_days), 1) AS pct_back
FROM flags
GROUP BY first_quarter
ORDER BY first_quarter;
Result
+---------------+---------------+-------------+----------------+----------+
| first_quarter | new_customers | had_30_days | back_within_30 | pct_back |
+---------------+---------------+-------------+----------------+----------+
| 2023-Q1       |           243 |         243 |             49 |     20.2 |
| 2023-Q2       |           254 |         254 |             24 |      9.4 |
| 2023-Q3       |           279 |         279 |             37 |     13.3 |
| 2023-Q4       |           313 |         313 |             63 |     20.1 |
| 2024-Q1       |           167 |         167 |             16 |      9.6 |
| 2024-Q2       |           274 |         274 |             29 |     10.6 |
| 2024-Q3       |           299 |         299 |             39 |     13.0 |
| 2024-Q4       |           286 |         189 |             38 |     20.1 |
+---------------+---------------+-------------+----------------+----------+

Trap 1: NULL. For a customer who never came back, second_order is NULL, so the comparison is NULL too, not 0. If you'd written AVG(second_order < first_order + INTERVAL 30 DAY), AVG would quietly skip everyone who never came back, and the answer would be the share of returning customers who returned quickly: 72.6% for 2024-Q4 instead of the real figure. That's why COALESCE(..., 0) is there (Day 5's NULL rules).

Trap 2: not everyone had 30 days. The last completed order is on 28 December 2024, and Day 12 showed that orders from the last week haven't all settled, so the fair data ends on 24 December. Someone whose first order was on 10 December had no real chance to come back within 30 days, and counting them as "didn't come back" makes the latest quarter look worse than it is. So only customers whose first order was before 25 November count, because their 30 days end by 24 December. Without this fix, 2024-Q4 shows 15.7%. With it, only the 189 customers who had a full, settled 30 days are counted, in the top and the bottom of the fraction, giving 20.1% (Day 13's rule: give everyone the same time, and only count settled data). Then the answer: "Between 1 in 10 and 1 in 5 new customers order again within a month. It's about 20% for customers who first bought in October to December, the festive quarters (and in the shop's very first quarter), and 10 to 13% the rest of the time."

3Practice: find the bug

A favourite format: "Here's a query a colleague wrote. It runs, and it's going into a report tomorrow. Is it right?" Every query below runs without an error, and every one is wrong. Read each one slowly, look at the output, and say what you'd check before opening the answer.

1. Revenue by payment method

SQL
SELECT p.payment_method,
       ROUND(SUM(s.line_total)) AS revenue
FROM clean_sales s
JOIN clean_payments p ON p.order_id = s.order_id
GROUP BY p.payment_method WITH ROLLUP;
Result
+----------------+----------+
| payment_method | revenue  |
+----------------+----------+
| Card           |  3420370 |
| COD            |  2330545 |
| NetBanking     |   941611 |
| UPI            |  6442167 |
| Wallet         |   721149 |
| NULL           | 13855840 |
+----------------+----------+
Show the bug

The total is 13,855,840, but total revenue is 13,172,860 (Day 17, and yesterday's financial years). Whenever a join is involved and a total grows, suspect fan-out (Day 7): some orders have more than one payment row. A failed card payment followed by a successful one gives two rows, so every line of that order was counted twice. The fix is to decide which payment counts, which is the successful one:

SQL
SELECT p.payment_method,
       ROUND(SUM(s.line_total)) AS revenue
FROM clean_sales s
JOIN clean_payments p ON p.order_id = s.order_id
                     AND p.payment_status = 'success'
GROUP BY p.payment_method WITH ROLLUP;
Result
+----------------+----------+
| payment_method | revenue  |
+----------------+----------+
| Card           |  3127178 |
| COD            |  2330545 |
| NetBanking     |   816175 |
| UPI            |  6201995 |
| Wallet         |   696967 |
| NULL           | 13172860 |
+----------------+----------+

The total matches now, and the method matters: Card fell by almost 300,000, because failed card payments are common. The habit to describe in the interview: check the total against a number you trust, and before joining, ask "can this table have more than one row per order?"

2. Employees who manage nobody

SQL
SELECT e.employee_id, e.first_name, COUNT(*) AS direct_reports
FROM employees e
LEFT JOIN employees r ON r.manager_id = e.employee_id
GROUP BY e.employee_id, e.first_name
HAVING COUNT(*) = 0;
Result
(no rows)
Show the bug

No rows, in a company of 30 where most people manage nobody. The LEFT JOIN is right: it keeps people with no reports, with NULLs in the r columns. But COUNT(*) counts rows, and that NULL row is still a row, so everybody has at least 1 (Day 6). Count a column from the right-hand table instead, which ignores NULLs:

SQL
SELECT e.employee_id,
       CONCAT(e.first_name, ' ', e.last_name) AS employee,
       e.job_title
FROM employees e
LEFT JOIN employees r ON r.manager_id = e.employee_id
GROUP BY e.employee_id, e.first_name, e.last_name, e.job_title
HAVING COUNT(r.employee_id) = 0
ORDER BY e.employee_id;

3. Two categories' share of 2024 revenue

SQL
SELECT category_name,
       ROUND(SUM(line_total)) AS revenue,
       ROUND(100 * SUM(line_total) / SUM(SUM(line_total)) OVER (), 1) AS share_pct
FROM clean_sales
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'
  AND category_name IN ('Electronics', 'Clothing')
GROUP BY category_name;
Result
+---------------+---------+-----------+
| category_name | revenue | share_pct |
+---------------+---------+-----------+
| Clothing      | 2002168 |      43.4 |
| Electronics   | 2609135 |      56.6 |
+---------------+---------+-----------+
Show the bug

The shares add up to exactly 100%, which would mean the shop sold nothing else. Remember the order MySQL works in (Day 15): WHERE runs first, and window functions run near the end, so SUM(...) OVER () only sees the two categories that survived the filter. The denominator is wrong. Calculate the shares on everything first, and filter afterwards:

SQL
WITH by_category AS (
    SELECT category_name,
           SUM(line_total) AS revenue,
           100 * SUM(line_total) / SUM(SUM(line_total)) OVER () AS share_pct
    FROM clean_sales
    WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'
    GROUP BY category_name
)
SELECT category_name, ROUND(revenue) AS revenue, ROUND(share_pct, 1) AS share_pct
FROM by_category
WHERE category_name IN ('Electronics', 'Clothing');
Result
+---------------+---------+-----------+
| category_name | revenue | share_pct |
+---------------+---------+-----------+
| Clothing      | 2002168 |      25.1 |
| Electronics   | 2609135 |      32.7 |
+---------------+---------+-----------+

Together they're 57.8% of 2024 revenue, not 100%. The general rule: shares, ranks and running totals depend on which rows the window can see, so filter after the window when you want the whole picture.

4Practice: why did the number fall?

The question: "Revenue fell 23% from January to February 2024. The head of sales wants to know why by this afternoon."

This is the most common case question for analysts, and the worst answer is a guess. A good answer follows a routine, like a doctor ruling things out: is the data right? Is it normal for the time of year? Which part of the number moved? Who or what moved it? Try writing the queries yourself first.

Show the investigation

Step 1: is it real, and is it normal? Check that both months are complete, and compare with the same months last year. Put the numbers per day, because February is shorter:

SQL
SELECT DATE_FORMAT(order_date, '%Y-%m')       AS month,
       COUNT(DISTINCT DATE(order_date))       AS days_with_sales,
       COUNT(DISTINCT order_id)               AS orders,
       ROUND(SUM(line_total))                 AS revenue,
       ROUND(SUM(line_total) / COUNT(DISTINCT DATE(order_date))) AS revenue_per_day,
       ROUND(SUM(line_total) / COUNT(DISTINCT order_id))         AS avg_order_value
FROM clean_sales
WHERE (order_date >= '2023-01-01' AND order_date < '2023-03-01')
   OR (order_date >= '2024-01-01' AND order_date < '2024-03-01')
GROUP BY month
ORDER BY month;
Result
+---------+-----------------+--------+---------+-----------------+-----------------+
| month   | days_with_sales | orders | revenue | revenue_per_day | avg_order_value |
+---------+-----------------+--------+---------+-----------------+-----------------+
| 2023-01 |              31 |    126 |  256113 |            8262 |            2033 |
| 2023-02 |              28 |    102 |  205905 |            7354 |            2019 |
| 2024-01 |              31 |    245 |  592610 |           19116 |            2419 |
| 2024-02 |              29 |    200 |  456942 |           15757 |            2285 |
+---------+-----------------+--------+---------+-----------------+-----------------+

Every day has sales, so no data is missing. Part of the fall is the calendar: February 2024 had 29 days against January's 31, and last year February also fell about 20% after January. But per day, 2024 fell further (from about 19,100 to 15,800, down 18%, against 11% the year before). And the drop is mostly in the number of orders (245 to 200, down 18%), not their size (average order value down about 6%). So the question becomes: who stopped ordering?

Step 2: split it. Two natural splits for a shop: new versus returning customers, and app versus website. One row per order first, then ROLLUP for the subtotals (Day 16):

SQL
WITH first_orders AS (
    SELECT customer_id, MIN(order_date) AS first_order
    FROM clean_sales
    GROUP BY customer_id
), orders AS (
    SELECT s.order_id,
           MIN(s.order_date)    AS order_date,
           MIN(s.channel)       AS channel,
           CASE WHEN MIN(s.order_date) = MIN(f.first_order) THEN 'new' ELSE 'returning' END AS customer_type,
           SUM(s.line_total)    AS revenue
    FROM clean_sales s
    JOIN first_orders f ON f.customer_id = s.customer_id
    WHERE s.order_date >= '2024-01-01' AND s.order_date < '2024-03-01'
    GROUP BY s.order_id
)
SELECT customer_type, channel,
       SUM(order_date <  '2024-02-01') AS jan_orders,
       SUM(order_date >= '2024-02-01') AS feb_orders,
       ROUND(SUM(CASE WHEN order_date <  '2024-02-01' THEN revenue END)) AS jan_revenue,
       ROUND(SUM(CASE WHEN order_date >= '2024-02-01' THEN revenue END)) AS feb_revenue
FROM orders
GROUP BY customer_type, channel WITH ROLLUP;
Result
+---------------+---------+------------+------------+-------------+-------------+
| customer_type | channel | jan_orders | feb_orders | jan_revenue | feb_revenue |
+---------------+---------+------------+------------+-------------+-------------+
| new           | app     |         18 |         25 |       45943 |       48800 |
| new           | web     |         29 |         33 |       47903 |       66555 |
| new           | NULL    |         47 |         58 |       93847 |      115355 |
| returning     | app     |         91 |         77 |      240371 |      207679 |
| returning     | web     |        107 |         65 |      258392 |      133908 |
| returning     | NULL    |        198 |        142 |      498763 |      341587 |
| NULL          | NULL    |        245 |        200 |      592610 |      456942 |
+---------------+---------+------------+------------+-------------+-------------+

Now it's clear. Revenue fell by about 136,000 in total. New customers actually grew (93,847 to 115,355). Returning customers on the app dipped a little. Almost the whole drop is returning customers on the website: 107 orders to 65, and 258,392 to 133,908, a fall of about 124,000, or 9 out of every 10 rupees lost.

Step 3: one month, or a trend?

SQL
WITH first_orders AS (
    SELECT customer_id, MIN(order_date) AS first_order
    FROM clean_sales
    GROUP BY customer_id
), orders AS (
    SELECT s.order_id,
           MIN(s.order_date) AS order_date,
           MIN(s.channel)    AS channel,
           MIN(s.order_date) > MIN(f.first_order) AS is_returning
    FROM clean_sales s
    JOIN first_orders f ON f.customer_id = s.customer_id
    WHERE s.order_date >= '2023-11-01' AND s.order_date < '2024-04-01'
    GROUP BY s.order_id
)
SELECT DATE_FORMAT(order_date, '%Y-%m')          AS month,
       SUM(is_returning AND channel = 'web')     AS returning_web,
       SUM(is_returning AND channel = 'app')     AS returning_app,
       SUM(NOT is_returning)                     AS new_customers
FROM orders
GROUP BY month
ORDER BY month;
Result
+---------+---------------+---------------+---------------+
| month   | returning_web | returning_app | new_customers |
+---------+---------------+---------------+---------------+
| 2023-11 |           119 |           100 |            96 |
| 2023-12 |            99 |            81 |           103 |
| 2024-01 |           107 |            91 |            47 |
| 2024-02 |            65 |            77 |            58 |
| 2024-03 |            84 |            69 |            62 |
+---------+---------------+---------------+---------------+

Returning website orders ran at about 100 to 120 a month, dropped to 65 in February, and partly recovered to 84 in March. A dip, not a collapse, and limited to one group.

Step 4: the answer, and what you can't know yet. "Part of the fall is normal for February: it's a shorter month, and sales dipped after January last year too. But this year's dip was bigger, and almost all of it came from returning customers ordering on the website, whose orders fell by about 40% in February and partly recovered in March. New customers and app orders held up. Something may have affected returning customers on the website in February: a login problem, a change to the site, or an email campaign that stopped. Our website tracking only starts in October 2024, so I can't check that from the data. I'd ask the web team what changed that month."

Notice what that answer does: it starts with the conclusion, gives numbers rounded enough to remember, separates what the data shows from what it suggests, and ends with a next step. That's the whole skill.

5Practice: make it faster

The question: "This query powers a dashboard tile, 'the latest 10 orders of the year'. On the real orders table, which has 50 million rows, it takes 20 seconds. Walk me through what you'd do."

SQL
SELECT order_id, customer_id, order_date
FROM orders
WHERE YEAR(order_date) = 2024
ORDER BY order_date DESC
LIMIT 10;
Show the answer

Follow Day 18's routine, starting with the plan, not a guess:

SQL
EXPLAIN
SELECT order_id, customer_id, order_date
FROM orders
WHERE YEAR(order_date) = 2024
ORDER BY order_date DESC
LIMIT 10;
Result
+----+-------------+--------+------------+------+---------------+------+---------+------+------+----------+-----------------------------+
| id | select_type | table  | partitions | type | possible_keys | key  | key_len | ref  | rows | filtered | Extra                       |
+----+-------------+--------+------------+------+---------------+------+---------+------+------+----------+-----------------------------+
|  1 | SIMPLE      | orders | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 6285 |   100.00 | Using where; Using filesort |

Say what you see: "type: ALL, so every row is read. Using filesort, so all the 2024 rows are sorted just to keep 10. There's no index on order_date, and even if there were, YEAR() would hide the column from it." Two fixes, in this order: make the condition sargable (Day 12's half-open range), then suggest an index on the column you filter and sort by:

Build: try the index
CREATE INDEX idx_orders_date ON orders (order_date);
SQL
EXPLAIN
SELECT order_id, customer_id, order_date
FROM orders
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'
ORDER BY order_date DESC
LIMIT 10;

A range on the new index, read backwards from the newest order, with no filesort. MySQL can stop after the first 10. (The rows estimate is for the whole range. The LIMIT is applied as it reads.)

A sharp interviewer follows up: "With the index, the YEAR() version also shows a backward index scan in EXPLAIN. So does sargability still matter?" Yes, and you can prove it by counting the rows read for a year that isn't the newest (Day 18's counters):

SQL
FLUSH STATUS;
SELECT COUNT(*) AS found FROM (
    SELECT order_id FROM orders
    WHERE YEAR(order_date) = 2023
    ORDER BY order_date DESC LIMIT 10) latest;
SHOW SESSION STATUS WHERE Variable_name = 'Handler_read_prev';

FLUSH STATUS;
SELECT COUNT(*) AS found FROM (
    SELECT order_id FROM orders
    WHERE order_date >= '2023-01-01' AND order_date < '2024-01-01'
    ORDER BY order_date DESC LIMIT 10) latest;
SHOW SESSION STATUS WHERE Variable_name = 'Handler_read_prev';

+-------------------+-------+

(The outer COUNT just keeps the output short. Handler_read_prev counts steps backwards through an index.) The YEAR() version walks backwards through every 2024 order, over 3,600 of them, checking YEAR() on each, before it reaches 2023. The range jumps straight to the end of 2023 and reads only the 10 it needs. On 50 million rows, that's the difference between milliseconds and the 20 seconds you started with. Finally, tidy up, because this isn't our database to change:

Build: remove the practice index
DROP INDEX idx_orders_date ON orders;

In a real job, you'd bring the two plans to the database team rather than create the index yourself (Day 18).

Quick performance questions

These are usually asked in a minute or two each, without a computer:

  • "Your query uses SELECT DISTINCT and it's slow." Ask why there are duplicates. Usually it's a join that multiplies rows (Day 7), and the fix is EXISTS or aggregating before the join, which is faster and honest.
  • "A correlated subquery finds each customer's latest order." It runs once per row, unless the optimizer rewrites it (Day 8). ROW_NUMBER() in one pass is usually clearer and faster (Day 9). When unsure, compare plans.
  • "Which columns would you index?" The ones you join on, filter on and sort by, starting with foreign keys. One good composite index, with the equality column first, beats several single ones (Day 18).
  • "Why not index everything?" Space, and slower writes. In Day 18, four indexes took more space than the table itself.

6Practice: design, and "what would you do if..."

A design question

The question: "Design the tables for a food delivery app. Customers order from restaurants. Each order has several dishes, and a delivery partner brings it. We want to report the average delivery time by restaurant and hour of the day."

Show a good answer

Start by listing the things (nouns become tables) and how they relate, out loud, before writing anything: a customer places many orders, a restaurant receives many orders and has many dishes, an order has many dishes and each dish appears in many orders (many-to-many, so a junction table, Day 17), and one partner delivers each order. Then the tables:

Sketch: the tables
CREATE TABLE customers (
    customer_id   INT PRIMARY KEY,
    name          VARCHAR(100) NOT NULL,
    phone         VARCHAR(20),
    city          VARCHAR(50)
);
CREATE TABLE restaurants (
    restaurant_id INT PRIMARY KEY,
    name          VARCHAR(100) NOT NULL,
    city          VARCHAR(50),
    cuisine       VARCHAR(50)
);
CREATE TABLE dishes (
    dish_id       INT PRIMARY KEY,
    restaurant_id INT NOT NULL,
    name          VARCHAR(100) NOT NULL,
    price         DECIMAL(8,2) NOT NULL,
    FOREIGN KEY (restaurant_id) REFERENCES restaurants (restaurant_id)
);
CREATE TABLE partners (
    partner_id    INT PRIMARY KEY,
    name          VARCHAR(100) NOT NULL,
    vehicle       VARCHAR(20)
);
CREATE TABLE orders (
    order_id      INT PRIMARY KEY,
    customer_id   INT NOT NULL,
    restaurant_id INT NOT NULL,
    partner_id    INT,                          -- NULL until a partner is assigned
    status        VARCHAR(20) NOT NULL,
    placed_at     DATETIME NOT NULL,
    picked_up_at  DATETIME,
    delivered_at  DATETIME,
    FOREIGN KEY (customer_id)   REFERENCES customers (customer_id),
    FOREIGN KEY (restaurant_id) REFERENCES restaurants (restaurant_id),
    FOREIGN KEY (partner_id)    REFERENCES partners (partner_id)
);
CREATE TABLE order_items (
    order_id      INT NOT NULL,
    dish_id       INT NOT NULL,
    quantity      INT NOT NULL CHECK (quantity > 0),
    unit_price    DECIMAL(8,2) NOT NULL,        -- the price paid, which may change later
    PRIMARY KEY (order_id, dish_id),
    FOREIGN KEY (order_id) REFERENCES orders (order_id),
    FOREIGN KEY (dish_id)  REFERENCES dishes (dish_id)
);

Then explain the choices that show judgment:

  • unit_price in order_items, even though dishes has a price. Menu prices change, and an old order must keep the price that was paid. It's not duplication. It's a different fact (Day 17).
  • partner_id can be NULL, because an order exists before anyone is assigned. Timestamps for each stage (placed_at, picked_up_at, delivered_at) make delivery time a simple subtraction.
  • The report: "average delivery time by restaurant and hour" has the grain one row per order: AVG(TIMESTAMPDIFF(MINUTE, placed_at, delivered_at)) grouped by restaurant_id and HOUR(placed_at), for delivered orders only. Say the trap: cancelled orders have no delivered_at, and must be left out, not counted as zero.
  • What you'd ask: Can one order come from two restaurants? Can a delivery be reassigned to another partner? If so, a separate deliveries table, with one row per attempt, is better. Asking this is the point of the question.

"What would you do if..."

Scenario questions check judgment more than knowledge. Answer with what you'd do first, then why.

S1. You ran an UPDATE without a WHERE on the live database.

Show a good answer

If you're still inside a transaction: ROLLBACK, and nothing happened (Day 4). If it was committed: tell someone straight away, the database team or your manager, with exactly what you ran and when. Don't try to fix it quietly with another UPDATE, which can make it worse. Teams can usually restore the data from a backup and the binary log (Day 19). Then the lesson that prevents it: changes go in a transaction with a check of rows affected, and day-to-day work uses a read-only user.

S2. Two dashboards show different revenue for last month.

Show a good answer

Don't pick one. Find out why they differ, by comparing definitions in order: which statuses count (completed, shipped, refunds?), order date or payment date, which time zone the month is cut in (Day 12), test and duplicate orders (Day 11), and when each was last refreshed (Day 17's nightly loads). Then calculate both versions yourself, explain the difference in a sentence, and agree one definition, ideally as a shared view (Day 13).

S3. Your query has been running for 10 minutes.

Show a good answer

Stop it (in Workbench, the stop button; or KILL QUERY with its ID from SHOW PROCESSLIST), so it doesn't slow down everyone else. Then EXPLAIN it: look for full scans of big tables, a join without a condition that multiplies rows, or a function on an indexed column (Day 18). If it isn't running at all but waiting, someone may be holding a lock, maybe your own forgotten transaction in another tab (Day 19).

S4. A partner agency asks for a copy of the customer table.

Show a good answer

Ask what they actually need to answer. Usually it's counts or spending, not names and phone numbers. Share the least that answers it: an aggregated extract, or a view without personal columns, and access through a role with only that view (Day 19). Personal data leaving the company also needs your data protection rules followed, so check with whoever owns them before sending anything.

7Talking about your work

Most interviews include "tell me about an analysis you did". Your portfolio project (Day 15's checkpoint) is the answer, and a clear structure makes it sound twice as good. Five parts, about a minute each:

  1. The question. "An online shop wanted to know which new customers become regulars."
  2. The data, and what was wrong with it. "Ten linked tables. About 600 sign-up dates in three formats, duplicate customer accounts, test orders." Interviewers love this part, because real data is always messy.
  3. What you did. "Cleaned it in views so the raw data stayed untouched, then built cohorts and a 30-day return rate." Mention one decision you made and why.
  4. What you found. One or two numbers, rounded: "About 1 in 5 festive-season customers came back within a month, twice the rate in spring."
  5. What you'd do next, or differently. "Check whether the festive coupon brought in bargain hunters who never return." This shows you think beyond the query.

When you explain a result to someone who doesn't read SQL, lead with the answer, not the method. Round the numbers ("about 1 in 5", not "19.12%"). Say what the number does not show. And never present one you haven't checked against a total you trust.

Ask them questions too. "Which database and tools does the team use?" "Where does the data come from, and who fixes it when it's wrong?" "How are metric definitions agreed?" Good questions show you've done real work, and the answers tell you whether you want the job.

Set a timer, answer out loud as if someone were listening, and only then open the answers. Roughly: 15 minutes for question 1, 10 for each of the others.

  1. SQL. For customers who placed at least two orders, how many days passed between their first and second order? Give the median and the average, and explain the difference.
  2. Find the bug. A colleague's query for orders and average order value by channel in 2024 is below. What's wrong?
  3. Case. The December 2024 dashboard says the cancellation rate fell to 3.9%, the best month of the year. Your manager wants to celebrate. What do you say?
  4. Performance. A query with WHERE DATE(created_at) = CURDATE() on a 200-million-row events table times out. What's wrong, and how do you fix it?
Question 2: the colleague's query
SELECT channel,
       COUNT(*)                          AS orders,
       ROUND(SUM(line_total))            AS revenue,
       ROUND(SUM(line_total) / COUNT(*)) AS avg_order_value
FROM clean_sales
WHERE order_date >= '2024-01-01'
GROUP BY channel;
Result
+---------+--------+---------+-----------------+
| channel | orders | revenue | avg_order_value |
+---------+--------+---------+-----------------+
| app     |   2815 | 4097976 |            1456 |
| web     |   2760 | 3884457 |            1407 |
+---------+--------+---------+-----------------+
Show the answers

1. Day 16's median, on top of this article's second-order steps:

SQL
WITH orders AS (
    SELECT DISTINCT customer_id, order_id, order_date FROM clean_sales
), ranked AS (
    SELECT customer_id, order_date,
           ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date, order_id) AS n
    FROM orders
), gaps AS (
    SELECT customer_id,
           DATEDIFF(MAX(CASE WHEN n = 2 THEN order_date END),
                    MAX(CASE WHEN n = 1 THEN order_date END)) AS days_to_second
    FROM ranked
    GROUP BY customer_id
    HAVING days_to_second IS NOT NULL                -- only customers with a second order
), positioned AS (
    SELECT days_to_second,
           ROW_NUMBER() OVER (ORDER BY days_to_second) AS position,
           COUNT(*) OVER ()                           AS how_many
    FROM gaps
)
SELECT MAX(how_many)                                  AS customers,
       AVG(days_to_second)                            AS median_days,
       (SELECT ROUND(AVG(days_to_second), 1) FROM gaps) AS average_days
FROM positioned
WHERE position IN (FLOOR((how_many + 1) / 2), CEIL((how_many + 1) / 2));
Result
+-----------+-------------+--------------+
| customers | median_days | average_days |
+-----------+-------------+--------------+
|       819 |     44.0000 |         72.8 |
+-----------+-------------+--------------+

A typical customer comes back after about 6 weeks (the median, 44 days), but the average is over 10 weeks (73 days), because a few customers return after many months and pull it up. For "when should we send a reminder?", the median is the better guide (Day 16). Notice MAX(how_many): after the WHERE keeps only the middle rows, COUNT(*) would say 1 or 2, so the count comes from the window instead.

2. clean_sales has one row per order line, not per order, so COUNT(*) counts lines. The "orders" are inflated, and the average order value is really the average line value. The grain mistake (Day 10). Count distinct orders:

SQL
SELECT channel,
       COUNT(DISTINCT order_id)                          AS orders,
       ROUND(SUM(line_total))                            AS revenue,
       ROUND(SUM(line_total) / COUNT(DISTINCT order_id)) AS avg_order_value
FROM clean_sales
WHERE order_date >= '2024-01-01'
GROUP BY channel;
Result
+---------+--------+---------+-----------------+
| channel | orders | revenue | avg_order_value |
+---------+--------+---------+-----------------+
| app     |   1664 | 4097976 |            2463 |
| web     |   1655 | 3884457 |            2347 |
+---------+--------+---------+-----------------+

About 1,660 orders per channel, not 2,800, and an average order of about ₹2,400, not ₹1,400. Revenue was right all along, which is why this kind of bug survives: one column looks fine, so nobody checks the others.

3. Check whether December is finished first:

SQL
SELECT DATE_FORMAT(order_date, '%Y-%m')       AS month,
       COUNT(*)                               AS orders,
       SUM(status = 'Cancelled')              AS cancelled,
       SUM(status IN ('Pending', 'Shipped'))  AS still_open,
       ROUND(100 * AVG(status = 'Cancelled'), 1) AS cancel_rate_pct
FROM clean_orders
WHERE is_test = 0 AND is_duplicate = 0
  AND order_date >= '2024-09-01'
GROUP BY month
ORDER BY month;
Result
+---------+--------+-----------+------------+-----------------+
| month   | orders | cancelled | still_open | cancel_rate_pct |
+---------+--------+-----------+------------+-----------------+
| 2024-09 |    332 |        24 |          0 |             7.2 |
| 2024-10 |    452 |        26 |          0 |             5.8 |
| 2024-11 |    422 |        25 |          0 |             5.9 |
| 2024-12 |    381 |        15 |         73 |             3.9 |
+---------+--------+-----------+------------+-----------------+

73 December orders are still pending or shipped. Some of them will be cancelled, and then December's rate will rise. Earlier months have no open orders left, so they're final. It's an unfinished period (Days 12 and 13). Counting only the finished December orders gives 15 out of 308, about 4.9%, close to the 5 to 7% of other months. That's not the whole answer either, because the orders still open are the newest ones, so the fair comparison is each month's rate at the same age, for example "cancelled within 7 days of ordering". The answer to your manager: "Not yet. December isn't finished, and once it is, it'll probably look like a normal month. I'll re-check in January."

4. DATE(created_at) wraps the column in a function, so an index on created_at can't be used to find today's rows, and all 200 million rows are read (Day 18). Leave the column bare, with a half-open range (Day 12):

SQL
WHERE created_at >= CURDATE()
  AND created_at <  CURDATE() + INTERVAL 1 DAY

Then confirm with EXPLAIN that it shows range on an index on created_at, and if there's no such index, take the plan to the database team. On a table this size, also ask whether the table is partitioned by date (Day 18).

🎯 Interview corner: the rapid-fire round, Days 16 to 19

Day 15 had the rapid-fire questions for Days 1 to 14. Here are the ones for the good-to-have days. Answer each in two or three sentences, out loud.

Advanced patterns (Day 16)

Q1How do you calculate a median in MySQL, and when do you prefer it to an average?

MySQL has no MEDIAN function, so number the rows with ROW_NUMBER() in order, count them with COUNT(*) OVER (), and average the middle one or two. Prefer the median when a few extreme values pull the average, like order values or days between orders.

Q2How do you find streaks, like consecutive days of activity?

Gaps and islands: subtract a row number from the date (or from a month counter). Within a streak, both go up by one each time, so the difference stays the same, and grouping by it gives one row per streak.

Q3How do you split events into sessions?

Use LAG to get each event's previous time, flag a new session when the gap is over the limit (often 30 minutes), then a running SUM of the flags gives a session number. Use the same tie-breaker in every window.

Q4What is a recursive CTE good for?

Walking hierarchies of unknown depth (an employee's whole reporting chain), and generating sequences (every date in a range). It has an anchor part, and a recursive part that joins to the CTE itself, until it returns no new rows.

Design and warehouses (Day 17)

Q5Normalised tables or a star schema?

Normalised tables for the systems that run the business, where data is written all day and every fact should be stored once. A star schema (a fact table surrounded by dimensions) for analysis, where reading is far more common than writing, and simple joins matter more than avoiding repetition.

Q6What's the grain of a fact table?

What one row means, such as "one order line". Decide it first, because it determines which measures and dimensions make sense, and mixing grains causes double counting.

Q7What's a Type 2 slowly changing dimension?

When an attribute changes, like a customer's city, a new row is added with valid-from and valid-to dates, instead of overwriting. Each fact links to the version that was true at the time, so history stays correct.

Q8Why is selecting fewer columns faster in a cloud warehouse?

They store data by column, so a query only reads the columns it names. Fewer columns means less data read, which means faster queries and, often, a smaller bill.

Performance (Day 18)

Q9What does EXPLAIN tell you, and what are the warning signs?

The plan: how each table is read (type), which index is used (key), estimated rows, and extra work (Extra). Warning signs on big tables: type: ALL, huge row estimates, Using filesort, Using temporary.

Q10What makes a condition sargable?

The column stands alone on one side of the comparison, so an index can find the range directly. YEAR(d) = 2024 isn't sargable. d >= '2024-01-01' AND d < '2025-01-01' is.

Q11Explain composite and covering indexes.

A composite index covers several columns, sorted by the first and then the next, so it helps searches on its leftmost columns (equality first, range last). A covering index contains every column a query needs, so the table itself isn't read (Using index).

Q12When can an index make a query slower?

When the value matches a large share of the table: each match needs a jump back to the table, and many scattered jumps cost more than one straight read. The optimizer's estimates can be wrong, so measure.

Beyond SELECT (Day 19)

Q13Procedure, function, view or trigger?

A view is a saved query used like a table. A function returns one value inside a query. A procedure is a saved script you CALL, which can change data. A trigger runs by itself when rows in its table change.

Q14How do you give someone access to results without the underlying data?

Grant SELECT on a view, or EXECUTE on a procedure, and nothing on the tables. Both run with their definer's rights by default. Use a role if several people need the same access.

Q15What's MySQL's default isolation level, and what does it mean for a report?

REPEATABLE READ. Inside one transaction, every query sees the same snapshot, taken at the first read. So running a report's queries in one transaction makes them consistent with each other, and leaving a transaction open means you keep seeing old data.

Q16What is a deadlock?

Two transactions each hold a lock the other needs. The database detects it, rolls one back (error 1213 in MySQL), and the application should retry. Short transactions, and changing rows in the same order everywhere, make it rarer.

Quick recap

  • Harder rounds test judgment: multi-step problems, finding bugs, explaining a change, performance, design and scenarios. Day 15's five steps still apply. Add: name the trade-off, check against a number you trust, say what you'd do next.
  • Multi-step problems hide traps: ties in window ordering, NULLs that AVG silently skips, and recent customers who haven't had the full time window.
  • The common bugs in queries that run: fan-out from a join, COUNT(*) counting the NULL row of a LEFT JOIN, filters that change a window's denominator, and counting lines instead of orders.
  • To explain a change: check the data, compare with the same period last year, split the number into its parts (orders and order value), then by segment, and end with what the data can't tell you.
  • Performance answers start with EXPLAIN, then a sargable rewrite, then an index, and prove the difference by counting rows read.
  • In design questions, say the relationships first, then the tables, then the questions you'd ask. In scenarios, say what you'd do first, and be honest about mistakes.
  • Talk about your work as question, data, method, finding, next step. Lead with the answer, round the numbers, and say what the number doesn't show.
