On Day 3 you built the shop's database, and on Day 4 you filled it. Now comes the part analysts do all day: asking it questions. Today you meet SELECT, the one command of DQL, the Data Query Language. By the end, you'll be able to pull out any slice of the shop's data: the columns you want, the rows that matter, in the order you need.

Here's some good news. SELECT only reads. It never changes a single row. That means you can't break anything today, so you can put away START TRANSACTION and ROLLBACK and try whatever you like. Think of it as reading a library book: you can read it a hundred times, and it stays the same.

Before you start. Every query below runs on online_store exactly as you loaded it on Day 4. Run USE online_store; first. If your data looks different from the results shown here, reset it with complete_setup.sql (Day 4, section 5).

1SELECT: pick your columns

Every query starts with two questions: which columns do you want, and from which table? That's all a basic SELECT needs:

The shape of a basic SELECT
SELECT column1, column2
FROM table_name;

The star * means "every column". It's the quickest way to see what a table holds:

SQL
SELECT * FROM products;
Result

Think of a big spreadsheet where you hide the columns you don't need. The data is all still there. You're just choosing what to look at. The columns come back in the order you list them, not the order they sit in the table. Write price, product_name, and price comes first.

Why not always use SELECT *? At work, tables often have 50 or 100 columns and millions of rows. Pulling everything is slow and makes results hard to read. And if someone adds a column to the table later, a report built on * suddenly changes shape. Use * to take a quick look, then name your columns for real work.

2Calculations and aliases

A SELECT can do more than copy columns. It can work things out, like a calculator. Say the owner asks: "How much money is sitting on the shelves for each product?" That's price × stock:

SQL
SELECT product_name, price, stock_quantity, price * stock_quantity
FROM products;
Result
+------------------------------+---------+----------------+------------------------+
| product_name                 | price   | stock_quantity | price * stock_quantity |
+------------------------------+---------+----------------+------------------------+
| Wireless Mouse               |  799.00 |            150 |              119850.00 |
| Mechanical Keyboard          | 2499.00 |             80 |              199920.00 |
| USB-C Hub                    | 1299.00 |             60 |               77940.00 |
| Noise-Cancelling Headphones  | 7999.00 |             40 |              319960.00 |
| SQL Fundamentals             |  599.00 |            200 |              119800.00 |
| Data Science Handbook        | 1199.00 |            120 |              143880.00 |
| The Pragmatic Programmer     |  899.00 |             90 |               80910.00 |
| Cotton T-Shirt               |  499.00 |            300 |              149700.00 |
| Denim Jeans                  | 1799.00 |            110 |              197890.00 |
| Hooded Sweatshirt            | 1499.00 |             75 |              112425.00 |
| Stainless Steel Water Bottle |  699.00 |            250 |              174750.00 |
| Ceramic Coffee Mug           |  349.00 |            180 |               62820.00 |
| Non-Stick Frying Pan         | 1599.00 |             50 |               79950.00 |
| Yoga Mat                     |  999.00 |            130 |              129870.00 |
| Resistance Bands Set         |  599.00 |              0 |                   0.00 |
+------------------------------+---------+----------------+------------------------+

MySQL did the maths on every row. But the last column's name is just the formula, which is ugly. Give it a proper name with AS. This is called an alias:

SQL
SELECT product_name,
       price * stock_quantity AS stock_value
FROM products;
Result
+------------------------------+-------------+
| product_name                 | stock_value |
+------------------------------+-------------+
| Wireless Mouse               |   119850.00 |
| Mechanical Keyboard          |   199920.00 |
| USB-C Hub                    |    77940.00 |
| Noise-Cancelling Headphones  |   319960.00 |
| SQL Fundamentals             |   119800.00 |
| Data Science Handbook        |   143880.00 |
| The Pragmatic Programmer     |    80910.00 |
| Cotton T-Shirt               |   149700.00 |
| Denim Jeans                  |   197890.00 |
| Hooded Sweatshirt            |   112425.00 |
| Stainless Steel Water Bottle |   174750.00 |
| Ceramic Coffee Mug           |    62820.00 |
| Non-Stick Frying Pan         |    79950.00 |
| Yoga Mat                     |   129870.00 |
| Resistance Bands Set         |        0.00 |
+------------------------------+-------------+

An alias is like a nickname. It only changes the label in the result. The table itself is not touched, and there is no real column called stock_value anywhere.

  • You can rename normal columns too: product_name AS product.
  • If the alias has spaces, wrap it in backticks: AS `Stock value`. It's easier to stick to snake_case, though, the same naming habit as Day 2.
  • AS is optional in MySQL (price * stock_quantity stock_value also works), but always writing it makes your query easier to read.

You can use +, -, * and /, and brackets work just like in school maths. ROUND(number, 2) rounds to 2 decimal places. Here is every product's price after a 15% discount:

SQL
SELECT product_name,
       price,
       ROUND(price * 0.85, 2) AS sale_price
FROM products
LIMIT 5;
Result
+-----------------------------+---------+------------+
| product_name                | price   | sale_price |
+-----------------------------+---------+------------+
| Wireless Mouse              |  799.00 |     679.15 |
| Mechanical Keyboard         | 2499.00 |    2124.15 |
| USB-C Hub                   | 1299.00 |    1104.15 |
| Noise-Cancelling Headphones | 7999.00 |    6799.15 |
| SQL Fundamentals            |  599.00 |     509.15 |
+-----------------------------+---------+------------+

(LIMIT 5 just keeps the result short here. In section 11 you'll see why, in real work, it should always come with ORDER BY.)

3Working with text

If you have used Excel, you already know most of these. MySQL has text functions that work the same way:

In ExcelIn MySQLWhat it does
CONCATENATE or &CONCAT(a, b, ...)Joins pieces of text together
UPPER, LOWERUPPER(x), LOWER(x)Changes to capitals or small letters
LENCHAR_LENGTH(x)Counts the characters
TRIMTRIM(x)Removes spaces at the start and end
MIDSUBSTRING(x, start, length)Cuts out part of the text
FINDLOCATE(what, x)Finds where something appears
SQL
SELECT CONCAT(first_name, ' ', last_name) AS full_name,
       UPPER(city)                        AS city_caps,
       CHAR_LENGTH(email)                 AS email_length
FROM customers;
Result
+--------------+-----------+--------------+
| full_name    | city_caps | email_length |
+--------------+-----------+--------------+
| Aarav Sharma | JAIPUR    |           22 |
| Diya Patel   | MUMBAI    |           20 |
| Rohan Mehta  | DELHI     |           21 |
| Ananya Reddy | HYDERABAD |           22 |
| Vivaan Singh | BENGALURU |           22 |
| Ishaan Gupta | PUNE      |           22 |
| Saanvi Iyer  | CHENNAI   |           21 |
| Kabir Khan   | LAHORE    |           20 |
| Mia Williams | LONDON    |           22 |
| Noah Brown   | NULL      |           20 |
+--------------+-----------+--------------+

Notice two things. CONCAT needs the ' ' in the middle, or you'd get "AaravSharma". And Noah's city is NULL, so UPPER(city) is NULL too. Doing anything to an unknown value gives an unknown value, the same rule you saw for maths on Day 2.

A real example: email domains

Analysts often want to know which email providers customers use. Everything after the @ is the domain. LOCATE('@', email) finds the position of the @, and SUBSTRING cuts from the next character to the end:

SQL
SELECT email,
       LOCATE('@', email)                        AS at_position,
       SUBSTRING(email, LOCATE('@', email) + 1)  AS domain
FROM customers;
Result
+------------------------+-------------+-----------+
| email                  | at_position | domain    |
+------------------------+-------------+-----------+
| aarav.sharma@email.com |          13 | email.com |
| ananya.reddy@email.com |          13 | email.com |
| diya.patel@email.com   |          11 | email.com |
| ishaan.gupta@email.com |          13 | email.com |
| kabir.khan@email.com   |          11 | email.com |
| mia.williams@email.com |          13 | email.com |
| noah.brown@email.com   |          11 | email.com |
| rohan.mehta@email.com  |          12 | email.com |
| saanvi.iyer@email.com  |          12 | email.com |
| vivaan.singh@email.com |          13 | email.com |
+------------------------+-------------+-----------+

When you leave out the length, SUBSTRING carries on to the end of the text. Every customer in our shop uses email.com. In the bigger, messier dataset on Day 10, this same query will tell a much more interesting story.

Going deeper: LENGTH vs CHAR_LENGTH

MySQL also has LENGTH(), and many tutorials use it to count characters. But it counts bytes, the space the text takes up on disk, not characters. For plain English letters, one character is one byte, so you won't notice. For anything else, you will:

SQL
SELECT LENGTH('₹799'), CHAR_LENGTH('₹799');
Result
+------------------+-----------------------+
| LENGTH('₹799')   | CHAR_LENGTH('₹799')   |
+------------------+-----------------------+
|                6 |                     4 |
+------------------+-----------------------+

The ₹ sign takes 3 bytes, so LENGTH says 6 for something you can see is 4 characters long. Names in Hindi, Tamil or with accents (like Zoë) have the same problem. Use CHAR_LENGTH when you mean "how many characters".

4DISTINCT: each value once

Which countries do our customers come from? If you just select the column, you get one row per customer, with India repeated seven times. DISTINCT keeps one copy of each value:

SQL
SELECT DISTINCT country
FROM customers;
Result
+----------+
| country  |
+----------+
| India    |
| Pakistan |
| UK       |
| USA      |
+----------+

Think of the guest list for a wedding: 300 names, but you only want to know which cities the guests are coming from. DISTINCT gives you that short list.

This is one of the first things an analyst does with a new table: "what values does this column actually contain?"

SQL
SELECT DISTINCT status
FROM orders;
Result
+-----------+
| status    |
+-----------+
| Completed |
| Pending   |
| Cancelled |
+-----------+

Three statuses, nothing unexpected. On messy data, this is where you'd spot problems like "completed", "Completed " and "COMPLETE" all meaning the same thing.

DISTINCT works on the whole row you select, not just the first column. With two columns, it keeps each different pair:

SQL
SELECT DISTINCT customer_id, status
FROM orders
WHERE customer_id IN (1, 2);
Result
+-------------+-----------+
| customer_id | status    |
+-------------+-----------+
|           1 | Completed |
|           2 | Completed |
|           2 | Cancelled |
+-------------+-----------+

Aarav (customer 1) has three orders, all Completed, so he appears once. Diya (customer 2) has one Completed and one Cancelled order, so she appears twice. (WHERE ... IN keeps only customers 1 and 2. Both are coming up shortly.)

5WHERE: keep only the rows you want

SELECT chooses columns. WHERE chooses rows. It works like a sieve: every row is tested against your condition, and only the rows that pass come through. It's the same idea as the filter button in Excel.

SQL
SELECT first_name, last_name, city
FROM customers
WHERE country = 'India';
Result
+------------+-----------+-----------+
| first_name | last_name | city      |
+------------+-----------+-----------+
| Aarav      | Sharma    | Jaipur    |
| Diya       | Patel     | Mumbai    |
| Rohan      | Mehta     | Delhi     |
| Ananya     | Reddy     | Hyderabad |
| Vivaan     | Singh     | Bengaluru |
| Ishaan     | Gupta     | Pune      |
| Saanvi     | Iyer      | Chennai   |
+------------+-----------+-----------+

7 of the 10 customers live in India. These are the comparison operators you can use:

OperatorMeansExample
=equal tostatus = 'Completed'
!= or <>not equal tostatus != 'Cancelled'
>, <greater than, less thanprice > 1000
>=, <=greater or equal, less or equalorder_date >= '2024-04-01'

Numbers. Products that cost more than ₹1,000:

SQL
SELECT product_name, price
FROM products
WHERE price > 1000;
Result
+-----------------------------+---------+
| product_name                | price   |
+-----------------------------+---------+
| Mechanical Keyboard         | 2499.00 |
| USB-C Hub                   | 1299.00 |
| Noise-Cancelling Headphones | 7999.00 |
| Data Science Handbook       | 1199.00 |
| Denim Jeans                 | 1799.00 |
| Hooded Sweatshirt           | 1499.00 |
| Non-Stick Frying Pan        | 1599.00 |
+-----------------------------+---------+

Dates. Dates are written in quotes as 'YYYY-MM-DD', and "greater than" means "later than". Orders placed on or after 1 April 2024:

SQL
SELECT order_id, order_date, status
FROM orders
WHERE order_date >= '2024-04-01';
Result
+----------+------------+-----------+
| order_id | order_date | status    |
+----------+------------+-----------+
|        9 | 2024-04-02 | Completed |
|       10 | 2024-04-18 | Completed |
|       11 | 2024-04-30 | Pending   |
|       12 | 2024-05-07 | Completed |
|       13 | 2024-05-19 | Completed |
|       14 | 2024-06-01 | Cancelled |
|       15 | 2024-06-15 | Completed |
+----------+------------+-----------+

Text. Text goes in single quotes. Orders that are not completed:

SQL
SELECT order_id, customer_id, status
FROM orders
WHERE status != 'Completed';
Result
+----------+-------------+-----------+
| order_id | customer_id | status    |
+----------+-------------+-----------+
|        5 |           4 | Pending   |
|        7 |           2 | Cancelled |
|       11 |           8 | Pending   |
|       14 |           5 | Cancelled |
+----------+-------------+-----------+

Capital letters don't matter in comparisons. With MySQL's default settings, WHERE country = 'india' finds the same 7 customers as 'India'. Usually that's what you want. But it can hide messy data, so don't assume a table is clean just because your query works. (Other databases, like PostgreSQL, do care about capitals.)

6AND, OR, NOT

Real questions usually have more than one condition. Three small words join them:

  • AND: both must be true. "Electronics and under ₹2,000."
  • OR: at least one must be true. "From Pakistan or the UK."
  • NOT: flips a condition. "Not in Books."
SQL
SELECT product_name, price
FROM products
WHERE category_id = 1 AND price < 2000;
Result
+----------------+---------+
| product_name   | price   |
+----------------+---------+
| Wireless Mouse |  799.00 |
| USB-C Hub      | 1299.00 |
+----------------+---------+
SQL
SELECT first_name, last_name, country
FROM customers
WHERE country = 'Pakistan' OR country = 'UK';
Result
+------------+-----------+----------+
| first_name | last_name | country  |
+------------+-----------+----------+
| Kabir      | Khan      | Pakistan |
| Mia        | Williams  | UK       |
+------------+-----------+----------+

The bracket trap

When you mix AND and OR, MySQL does the AND first, the same way maths does × before +. That can quietly change your answer. Say you want "Electronics or Books, priced under ₹1,000":

Without brackets
SELECT product_name, category_id, price
FROM products
WHERE category_id = 1 OR category_id = 2 AND price < 1000;
Result
+-----------------------------+-------------+---------+
| product_name                | category_id | price   |
+-----------------------------+-------------+---------+
| Wireless Mouse              |           1 |  799.00 |
| Mechanical Keyboard         |           1 | 2499.00 |
| USB-C Hub                   |           1 | 1299.00 |
| Noise-Cancelling Headphones |           1 | 7999.00 |
| SQL Fundamentals            |           2 |  599.00 |
| The Pragmatic Programmer    |           2 |  899.00 |
+-----------------------------+-------------+---------+

₹7,999 headphones are not under ₹1,000. MySQL read the condition as category_id = 1 OR (category_id = 2 AND price < 1000): every Electronics product, plus cheap books. Add brackets to say what you mean:

With brackets
SELECT product_name, category_id, price
FROM products
WHERE (category_id = 1 OR category_id = 2) AND price < 1000;
Result
+--------------------------+-------------+--------+
| product_name             | category_id | price  |
+--------------------------+-------------+--------+
| Wireless Mouse           |           1 | 799.00 |
| SQL Fundamentals         |           2 | 599.00 |
| The Pragmatic Programmer |           2 | 899.00 |
+--------------------------+-------------+--------+

Now it's right. The rule is simple: whenever you mix AND with OR, add brackets. They cost nothing and remove all doubt.

7BETWEEN and IN

Two shortcuts that make common filters shorter and easier to read.

BETWEEN: a range

BETWEEN a AND b keeps values from a to b, including both ends. Think of "children aged 5 to 12": a 5-year-old and a 12-year-old both count.

SQL
SELECT product_name, price
FROM products
WHERE price BETWEEN 500 AND 1000;
Result
+------------------------------+--------+
| product_name                 | price  |
+------------------------------+--------+
| Wireless Mouse               | 799.00 |
| SQL Fundamentals             | 599.00 |
| The Pragmatic Programmer     | 899.00 |
| Stainless Steel Water Bottle | 699.00 |
| Yoga Mat                     | 999.00 |
| Resistance Bands Set         | 599.00 |
+------------------------------+--------+

This is exactly the same as price >= 500 AND price <= 1000, just shorter. It's very handy for dates. All orders in the first three months of 2024:

SQL
SELECT order_id, order_date, status
FROM orders
WHERE order_date BETWEEN '2024-01-01' AND '2024-03-31';
Result
+----------+------------+-----------+
| order_id | order_date | status    |
+----------+------------+-----------+
|        1 | 2024-01-10 | Completed |
|        2 | 2024-01-15 | Completed |
|        3 | 2024-02-03 | Completed |
|        4 | 2024-02-20 | Completed |
|        5 | 2024-02-28 | Pending   |
|        6 | 2024-03-05 | Completed |
|        7 | 2024-03-12 | Cancelled |
|        8 | 2024-03-25 | Completed |
+----------+------------+-----------+

A date trap for later. Our order_date is a DATE, so this works perfectly. But if a column is a DATETIME, '2024-03-31' means midnight at the very start of 31 March, and every order placed later that day gets left out. For date-and-time columns, the safe way is order_time >= '2024-01-01' AND order_time < '2024-04-01'. You'll use this a lot on Day 12.

IN: a list

IN checks whether a value is in a list. It replaces a long chain of ORs:

SQL
SELECT order_id, customer_id, status
FROM orders
WHERE status IN ('Pending', 'Cancelled');
Result
+----------+-------------+-----------+
| order_id | customer_id | status    |
+----------+-------------+-----------+
|        5 |           4 | Pending   |
|        7 |           2 | Cancelled |
|       11 |           8 | Pending   |
|       14 |           5 | Cancelled |
+----------+-------------+-----------+

That's the same as status = 'Pending' OR status = 'Cancelled', and it stays easy to read even with ten items in the list. Put NOT in front to get everything that's not in the list: NOT IN, NOT BETWEEN. (There's a trap with NOT IN and NULL. It gets its own section below.)

8LIKE and REGEXP: matching patterns

Sometimes you don't know the exact text, only part of it. "Customers whose name starts with A." "Products with 'Mug' somewhere in the name." LIKE does this with two wildcards:

WildcardMeansExampleMatches
%any number of characters, even none'A%'Aarav, Ananya, A
_exactly one character'_ia'Mia, Dia, but not Diya

Think of a crossword clue like "D _ _ Y A": you know some letters and need the rest filled in.

SQL
SELECT first_name, last_name
FROM customers
WHERE first_name LIKE 'A%';
Result
+------------+-----------+
| first_name | last_name |
+------------+-----------+
| Aarav      | Sharma    |
| Ananya     | Reddy     |
+------------+-----------+

% at both ends means "anywhere in the text":

SQL
SELECT product_name
FROM products
WHERE product_name LIKE '%set%';
Result
+----------------------+
| product_name         |
+----------------------+
| Resistance Bands Set |
+----------------------+

Like =, LIKE ignores capital letters by default, so '%set%' found "Set" too. And it doesn't care about whole words: '%set%' would also match a product called "Closet Organiser". Patterns match letters, not meaning.

Customers whose first name is exactly four letters long (four underscores):

SQL
SELECT first_name
FROM customers
WHERE first_name LIKE '____';
Result
+------------+
| first_name |
+------------+
| Diya       |
| Noah       |
+------------+

Going deeper: REGEXP for harder patterns

LIKE runs out of power quickly. "Starts with W or D" needs two LIKEs joined with OR. REGEXP (a regular expression) can say it in one go:

SQL
SELECT product_name
FROM products
WHERE product_name REGEXP '^[WD]';
Result
+-----------------------+
| product_name          |
+-----------------------+
| Wireless Mouse        |
| Data Science Handbook |
| Denim Jeans           |
+-----------------------+

A few building blocks cover most everyday needs:

PieceMeansExample
^start of the text'^S': starts with S
$end of the text't$': ends with t
[abc]any one of these characters'^[aeiou]': starts with a vowel
[0-9]any digit'[0-9]': contains a number
|or'Mug|Mat': contains Mug or Mat

Unlike LIKE, a REGEXP matches anywhere in the text unless you use ^ or $. Reach for LIKE first because it's simpler, and use REGEXP when % and _ aren't enough.

Looking for a real % or _? Because they are wildcards, a product called "50% Off Voucher" needs the % to be treated as a normal character. Put a backslash in front: LIKE '50\% Off%'.

9NULL in filters

On Day 2 you learned that NULL means "unknown", and that comparing anything with NULL gives UNKNOWN, not TRUE. WHERE only keeps rows where the answer is TRUE. That one rule explains three traps.

Trap 1: = NULL never matches

Wrong
SELECT first_name FROM customers WHERE city = NULL;
Result
(no rows)
Right
SELECT first_name FROM customers WHERE city IS NULL;
Result
+------------+
| first_name |
+------------+
| Noah       |
+------------+

Always use IS NULL and IS NOT NULL to check for missing values.

Trap 2: != quietly drops NULLs

"Show me every customer who is not from Jaipur." There are 10 customers and only Aarav is from Jaipur, so you'd expect 9 rows:

SQL
SELECT first_name, city
FROM customers
WHERE city != 'Jaipur';
Result
+------------+-----------+
| first_name | city      |
+------------+-----------+
| Diya       | Mumbai    |
| Rohan      | Delhi     |
| Ananya     | Hyderabad |
| Vivaan     | Bengaluru |
| Ishaan     | Pune      |
| Saanvi     | Chennai   |
| Kabir      | Lahore    |
| Mia        | London    |
+------------+-----------+

Only 8. Noah is missing. Is "unknown city" different from Jaipur? MySQL doesn't know, so the answer is UNKNOWN, and Noah is dropped. If you want him included, you have to ask for him:

SQL
SELECT first_name, city
FROM customers
WHERE city != 'Jaipur' OR city IS NULL;
Result
+------------+-----------+
| first_name | city      |
+------------+-----------+
| Diya       | Mumbai    |
| Rohan      | Delhi     |
| Ananya     | Hyderabad |
| Vivaan     | Bengaluru |
| Ishaan     | Pune      |
| Saanvi     | Chennai   |
| Kabir      | Lahore    |
| Mia        | London    |
| Noah       | NULL      |
+------------+-----------+

This trap causes real mistakes in real reports, because nothing tells you a row went missing. When a column can be NULL, always ask yourself: "What should happen to the NULL rows here?"

Trap 3: NOT IN with a NULL in the list

This one surprises even experienced people:

SQL
SELECT first_name
FROM customers
WHERE city NOT IN ('Jaipur', NULL);
Result
(no rows)

Nothing at all. NOT IN ('Jaipur', NULL) means "not Jaipur and not NULL". For Diya in Mumbai: "Mumbai is not Jaipur" is TRUE, but "Mumbai is not NULL" is UNKNOWN. TRUE and UNKNOWN together give UNKNOWN, so she's dropped, and so is everyone else. You'd never type a NULL into a list on purpose. But on Day 8 you'll build these lists from other queries, and a NULL can sneak in without you noticing. Remember this one.

As you saw on Day 4, a table has no built-in order. Without ORDER BY, MySQL returns rows in whatever order is quickest, and that order can change. If the order matters, say so.

FROM products
ORDER BY price DESC;
Result

11LIMIT and OFFSET

LIMIT n keeps only the first n rows. Together with ORDER BY, it answers every "top 5" question:

SQL
SELECT product_name, price
FROM products
ORDER BY price DESC
LIMIT 3;
Result
+-----------------------------+---------+
| product_name                | price   |
+-----------------------------+---------+
| Noise-Cancelling Headphones | 7999.00 |
| Mechanical Keyboard         | 2499.00 |
| Denim Jeans                 | 1799.00 |
+-----------------------------+---------+

It's also a good safety habit. When you explore a big table, add LIMIT 10 so you don't pull a million rows by accident.

OFFSET skips rows first. It's how websites show results page by page. Page 2, with 3 products per page:

SQL
SELECT product_name, price
FROM products
ORDER BY price DESC
LIMIT 3 OFFSET 3;
Result
+----------------------+---------+
| product_name         | price   |
+----------------------+---------+
| Non-Stick Frying Pan | 1599.00 |
| Hooded Sweatshirt    | 1499.00 |
| USB-C Hub            | 1299.00 |
+----------------------+---------+

MySQL also accepts a short form, LIMIT 3, 3, which means "skip 3, then take 3". The skip comes first, which confuses people, so the OFFSET form is clearer.

The tie trap

What are the 3 cheapest products?

SQL
SELECT product_name, price
FROM products
ORDER BY price
LIMIT 3;
Result
+----------------------+--------+
| product_name         | price  |
+----------------------+--------+
| Ceramic Coffee Mug   | 349.00 |
| Cotton T-Shirt       | 499.00 |
| Resistance Bands Set | 599.00 |
+----------------------+--------+

Look back at the full price list in section 10. SQL Fundamentals and the Resistance Bands Set both cost ₹599, so they tie for third place. LIMIT 3 kept one and quietly dropped the other, and which one survives is up to MySQL. To make the result stable, add a second sort column to break the tie, such as ORDER BY price, product_id. Even then, ask yourself whether "top 3" should include ties. On Day 9, window functions give you a proper answer to that.

Rule: never use LIMIT without ORDER BY. Without it, "the first 3 rows" means "any 3 rows", and that can change from one run to the next.

12The order MySQL really runs a query in

You write a query in this order: SELECT, FROM, WHERE, ORDER BY, LIMIT. But MySQL works through it in a different order:

  1. 1FROM

    Find the table

  2. 2WHERE

    Keep the rows that pass

  3. 3SELECT

    Pick and work out the columns

  4. 4ORDER BY

    Sort them

  5. 5LIMIT

    Cut the list short

Think of making a fruit salad. First you take the fruit out of the fridge (FROM). You throw away anything that's gone bad (WHERE). You chop what's left (SELECT). You arrange it in the bowl (ORDER BY). Then you serve three spoonfuls (LIMIT). You can't arrange fruit you haven't chopped yet, and you can't chop fruit you haven't taken out.

(DISTINCT happens just after SELECT. On Day 6, GROUP BY and HAVING will slot in between WHERE and SELECT.)

Why this matters: aliases in WHERE

This order explains an error every beginner meets. Try to filter on an alias:

SQL
SELECT product_name,
       price * stock_quantity AS stock_value
FROM products
WHERE stock_value > 100000;
MySQL says
ERROR 1054 (42S22): Unknown column 'stock_value' in 'where clause'

WHERE runs at step 2, and the alias stock_value is only made at step 3. At step 2, it doesn't exist yet. That's also why ORDER BY (step 4) can use it, as you saw in section 10. The fix is to repeat the calculation in the WHERE:

SQL
SELECT product_name,
       price * stock_quantity AS stock_value
FROM products
WHERE price * stock_quantity > 100000
ORDER BY stock_value DESC;
Result
+------------------------------+-------------+
| product_name                 | stock_value |
+------------------------------+-------------+
| Noise-Cancelling Headphones  |   319960.00 |
| Mechanical Keyboard          |   199920.00 |
| Denim Jeans                  |   197890.00 |
| Stainless Steel Water Bottle |   174750.00 |
| Cotton T-Shirt               |   149700.00 |
| Data Science Handbook        |   143880.00 |
| Yoga Mat                     |   129870.00 |
| Wireless Mouse               |   119850.00 |
| SQL Fundamentals             |   119800.00 |
| Hooded Sweatshirt            |   112425.00 |
+------------------------------+-------------+

Putting it all together

A real question from the owner: "Which in-stock Electronics or Clothing products cost between ₹500 and ₹2,000? Show the dearest first, with the price after a 10% discount."

SQL
SELECT product_name,
       price,
       ROUND(price * 0.90, 2) AS discounted_price
FROM products
WHERE category_id IN (1, 3)
  AND price BETWEEN 500 AND 2000
  AND stock_quantity > 0
ORDER BY price DESC;
Result
+-------------------+---------+------------------+
| product_name      | price   | discounted_price |
+-------------------+---------+------------------+
| Denim Jeans       | 1799.00 |          1619.10 |
| Hooded Sweatshirt | 1499.00 |          1349.10 |
| USB-C Hub         | 1299.00 |          1169.10 |
| Wireless Mouse    |  799.00 |           719.10 |
+-------------------+---------+------------------+

Follow it in MySQL's order:

  1. FROM: start with all 15 products.
  2. WHERE: keep Electronics or Clothing (7 products), priced ₹500 to ₹2,000 (the Keyboard, Headphones and the ₹499 T-Shirt drop out), with stock above 0 (all 4 left pass).
  3. SELECT: show the name and price, and work out the discounted price.
  4. ORDER BY: dearest first.

That's the analyst's everyday workflow: start with a whole table, filter down to what matters, shape the columns, and sort it so the answer is easy to read.

🎯 Interview corner

Filtering and sorting questions come up in almost every SQL interview, and the NULL questions are favourites because so many people get them wrong. Answer out loud first, then open.

Concept questions

Q1In what order does SQL run the parts of a SELECT query?

FROM, then WHERE, then GROUP BY and HAVING (Day 6), then SELECT (and DISTINCT), then ORDER BY, then LIMIT. This is the logical order. The database may take shortcuts inside, but the result is always as if it followed these steps.

Q2Why can't you use a column alias in the WHERE clause?

Because WHERE runs before SELECT, and the alias is created in SELECT. When WHERE runs, the alias doesn't exist yet, so MySQL gives error 1054, "Unknown column". You repeat the expression in WHERE instead. ORDER BY runs after SELECT, so it can use the alias.

Q3What's the difference between = NULL and IS NULL?

= NULL compares a value with "unknown", which always gives UNKNOWN, so it never matches any row. IS NULL is the special check for missing values and works correctly. The same goes for != NULL versus IS NOT NULL.

Q4A table has 10 customers, one in Jaipur and one with a NULL city. How many rows does WHERE city != 'Jaipur' return?

8, not 9. The NULL row gives UNKNOWN for "is this not Jaipur?", and WHERE only keeps TRUE rows. To include it, add OR city IS NULL.

Q5Why can NOT IN return no rows at all?

If the list contains a NULL, then x NOT IN (a, NULL) means x != a AND x != NULL. The second part is always UNKNOWN, so the whole condition can never be TRUE, and no rows come back. It most often happens when the list comes from a subquery on a column with NULLs. NOT EXISTS (Day 8) avoids the problem.

Q6What does DISTINCT do when you select more than one column?

It removes rows where the whole combination is repeated. SELECT DISTINCT customer_id, status keeps each different pair, so a customer with Completed and Cancelled orders appears twice. It does not make each column unique on its own.

Q7Is BETWEEN inclusive? What's the catch with dates?

Yes, both ends are included: BETWEEN 500 AND 1000 is >= 500 AND <= 1000. The catch is with DATETIME columns: BETWEEN '2024-01-01' AND '2024-03-31' stops at midnight at the start of 31 March, so most of that day is missed. Use >= '2024-01-01' AND < '2024-04-01' instead.

Q8What are the wildcards in LIKE? Is LIKE case-sensitive in MySQL?

% matches any number of characters (even none) and _ matches exactly one. With MySQL's default settings, LIKE is not case-sensitive, so 'a%' and 'A%' give the same rows. To search for a real % or _, put a backslash in front of it.

Q9Which runs first, AND or OR?

AND runs before OR (and NOT before both), like × before + in maths. So a OR b AND c means a OR (b AND c). Always use brackets when you mix them, so the meaning is clear to MySQL and to the next reader.

Q10Why is SELECT * considered bad practice?

It pulls every column, which is slower and uses more memory on wide tables. It makes results harder to read. And it makes reports fragile: if a column is added, removed or reordered, anything relying on the column positions can break. It's fine for a quick look at a table, but name your columns in real work.

Q11Where does MySQL put NULLs when sorting? How do you move them?

MySQL treats NULL as smaller than any value: first in ASC, last in DESC. To put NULLs last in an ascending sort, use ORDER BY col IS NULL, col. PostgreSQL does the opposite by default and has NULLS FIRST / NULLS LAST, which MySQL doesn't support.

Q12What happens if you use LIMIT without ORDER BY?

You get some rows, but which ones isn't guaranteed and can change between runs. Even with ORDER BY, ties at the cut-off are broken in no particular order, so add a tie-breaker column (like the ID) if you need the same answer every time.

Practical questions

P1Find the second most expensive product.
SQL
SELECT product_name, price
FROM products
ORDER BY price DESC
LIMIT 1 OFFSET 1;
Result
+---------------------+---------+
| product_name        | price   |
+---------------------+---------+
| Mechanical Keyboard | 2499.00 |
+---------------------+---------+

Sort by price, biggest first, skip one row, take one. A good follow-up to mention: if two products tied for the top price, this would return the other top product, not the second-highest price. To get the second-highest price, sort the distinct prices instead: SELECT DISTINCT price FROM products ORDER BY price DESC LIMIT 1 OFFSET 1;. This "Nth highest" question is a classic, and you'll solve it more neatly on Day 9.

P2Find orders placed in March 2024 that were not cancelled, newest first.
SQL
SELECT order_id, customer_id, order_date, status
FROM orders
WHERE order_date >= '2024-03-01'
  AND order_date < '2024-04-01'
  AND status != 'Cancelled'
ORDER BY order_date DESC;
Result
+----------+-------------+------------+-----------+
| order_id | customer_id | order_date | status    |
+----------+-------------+------------+-----------+
|        8 |           6 | 2024-03-25 | Completed |
|        6 |           5 | 2024-03-05 | Completed |
+----------+-------------+------------+-----------+

The >= and < pattern is a good habit for any date range, because it works for both DATE and DATETIME columns.

P3List every customer who is not from India. Make sure nobody is lost, even if their country were missing.
SQL
SELECT first_name, last_name, country
FROM customers
WHERE country != 'India' OR country IS NULL;
Result
+------------+-----------+----------+
| first_name | last_name | country  |
+------------+-----------+----------+
| Kabir      | Khan      | Pakistan |
| Mia        | Williams  | UK       |
| Noah       | Brown     | USA      |
+------------+-----------+----------+

Nobody in our data has a NULL country, so the result is the same either way. The interviewer wants to see that you thought about NULLs, because country isn't protected by NOT NULL and could hold one tomorrow.

Quick recap

  • SELECT only reads, so it's always safe to try. Name your columns, and use * only for a quick look.
  • SELECT can calculate. Name the result with AS. Text functions: CONCAT, UPPER, LOWER, CHAR_LENGTH, TRIM, SUBSTRING, LOCATE.
  • DISTINCT keeps each different value, or each different combination, once.
  • WHERE keeps rows where the condition is TRUE. Use =, !=, >, <, BETWEEN (both ends included), IN, LIKE (% and _) and REGEXP.
  • AND runs before OR. Use brackets whenever you mix them.
  • NULL traps: use IS NULL, remember that != drops NULL rows, and never let a NULL into a NOT IN list.
  • ORDER BY sorts (ASC by default, NULLs first in MySQL). LIMIT and OFFSET cut the list. Never use LIMIT without ORDER BY, and watch for ties.
  • MySQL runs a query in the order FROM → WHERE → SELECT → ORDER BY → LIMIT, which is why WHERE can't use an alias but ORDER BY can.
