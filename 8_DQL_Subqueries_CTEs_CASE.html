Some questions can't be answered in one go. "Which products cost more than average?" You first need the average, and only then can you compare. So far, you'd run one query, write the number down, and type it into a second query. Today you learn to let SQL do both steps at once. You'll also learn to give each step a name, so even long questions stay easy to read, and to turn raw values into words like "Premium" or "VIP".

Several loose ends from earlier days get tied up today too: the NULL that should be 0, the total you typed by hand on Day 6, and the broken category report from Day 7.

1A query inside a query

"Which products cost more than the average product?" Here's the two-step way:

Step 1: find the average
SELECT AVG(price) FROM products;
Result
+-------------+
| AVG(price)  |
+-------------+
| 1555.666667 |
+-------------+
Step 2: type it into a second query
SELECT product_name, price
FROM products
WHERE price > 1555.67;

It works, but the number you typed goes out of date the moment a price changes. Instead, put the first query inside the second, in brackets, right where the number was:

One step: a subquery
SELECT product_name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products)
ORDER BY price DESC;
Result
+-----------------------------+---------+
| product_name                | price   |
+-----------------------------+---------+
| Noise-Cancelling Headphones | 7999.00 |
| Mechanical Keyboard         | 2499.00 |
| Denim Jeans                 | 1799.00 |
| Non-Stick Frying Pan        | 1599.00 |
+-----------------------------+---------+

The query in brackets is a subquery (some people say inner query). MySQL runs it first, gets ₹1,555.67, and uses that value in the outer query. It's like asking a friend, "What's the average price?" and using their answer to finish your own question, without ever writing it down.

Subqueries come in a few shapes, depending on what they give back:

2Scalar subqueries: one value

A scalar subquery gives back exactly one value: one row, one column. You can use it anywhere a single number would go.

As a column

Show each product's price next to the average, and how far above or below it is:

SQL
SELECT product_name,
       price,
       ROUND((SELECT AVG(price) FROM products), 2)         AS avg_price,
       ROUND(price - (SELECT AVG(price) FROM products), 2) AS difference
FROM products
ORDER BY difference DESC
LIMIT 5;
Result
+-----------------------------+---------+-----------+------------+
| product_name                | price   | avg_price | difference |
+-----------------------------+---------+-----------+------------+
| Noise-Cancelling Headphones | 7999.00 |   1555.67 |    6443.33 |
| Mechanical Keyboard         | 2499.00 |   1555.67 |     943.33 |
| Denim Jeans                 | 1799.00 |   1555.67 |     243.33 |
| Non-Stick Frying Pan        | 1599.00 |   1555.67 |      43.33 |
| Hooded Sweatshirt           | 1499.00 |   1555.67 |     -56.67 |
+-----------------------------+---------+-----------+------------+

Shares of a total

On Day 6 you worked out each status's share of orders by typing the total, 15, by hand. A scalar subquery reads the total for you, so it's always up to date:

SQL
SELECT status,
       COUNT(*) AS orders,
       ROUND(COUNT(*) * 100 / (SELECT COUNT(*) FROM orders), 1) AS pct_of_orders
FROM orders
GROUP BY status
ORDER BY orders DESC;
Result
+-----------+--------+---------------+
| status    | orders | pct_of_orders |
+-----------+--------+---------------+
| Completed |     11 |          73.3 |
| Pending   |      2 |          13.3 |
| Cancelled |      2 |          13.3 |
+-----------+--------+---------------+

"One value" means exactly one. If a subquery used with = or > returns more than one row, MySQL stops with ERROR 1242: Subquery returns more than 1 row. If it returns no rows, it counts as NULL, and comparing with NULL never matches (Day 5). When you write a scalar subquery, be sure it can only ever give one row, usually because it uses an aggregate like AVG or MAX.

3Lists: IN, ANY and ALL

When a subquery returns a whole column of values, use IN to check whether a value is in that list. On Day 5 you typed lists by hand: IN ('Pending', 'Cancelled'). Now the list can come from a query.

Which customers have bought something from Electronics?

SQL
SELECT first_name, last_name
FROM customers
WHERE customer_id IN (
    SELECT o.customer_id
    FROM orders o
    JOIN order_items oi ON oi.order_id  = o.order_id
    JOIN products p     ON p.product_id = oi.product_id
    WHERE p.category_id = 1
);
Result
+------------+-----------+
| first_name | last_name |
+------------+-----------+
| Aarav      | Sharma    |
| Rohan      | Mehta     |
| Ananya     | Reddy     |
| Diya       | Patel     |
+------------+-----------+

Read it from the inside out. The subquery builds a list of customer IDs who bought Electronics. The outer query keeps customers whose ID is in that list. Notice that each customer appears only once, even Aarav, who bought Electronics in three different orders. IN only asks "is it in the list?", so repeats in the list don't matter. A join would have given Aarav once per matching order line.

The NOT IN trap, for real this time

On Day 5 you saw that a NULL inside a NOT IN list makes the whole thing return nothing. Back then the NULL was typed on purpose. Here's how it sneaks in from a subquery. The owner asks: "Which customers live in a city where none of our overseas customers live?"

SQL
SELECT first_name, city
FROM customers
WHERE city NOT IN (SELECT city FROM customers WHERE country != 'India');
Result
(no rows)

Nothing. The overseas customers are Kabir (Lahore), Mia (London) and Noah, whose city is NULL. So the list is ('Lahore', 'London', NULL), and as Day 5 showed, that NULL makes every row UNKNOWN. Nobody gets an error, and the report is simply empty. One fix is to keep NULLs out of the list:

SQL
SELECT first_name, city
FROM customers
WHERE city NOT IN (SELECT city FROM customers
                   WHERE country != 'India' AND city IS NOT NULL);
Result
+------------+-----------+
| first_name | city      |
+------------+-----------+
| Aarav      | Jaipur    |
| Diya       | Mumbai    |
| Rohan      | Delhi     |
| Ananya     | Hyderabad |
| Vivaan     | Bengaluru |
| Ishaan     | Pune      |
| Saanvi     | Chennai   |
+------------+-----------+

The better fix is NOT EXISTS, which never has this problem. You'll see it in section 5.

ANY and ALL

ALL means "compared with every value in the list". Which products cost more than every book?

SQL
SELECT product_name, price
FROM products
WHERE price > ALL (SELECT price FROM products WHERE category_id = 2)
ORDER BY price DESC;
Result
+-----------------------------+---------+
| product_name                | price   |
+-----------------------------+---------+
| Noise-Cancelling Headphones | 7999.00 |
| Mechanical Keyboard         | 2499.00 |
| Denim Jeans                 | 1799.00 |
| Non-Stick Frying Pan        | 1599.00 |
| Hooded Sweatshirt           | 1499.00 |
| USB-C Hub                   | 1299.00 |
+-----------------------------+---------+

The dearest book is ₹1,199, so these are the products above that. > ALL (list) is the same as > (SELECT MAX(...)). ANY means "compared with at least one value", so > ANY (list) is the same as > (SELECT MIN(...)). You'll see ANY and ALL in older code and in interviews, but MAX and MIN are usually easier to read.

4Correlated subqueries: a new answer for every row

Every subquery so far ran once and gave one answer for the whole outer query. A correlated subquery is different: it refers to the row the outer query is looking at, so it runs again for every row.

"Which products cost more than the average of their own category?" A ₹1,299 hub is cheap for Electronics but would be expensive for Books, so each product must be compared with its own category's average:

SQL
SELECT p.product_name,
       p.category_id,
       p.price
FROM products p
WHERE p.price > (
    SELECT AVG(p2.price)
    FROM products p2
    WHERE p2.category_id = p.category_id
)
ORDER BY p.category_id, p.price DESC;
Result
+-----------------------------+-------------+---------+
| product_name                | category_id | price   |
+-----------------------------+-------------+---------+
| Noise-Cancelling Headphones |           1 | 7999.00 |
| Data Science Handbook       |           2 | 1199.00 |
| Denim Jeans                 |           3 | 1799.00 |
| Hooded Sweatshirt           |           3 | 1499.00 |
| Non-Stick Frying Pan        |           4 | 1599.00 |
| Yoga Mat                    |           5 |  999.00 |
+-----------------------------+-------------+---------+

Look at WHERE p2.category_id = p.category_id. The inner p2 is a second look at the products table, and p is the row the outer query is checking right now. For the Wireless Mouse, the subquery averages Electronics. For SQL Fundamentals, it averages Books. Think of a teacher going down the class list: for each student, "is this student above their own section's average?"

Another classic: each customer's most recent order.

SQL
SELECT o.customer_id, o.order_id, o.order_date
FROM orders o
WHERE o.order_date = (
    SELECT MAX(o2.order_date)
    FROM orders o2
    WHERE o2.customer_id = o.customer_id
)
ORDER BY o.customer_id;
Result
+-------------+----------+------------+
| customer_id | order_id | order_date |
+-------------+----------+------------+
|           1 |       12 | 2024-05-07 |
|           2 |        7 | 2024-03-12 |
|           3 |       10 | 2024-04-18 |
|           4 |       15 | 2024-06-15 |
|           5 |       14 | 2024-06-01 |
|           6 |        8 | 2024-03-25 |
|           7 |        9 | 2024-04-02 |
|           8 |       11 | 2024-04-30 |
|           9 |       13 | 2024-05-19 |
+-------------+----------+------------+

About speed. Because a correlated subquery runs once per outer row, it can be slow on big tables. MySQL often rewrites it into something faster behind the scenes, but not always. On Day 9 you'll learn window functions, which answer "compare each row with its group" questions more neatly and usually faster.

5EXISTS and NOT EXISTS

Sometimes you don't need any value from the other table. You only need to know: is there at least one matching row? That's EXISTS. Think of checking whether a friend has any messages from you. You don't need to read them, just to see whether there's at least one.

SQL
SELECT c.first_name, c.last_name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.status = 'Cancelled'
);
Result
+------------+-----------+
| first_name | last_name |
+------------+-----------+
| Diya       | Patel     |
| Vivaan     | Singh     |
+------------+-----------+

"Customers who have at least one cancelled order." EXISTS is TRUE as soon as the subquery finds one row, and MySQL stops looking right there. What the subquery selects doesn't matter, so people write SELECT 1 by habit. It's always correlated: it refers to the outer row (c.customer_id).

NOT EXISTS: the safe way to find what's missing

Customers who have never ordered:

SQL
SELECT c.first_name, c.last_name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
);
Result
+------------+-----------+
| first_name | last_name |
+------------+-----------+
| Noah       | Brown     |
+------------+-----------+

You now know three ways to ask "which rows have no match?". All three give Noah here, but they don't behave the same:

WayLooks likeSafe with NULLs?
LEFT JOIN ... IS NULL (Day 7)LEFT JOIN orders o ON ... WHERE o.order_id IS NULLYes
NOT EXISTSWHERE NOT EXISTS (SELECT 1 FROM orders o WHERE ...)Yes
NOT INWHERE customer_id NOT IN (SELECT customer_id FROM orders)No: one NULL in the list returns nothing

Our orders.customer_id is NOT NULL, so NOT IN happens to work on it. But habits matter more than luck. Prefer NOT EXISTS (or the left join): it reads clearly, it's NULL-safe, and MySQL runs it efficiently.

6Derived tables: a subquery in FROM

A subquery can also stand in for a whole table. Put it in FROM, give it a name, and the outer query treats it like any other table. This is called a derived table.

Its biggest use is "summarise first, then work with the summary". What's the average order value of all orders, cancelled ones included? You can't average order totals directly, because order_items has lines, not orders. So first build a little table of order totals, then average it:

SQL
SELECT COUNT(*)                 AS orders,
       ROUND(AVG(order_total), 2) AS avg_order_value,
       MAX(order_total)         AS biggest_order
FROM (
    SELECT order_id, SUM(quantity * unit_price) AS order_total
    FROM order_items
    GROUP BY order_id
) AS order_totals;
Result
+--------+-----------------+---------------+
| orders | avg_order_value | biggest_order |
+--------+-----------------+---------------+
|     15 |         3230.87 |       9198.00 |
+--------+-----------------+---------------+

The inner query makes 15 rows, one per order. The outer query averages them. It's an aggregate of an aggregate, which you can't write in one level (AVG(SUM(...)) isn't allowed).

The name after the brackets (AS order_totals) is required. Leave it out and MySQL refuses:

SQL
SELECT AVG(order_total)
FROM (SELECT order_id, SUM(quantity * unit_price) AS order_total
      FROM order_items GROUP BY order_id);
MySQL says
ERROR 1248 (42000): Every derived table must have its own alias

Derived tables work, but nest a few of them and the query becomes hard to read from the inside out. That's exactly the problem CTEs solve.

7CTEs: give each step a name

A CTE (Common Table Expression) is a derived table that you write at the top of the query and give a name with WITH. Then the main query uses it by name. Here's the same query as above:

SQL
WITH order_totals AS (
    SELECT order_id, SUM(quantity * unit_price) AS order_total
    FROM order_items
    GROUP BY order_id
)
SELECT COUNT(*)                 AS orders,
       ROUND(AVG(order_total), 2) AS avg_order_value,
       MAX(order_total)         AS biggest_order
FROM order_totals;
Result
+--------+-----------------+---------------+
| orders | avg_order_value | biggest_order |
+--------+-----------------+---------------+
|     15 |         3230.87 |       9198.00 |
+--------+-----------------+---------------+

Same answer, but now it reads top to bottom, like a recipe: "first, make the order totals. Then, average them." It's like using a helper sheet in Excel. You work something out on one sheet, give it a name, and use it on the next.

Several steps in a row

You can define several CTEs, separated by commas, and each one can use the ones before it. Here's the question from the top of the page: "Which customers spend more than the average customer?" (completed orders only).

SQL
WITH completed_lines AS (            -- step 1: only lines from completed orders
    SELECT o.customer_id, oi.quantity * oi.unit_price AS amount
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE o.status = 'Completed'
),
customer_spend AS (                  -- step 2: total per customer
    SELECT customer_id, SUM(amount) AS total_spent
    FROM completed_lines
    GROUP BY customer_id
)
SELECT c.first_name,                 -- step 3: compare with the average
       cs.total_spent,
       ROUND((SELECT AVG(total_spent) FROM customer_spend), 2) AS avg_customer_spend
FROM customer_spend cs
JOIN customers c ON c.customer_id = cs.customer_id
WHERE cs.total_spent > (SELECT AVG(total_spent) FROM customer_spend)
ORDER BY cs.total_spent DESC;
Result
+------------+-------------+--------------------+
| first_name | total_spent | avg_customer_spend |
+------------+-------------+--------------------+
| Aarav      |    15193.00 |            4996.13 |
| Diya       |     7999.00 |            4996.13 |
| Rohan      |     6594.00 |            4996.13 |
+------------+-------------+--------------------+

The average among the 8 customers with completed orders is ₹4,996.13. Only Aarav, Diya and Rohan beat it. Each step is small enough to check on its own. If the answer looks wrong, run just SELECT * FROM customer_spend (with the WITH part above it) and see where it goes off.

Fixing Day 7's broken category report

Day 7's last interview question tried to show every category with its completed revenue, and counted cancelled lines by mistake. A CTE fixes it the clean way: summarise the completed revenue first, then left join it to all categories.

SQL
WITH category_revenue AS (
    SELECT p.category_id,
           SUM(oi.quantity * oi.unit_price) AS revenue
    FROM orders o
    JOIN order_items oi ON oi.order_id  = o.order_id
    JOIN products p     ON p.product_id = oi.product_id
    WHERE o.status = 'Completed'
    GROUP BY p.category_id
)
SELECT cat.category_name,
       COALESCE(cr.revenue, 0) AS revenue
FROM categories cat
LEFT JOIN category_revenue cr ON cr.category_id = cat.category_id
ORDER BY revenue DESC;
Result
+----------------+----------+
| category_name  | revenue  |
+----------------+----------+
| Electronics    | 25491.00 |
| Books          |  4494.00 |
| Clothing       |  4294.00 |
| Home & Kitchen |  3493.00 |
| Sports         |  2197.00 |
+----------------+----------+

These match the trusted numbers from Day 7 exactly. And because categories is on the left, a category with no sales would still appear, with 0 (that's what COALESCE does, coming up in section 9). This "summarise first, then join" pattern is also the clean fix for the row-multiplying trap from Day 7: each summary has one row per key, so nothing gets multiplied.

CTEs need MySQL 8.0 or newer. In older versions, you'd write the same thing as derived tables. A CTE only exists while its query runs. If you need the same step in many queries, a view (Day 9) saves it permanently. WITH RECURSIVE, a special CTE that refers to itself, is covered on Day 16.

8CASE: turn values into labels

CASE is SQL's "if this, then that". It checks conditions in order and gives back the value for the first one that's true. If you know Excel's nested IF, this is the same idea, but much easier to read.

SQL
SELECT product_name,
       price,
       CASE
           WHEN price >= 2000 THEN 'Premium'
           WHEN price >= 1000 THEN 'Mid-range'
           ELSE 'Budget'
       END AS price_band
FROM products
ORDER BY price DESC;
Result
+------------------------------+---------+------------+
| product_name                 | price   | price_band |
+------------------------------+---------+------------+
| Noise-Cancelling Headphones  | 7999.00 | Premium    |
| Mechanical Keyboard          | 2499.00 | Premium    |
| Denim Jeans                  | 1799.00 | Mid-range  |
| Non-Stick Frying Pan         | 1599.00 | Mid-range  |
| Hooded Sweatshirt            | 1499.00 | Mid-range  |
| USB-C Hub                    | 1299.00 | Mid-range  |
| Data Science Handbook        | 1199.00 | Mid-range  |
| Yoga Mat                     |  999.00 | Budget     |
| The Pragmatic Programmer     |  899.00 | Budget     |
| Wireless Mouse               |  799.00 | Budget     |
| Stainless Steel Water Bottle |  699.00 | Budget     |
| SQL Fundamentals             |  599.00 | Budget     |
| Resistance Bands Set         |  599.00 | Budget     |
| Cotton T-Shirt               |  499.00 | Budget     |
| Ceramic Coffee Mug           |  349.00 | Budget     |
+------------------------------+---------+------------+

How MySQL reads each row:

  • Check the WHENs from top to bottom, and stop at the first one that's true. The ₹2,499 keyboard matches >= 2000 and never reaches the second line. So order matters: if >= 1000 came first, the keyboard would be called "Mid-range".
  • If no WHEN is true, use the ELSE. Without an ELSE, you get NULL.
  • Finish with END, and give the result a name with AS.

Once you have labels, group by them like any other column:

SQL
SELECT CASE
           WHEN price >= 2000 THEN 'Premium'
           WHEN price >= 1000 THEN 'Mid-range'
           ELSE 'Budget'
       END AS price_band,
       COUNT(*) AS products
FROM products
GROUP BY price_band
ORDER BY products DESC;
Result
+------------+----------+
| price_band | products |
+------------+----------+
| Budget     |        8 |
| Mid-range  |        5 |
| Premium    |        2 |
+------------+----------+

The short form

When every condition compares the same column with a single value, there's a shorter way to write it:

SQL
SELECT order_id,
       status,
       CASE status
           WHEN 'Completed' THEN 'Done'
           WHEN 'Pending'   THEN 'In progress'
           WHEN 'Cancelled' THEN 'Did not happen'
       END AS meaning
FROM orders
WHERE order_id IN (4, 5, 7);
Result
+----------+-----------+----------------+
| order_id | status    | meaning        |
+----------+-----------+----------------+
|        4 | Completed | Done           |
|        5 | Pending   | In progress    |
|        7 | Cancelled | Did not happen |
+----------+-----------+----------------+

A custom sort order

Alphabetical order isn't always useful. An operations team wants Pending orders first (they need action), then Completed, then Cancelled. CASE inside ORDER BY gives each status a number to sort by:

SQL
SELECT order_id, status, order_date
FROM orders
ORDER BY CASE status
             WHEN 'Pending'   THEN 1
             WHEN 'Completed' THEN 2
             WHEN 'Cancelled' THEN 3
         END,
         order_date DESC
LIMIT 6;
Result
+----------+-----------+------------+
| order_id | status    | order_date |
+----------+-----------+------------+
|       11 | Pending   | 2024-04-30 |
|        5 | Pending   | 2024-02-28 |
|       15 | Completed | 2024-06-15 |
|       13 | Completed | 2024-05-19 |
|       12 | Completed | 2024-05-07 |
|       10 | Completed | 2024-04-18 |
+----------+-----------+------------+

CASE works anywhere a value can go: in SELECT, WHERE, ORDER BY, GROUP BY, and inside aggregates, which is where it gets really powerful (section 10).

9COALESCE: dealing with NULLs

COALESCE(a, b, c, ...) gives back the first value that isn't NULL. Think of a list of phone numbers for someone: try their mobile, and if there isn't one, try home, and if not, try work. The most common use is replacing NULL with something sensible:

SQL
SELECT first_name,
       city,
       COALESCE(city, 'Not given') AS city_for_report
FROM customers
WHERE customer_id IN (1, 9, 10);
Result
+------------+--------+-----------------+
| first_name | city   | city_for_report |
+------------+--------+-----------------+
| Aarav      | Jaipur | Jaipur          |
| Mia        | London | London          |
| Noah       | NULL   | Not given       |
+------------+--------+-----------------+

The NULL that should have been 0

On Day 7, the Frying Pan's units_sold came out as NULL, because SUM of nothing is NULL. Wrap the SUM in COALESCE, and it becomes the 0 it should be:

SQL
SELECT p.product_name,
       COUNT(oi.order_item_id)         AS times_ordered,
       COALESCE(SUM(oi.quantity), 0)   AS units_sold
FROM products p
LEFT JOIN order_items oi ON oi.product_id = p.product_id
GROUP BY p.product_id, p.product_name
ORDER BY units_sold, p.product_name
LIMIT 3;
Result
+--------------------------+---------------+------------+
| product_name             | times_ordered | units_sold |
+--------------------------+---------------+------------+
| Non-Stick Frying Pan     |             0 |          0 |
| Hooded Sweatshirt        |             1 |          1 |
| The Pragmatic Programmer |             1 |          1 |
+--------------------------+---------------+------------+

Only replace NULL with 0 when NULL really means "none", like here. If a NULL means "we don't know" (Noah's city, a missing price), turning it into 0 would hide that the data is missing and give wrong averages.

Cousins of COALESCE. IFNULL(a, b) is MySQL's two-value version. SQL Server calls it ISNULL, Oracle calls it NVL. COALESCE works everywhere and takes as many values as you like, so it's the one to learn. And its opposite, NULLIF(a, b) from Day 4, turns a value into NULL. It's handy for avoiding division by zero: x / NULLIF(y, 0) gives NULL instead of failing when y is 0.

10Conditional aggregation

This is CASE inside an aggregate, and it's one of the most useful patterns in analysis. It lets you count or add up several different things in one pass over the table.

On Day 6 you used MySQL's shortcut, SUM(status = 'Cancelled'). Here is the version that works in every database:

SQL
SELECT COUNT(*) AS all_orders,
       SUM(CASE WHEN status = 'Completed' THEN 1 ELSE 0 END) AS completed,
       SUM(CASE WHEN status = 'Pending'   THEN 1 ELSE 0 END) AS pending,
       SUM(CASE WHEN status = 'Cancelled' THEN 1 ELSE 0 END) AS cancelled
FROM orders;
Result
+------------+-----------+---------+-----------+
| all_orders | completed | pending | cancelled |
+------------+-----------+---------+-----------+
|         15 |        11 |       2 |         2 |
+------------+-----------+---------+-----------+

For each row, the CASE gives 1 if the condition is true and 0 if not. Adding up those 1s counts the matching rows. Think of a teacher with a register who puts a tick in one of three columns for each student, then adds up each column.

Turning rows into columns (pivoting)

Combine it with GROUP BY, and you can spread values across columns. Completed revenue per category, split into the first quarter (January to March) and the second (April to June):

SQL
SELECT cat.category_name,
       SUM(CASE WHEN o.order_date <  '2024-04-01' THEN oi.quantity * oi.unit_price ELSE 0 END) AS jan_to_mar,
       SUM(CASE WHEN o.order_date >= '2024-04-01' THEN oi.quantity * oi.unit_price ELSE 0 END) AS apr_to_jun,
       SUM(oi.quantity * oi.unit_price) AS total
FROM orders o
JOIN order_items oi  ON oi.order_id     = o.order_id
JOIN products p      ON p.product_id    = oi.product_id
JOIN categories cat  ON cat.category_id = p.category_id
WHERE o.status = 'Completed'
GROUP BY cat.category_name
ORDER BY total DESC;
Result
+----------------+------------+------------+----------+
| category_name  | jan_to_mar | apr_to_jun | total    |
+----------------+------------+------------+----------+
| Electronics    |   13395.00 |   12096.00 | 25491.00 |
| Books          |     599.00 |    3895.00 |  4494.00 |
| Clothing       |    3296.00 |     998.00 |  4294.00 |
| Home & Kitchen |    2794.00 |     699.00 |  3493.00 |
| Sports         |    2197.00 |       0.00 |  2197.00 |
+----------------+------------+------------+----------+

This is a pivot: the time periods, which would normally be rows, became columns. It's the same as a pivot table in Excel, written in SQL. Books sold far more in the second quarter. Clothing and Home & Kitchen did most of their business in the first, and Sports all of it.

The other fix for Day 7's report

Conditional aggregation also fixes Day 7's broken query, in a different way from the CTE. Keep every order line in the joins, but only count the amount when the order is completed:

SQL
SELECT cat.category_name,
       SUM(CASE WHEN o.status = 'Completed'
                THEN oi.quantity * oi.unit_price
                ELSE 0 END)                  AS completed_revenue,
       SUM(CASE WHEN o.status = 'Cancelled'
                THEN oi.quantity * oi.unit_price
                ELSE 0 END)                  AS cancelled_value
FROM categories cat
LEFT JOIN products p     ON p.category_id = cat.category_id
LEFT JOIN order_items oi ON oi.product_id = p.product_id
LEFT JOIN orders o       ON o.order_id    = oi.order_id
GROUP BY cat.category_name
ORDER BY completed_revenue DESC;
Result
+----------------+-------------------+-----------------+
| category_name  | completed_revenue | cancelled_value |
+----------------+-------------------+-----------------+
| Electronics    |          25491.00 |            0.00 |
| Books          |           4494.00 |            0.00 |
| Clothing       |           4294.00 |         1499.00 |
| Home & Kitchen |           3493.00 |            0.00 |
| Sports         |           2197.00 |          999.00 |
+----------------+-------------------+-----------------+

Correct revenue again, and a bonus column: the value of cancelled orders per category, in the same query. That's the power of this pattern.

COUNT with CASE. You'll also see COUNT(CASE WHEN condition THEN 1 END). With no ELSE, rows that don't match give NULL, and COUNT skips NULLs (Day 6), so it counts only the matches. It gives the same answer as the SUM(... THEN 1 ELSE 0 END) form.

11Putting it together: a customer segment report

The owner wants every customer put into a group, so the marketing team can treat them differently. The rules:

  • VIP: ₹10,000 or more in completed orders
  • Regular: ₹2,000 to ₹9,999
  • Occasional: less than ₹2,000
  • No purchases yet: no completed orders at all

Every tool from today, plus Day 7's left join, in one query:

SQL
WITH customer_spend AS (
    SELECT o.customer_id,
           COUNT(DISTINCT o.order_id)       AS completed_orders,
           SUM(oi.quantity * oi.unit_price) AS total_spent
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE o.status = 'Completed'
    GROUP BY o.customer_id
)
SELECT c.first_name,
       c.last_name,
       COALESCE(cs.completed_orders, 0) AS completed_orders,
       COALESCE(cs.total_spent, 0)      AS total_spent,
       CASE
           WHEN cs.total_spent IS NULL  THEN 'No purchases yet'
           WHEN cs.total_spent >= 10000 THEN 'VIP'
           WHEN cs.total_spent >= 2000  THEN 'Regular'
           ELSE 'Occasional'
       END AS segment
FROM customers c
LEFT JOIN customer_spend cs ON cs.customer_id = c.customer_id
ORDER BY total_spent DESC;
Result
+------------+-----------+------------------+-------------+------------------+
| first_name | last_name | completed_orders | total_spent | segment          |
+------------+-----------+------------------+-------------+------------------+
| Aarav      | Sharma    |                3 |    15193.00 | VIP              |
| Diya       | Patel     |                1 |     7999.00 | Regular          |
| Rohan      | Mehta     |                2 |     6594.00 | Regular          |
| Ishaan     | Gupta     |                1 |     2794.00 | Regular          |
| Ananya     | Reddy     |                1 |     2696.00 | Regular          |
| Vivaan     | Singh     |                1 |     2197.00 | Regular          |
| Saanvi     | Iyer      |                1 |     1498.00 | Occasional       |
| Mia        | Williams  |                1 |      998.00 | Occasional       |
| Kabir      | Khan      |                0 |        0.00 | No purchases yet |
| Noah       | Brown     |                0 |        0.00 | No purchases yet |
+------------+-----------+------------------+-------------+------------------+

Follow it step by step:

  1. The CTE adds up completed spend per customer (8 customers have some).
  2. A left join from customers keeps all 10, including Kabir (only a pending order) and Noah (no orders).
  3. COALESCE turns their NULL totals into 0 for display.
  4. CASE checks IS NULL first, because a NULL total would fail every other test and fall into ELSE, wrongly labelling Kabir and Noah "Occasional".

That last point is the kind of detail that separates a correct report from a nearly correct one. On Day 13 you'll build a fuller version of this, called RFM segmentation, which also looks at how recently and how often people buy.

Going deeper: subquery, CTE or join?

Many questions can be answered more than one way. A rough guide:

  • Need columns from the other table? Join. A subquery in WHERE can only filter, not bring back columns.
  • Only need to know whether a match exists? EXISTS / NOT EXISTS. They never multiply rows, and they're NULL-safe.
  • Comparing with one summary number? A scalar subquery.
  • More than two steps, or the same step used twice? CTEs. Readability is worth a lot when someone (often you) has to fix the query later.

Modern MySQL often runs these different-looking queries the same way behind the scenes, so pick the one that's clearest to read. You'll learn to check what MySQL actually does with EXPLAIN on Day 18.

🎯 Interview corner

Interviewers use subqueries and CTEs to see how you break a problem down. Say your steps out loud before you write them, then open the answer.

Concept questions

Q1What is a subquery? What types are there?

A query inside another query, in brackets. By what it returns: scalar (one value, used with = or >, or as a column), multi-row (a list, used with IN, ANY, ALL), and table subqueries in FROM (derived tables). By how it runs: non-correlated (runs once) or correlated (refers to the outer row, so it runs for each row).

Q2What's the difference between a correlated and a non-correlated subquery?

A non-correlated subquery stands on its own: you could run it by itself, and it gives one answer for the whole outer query. A correlated subquery refers to a column of the outer query (like p2.category_id = p.category_id), so its answer is different for each outer row, and it can't run on its own. Correlated subqueries can be slow on big tables. Window functions or a join to a summary are often faster.

Q3What's the difference between IN and EXISTS?

IN checks whether a value is in a list of values. EXISTS checks whether a correlated subquery returns at least one row, and stops at the first one. For positive checks they usually give the same result, and modern MySQL often runs them the same way. The big difference is with the negative forms: NOT IN returns nothing if the list contains a NULL, while NOT EXISTS works correctly.

Q4What is a CTE? How is it different from a subquery, a temporary table and a view?

A CTE is a named result defined with WITH at the start of a query and used by name in it. Compared with a derived table, it reads top to bottom and can be used more than once in the same query. A temporary table is really created and lasts for your whole session, so it can be reused across queries and indexed. A view is a saved query stored in the database, usable by anyone, until it's dropped. A CTE only lives for one query.

Q5Why does "Every derived table must have its own alias" appear?

Because a subquery in FROM acts as a table, and every table in a query needs a name for the outer query to refer to it. Add AS some_name after the closing bracket.

Q6How does CASE decide which result to give?

It checks the WHEN conditions from top to bottom and returns the result of the first true one, then stops. If none is true, it returns the ELSE value, or NULL if there's no ELSE. So put the most specific conditions first. A common bug is a NULL that fails every WHEN and silently lands in ELSE, so check IS NULL first when NULLs are possible.

Q7What's the difference between COALESCE, IFNULL and NULLIF?

COALESCE(a, b, ...) returns the first non-NULL value from any number of arguments, and works in every database. IFNULL(a, b) is MySQL's two-argument version (SQL Server: ISNULL, Oracle: NVL). NULLIF(a, b) does the opposite: it returns NULL when a equals b, which is handy for avoiding division by zero.

Q8What is conditional aggregation?

Putting a CASE inside an aggregate, like SUM(CASE WHEN status = 'Completed' THEN amount ELSE 0 END), so one pass over the table can produce several different totals or counts. It's how you pivot rows into columns, and how you count different categories side by side in one query.

Q9When would you use a subquery instead of a join?

Use a join when you need columns from the other table. Use EXISTS / IN when you only need to filter by whether a match exists, since they don't multiply rows. Use a scalar subquery to compare with a single summary value, like an average. For multi-step logic, CTEs keep it readable. Often several forms are correct, so choose the clearest one, and check performance with EXPLAIN if it matters.

Practical questions

P1Find the second highest product price, without using LIMIT.

The subquery finds the highest price. The outer query finds the highest price below that. Quick recap

  • A subquery is a query in brackets inside another query. It replaces a number or list you'd otherwise type by hand.
  • Scalar subqueries return one value (compare with it, or show it as a column). Lists go with IN, ANY, ALL.
  • Correlated subqueries refer to the outer row and run once per row. Good for "compared with its own group", but can be slow.
  • EXISTS asks "is there at least one?". Use NOT EXISTS (or LEFT JOIN ... IS NULL) to find what's missing, never NOT IN on a column that could hold NULL.
  • A derived table is a subquery in FROM, and it needs an alias. A CTE (WITH name AS (...)) is the same idea, named and written at the top. Chain several CTEs to solve a big question in small steps.
  • CASE WHEN ... THEN ... ELSE ... END turns values into labels. The first true WHEN wins, so check IS NULL first when needed.
  • COALESCE replaces NULL with the first non-NULL value. Use it only when NULL really means "none".
  • Conditional aggregation, SUM(CASE WHEN ... THEN x ELSE 0 END), counts or totals several things at once and pivots rows into columns.
