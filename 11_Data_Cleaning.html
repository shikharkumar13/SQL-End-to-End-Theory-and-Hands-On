1How to clean without breaking anything

Think of editing a photo on your phone. A good editing app never paints over the original. It keeps the original photo and saves your edits as a list of steps (brightness up, crop, filter) that you can change or undo any time. Cleaning data should work the same way.

Four rules, all built on things you already know:

  1. Never change the raw tables. No UPDATE on orders or customers. The raw data is your evidence. If a cleaning rule turns out to be wrong, you need the original to fix it.
  2. Clean in views (Day 9). A view stores the cleaning steps, not a cleaned copy. When new orders arrive, they get cleaned automatically, because the view runs on the current data every time.
  3. Write every decision down. "New Delhi counts as Delhi" is a business decision, not a fact. Put it in the SQL, where anyone can see it, question it, and change it.
  4. Count before and after. Every fix should change exactly the rows you expected, and no others. If you meant to fix 60 statuses and 600 changed, stop.

2Fixing text

Most text mess is one of three things: extra spaces, inconsistent capitals, or extra characters. Each has a tool.

Spaces and capitals: TRIM, LOWER, UPPER

You met these on Day 5. Here they do real work. First names have stray spaces and shouting capitals:

SQL
SELECT customer_id,
       CONCAT('[', first_name, ']') AS raw_first_name,
       CONCAT(UPPER(LEFT(TRIM(first_name), 1)),
              LOWER(SUBSTRING(TRIM(first_name), 2))) AS clean_first_name
FROM customers
WHERE customer_id IN (18, 82, 107, 126);
Result
+-------------+----------------+------------------+
| customer_id | raw_first_name | clean_first_name |
+-------------+----------------+------------------+
|          18 | [RAVI]         | Ravi             |
|          82 | [ Vikram]      | Vikram           |
|         107 | [ Vihaan]      | Vihaan           |
|         126 | [KRITIKA]      | Kritika          |
+-------------+----------------+------------------+

Read the formula from the inside out: TRIM removes the spaces, LEFT(..., 1) takes the first letter and UPPER makes it a capital, then SUBSTRING(..., 2) takes the rest and LOWER makes it small. CONCAT glues the two back together. MySQL has no ready-made "capitalise the first letter" function, so this little pattern is worth remembering.

Don't do this to every name. It's safe on our first names, which are single words. Try it on last names, and D'Souza becomes D'souza, Al-Mansoori becomes Al-mansoori, and O'Brien becomes O'brien. All three are in our data. A cleaning rule that breaks good data is worse than no rule. Only fix what's actually broken.

Emails are simpler: capitals don't matter in an email address, so the clean version is all lower case, with no spaces. LOWER(TRIM(email)) is exactly what you used to find the duplicates yesterday.

Extra characters: REPLACE and REGEXP_REPLACE

Phone numbers came in at least four shapes. The trick is to throw away everything that isn't a digit, then build the number back up in one standard format. REPLACE(text, 'find', 'replace with') swaps one exact piece of text, so REPLACE(phone, ' ', '') removes spaces. But you'd need another REPLACE for +, another for -, and so on. REGEXP_REPLACE does it in one go with a pattern: [^0-9] means "any character that is not a digit".

SQL
SELECT phone,
       country,
       REGEXP_REPLACE(phone, '[^0-9]', '') AS digits_only,
       CASE
           WHEN phone IS NULL THEN NULL
           WHEN LOWER(TRIM(country)) IN ('india', 'in')
                THEN CONCAT('+91', RIGHT(REGEXP_REPLACE(phone, '[^0-9]', ''), 10))
           ELSE CONCAT('+', REGEXP_REPLACE(phone, '[^0-9]', ''))
       END AS clean_phone
FROM customers
WHERE customer_id IN (1, 2, 4, 9, 12);
Result
+-----------------+---------+--------------+---------------+
| phone           | country | digits_only  | clean_phone   |
+-----------------+---------+--------------+---------------+
| 7655010505      | India   | 7655010505   | +917655010505 |
| +916016001695   | India   | 916016001695 | +916016001695 |
| 065970 57267    | INDIA   | 06597057267  | +916597057267 |
| +1 2920848108   | US      | 12920848108  | +12920848108  |
| +91 61829 97536 | India   | 916182997536 | +916182997536 |
+-----------------+---------+--------------+---------------+

The four Indian numbers arrived in four different shapes: ten bare digits, +91 stuck on the front, +91 with spaces, and a leading 0. Indian mobile numbers are always 10 digits, so RIGHT(digits, 10) keeps the last 10, whatever came in front. Then +91 goes on the front. All four became one shape: +91 followed by ten digits. That's the format most phone and messaging systems expect. The US number already starts with its country code, so it just gets a +. And a missing phone stays NULL, which is why the CASE checks for that first.

3Messy categories: CASE on a tidied value

For a column with a handful of allowed values, the pattern is always the same: tidy the value first with LOWER(TRIM(...)), then use CASE (Day 8) to turn each tidied spelling into the one name you want.

SQL
SELECT CONCAT('[', status, ']') COLLATE utf8mb4_0900_bin AS raw_status,
       CASE LOWER(TRIM(status))
           WHEN 'completed' THEN 'Completed'
           WHEN 'complete'  THEN 'Completed'
           WHEN 'cancelled' THEN 'Cancelled'
           WHEN 'canceled'  THEN 'Cancelled'
           WHEN 'pending'   THEN 'Pending'
           WHEN 'shipped'   THEN 'Shipped'
           ELSE 'Unknown'
       END AS clean_status,
       COUNT(*) AS orders
FROM orders
GROUP BY raw_status, clean_status
ORDER BY clean_status, orders DESC;
Result
+--------------+--------------+--------+
| raw_status   | clean_status | orders |
+--------------+--------------+--------+
| [Cancelled]  | Cancelled    |    216 |
| [cancelled]  | Cancelled    |     92 |
| [Canceled]   | Cancelled    |     69 |
| [Completed]  | Completed    |   4426 |
| [completed]  | Completed    |   1183 |
| [Completed ] | Completed    |     60 |
| [COMPLETE]   | Completed    |     19 |
| [Pending]    | Pending      |     40 |
| [Shipped]    | Shipped      |     39 |
+--------------+--------------+--------+

Nine raw spellings, four clean statuses, and nothing left over. Checking that every raw value landed in the right clean group like this is the "count before and after" rule in action.

Look at the last line of the CASE: ELSE 'Unknown'. It's tempting to write ELSE status and let anything unexpected pass through unchanged. Don't. If the app starts writing "Delivered" next month, you want it to show up loudly as Unknown in your health check (section 10), not to slip quietly into your reports as a fifth status.

Country, the same way

SQL
SELECT CASE LOWER(TRIM(country))
           WHEN 'india'          THEN 'India'
           WHEN 'in'             THEN 'India'
           WHEN 'uk'             THEN 'UK'
           WHEN 'united kingdom' THEN 'UK'
           WHEN 'usa'            THEN 'USA'
           WHEN 'us'             THEN 'USA'
           WHEN 'united states'  THEN 'USA'
           ELSE TRIM(country)
       END AS clean_country,
       COUNT(*) AS customers
FROM customers
GROUP BY clean_country
ORDER BY customers DESC;
Result
+---------------+-----------+
| clean_country | customers |
+---------------+-----------+
| India         |      2646 |
| USA           |       102 |
| UK            |        87 |
| UAE           |        78 |
| Singapore     |        54 |
| Canada        |        27 |
| Australia     |        18 |
| Germany       |        16 |
+---------------+-----------+

Fourteen raw spellings (twelve if you ignore capitals, as MySQL does) became eight real countries. The UK more than doubled from the 56 rows spelled "UK" to 87, and the USA went from 48 to 102. A "customers by country" chart built on the raw column would have been badly wrong. (Here we used ELSE TRIM(country) on purpose: the other countries, like UAE and Singapore, were already clean. A check in section 10 still catches any new spelling.)

4Lookup tables: when CASE gets too long

A CASE is fine for 6 or 7 values. Cities have about 40, and new ones will keep arriving. Hiding a 40-line CASE inside a view makes it hard to read and hard to change. The better tool is a lookup table (also called a mapping table): a small table with one row per spelling, saying which clean name it should become.

Think of the contacts app on your phone. Your friend's number is saved once, with a proper name. Whether they ring from their mobile or their office line, your phone shows "Ananya". A lookup table does that for cities.

Build 1: the city lookup table
DROP TABLE IF EXISTS city_lookup;

CREATE TABLE city_lookup (
    city_key   VARCHAR(50) PRIMARY KEY,   -- the tidied raw spelling: lower case, no spaces
    clean_city VARCHAR(50) NOT NULL       -- the name we want in reports
);

INSERT INTO city_lookup (city_key, clean_city) VALUES
('abu dhabi','Abu Dhabi'), ('ahmedabad','Ahmedabad'), ('bangalore','Bengaluru'), ('bengaluru','Bengaluru'),
('berlin','Berlin'), ('bhopal','Bhopal'), ('bombay','Mumbai'), ('calcutta','Kolkata'),
('chandigarh','Chandigarh'), ('chennai','Chennai'), ('chicago','Chicago'), ('coimbatore','Coimbatore'),
('delhi','Delhi'), ('dubai','Dubai'), ('gurgaon','Gurugram'), ('gurugram','Gurugram'),
('hyderabad','Hyderabad'), ('indore','Indore'), ('jaipur','Jaipur'), ('kochi','Kochi'),
('kolkata','Kolkata'), ('london','London'), ('lucknow','Lucknow'), ('madras','Chennai'),
('manchester','Manchester'), ('melbourne','Melbourne'), ('mumbai','Mumbai'), ('munich','Munich'),
('nagpur','Nagpur'), ('new delhi','Delhi'), ('new york','New York'), ('noida','Noida'),
('pune','Pune'), ('san francisco','San Francisco'), ('singapore','Singapore'), ('surat','Surat'),
('sydney','Sydney'), ('toronto','Toronto'), ('vancouver','Vancouver'), ('visakhapatnam','Visakhapatnam');

Notice the key is the tidied spelling, LOWER(TRIM(city)). So one row, 'bengaluru', catches "Bengaluru", "bengaluru" and "Bengaluru " all at once. Only true aliases, like "Bangalore", need a row of their own.

And one row records a decision: ('new delhi', 'Delhi'). On Day 10 we said that's a business question, not a spelling fix. Say the owner answered: "Report New Delhi under Delhi." The lookup table is where that answer lives. If the owner changes their mind, you change one row, and every report follows.

Now join to it, and compare the before and after for the cities that had aliases:

SQL
SELECT l.clean_city,
       COUNT(*) AS customers,
       GROUP_CONCAT(DISTINCT CONCAT('[', c.city, ']') ORDER BY c.city SEPARATOR ' ') AS raw_spellings
FROM customers c
JOIN city_lookup l ON l.city_key = LOWER(TRIM(c.city))
WHERE l.clean_city IN ('Bengaluru', 'Mumbai', 'Delhi', 'Gurugram', 'Kolkata', 'Chennai')
GROUP BY l.clean_city
ORDER BY customers DESC;
Result
+------------+-----------+--------------------------------------+
| clean_city | customers | raw_spellings                        |
+------------+-----------+--------------------------------------+
| Mumbai     |       348 | [ Mumbai] [Bombay] [mumbai]          |
| Delhi      |       321 | [Delhi] [New Delhi]                  |
| Bengaluru  |       299 | [Bangalore] [Bengaluru] [Bengaluru ] |
| Chennai    |       183 | [Chennai] [Madras]                   |
| Kolkata    |       175 | [Calcutta] [Kolkata]                 |
| Gurugram   |        79 | [Gurgaon] [Gurugram]                 |
+------------+-----------+--------------------------------------+

Bengaluru is now 299 customers, not the 187 the raw data showed: that's 60% more. Mumbai and Delhi grow too. (The GROUP_CONCAT(DISTINCT ...) list uses the same case-insensitive collation, so it treats Mumbai and mumbai as one spelling and shows just one of them. Trailing spaces do count, which is why [Bengaluru ] appears on its own. Either way, every row is in the count.)

The best part of a lookup table is that it tells you what it doesn't know. Any city whose tidied spelling has no row is a new spelling you haven't mapped yet. Section 10 turns that into a check that should always return 0.

5What does missing mean?

Back on Day 4, Riya was stored with the city 'NULL' in quotes, and every query looking for missing cities skipped her. Day 10 found the same problem for real: missing cities hide as NULL, as empty text '', and as the text 'N/A'. The fix is to turn every fake NULL into a real NULL, so IS NULL, COUNT(column) and COALESCE all work properly again.

The lookup table has already done it for city: '' and 'n/a' have no row, so the LEFT JOIN gives NULL. When there's no lookup table, the general pattern uses NULLIF (Day 4) twice:

SQL
SELECT CONCAT('[', city, ']') AS raw_city,
       NULLIF(NULLIF(TRIM(city), ''), 'N/A') AS clean_city,
       COUNT(*) AS customers
FROM customers
WHERE city IS NULL OR TRIM(city) IN ('', 'N/A')
GROUP BY raw_city, clean_city;
Result
+----------+------------+-----------+
| raw_city | clean_city | customers |
+----------+------------+-----------+
| NULL     | NULL       |        91 |
| [N/A]    | NULL       |        14 |
| []       | NULL       |        32 |
+----------+------------+-----------+

Read it from the inside: trim the city, turn '' into NULL, then turn 'N/A' into NULL. All 137 customers without a city now look the same: NULL. (CONCAT with a NULL inside gives NULL, which is why the first row's raw_city shows NULL rather than [NULL].)

Missing in a join: the product with no category

Here's an issue that wasn't in yesterday's log, and it's a sneaky one. One product has no category at all:

SQL
SELECT p.product_id, p.product_name, p.category_id, p.launch_date,
       COUNT(oi.order_item_id) AS lines_sold
FROM products p
LEFT JOIN order_items oi ON oi.product_id = p.product_id
WHERE p.category_id IS NULL
GROUP BY p.product_id, p.product_name, p.category_id, p.launch_date;
Result
+------------+--------------------+-------------+-------------+------------+
| product_id | product_name       | category_id | launch_date | lines_sold |
+------------+--------------------+-------------+-------------+------------+
|         61 | Smart Fitness Band |        NULL | 2024-12-01  |         10 |
+------------+--------------------+-------------+-------------+------------+

A new product, launched in December 2024, that nobody got round to putting in a category. Any revenue report that does JOIN categories (an inner join) drops all of its sales without a word: Day 7's "no match, no row". The fix in the clean layer is a LEFT JOIN to categories, with COALESCE(category_name, 'Uncategorised') for the label. Now its sales stay in, and the label tells everyone this product needs a category.

When to use COALESCE, and when not to

Day 8's rule still holds: only replace NULL with a value when you know what NULL means.

  • A missing category label for display? 'Uncategorised' is honest. It's a label, not a made-up fact.
  • A missing city? Leave it NULL in the clean layer. Only at report time, write COALESCE(city, 'Not given'), so a chart shows a "Not given" bar instead of a blank.
  • Never turn a missing number into 0 unless 0 is really true. A missing rating is not a 1-star review, and a missing price is not free.

6Dates and types

Text into dates: STR_TO_DATE

Day 10 found three formats in signup_date. STR_TO_DATE(text, format) reads text as a date, if you tell it the pattern. The format uses codes: %Y is a four-digit year, %m a two-digit month, %d the day, and %b a short month name like "Mar".

SQL
SELECT signup_date AS raw_text,
       CASE
           WHEN signup_date REGEXP '^[0-9]{4}-[0-9]{2}-[0-9]{2}$'    THEN STR_TO_DATE(signup_date, '%Y-%m-%d')
           WHEN signup_date REGEXP '^[0-9]{2}/[0-9]{2}/[0-9]{4}$'    THEN STR_TO_DATE(signup_date, '%d/%m/%Y')
           WHEN signup_date REGEXP '^[0-9]{2}-[A-Za-z]{3}-[0-9]{4}$' THEN STR_TO_DATE(signup_date, '%d-%b-%Y')
       END AS real_date
FROM customers
WHERE customer_id IN (1, 21, 26, 32);
Result
+-------------+------------+
| raw_text    | real_date  |
+-------------+------------+
| 2023-11-02  | 2023-11-02 |
| 07/03/2024  | 2024-03-07 |
| 21/07/2024  | 2024-07-21 |
| 02-Dec-2022 | 2022-12-02 |
+-------------+------------+

It's the same CASE and REGEXP you used yesterday to count the formats, now used to read them. Each format gets the matching pattern, and they all come out as proper dates.

Two dangers with STR_TO_DATE. First, if the text doesn't match the pattern, or the date is impossible (31 February), you get NULL and only a warning, not an error. So always count how many NULLs your conversion produced (section 10 does). Second, 03/04/2024 means 3 April in India and 4 March in the US, and SQL can't tell which one the system meant. We used %d/%m/%Y (day first) because this shop is Indian, and the data agrees: 272 of the slash dates start with a number above 12, like 21/07/2024, which can only be a day, and none has a middle number above 12. Still, it's a decision. Write it down.

Now MIN and MAX finally mean something:

SQL
SELECT MIN(real_date) AS first_signup,
       MAX(real_date) AS last_signup,
       SUM(real_date IS NULL) AS failed_to_convert
FROM (
    SELECT CASE
               WHEN signup_date REGEXP '^[0-9]{4}-[0-9]{2}-[0-9]{2}$'    THEN STR_TO_DATE(signup_date, '%Y-%m-%d')
               WHEN signup_date REGEXP '^[0-9]{2}/[0-9]{2}/[0-9]{4}$'    THEN STR_TO_DATE(signup_date, '%d/%m/%Y')
               WHEN signup_date REGEXP '^[0-9]{2}-[A-Za-z]{3}-[0-9]{4}$' THEN STR_TO_DATE(signup_date, '%d-%b-%Y')
           END AS real_date
    FROM customers
) AS converted;
Result
+--------------+-------------+-------------------+
| first_signup | last_signup | failed_to_convert |
+--------------+-------------+-------------------+
| 2022-07-05   | 2024-12-31  |                 0 |
+--------------+-------------+-------------------+

The first sign-up was in July 2022, not "01-Aug-2023", and every one of the 3,028 values converted.

Types matter: CAST

Text that looks like a number or a date still behaves like text. Text is compared letter by letter, like words in a dictionary:

SQL
SELECT '10' < '9'                                    AS compared_as_text,
       10 < 9                                        AS compared_as_numbers,
       CAST('10' AS UNSIGNED) < CAST('9' AS UNSIGNED) AS after_cast;
Result
+------------------+---------------------+------------+
| compared_as_text | compared_as_numbers | after_cast |
+------------------+---------------------+------------+
|                1 |                   0 |          0 |
+------------------+---------------------+------------+

As text, "10" comes before "9", because "1" comes before "9". That's the same reason MIN(signup_date) gave nonsense yesterday. CAST(value AS type) converts a value to a proper type: UNSIGNED or SIGNED for whole numbers, DECIMAL(10,2) for money, DATE for dates already in YYYY-MM-DD form. Whenever numbers or dates arrive as text, convert them first, then compare, sort or do maths.

The two orders from the future

Yesterday's evidence was strong: orders 5012 and 5497 sit between October and November 2024 orders, with the year typed as 2025. The fix moves them back one year, and keeps a flag so the change is never invisible:

SQL
SELECT order_id,
       order_date AS raw_date,
       CASE WHEN order_date > '2024-12-31 23:59:59'
            THEN order_date - INTERVAL 1 YEAR
            ELSE order_date END              AS clean_date,
       (order_date > '2024-12-31 23:59:59')  AS date_was_fixed
FROM orders
WHERE order_id IN (5011, 5012, 5013);
Result
+----------+---------------------+---------------------+----------------+
| order_id | raw_date            | clean_date          | date_was_fixed |
+----------+---------------------+---------------------+----------------+
|     5011 | 2024-10-08 13:04:56 | 2024-10-08 13:04:56 |              0 |
|     5012 | 2025-10-08 13:34:15 | 2024-10-08 13:34:15 |              1 |
|     5013 | 2024-10-08 17:18:57 | 2024-10-08 17:18:57 |              0 |
+----------+---------------------+---------------------+----------------+

After the fix, order 5012 sits neatly between its neighbours, which confirms the decision. - INTERVAL 1 YEAR is date arithmetic, a preview of tomorrow. Another reasonable choice would have been to leave these two orders out. What matters is that you choose, write it down, and can find the affected rows later through the flag.

7Duplicates, three ways

"Duplicate" means different things depending on what's repeated. There are three kinds in this data, and each needs its own approach.

1. Exact copies of a row

Some reviews were submitted twice: same product, same customer, same rating, same text, same day. Only the review_id differs. Day 9's ROW_NUMBER() finds them: number the rows inside each group of identical values, and every row numbered 2 or more is a copy.

SQL
WITH numbered AS (
    SELECT review_id,
           ROW_NUMBER() OVER (PARTITION BY product_id, customer_id, rating, review_text, review_date
                              ORDER BY review_id) AS copy_number
    FROM reviews
)
SELECT COUNT(*)                AS all_reviews,
       SUM(copy_number = 1)    AS keep,
       SUM(copy_number > 1)    AS exact_copies
FROM numbered;
Result
+-------------+------+--------------+
| all_reviews | keep | exact_copies |
+-------------+------+--------------+
|        2117 | 2097 |           20 |
+-------------+------+--------------+

Twenty copies. To keep one of each, filter WHERE copy_number = 1. ORDER BY review_id decides which copy survives: the first one submitted. (PARTITION BY treats NULLs as equal, so two copies that both have no text still land in the same group. That's what we want here.) This is today's Try this.

2. Same customer, two accounts

The 25 customers who signed up twice can't simply be deleted: both accounts have real orders. Instead, give every account a master ID: the first account the person created. Then point everything at the master.

SQL
SELECT customer_id,
       email,
       MIN(customer_id) OVER (PARTITION BY LOWER(TRIM(email))) AS master_customer_id
FROM customers
WHERE LOWER(TRIM(email)) IN ('reyansh.kapoor@gmail.com', 'aditi.patil@gmail.com', 'kavya.choudhury@icloud.com');
Result
+-------------+----------------------------+--------------------+
| customer_id | email                      | master_customer_id |
+-------------+----------------------------+--------------------+
|        2688 | aditi.patil@gmail.com      |               2688 |
|        3030 | Aditi.patil@gmail.com      |               2688 |
|           1 | kavya.choudhury@icloud.com |                  1 |
|        1247 | reyansh.kapoor@gmail.com   |               1247 |
|        3012 | reyansh.kapoor@gmail.com   |               1247 |
+-------------+----------------------------+--------------------+

MIN(customer_id) OVER (PARTITION BY ...) is a window function (Day 9): for each row, the smallest ID among all accounts with the same tidied email. Reyansh's second account, 3012, gets master 1247. Kavya has only one account, so she is her own master. Now an order placed on account 3012 can be counted as Reyansh's, and "orders per customer" becomes right. Across the whole table, 34 orders move to their master account.

3. Double-submitted orders

On Day 10 you found 15 pairs of orders from the same customer less than five minutes apart, and said Day 11 would compare the items. Two orders a few minutes apart could be a real second purchase ("oh, I forgot the charger"). It's only a double submit if the basket is the same. So first, build a basket "fingerprint" for every order: its products and quantities as one piece of text.

SQL
WITH baskets AS (
    SELECT o.order_id,
           o.customer_id,
           o.order_date,
           GROUP_CONCAT(oi.product_id, 'x', oi.quantity ORDER BY oi.product_id) AS basket
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    GROUP BY o.order_id, o.customer_id, o.order_date
)
SELECT a.order_id AS first_order,
       b.order_id AS repeat_order,
       a.basket,
       TIMESTAMPDIFF(SECOND, a.order_date, b.order_date) AS seconds_apart
FROM baskets a
JOIN baskets b ON b.customer_id = a.customer_id
              AND b.order_id    > a.order_id
              AND b.basket      = a.basket
              AND TIMESTAMPDIFF(SECOND, a.order_date, b.order_date) BETWEEN 0 AND 300
ORDER BY a.order_id
LIMIT 6;
Result
+-------------+--------------+----------------+---------------+
| first_order | repeat_order | basket         | seconds_apart |
+-------------+--------------+----------------+---------------+
|         188 |          189 | 19x1,22x1,40x1 |           136 |
|         207 |          208 | 4x1            |           149 |
|         804 |          805 | 23x1           |           117 |
|        1111 |         1112 | 43x1           |            52 |
|        1577 |         1578 | 56x1           |            91 |
|        2080 |         2081 | 28x3,40x1      |            46 |
+-------------+--------------+----------------+---------------+

19x1,22x1,40x1 means "one of product 19, one of 22, one of 40". ORDER BY product_id inside the GROUP_CONCAT matters: without it, the same basket could come out as "22x1,19x1" one time and "19x1,22x1" the next, and two identical baskets wouldn't match. All 15 pairs from Day 10 have identical baskets.

Can we be sure? Look at what happened to the money for the repeat orders:

SQL
SELECT payment_status, COUNT(*) AS payments
FROM payments
WHERE order_id IN (189, 208, 805, 1112, 1578, 2081, 3466, 3990,
                   4206, 4570, 4829, 5298, 5830, 5880, 5937)
GROUP BY payment_status;
Result
+----------------+----------+
| payment_status | payments |
+----------------+----------+

Every repeat order was refunded. The shop's own payment system already treated them as mistakes, which is strong evidence our rule is right. Checking a cleaning rule against a second source of truth like this is one of the best habits you can build. The clean layer will flag the later order of each pair as a duplicate, and leave it out of sales.

8Rows that shouldn't count

Some rows aren't wrong, they just aren't business. Test orders, zero-quantity lines and stuck orders all fall into this group.

An exclusion list for test accounts

Yesterday's search for '%test%' found three test accounts, and we noted that real companies usually keep a list. So let's make one. A table means the list is written down once, with a reason, and anyone can add to it when engineering finds another test account:

This is INSERT ... SELECT: instead of typing values, insert the rows a query returns. It's how you fill a table from data you already have. We flag these customers rather than delete them, so their orders stay in the raw data, with a reason anyone can read.

Zero-quantity lines and stuck orders

  • The 4 lines with quantity 0 are left out of the clean layer: WHERE quantity > 0. They can't be a sale.
  • The 6 orders stuck on Pending since 2023 keep their status. Our revenue definition only counts Completed orders, so they're already left out of sales. They stay on the health check as an open question for the operations team.
  • The 12 payments missing the shipping fee can't be fixed by an analyst. Was the customer under-charged, or did the payment record lose the fee? That's a question for finance. Until it's answered, the check stays open.

Knowing what not to fix is part of the job. Some problems need a person with access to the real-world facts.

9Build the clean layer

Now put every fix into views. Each view does one table's cleaning, and the last one, clean_sales, brings it all together for reports. It's the same idea as Day 9's completed_sales, but built on clean data.

Build 3: clean_customers
CREATE OR REPLACE VIEW clean_customers AS
SELECT c.customer_id,
       MIN(c.customer_id) OVER (PARTITION BY LOWER(TRIM(c.email))) AS master_customer_id,
       CONCAT(UPPER(LEFT(TRIM(c.first_name), 1)),
              LOWER(SUBSTRING(TRIM(c.first_name), 2)))              AS first_name,
       TRIM(c.last_name)                                            AS last_name,
       LOWER(TRIM(c.email))                                         AS email,
       CASE
           WHEN c.phone IS NULL THEN NULL
           WHEN LOWER(TRIM(c.country)) IN ('india', 'in')
                THEN CONCAT('+91', RIGHT(REGEXP_REPLACE(c.phone, '[^0-9]', ''), 10))
           ELSE CONCAT('+', REGEXP_REPLACE(c.phone, '[^0-9]', ''))
       END                                                          AS phone,
       l.clean_city                                                 AS city,
       CASE LOWER(TRIM(c.country))
           WHEN 'india' THEN 'India'   WHEN 'in' THEN 'India'
           WHEN 'uk'    THEN 'UK'      WHEN 'united kingdom' THEN 'UK'
           WHEN 'usa'   THEN 'USA'     WHEN 'us' THEN 'USA'   WHEN 'united states' THEN 'USA'
           ELSE TRIM(c.country)
       END                                                          AS country,
       CASE
           WHEN c.signup_date REGEXP '^[0-9]{4}-[0-9]{2}-[0-9]{2}$'    THEN STR_TO_DATE(c.signup_date, '%Y-%m-%d')
           WHEN c.signup_date REGEXP '^[0-9]{2}/[0-9]{2}/[0-9]{4}$'    THEN STR_TO_DATE(c.signup_date, '%d/%m/%Y')
           WHEN c.signup_date REGEXP '^[0-9]{2}-[A-Za-z]{3}-[0-9]{4}$' THEN STR_TO_DATE(c.signup_date, '%d-%b-%Y')
       END                                                          AS signup_date,
       c.acquisition_channel,
       (x.customer_id IS NOT NULL)                                  AS is_test
FROM customers c
LEFT JOIN city_lookup l        ON l.city_key    = LOWER(TRIM(c.city))
LEFT JOIN excluded_customers x ON x.customer_id = c.customer_id;
Build 4: clean_orders
CREATE OR REPLACE VIEW clean_orders AS
WITH baskets AS (
    SELECT o.order_id, o.customer_id, o.order_date,
           GROUP_CONCAT(oi.product_id, 'x', oi.quantity ORDER BY oi.product_id) AS basket
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    GROUP BY o.order_id, o.customer_id, o.order_date
),
double_submits AS (
    SELECT DISTINCT b.order_id
    FROM baskets a
    JOIN baskets b ON b.customer_id = a.customer_id
                  AND b.order_id    > a.order_id
                  AND b.basket      = a.basket
                  AND TIMESTAMPDIFF(SECOND, a.order_date, b.order_date) BETWEEN 0 AND 300
)
SELECT o.order_id,
       cc.master_customer_id                  AS customer_id,
       o.customer_id                          AS original_customer_id,
       CASE WHEN o.order_date > '2024-12-31 23:59:59'
            THEN o.order_date - INTERVAL 1 YEAR
            ELSE o.order_date END             AS order_date,
       (o.order_date > '2024-12-31 23:59:59') AS date_was_fixed,
       CASE LOWER(TRIM(o.status))
            WHEN 'completed' THEN 'Completed' WHEN 'complete' THEN 'Completed'
            WHEN 'cancelled' THEN 'Cancelled' WHEN 'canceled' THEN 'Cancelled'
            WHEN 'pending'   THEN 'Pending'   WHEN 'shipped'  THEN 'Shipped'
            ELSE 'Unknown' END                AS status,
       o.channel,
       o.coupon_code,
       o.shipping_fee,
       cc.is_test,
       (d.order_id IS NOT NULL)               AS is_duplicate
FROM orders o
JOIN clean_customers cc    ON cc.customer_id = o.customer_id
LEFT JOIN double_submits d ON d.order_id     = o.order_id;
Build 5: clean_order_items, clean_payments and clean_returns
CREATE OR REPLACE VIEW clean_order_items AS
SELECT order_item_id, order_id, product_id, quantity, unit_price
FROM order_items
WHERE quantity > 0;

CREATE OR REPLACE VIEW clean_payments AS
SELECT payment_id,
       order_id,
       payment_date,
       CASE LOWER(TRIM(payment_method))
            WHEN 'upi'              THEN 'UPI'
            WHEN 'credit card'      THEN 'Card'
            WHEN 'debit card'       THEN 'Card'
            WHEN 'card'             THEN 'Card'
            WHEN 'cod'              THEN 'COD'
            WHEN 'cash on delivery' THEN 'COD'
            WHEN 'netbanking'       THEN 'NetBanking'
            WHEN 'net banking'      THEN 'NetBanking'
            WHEN 'wallet'           THEN 'Wallet'
            WHEN 'paytm wallet'     THEN 'Wallet'
            ELSE 'Unknown' END AS payment_method,
       amount,
       LOWER(TRIM(payment_status)) AS payment_status
FROM payments;

CREATE OR REPLACE VIEW clean_returns AS
SELECT return_id,
       order_item_id,
       return_date,
       reason AS raw_reason,
       CASE
            WHEN reason IS NULL                         THEN 'Not given'
            WHEN reason LIKE '%size%'                   THEN 'Size problem'
            WHEN reason IN ('Damaged', 'Defective', 'Not working')
                                                        THEN 'Damaged or faulty'
            WHEN reason IN ('Not as described', 'Colour different from photo')
                                                        THEN 'Not as described'
            WHEN reason IN ('Changed mind', 'Ordered by mistake')
                                                        THEN 'Changed mind'
            WHEN reason = 'Late delivery'               THEN 'Late delivery'
            ELSE 'Other'
       END AS reason_group,
       refund_amount,
       processed_by
FROM returns;

(The return reasons use plain =, IN and LIKE without LOWER, because MySQL's comparisons already ignore capitals, as Day 10 showed. 'damaged' matches 'Damaged'. In a database that cares about capitals, like PostgreSQL, you'd add LOWER.)

Build 6: clean_sales, the one view reports should use
CREATE OR REPLACE VIEW clean_sales AS
SELECT o.order_id,
       o.order_date,
       o.customer_id,
       o.channel,
       o.coupon_code,
       oi.order_item_id,
       oi.product_id,
       p.product_name,
       COALESCE(cat.category_name, 'Uncategorised') AS category_name,
       oi.quantity,
       oi.unit_price,
       oi.quantity * oi.unit_price AS line_total,
       oi.quantity * p.cost_price  AS line_cost
FROM clean_orders o
JOIN clean_order_items oi ON oi.order_id     = o.order_id
JOIN products p           ON p.product_id    = oi.product_id
LEFT JOIN categories cat  ON cat.category_id = p.category_id
WHERE o.status = 'Completed'
  AND o.is_test = 0
  AND o.is_duplicate = 0;

That's the whole clean layer: two small helper tables and six views. Notice how clean_sales reads like a sentence: completed orders, not test, not duplicates, with their lines, products and categories. Each view handles one job, and they build on each other: clean_orders uses clean_customers for the master IDs and the test flag, and clean_sales uses clean_orders. Change a rule in one place, and everything above it follows.

A quick look at how the orders came through:

SQL
SELECT status,
       COUNT(*)                                AS orders,
       SUM(is_test)                            AS test,
       SUM(is_duplicate)                       AS duplicates,
       SUM(date_was_fixed)                     AS dates_fixed,
       SUM(customer_id <> original_customer_id) AS moved_to_master
FROM clean_orders
GROUP BY status
ORDER BY orders DESC;
Result
+-----------+--------+------+------------+-------------+-----------------+
| status    | orders | test | duplicates | dates_fixed | moved_to_master |
+-----------+--------+------+------------+-------------+-----------------+
| Completed |   5688 |    9 |         15 |           2 |              32 |
| Cancelled |    377 |    0 |          0 |           0 |               2 |
| Pending   |     40 |    0 |          0 |           0 |               0 |
| Shipped   |     39 |    0 |          0 |           0 |               0 |
+-----------+--------+------+------------+-------------+-----------------+

Four clean statuses, and every flag matches what we found earlier: 9 test orders, 15 duplicates, 2 fixed dates, and 32 + 2 = 34 orders moved to their master account. The test orders, duplicates and future dates were all marked Completed, which is exactly why they would have leaked into revenue.

Views or new tables? Views always show current data, cost no storage and can't go out of date. But they redo the work every time you query them. On our data that's a fraction of a second. On a table with a hundred million rows, teams often save the cleaned result into real tables on a schedule instead, for example every night. That's the job of data engineering tools, and the idea is the same: raw stays raw, cleaning is written as code.

10Data quality checks: a smoke alarm for your data

Cleaning once isn't enough. Tomorrow a new spelling arrives, or the app gets a bug. A smoke alarm doesn't put out fires, but it tells you the moment one starts. A data quality check is the same: a query that should return 0, and shouts when it doesn't. Put several together, and you get a health check you can run every morning.

The health check: run it whenever the data changes
SELECT 'Order statuses we do not recognise' AS check_name,
       COUNT(*) AS problems, 'fixed' AS kind
FROM clean_orders WHERE status = 'Unknown'
UNION ALL
SELECT 'Payment methods we do not recognise', COUNT(*), 'fixed'
FROM clean_payments WHERE payment_method = 'Unknown'
UNION ALL
SELECT 'Return reasons we do not recognise', COUNT(*), 'fixed'
FROM clean_returns WHERE reason_group = 'Other'
UNION ALL
SELECT 'Countries we do not recognise', COUNT(*), 'fixed'
FROM clean_customers
WHERE country NOT IN ('India', 'USA', 'UK', 'UAE', 'Singapore', 'Canada', 'Australia', 'Germany')
UNION ALL
SELECT 'Sign-up dates that would not convert', COUNT(*), 'fixed'
FROM clean_customers WHERE signup_date IS NULL
UNION ALL
SELECT 'City spellings missing from the lookup', COUNT(*), 'fixed'
FROM customers c
LEFT JOIN city_lookup l ON l.city_key = LOWER(TRIM(c.city))
WHERE TRIM(c.city) NOT IN ('', 'N/A') AND l.city_key IS NULL
UNION ALL
SELECT 'Orders dated after the data ends', COUNT(*), 'fixed'
FROM clean_orders WHERE order_date > '2024-12-31 23:59:59'
UNION ALL
SELECT 'Sales lines with quantity of zero or less', COUNT(*), 'fixed'
FROM clean_sales WHERE quantity <= 0
UNION ALL
SELECT 'Real customers whose first order is before their sign-up', COUNT(*), 'fixed'
FROM clean_customers cc
JOIN (SELECT customer_id, MIN(order_date) AS first_order
      FROM clean_orders GROUP BY customer_id) f ON f.customer_id = cc.customer_id
WHERE cc.is_test = 0 AND DATE(f.first_order) < cc.signup_date
UNION ALL
SELECT 'Successful payments that do not match the order total', COUNT(*), 'open: ask finance'
FROM payments p
JOIN (SELECT o.order_id, SUM(oi.quantity * oi.unit_price) + o.shipping_fee AS total
      FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
      GROUP BY o.order_id, o.shipping_fee) t ON t.order_id = p.order_id
WHERE p.payment_status = 'success' AND p.amount <> t.total
UNION ALL
SELECT 'Orders pending for more than 30 days', COUNT(*), 'open: ask operations'
FROM clean_orders WHERE status = 'Pending' AND order_date < '2024-12-01';
Result
+----------------------------------------------------------+----------+----------------------+
| check_name                                               | problems | kind                 |
+----------------------------------------------------------+----------+----------------------+
| Order statuses we do not recognise                       |        0 | fixed                |
| Payment methods we do not recognise                      |        0 | fixed                |
| Return reasons we do not recognise                       |        0 | fixed                |
| Countries we do not recognise                            |        0 | fixed                |
| Sign-up dates that would not convert                     |        0 | fixed                |
| City spellings missing from the lookup                   |        0 | fixed                |
| Orders dated after the data ends                         |        0 | fixed                |
| Sales lines with quantity of zero or less                |        0 | fixed                |
| Real customers whose first order is before their sign-up |        0 | fixed                |
| Successful payments that do not match the order total    |       12 | open: ask finance    |
| Orders pending for more than 30 days                     |        6 | open: ask operations |
+----------------------------------------------------------+----------+----------------------+

Every "fixed" check is 0, and the two open issues show their counts, so nobody forgets them. Some details worth noticing:

  • Checks run on the clean layer where possible. They test that your fixes work, not that the raw data is still messy (it is, and it always will be).
  • The sign-up check had a surprise. When I first ran it without cc.is_test = 0, it found one customer whose first order came before they signed up. It was a test account. Test data breaks the rules of real data, which is one more reason to exclude it.
  • The "do not recognise" checks are why the cleaning CASEs ended in a catch-all, 'Unknown' or 'Other'. For country, which passes clean values through with ELSE TRIM(country), the check uses a list of the countries we expect instead. A new spelling turns a 0 into a 1, and you find out on the first day, not in next quarter's board meeting.

🎯 Interview corner

Cleaning questions test judgement as much as SQL. Interviewers want to hear how you'd decide, not just which function you'd use.

Concept questions

Q1How do you approach cleaning a messy table?

First profile it and list the issues (Day 10). Then, without changing the raw data, write each fix as SQL in a view or a separate cleaned table: tidy text, map categories, convert types, turn fake NULLs into real ones, handle duplicates and exclude test data. Record every business decision where people can see it. Check row counts before and after each step, and finish with data quality checks that should return 0, so new problems are caught early.

Q2Why not just UPDATE the raw table to fix the data?

Because the raw data is the evidence. If a cleaning rule is wrong (say, the date format was really month-first), an UPDATE has destroyed the original, and you can't recover it. Cleaning in views or in a separate layer keeps the original, makes every rule visible, and automatically cleans new rows as they arrive. Also, an analyst often doesn't have permission to change source tables, and shouldn't need it.

Q3How do you find and remove duplicate rows?

To find them: GROUP BY the columns that define "the same", with HAVING COUNT(*) > 1. To keep one of each: ROW_NUMBER() OVER (PARTITION BY those columns ORDER BY something) and keep row number 1, where the ORDER BY decides which copy survives (for example the earliest). The hard part is defining "the same": exact copies, the same customer with a different email spelling, or two orders with the same basket a minute apart all need different rules.

Q4What does STR_TO_DATE return for a value that doesn't match the format?

NULL, with a warning, not an error, so bad conversions can pass silently. Always count the NULLs your conversion produces. Also, formats like 03/04/2024 are ambiguous (day-first or month-first), so check the data (a first number above 12, like 21/07/2024, proves day-first) and document the choice.

Q5What's the difference between REPLACE and REGEXP_REPLACE?

REPLACE(text, 'a', 'b') swaps one exact piece of text for another. REGEXP_REPLACE(text, pattern, 'b') swaps anything matching a pattern, so REGEXP_REPLACE(phone, '[^0-9]', '') removes every non-digit in one go. REGEXP_REPLACE needs MySQL 8.0 or newer.

Q6When would you use a lookup table instead of CASE?

When there are many values, when the mapping changes over time, or when business people should be able to maintain it. A lookup table keeps the mapping as data rather than code, can be joined anywhere, and makes unmapped values easy to find with an anti-join. CASE is fine for a short, stable list, like four order statuses.

Q7Why end a cleaning CASE with ELSE 'Unknown' rather than ELSE the original value?

So that unexpected values become visible. With ELSE status, a new spelling slips into reports as an extra category without anyone noticing. With ELSE 'Unknown', a data quality check counting 'Unknown' catches it the first day it appears.

Q8What is a data quality check?

A query that should return zero (or an expected number) when the data is healthy, for example "orders with an unknown status", "dates that failed to convert", "lines with quantity of zero or less", or "payments that don't match the order total". Run together on a schedule, they work like a smoke alarm: they don't fix anything, but they tell you right away when something breaks.

Practical questions

P1Keep only the latest review per customer per product.
SQL
WITH ranked AS (
    SELECT review_id, product_id, customer_id, rating, review_date,
           ROW_NUMBER() OVER (PARTITION BY customer_id, product_id
                              ORDER BY review_date DESC, review_id DESC) AS rn
    FROM clean_reviews
)
SELECT COUNT(*) AS latest_reviews
FROM ranked
WHERE rn = 1;
Result
+----------------+
| latest_reviews |
+----------------+
|           2053 |
+----------------+

Same pattern as removing exact copies, but here "the same" means the same customer and product, and ORDER BY ... DESC makes the newest review row 1. The review_id DESC tie-breaker makes the choice stable when two reviews share a date (Day 9).

P2A column of prices was loaded as text, like '₹1,299.00'. Turn it into a number.
SQL
SELECT '₹1,299.00' AS raw_price,
       CAST(REPLACE(REPLACE('₹1,299.00', '₹', ''), ',', '') AS DECIMAL(10,2)) AS clean_price;
Result
+-------------+-------------+
| raw_price   | clean_price |
+-------------+-------------+
| ₹1,299.00   |     1299.00 |
+-------------+-------------+

Remove the currency sign and the thousands comma, then CAST to DECIMAL (never FLOAT for money, Day 2). In a real column, add a check: any value that's still NULL or 0 after conversion needs a look.

P3Find customers whose email isn't a valid shape (something@something.something).
SQL
SELECT COUNT(*) AS bad_emails
FROM customers
WHERE TRIM(email) NOT REGEXP '^[^@ ]+@[^@ ]+[.][^@ ]+$';
Result
+------------+
| bad_emails |
+------------+
|          0 |
+------------+

The pattern means: some characters that aren't @ or a space, then one @, then more of them, a dot, and more. Every email here has a valid shape, which is useful to know too. A good answer adds that a valid shape doesn't mean a real inbox. Only sending an email proves that.

Quick recap

  • Never change raw data. Clean in views, write every decision in SQL, and count before and after each fix.
  • Text: TRIM, LOWER, UPPER, the capitalise pattern (not on names like D'Souza), REPLACE, and REGEXP_REPLACE to keep only the characters you want.
  • Categories: CASE on LOWER(TRIM(...)), with a catch-all like ELSE 'Unknown' so new values show up. For long or changing lists, use a lookup table.
  • Missing values: turn '' and 'N/A' into real NULLs with NULLIF. Use COALESCE only when you know what NULL means. Watch for rows an inner join drops.
  • Types: STR_TO_DATE for text dates (it returns NULL on failure, so count them) and CAST for numbers. Text compares like words, not values.
  • Duplicates come in kinds: exact copies (ROW_NUMBER), one person with two accounts (a master ID with MIN() OVER), and double submits (compare the baskets, then confirm with another source).
  • Exclude what isn't business (test accounts, zero quantities), and leave open questions open.
  • Finish with data quality checks that should return 0. The clean revenue is ₹1,31,72,860, up 54% from 2023 to 2024.
