Yesterday was about making SELECT fast. Today is about everything around it. Databases can hold more than tables and views: formulas you write yourself, saved scripts, rules that run by themselves when data changes, and a list of who is allowed to do what. And they're shared by many people at once, which raises a question Day 4 left open: while someone else is changing the data, what exactly do you see? You won't write these things every day as an analyst, but you'll meet all of them, and some will explain numbers that otherwise make no sense.

Before you start. Everything runs on online_store_full, so run USE online_store_full; first. Log in as root (or another user with full rights), because today you'll create users. Data changes happen inside transactions that end with ROLLBACK, or on a small practice table, so the shop's data stays exactly as it is. Section 8 ends with a tidy-up.

1Logic that lives inside the database

On Day 13 you saved a query as a view, so that everyone who asks "how much has each customer spent?" uses the same definition. That was your first piece of logic stored inside the database, instead of in a file on your laptop. There are a few more kinds. Think of them as the shop's written procedures:

ObjectWhat it isHow you use itIn the shop
View (Day 13)A saved query that acts like a tableSELECT ... FROM customer_summaryA standard report everyone reads
FunctionA saved formula that returns one valueInside a query: SELECT fiscal_year(order_date)The rule for working out the financial year
ProcedureA saved script of one or more steps, with inputsCALL refresh_monthly_sales();The closing-time checklist
TriggerSteps that run by themselves when rows changeNobody calls it. It reacts to INSERT, UPDATE or DELETEThe bell that rings when the door opens

Together, procedures, functions and triggers are called stored programs (or "stored routines" for the first two). Then there are two things every shared database has to decide, whatever is stored in it: who may do what (permissions, section 5), and what each person sees while others are working (isolation, sections 6 and 7).

2Your own functions

You've used dozens of built-in functions: ROUND, COALESCE, DATE_FORMAT. But every business has calculations of its own that MySQL doesn't know. Here's a common one in India: the financial year runs from 1 April to 31 March, so 15 February 2024 is in "FY2023-24", and 15 April 2024 is in "FY2024-25". Finance teams report this way, and writing the rule out in every query is long and easy to get wrong.

Here's a trick: move a date back 3 months, and April becomes January. Then the ordinary YEAR() of the moved date is the year the financial year started. Let's save that as a function:

Build 1: a first attempt
CREATE FUNCTION fiscal_year(d DATETIME) RETURNS VARCHAR(9)
RETURN CONCAT('FY', YEAR(d - INTERVAL 3 MONTH), '-',
              RIGHT(YEAR(d - INTERVAL 3 MONTH) + 1, 2));
MySQL says
ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL, or READS SQL DATA in its declaration and binary logging is enabled (you *might* want to use the less safe log_bin_trust_function_creators variable)

Read the message: MySQL wants to know what kind of function this is. Most servers keep a binary log, a record of every change, used to copy data to other servers (like the read replicas from Day 18) and to restore backups. If a function could give a different answer each time it runs (like NOW() or RAND()), the copies could end up different from the original. So you have to declare it. DETERMINISTIC means "the same input always gives the same output", which is true for our function:

Build 2: fiscal_year and fiscal_quarter
CREATE FUNCTION fiscal_year(d DATETIME) RETURNS VARCHAR(9)
DETERMINISTIC
RETURN CONCAT('FY', YEAR(d - INTERVAL 3 MONTH), '-',
              RIGHT(YEAR(d - INTERVAL 3 MONTH) + 1, 2));

CREATE FUNCTION fiscal_quarter(d DATETIME) RETURNS TINYINT
DETERMINISTIC
RETURN QUARTER(d - INTERVAL 3 MONTH);       -- April to June is Q1

The parts: a name, the inputs with their types, RETURNS and the type of the answer, and after RETURN, the formula. The input is a DATETIME, so it accepts both dates and order times. Now test it on the dates where it could go wrong, the edges:

SQL
SELECT fiscal_year('2024-03-31')          AS last_day_of_march,
       fiscal_year('2024-04-01')          AS first_day_of_april,
       fiscal_quarter('2024-04-01')       AS april_quarter,
       fiscal_year('2025-01-15 10:00:00') AS a_january_order;
Result
+-------------------+--------------------+---------------+-----------------+
| last_day_of_march | first_day_of_april | april_quarter | a_january_order |
+-------------------+--------------------+---------------+-----------------+
| FY2023-24         | FY2024-25          |             1 | FY2024-25       |
+-------------------+--------------------+---------------+-----------------+

And use it like any built-in function:

SQL
SELECT fiscal_year(order_date)  AS fy,
       COUNT(DISTINCT order_id) AS orders,
       SUM(line_total)          AS revenue
FROM clean_sales
GROUP BY fy
ORDER BY fy;
Result
+-----------+--------+------------+
| fy        | orders | revenue    |
+-----------+--------+------------+
| FY2022-23 |    358 |  748760.63 |
| FY2023-24 |   2645 | 5992100.93 |
| FY2024-25 |   2659 | 6431998.91 |
+-----------+--------+------------+

The three years add up to 13,172,860, the same total as Day 17's warehouse. But the first and last rows aren't whole years: the data starts in January 2023 and ends in December 2024, so FY2022-23 has only 3 months and FY2024-25 has 9. Even so, those 9 months already earned more than the whole of FY2023-24. Day 13's warning applies: say how much of the period each number covers.

Two cautions. First, a function on a column in WHERE hides the column from its index, just like YEAR() did yesterday (Day 18). WHERE fiscal_year(order_date) = 'FY2024-25' has to calculate the function for every row, so for filtering, write the date range: order_date >= '2024-04-01' AND order_date < '2025-04-01'. Use the function to label and group. Second, a function is a promise. If you mark it DETERMINISTIC when it isn't, MySQL believes you, and the copies of the data can drift apart.

3Stored procedures

A function is a formula: values in, one value out. A procedure is more like a recipe. It can run many steps, change data, and return whole tables of results. You run it with CALL. Here's a report that the marketing team asks for every week, "sales by category between two dates", saved with the dates as inputs:

Build 3: a report with inputs
CREATE PROCEDURE sales_summary(IN p_start DATE, IN p_end DATE)
SELECT category_name,
       COUNT(DISTINCT order_id) AS orders,
       SUM(line_total)          AS revenue
FROM clean_sales
WHERE order_date >= p_start AND order_date < p_end   -- Day 12's half-open range
GROUP BY category_name
ORDER BY revenue DESC;
SQL
CALL sales_summary('2024-10-01', '2025-01-01');
Result
+----------------+--------+-----------+
| category_name  | orders | revenue   |
+----------------+--------+-----------+
| Electronics    |    401 | 960872.48 |
| Clothing       |    474 | 849245.26 |
| Sports         |    348 | 453228.88 |
| Home & Kitchen |    223 | 282387.32 |
| Books          |    187 | 176392.26 |
| Uncategorised  |      9 |  28490.50 |
+----------------+--------+-----------+

The last quarter of 2024, with one line. Anyone can run it for any dates without knowing how clean_sales works, and everyone gets the same definition of "sales". (Starting input names with p_ is a common habit. It keeps them from being confused with column names.)

More than one step: DELIMITER

Most procedures have several statements between BEGIN and END, each ending with ;. That causes a problem. Workbench and the mysql command line split your script at every ; and send the pieces one by one, so the procedure would be cut off after its first statement. The fix is to change the separator for a moment. DELIMITER $$ says "until further notice, a statement ends at $$". After the procedure, DELIMITER ; switches back. (DELIMITER is an instruction to your tool, not SQL. When Python sends a procedure, as on Day 14, it goes as one piece, and no DELIMITER is needed.)

Procedures can also hand values back through OUT inputs. Here's one that counts a customer's orders:

Build 4: a procedure with an OUT value
DELIMITER $$

CREATE PROCEDURE customer_order_count(IN p_customer INT, OUT p_orders INT)
BEGIN
    SELECT COUNT(DISTINCT order_id) INTO p_orders
    FROM clean_sales
    WHERE customer_id = p_customer;
END$$

DELIMITER ;
SQL
CALL customer_order_count(181, @orders);
SELECT @orders AS orders_for_181;
Result
+----------------+
| orders_for_181 |
+----------------+
|             12 |
+----------------+

@orders is a user variable: a value with a name, kept until you disconnect. The procedure filled it in, and you read it afterwards. Customer 181, whose 45 website events you followed yesterday, has placed 12 completed orders.

A real job: refreshing a summary table

Day 17 explained that dashboards often read small summary tables instead of adding up every order each time. Someone has to rebuild them every night. That's a perfect job for a procedure: the steps are always the same, and they must all happen, or none of them. First, the table:

Build 5: the summary table
CREATE TABLE monthly_sales (
    month_start   DATE          NOT NULL,
    category_name VARCHAR(50)   NOT NULL,
    orders        INT           NOT NULL,
    revenue       DECIMAL(14,2) NOT NULL,
    PRIMARY KEY (month_start, category_name)
);
Build 6: the refresh procedure
DELIMITER $$

CREATE PROCEDURE refresh_monthly_sales()
BEGIN
    -- If any step below fails: undo everything, then report the error
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        RESIGNAL;
    END;

    START TRANSACTION;
    DELETE FROM monthly_sales;                          -- empty it
    INSERT INTO monthly_sales (month_start, category_name, orders, revenue)
    SELECT DATE_FORMAT(order_date, '%Y-%m-01') AS month_start,
           category_name,
           COUNT(DISTINCT order_id),
           SUM(line_total)
    FROM clean_sales
    GROUP BY month_start, category_name;                -- fill it again
    COMMIT;

    SELECT COUNT(*)         AS rows_loaded,
           MIN(month_start) AS first_month,
           MAX(month_start) AS last_month,
           SUM(revenue)     AS total_revenue
    FROM monthly_sales;
END$$

DELIMITER ;
SQL
CALL refresh_monthly_sales();
Result
+-------------+-------------+------------+---------------+
| rows_loaded | first_month | last_month | total_revenue |
+-------------+-------------+------------+---------------+
|         121 | 2023-01-01  | 2024-12-01 |   13172860.47 |
+-------------+-------------+------------+---------------+

121 rows (24 months of 5 categories, plus the uncategorised products, which only sold in December 2024), and the same 13,172,860 in total. Call it again, and you get exactly the same result, because it empties the table before filling it. A job that's safe to run twice is easy to live with: if it's not sure whether last night's run worked, just run it again.

The interesting part is the handler at the top. It says: "if any statement fails with an error (SQLEXCEPTION), stop, roll the transaction back, and pass the error on (RESIGNAL)". To see why it matters, break the job on purpose. Rename a column, so the INSERT fails after the DELETE has already emptied the table:

SQL
ALTER TABLE monthly_sales RENAME COLUMN orders TO order_count;   -- someone renames a column

CALL refresh_monthly_sales();
MySQL says
ERROR 1054 (42S22): Unknown column 'orders' in 'field list'
SQL
SELECT COUNT(*) AS rows_still_there FROM monthly_sales;

ALTER TABLE monthly_sales RENAME COLUMN order_count TO orders;   -- put it back
Result
+------------------+
| rows_still_there |
+------------------+
|              121 |
+------------------+

The refresh failed, but the dashboard still has all of yesterday's numbers, because the handler rolled the DELETE back. Without the handler, the procedure would just stop, leaving the transaction open with the DELETE done and nothing inserted. The next COMMIT, or any CREATE or ALTER (which commit by themselves, Day 4), would save an empty table, and the dashboard would show zero sales. This is Day 4's atomicity, put to work.

Jobs like this usually run on a timer: MySQL has an event scheduler (CREATE EVENT ... ON SCHEDULE EVERY 1 DAY), and many teams use outside tools to run them. To see what procedures and functions a database already has, ask information_schema, and read any one with SHOW CREATE PROCEDURE name;:

SQL
SELECT routine_name, routine_type
FROM information_schema.routines
WHERE routine_schema = 'online_store_full'
ORDER BY routine_type, routine_name;
Result
+-----------------------+--------------+
| ROUTINE_NAME          | ROUTINE_TYPE |
+-----------------------+--------------+
| fiscal_quarter        | FUNCTION     |
| fiscal_year           | FUNCTION     |
| customer_order_count  | PROCEDURE    |
| refresh_monthly_sales | PROCEDURE    |
| sales_summary         | PROCEDURE    |
+-----------------------+--------------+

4Triggers

A trigger is a set of steps attached to a table, which runs by itself every time a row is inserted, updated or deleted. Like the bell above a shop door, nobody has to remember to ring it. A classic use is an audit log. Prices in products get overwritten, so once a price changes, the old one is gone, and the question "what did the mouse cost in March?" has no answer. A trigger can write down every change:

Build 7: a price history table and a trigger
CREATE TABLE price_history (
    change_id  INT AUTO_INCREMENT PRIMARY KEY,
    product_id INT           NOT NULL,
    old_price  DECIMAL(10,2) NOT NULL,
    new_price  DECIMAL(10,2) NOT NULL,
    changed_by VARCHAR(100)  NOT NULL,
    changed_at DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP
);

DELIMITER $$

CREATE TRIGGER trg_products_price_log
AFTER UPDATE ON products
FOR EACH ROW
BEGIN
    IF NEW.price <> OLD.price THEN
        INSERT INTO price_history (product_id, old_price, new_price, changed_by)
        VALUES (NEW.product_id, OLD.price, NEW.price, CURRENT_USER());
    END IF;
END$$

DELIMITER ;

Read it as a sentence: after any UPDATE on products, for each row that changed, if the price is different, write a line in the history. Inside a trigger, OLD is the row as it was, and NEW is the row as it is now. (An INSERT trigger has only NEW, and a DELETE trigger has only OLD.) Test it with Day 4's rule, inside a transaction:

SQL
START TRANSACTION;

UPDATE products SET price = 849 WHERE product_id = 1;                       -- the mouse
UPDATE products SET stock_quantity = stock_quantity - 1 WHERE product_id = 2; -- not a price change
UPDATE products SET price = ROUND(price * 1.10)
WHERE category_id = (SELECT category_id FROM categories WHERE category_name = 'Books');

SELECT product_id, old_price, new_price, changed_by FROM price_history;
Result
+------------+-----------+-----------+----------------+
| product_id | old_price | new_price | changed_by     |
+------------+-----------+-----------+----------------+
|          1 |    799.00 |    849.00 | root@localhost |
|          5 |    599.00 |    659.00 | root@localhost |
|          6 |   1199.00 |   1319.00 | root@localhost |
|          7 |    899.00 |    989.00 | root@localhost |
|         24 |   1499.00 |   1649.00 | root@localhost |
|         25 |    999.00 |   1099.00 | root@localhost |
|         26 |    499.00 |    549.00 | root@localhost |
|         27 |    699.00 |    769.00 | root@localhost |
|         28 |    399.00 |    439.00 | root@localhost |
|         29 |    449.00 |    494.00 | root@localhost |
|         30 |    549.00 |    604.00 | root@localhost |
|         31 |   1099.00 |   1209.00 | root@localhost |
|         32 |   1299.00 |   1429.00 | root@localhost |
+------------+-----------+-----------+----------------+

Thirteen lines: the mouse, and 12 books from one UPDATE, because the trigger ran once for each row. The stock change wasn't logged, because the IF only looks at prices. Now undo it all:

SQL
ROLLBACK;

SELECT COUNT(*) AS logged_changes FROM price_history;
Result
+----------------+
| logged_changes |
+----------------+
|              0 |
+----------------+

The history is empty again. A trigger's work belongs to the same transaction as the change that set it off, so a ROLLBACK undoes both. That's exactly right: a log of price changes that never happened would be wrong.

BEFORE triggers can say no

A trigger that runs BEFORE the change can check it, and stop it with SIGNAL, which raises an error with your own message. Suppose someone once typed 79.90 instead of 799.00, and the shop sold mice at a tenth of the price for a day. A guard:

Build 8: a guard trigger
DELIMITER $$

CREATE TRIGGER trg_products_price_guard
BEFORE UPDATE ON products
FOR EACH ROW
BEGIN
    IF NEW.price < OLD.price * 0.5 THEN
        SIGNAL SQLSTATE '45000'          -- '45000' means "an error I defined"
            SET MESSAGE_TEXT = 'Price cut of more than 50% blocked. Ask a manager.';
    END IF;
END$$

DELIMITER ;
SQL
START TRANSACTION;
UPDATE products SET price = 79.90 WHERE product_id = 1;
MySQL says
ERROR 1644 (45000): Price cut of more than 50% blocked. Ask a manager.
SQL
UPDATE products SET price = price * 0.4 WHERE product_id IN (1, 2, 3);
MySQL says
ERROR 1644 (45000): Price cut of more than 50% blocked. Ask a manager.
SQL
UPDATE products SET price = 699 WHERE product_id = 1;      -- a normal sale price

SELECT product_id, price FROM products WHERE product_id IN (1, 2, 3);
SELECT product_id, old_price, new_price FROM price_history;
ROLLBACK;
Result
+------------+---------+
| product_id | price   |
+------------+---------+
|          1 |  699.00 |
|          2 | 2499.00 |
|          3 | 1299.00 |
+------------+---------+
+------------+-----------+-----------+
| product_id | old_price | new_price |
+------------+-----------+-----------+
|          1 |    799.00 |    699.00 |
+------------+-----------+-----------+

The typo was blocked. The 60% cut on three products was blocked too, and none of the three changed: when one row fails, the whole statement is undone. The ordinary cut to 699 went through, and the logging trigger wrote it down. (For simple rules about one row, like "price can't be negative", Day 3's CHECK constraint is simpler. Triggers are for rules that compare old and new values, or touch other tables.)

Why analysts should know about triggers. They're invisible. You run an UPDATE, and rows appear in a table you never touched. Or a number changes and nobody knows why. When data behaves strangely, check for triggers: SHOW TRIGGERS;, or the query below. Also know their limits: they run once per row, so they slow down big updates, and they don't run for everything. TRUNCATE doesn't fire DELETE triggers, and neither do rows deleted by a foreign key's ON DELETE CASCADE.

SQL
SELECT trigger_name, action_timing, event_manipulation, event_object_table
FROM information_schema.triggers
WHERE trigger_schema = 'online_store_full';
Result
+--------------------------+---------------+--------------------+--------------------+
| TRIGGER_NAME             | ACTION_TIMING | EVENT_MANIPULATION | EVENT_OBJECT_TABLE |
+--------------------------+---------------+--------------------+--------------------+
| trg_products_price_log   | AFTER         | UPDATE             | products           |
| trg_products_price_guard | BEFORE        | UPDATE             | products           |
+--------------------------+---------------+--------------------+--------------------+

5Users and permissions

On Day 14 you connected Python as root, the user who can do anything. On your own computer that's fine. At work, nobody gets root. Everyone gets their own user, with only the rights their job needs. That's the principle of least privilege, and it's Day 2's DCL family: GRANT and REVOKE. A new analyst, Riya, joins the team:

Build 9: a user for Riya
CREATE USER 'riya'@'localhost' IDENTIFIED BY 'Riya#Reports24';

SHOW GRANTS FOR 'riya'@'localhost';
Result
+------------------------------------------+
| Grants for riya@localhost                |
+------------------------------------------+
| GRANT USAGE ON *.* TO `riya`@`localhost` |
+------------------------------------------+

A MySQL user is a name and a place: 'riya'@'localhost' can only log in from the server's own computer. 'riya'@'%' could log in from anywhere. USAGE means "no rights at all": Riya can log in and do nothing else. Give her read access to the shop's database:

SQL
GRANT SELECT ON online_store_full.* TO 'riya'@'localhost';

Now log in as Riya. In a terminal: mysql -u riya -p online_store_full. In Workbench, add a new connection with the user name riya.

Share the answer, not the raw data

Now a harder case. customers holds names, emails and phone numbers. Suppose Riya works with an outside agency, and should see each customer's spending but no personal details. Views and procedures solve this neatly. Take away the broad right, and give her only the door you want her to use:

Build 10: narrower rights
REVOKE SELECT ON online_store_full.* FROM 'riya'@'localhost';

GRANT EXECUTE ON PROCEDURE online_store_full.sales_summary TO 'riya'@'localhost';

SHOW TABLES lists only the one view she may read. She can't read customers, or any of the tables behind the view (orders, order lines, products), and yet the view works for her, and so does the procedure. That's because, by default, a view or procedure runs with the rights of the person who created it (its definer, here root), not the person using it. So you can hand someone a safe, finished answer without handing them the tables behind it. (Writing SQL SECURITY INVOKER when creating one makes it use the caller's rights instead.)

Roles: rights for a job, not a person

When ten people need the same rights, granting them one by one gets messy. A role is a named bundle of rights. You give rights to the role, and the role to people:

Build 11: a reporting role
CREATE ROLE 'reporting';
GRANT SELECT  ON online_store_full.customer_summary        TO 'reporting';
GRANT EXECUTE ON PROCEDURE online_store_full.sales_summary TO 'reporting';

CREATE USER 'arjun'@'localhost' IDENTIFIED BY 'Arjun#Reports24';
GRANT 'reporting' TO 'arjun'@'localhost';

Arjun logs in (mysql -u arjun -p) and tries the view:

As arjun
SELECT CURRENT_ROLE();
SELECT COUNT(*) AS customers FROM online_store_full.customer_summary;
MySQL says to Arjun
+----------------+
| CURRENT_ROLE() |
+----------------+
| NONE           |
+----------------+
ERROR 1142 (42000): SELECT command denied to user 'arjun'@'localhost' for table 'customer_summary'

Denied, even though his role allows it. This catches almost everyone the first time. Having a role isn't the same as using it, and CURRENT_ROLE() says NONE. He could switch it on for this session with SET ROLE 'reporting';, but the proper fix is to make it switch on every time he logs in:

Build 12: switch the role on at login
SET DEFAULT ROLE 'reporting' TO 'arjun'@'localhost';
As arjun (log in again)
SELECT CURRENT_ROLE();
SELECT COUNT(*) AS customers FROM online_store_full.customer_summary;
Arjun sees
+-----------------+
| CURRENT_ROLE()  |
+-----------------+
| `reporting`@`%` |
+-----------------+
+-----------+
| customers |
+-----------+
|      2115 |
+-----------+

When Arjun changes teams, one REVOKE 'reporting' FROM 'arjun'@'localhost'; takes it all away. When the reporting team needs a new view, one GRANT to the role gives it to everyone.

6Many people at once: isolation

Day 1's ACID had an I for isolation, and Day 4 promised to explain it. While the shop is open, orders arrive, stock goes down and prices change, all at the same moment you're running a report. Imagine counting the stock in a shop while customers keep taking things off the shelves. By the time you reach the last shelf, the first one has changed. Your total describes a moment that never existed. Databases have to decide how much of other people's unfinished and finished work you see. That decision is the isolation level.

There are three classic things that can go wrong:

ProblemWhat happensIn the shop
Dirty readYou see someone's change before they've committed it, and they might undo itYou count a sale the customer then cancels at the till
Non-repeatable readYou read the same row twice in one transaction and get different values, because someone committed a change in betweenThe mouse stock is 23 on your first count and 20 on your second
Phantom readYou run the same search twice and new rows appear (or vanish), because someone inserted them"Orders today" was 40, and is 42 a minute later in the same report

The SQL standard defines four levels, from least to most protected:

LevelDirty readNon-repeatable readPhantom read
READ UNCOMMITTEDpossiblepossiblepossible
READ COMMITTEDpreventedpossiblepossible
REPEATABLE READ (MySQL's default)preventedpreventedpossible in the standard, but prevented for plain reads in MySQL
SERIALIZABLEpreventedpreventedprevented

B's change was committed (autocommit, Day 4), but A still saw 23 until A's own transaction ended. At its first read, A's transaction took a snapshot of the data, and every later read in the same transaction sees that snapshot. Nobody waited for anybody: InnoDB keeps old versions of changed rows for as long as an open transaction might need them.

For an analyst, this is a gift. Run all the queries of a report inside one transaction, and they all describe the same moment, so the category totals add up to the grand total even while orders keep arriving. It's also a trap: if you leave a transaction open in Workbench and come back an hour later, you're still looking at data from an hour ago, and wondering why the new orders don't show up.

Same steps, different result: inside one transaction, A read 20 and then 18. That's a non-repeatable read. Each statement sees the latest committed data, which is often what you want for a quick lookup, but two queries in one report can now describe two different moments.

READ UNCOMMITTED: reading a change that never happened

7Locks and deadlocks

Reading never had to wait in section 6. Writing is different. Two people can't change the same row at the same moment, or one change would overwrite the other. So when a transaction changes a row, it holds a lock on that row until it commits or rolls back. Anyone else who wants to change the row has to wait.

Session A · step 1
START TRANSACTION;
UPDATE stock_levels SET stock = stock - 1 WHERE product_id = 1;   -- A now holds the lock
Session B · step 2 (waits)
UPDATE stock_levels SET stock = stock - 1 WHERE product_id = 1;
SELECT stock FROM stock_levels WHERE product_id = 1;

B's window seems to hang. It's waiting for A's lock. Now let A finish:

Session A · step 3
COMMIT;
Session B, after the wait
+-------+
| stock |
+-------+
|    16 |
+-------+

The moment A committed, B's UPDATE went ahead, and it used A's new value: 18, minus 1 for A, minus 1 for B, is 16. Neither sale was lost. That's what locks are for.

When the lock isn't released

What if A never finishes? A forgotten transaction in a Workbench tab, for example. B doesn't wait forever. After innodb_lock_wait_timeout seconds (50 by default, set to 5 here so you don't have to wait), it gives up:

Session A · step 4
START TRANSACTION;
UPDATE stock_levels SET stock = stock - 1 WHERE product_id = 1;   -- and then A goes to lunch
Session B · step 5 (waits)
SET SESSION innodb_lock_wait_timeout = 5;
UPDATE stock_levels SET stock = stock - 1 WHERE product_id = 1;
Session B, after the wait
ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
Session A · step 6
ROLLBACK;

Now imagine B is the shop's website, trying to record a sale. Customers would see errors at checkout because an analyst left an UPDATE uncommitted. Keep transactions that change data short, and always finish them.

Deadlocks: two people waiting for each other

Picture two shop assistants in a narrow aisle. One holds the mice and needs the keyboards. The other holds the keyboards and needs the mice. Each waits for the other, forever. In a database, that's a deadlock:

Session A · step 7
START TRANSACTION;
UPDATE stock_levels SET stock = stock - 1 WHERE product_id = 1;   -- A locks the mouse
Session B · step 8
START TRANSACTION;
UPDATE stock_levels SET stock = stock - 1 WHERE product_id = 2;   -- B locks the keyboard
Session A · step 9 (waits)
UPDATE stock_levels SET stock = stock - 1 WHERE product_id = 2;   -- A waits for B
SELECT product_id, stock FROM stock_levels WHERE product_id IN (1, 2);
Session B · step 10
UPDATE stock_levels SET stock = stock - 1 WHERE product_id = 1;   -- B waits for A: deadlock!
MySQL says to Session B
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
Session A, after the wait
+------------+-------+
| product_id | stock |
+------------+-------+
|          1 |    15 |
|          2 |   286 |
+------------+-------+
Session A · step 11
COMMIT;

InnoDB spots the circle at once, picks one transaction as the victim (here B), and rolls back all of its work, so B's keyboard change is gone too. That freed the keyboard, so A's waiting UPDATE went through: the mouse is down to 15, and the keyboard to 286. The message says what to do: try again. Applications that write a lot retry automatically. Deadlocks are rarer when every program changes rows in the same order (always the mouse first, then the keyboard), and when transactions are short.

8What this means for you

As an analyst, you'll read and use these things far more often than you write them. Some practical rules:

SituationWhat to doDay
A report with several queries must add upRun them in one transaction: START TRANSACTION READ ONLY; ... COMMIT;. You get one snapshot, and the database knows you won't change anything19
New data doesn't show upCheck for a transaction you left open, and end it19
Changing dataA transaction, check the rows affected, commit quickly. Never leave an UPDATE uncommitted4, 19
Numbers change and nobody knows whyLook for triggers and scheduled procedures: information_schema.triggers, .routines19
A calculation everyone repeatsA view (for a table of results) or a function (for one value)13, 19
A job that must run the same way every timeA procedure, with a transaction and an error handler, safe to re-run17, 19
Sharing data with someoneGrant the least they need. Prefer a view or procedure over the raw tables, especially with personal data13, 19
Connecting from Python or a dashboardIts own read-only user, password in an environment variable, never root14, 19
Heavy queries on a busy databaseAsk for a read replica18

One more judgment call: where should logic live? Logic inside the database is shared by every tool, close to the data, and fast. But it's also harder to see, test and track. Nobody reviews a trigger the way they review code, and a procedure edited directly on the server has no history. That's why many analytics teams keep their logic as SQL files in version control (Day 17's dbt) and keep stored programs for jobs that really belong to the database. If you do create them, keep their code in a file in Git too, and write a comment saying what each one is for.

🎯 Interview corner

Analyst interviews ask about these topics as concepts more often than as code: what's the difference, when would you use it, what can go wrong. Transactions and isolation come up especially often, because they test whether you understand that a database is shared.

Concept questions

Q1What's the difference between a stored procedure and a function?

A function returns a single value and is used inside a query (SELECT fiscal_year(order_date)). A procedure is run on its own with CALL, can run many statements, can change data and manage transactions, can return result sets, and passes values back through OUT parameters. Use a function for a reusable calculation, and a procedure for a job.

Q2View, procedure or function: how do you choose?

A view when you want a reusable table of results that people query with SELECT, filter and join. A function when you want one value per row, like a label or a formula. A procedure when the work has several steps, needs inputs, or changes data, like a report with dates or a refresh job.

Q3What is a trigger? What are the risks?

Code that runs automatically before or after an INSERT, UPDATE or DELETE on a table, once for each affected row, with OLD and NEW giving the row before and after. Good for audit logs and rules that compare old and new values. Risks: the logic is hidden, so changes happen that nobody expects; it slows down big updates; and it doesn't fire for everything (not for TRUNCATE, and not for rows deleted by foreign key cascades).

Q4What are GRANT and REVOKE? What is the principle of least privilege?

They're DCL commands that give and take away rights (SELECT, INSERT, EXECUTE and so on) on databases, tables, views and routines. Least privilege means giving each user only the rights their job needs, such as read-only access for analysts, or one view instead of a table with personal data. Roles bundle rights so they can be given to many users at once.

Q5Explain dirty reads, non-repeatable reads and phantom reads.

A dirty read sees another transaction's uncommitted change, which may be rolled back. A non-repeatable read reads the same row twice in one transaction and gets different values, because another transaction committed a change in between. A phantom read runs the same search twice and finds new or missing rows, because another transaction inserted or deleted some.

Q6What are the isolation levels, and which is MySQL's default?

READ UNCOMMITTED (allows dirty reads), READ COMMITTED (each statement sees the latest committed data), REPEATABLE READ (a transaction keeps seeing the snapshot from its first read) and SERIALIZABLE (transactions behave as if they ran one after another). MySQL's InnoDB defaults to REPEATABLE READ. PostgreSQL, SQL Server and Oracle default to READ COMMITTED. Higher levels give more consistency but more waiting.

Q7What is a deadlock, and how is it handled?

Two transactions each hold a lock the other needs, so neither can continue. InnoDB detects it immediately, rolls back one transaction (error 1213), and lets the other carry on. The application should retry the failed transaction. To make deadlocks rarer: keep transactions short, and change rows in the same order everywhere.

Q8Why do you need DELIMITER when creating a procedure?

Tools like Workbench and the mysql client split scripts into statements at each ;. A procedure body contains semicolons, so it would be cut into pieces. DELIMITER $$ changes the separator so the whole CREATE PROCEDURE is sent as one statement, and DELIMITER ; changes it back. It's a client command, not SQL, so code sent from Python doesn't need it.

Practical questions

P1Write a function that returns the Indian financial year label (like 'FY2024-25') for a date.

Move the date back 3 months, so April becomes January, and take the year:

SQL
CREATE FUNCTION fiscal_year(d DATETIME) RETURNS VARCHAR(9)
DETERMINISTIC
RETURN CONCAT('FY', YEAR(d - INTERVAL 3 MONTH), '-',
              RIGHT(YEAR(d - INTERVAL 3 MONTH) + 1, 2));

Mention DETERMINISTIC (required when binary logging is on, and true here), test the edges (31 March and 1 April), and say you'd use it for labels, not in WHERE, where a date range can use an index.

P2A colleague needs customer spending figures, but must not see emails or phone numbers. How do you set that up?

Create a view with only the columns they need (like customer_summary: ID, orders, revenue), and grant SELECT on that view only, ideally to a role. A view runs with its definer's rights, so they can read it without any rights on customers. Check with SHOW GRANTS, and by logging in as them.

P3A nightly job deletes a summary table and reloads it. One night the reload failed and the dashboard showed zero sales. What went wrong, and how do you fix it?

The delete and the reload weren't one unit: the delete was saved and the insert failed. Put both in one transaction, inside a procedure with an error handler (DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; END;), so a failure undoes the delete and the error is still reported. Then a failed run leaves yesterday's numbers in place, and the job can simply be run again.

Quick recap

  • Databases can store logic: views (a saved query), functions (one value), procedures (a saved script you CALL) and triggers (steps that run by themselves when rows change).
  • Functions need DETERMINISTIC (or another declaration) when binary logging is on. Use them to label and group, not to filter.
  • Multi-statement routines need DELIMITER in Workbench and the mysql client. A job that changes data belongs in a transaction with an error handler, so it's all or nothing and safe to re-run.
  • Triggers use OLD and NEW, run once per row, are undone by ROLLBACK with everything else, and can block changes with SIGNAL. They're invisible, so check for them when data behaves strangely.
  • GRANT and REVOKE control who can do what. Grant the least that's needed. Views and procedures let people use answers without seeing the tables. Roles bundle rights, and need SET DEFAULT ROLE.
  • Isolation decides what you see while others change data. MySQL's REPEATABLE READ gives each transaction a snapshot. READ COMMITTED shows the latest saved data. READ UNCOMMITTED allows dirty reads.
  • Writers lock the rows they change until they commit. Long or forgotten transactions block others (error 1205), and deadlocks are resolved by rolling one transaction back (error 1213). Keep transactions short.
