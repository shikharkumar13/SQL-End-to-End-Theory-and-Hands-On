Yesterday's answers were full of numbers that meant nothing on their own: "category 1", "product 8", "customer 4". The names were sitting in other tables the whole time. On Day 1 you learned that a good database splits data into separate tables linked by keys, so each fact is stored once. Today you learn to put those tables back together, whenever and however you need. This is the single most useful skill in SQL.

1Why we join

If you've used Excel, you've probably used VLOOKUP: "for each row in this sheet, find the matching row in that sheet and bring back a value". A join does the same thing, but it can bring back many columns at once, match on any condition, and handle millions of rows.

On Day 2 you traced order 1 by hand. You looked up customer 1 in customers, the lines in order_items, then each product in products. Every one of those lookups was a join done with your eyes. By the end of today, you'll do the whole trace in one query.

Joins follow the arrows in the schema diagram from Day 2. Each arrow is a foreign key pointing to a primary key, and that pair of columns is what you join on:

To connectJoin on
orders and customersorders.customer_id = customers.customer_id
order_items and ordersorder_items.order_id = orders.order_id
order_items and productsorder_items.product_id = products.product_id
products and categoriesproducts.category_id = categories.category_id

2Your first JOIN

Let's put a name on every product's category:

SQL
SELECT products.product_name,
       categories.category_name
FROM products
JOIN categories
  ON products.category_id = categories.category_id;
Result
+------------------------------+----------------+
| product_name                 | category_name  |
+------------------------------+----------------+
| SQL Fundamentals             | Books          |
| Data Science Handbook        | Books          |
| The Pragmatic Programmer     | Books          |
| Cotton T-Shirt               | Clothing       |
| Denim Jeans                  | Clothing       |
| Hooded Sweatshirt            | Clothing       |
| Wireless Mouse               | Electronics    |
| Mechanical Keyboard          | Electronics    |
| USB-C Hub                    | Electronics    |
| Noise-Cancelling Headphones  | Electronics    |
| Stainless Steel Water Bottle | Home & Kitchen |
| Ceramic Coffee Mug           | Home & Kitchen |
| Non-Stick Frying Pan         | Home & Kitchen |
| Yoga Mat                     | Sports         |
| Resistance Bands Set         | Sports         |
+------------------------------+----------------+

Read it as: "take products, bring in categories, and match each product to the category whose category_id is the same." ON gives the matching rule. Writing JOIN on its own means INNER JOIN. Both are the same thing.

Table aliases: shorter names

Typing products. and categories. again and again gets tiring. Give each table a short nickname right after its name, and use that instead:

SQL
SELECT p.product_name,
       c.category_name,
       p.price
FROM products p
JOIN categories c ON p.category_id = c.category_id
WHERE c.category_name = 'Books';
Result
+--------------------------+---------------+---------+
| product_name             | category_name | price   |
+--------------------------+---------------+---------+
| SQL Fundamentals         | Books         |  599.00 |
| Data Science Handbook    | Books         | 1199.00 |
| The Pragmatic Programmer | Books         |  899.00 |
+--------------------------+---------------+---------+

Now you can filter by the category's name instead of remembering that Books is number 2. Short aliases like p, c, o (orders) and oi (order_items) are a near-universal habit, and we'll use them from here on.

When a column name appears in both tables

Both orders and customers have a column called customer_id. If you don't say which one you mean, MySQL refuses:

SQL
SELECT order_id, first_name
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE customer_id = 1;
MySQL says
ERROR 1052 (23000): Column 'customer_id' in where clause is ambiguous

"Ambiguous" means "I can see two of these, which one?". Put the alias in front: WHERE o.customer_id = 1. A good habit is to prefix every column in a join, even ones that only exist in one table. Then anyone reading your query knows where each column comes from.

A shortcut: USING

When the two columns have exactly the same name, you can write USING (column) instead of the full ON:

SQL
SELECT o.order_id, c.first_name, o.order_date
FROM orders o
JOIN customers c USING (customer_id)
WHERE customer_id = 1;
Result
+----------+------------+------------+
| order_id | first_name | order_date |
+----------+------------+------------+
|        1 | Aarav      | 2024-01-10 |
|        4 | Aarav      | 2024-02-20 |
|       12 | Aarav      | 2024-05-07 |
+----------+------------+------------+

With USING, the two customer_id columns are merged into one, so WHERE customer_id = 1 is no longer ambiguous. This is one of the payoffs of the naming habit from Day 2: the same key has the same name in every table. ON works for everything, though, so learn that first.

3How matching works

A join compares rows from the two tables and keeps every pair where the ON condition is true. Here are four customers and their orders:

A match: the order's customer_id equals the customer's customer_idNo match: INNER JOIN drops Noah, LEFT JOIN keeps him

Three things to notice. They explain almost everything about joins.

  1. One customer, many orders, many rows. Aarav matches three orders, so he appears in three result rows. A join doesn't squeeze anything. Each matching pair becomes one row.
  2. No match, no row (in an INNER JOIN). Noah has no orders, so no pair includes him, and he vanishes from the result. That's the "inner" part: only the overlap is kept.
  3. The matching rule can be anything. ON usually compares a foreign key with a primary key, but any true-or-false condition works. You'll use that in sections 6 and 10.
SQL
SELECT c.customer_id, c.first_name, o.order_id, o.status
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE c.customer_id IN (1, 2, 8, 10)
ORDER BY c.customer_id, o.order_id;
Result
+-------------+------------+----------+-----------+
| customer_id | first_name | order_id | status    |
+-------------+------------+----------+-----------+
|           1 | Aarav      |        1 | Completed |
|           1 | Aarav      |        4 | Completed |
|           1 | Aarav      |       12 | Completed |
|           2 | Diya       |        2 | Completed |
|           2 | Diya       |        7 | Cancelled |
|           8 | Kabir      |       11 | Pending   |
+-------------+------------+----------+-----------+

Six rows: Aarav three times, Diya twice, Kabir once, Noah nowhere. Exactly like the diagram.

NULL never matches. If a foreign key is NULL (like a product with no category), NULL = 1 is UNKNOWN, not TRUE, so that row never finds a partner in an inner join. It's the same NULL rule from Day 5, showing up again.

4Joining three or more tables

Each JOIN adds one more table to the chain. Here's the hand trace of order 1 from Day 2, in one query. We walk the arrows: order → customer, order → its lines, line → product, product → category.

SQL
SELECT o.order_id,
       o.order_date,
       c.first_name,
       c.city,
       p.product_name,
       cat.category_name,
       oi.quantity,
       oi.unit_price,
       oi.quantity * oi.unit_price AS line_total
FROM orders o
JOIN customers   c   ON c.customer_id   = o.customer_id
JOIN order_items oi  ON oi.order_id     = o.order_id
JOIN products    p   ON p.product_id    = oi.product_id
JOIN categories  cat ON cat.category_id = p.category_id
WHERE o.order_id = 1;
Result
+----------+------------+------------+--------+------------------+---------------+----------+------------+------------+
| order_id | order_date | first_name | city   | product_name     | category_name | quantity | unit_price | line_total |
+----------+------------+------------+--------+------------------+---------------+----------+------------+------------+
|        1 | 2024-01-10 | Aarav      | Jaipur | Wireless Mouse   | Electronics   |        2 |     799.00 |    1598.00 |
|        1 | 2024-01-10 | Aarav      | Jaipur | SQL Fundamentals | Books         |        1 |     599.00 |     599.00 |
+----------+------------+------------+--------+------------------+---------------+----------+------------+------------+

Aarav from Jaipur, 2 Wireless Mice and 1 SQL Fundamentals, ₹1,598 + ₹599 = ₹2,197. It's the same answer you worked out by hand on Day 2, now in one query that works for any order. Change the 1 to 4, and you've solved Day 2's Try this.

A tip for long joins: write them one table at a time. Join two tables, run it, check the row count makes sense, then add the next table. If a result suddenly has far more or fewer rows than you expected, the last join you added is the problem.

5LEFT JOIN: keep everything on the left

An inner join quietly drops anything without a match. Often that's exactly wrong. "List all customers with their number of orders" should include Noah with 0, not leave him out.

Think of a class register and the marks from an exam. An inner join is the list of students who sat the exam. A left join is the full register, with a blank next to anyone who was absent. Nobody is lost.

SQL
SELECT c.customer_id, c.first_name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE c.customer_id IN (1, 8, 9, 10)
ORDER BY c.customer_id;
Result
+-------------+------------+----------+
| customer_id | first_name | order_id |
+-------------+------------+----------+
|           1 | Aarav      |        1 |
|           1 | Aarav      |        4 |
|           1 | Aarav      |       12 |
|           8 | Kabir      |       11 |
|           9 | Mia        |       13 |
|          10 | Noah       |     NULL |
+-------------+------------+----------+

LEFT JOIN keeps every row from the left table (the one written first, after FROM). Where there's a match, you get the matched columns. Where there isn't, you get NULLs. Noah is back, with NULL for order_id.

Finding what's missing

Those NULLs are useful. Keep only the rows where the right side found nothing, and you get "things that have no match". This is called an anti-join, and analysts use it constantly: customers who never ordered, products never sold, sign-ups who never logged in.

SQL
SELECT c.customer_id, c.first_name, c.last_name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;
Result
+-------------+------------+-----------+
| customer_id | first_name | last_name |
+-------------+------------+-----------+
|          10 | Noah       | Brown     |
+-------------+------------+-----------+
SQL
SELECT p.product_id, p.product_name
FROM products p
LEFT JOIN order_items oi ON oi.product_id = p.product_id
WHERE oi.order_item_id IS NULL;
Result
+------------+----------------------+
| product_id | product_name         |
+------------+----------------------+
|         13 | Non-Stick Frying Pan |
+------------+----------------------+

Noah has never ordered, and the Frying Pan has never sold. These are the two edge cases built into the data on Day 4. Check the right side's primary key for NULL. It can never be NULL in a real row, so a NULL there always means "no match".

6The ON vs WHERE trap

This is the most common join mistake, and a favourite interview question. The question: "Show every customer, with their completed orders."

The natural first try puts the status in WHERE:

Wrong: the WHERE throws customers away
SELECT c.first_name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'Completed'
ORDER BY c.customer_id, o.order_id;
Result
+------------+----------+-----------+
| first_name | order_id | status    |
+------------+----------+-----------+
| Aarav      |        1 | Completed |
| Aarav      |        4 | Completed |
| Aarav      |       12 | Completed |
| Diya       |        2 | Completed |
| Rohan      |        3 | Completed |
| Rohan      |       10 | Completed |
| Ananya     |       15 | Completed |
| Vivaan     |        6 | Completed |
| Ishaan     |        8 | Completed |
| Saanvi     |        9 | Completed |
| Mia        |       13 | Completed |
+------------+----------+-----------+

Noah and Kabir have disappeared, even though we used a LEFT JOIN to keep everyone. Here's why. Remember the running order: the join happens first, then WHERE. The join kept Noah, with a NULL status. Kabir's only order is Pending. Then WHERE o.status = 'Completed' checked every row, and NULL and 'Pending' both failed. A WHERE on the right table's columns quietly turns your LEFT JOIN back into an inner join.

The fix is to move the condition into ON, so it becomes part of the matching rule:

Right: the condition is part of the match
SELECT c.first_name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
                  AND o.status = 'Completed'
ORDER BY c.customer_id, o.order_id;
Result
+------------+----------+-----------+
| first_name | order_id | status    |
+------------+----------+-----------+
| Aarav      |        1 | Completed |
| Aarav      |        4 | Completed |
| Aarav      |       12 | Completed |
| Diya       |        2 | Completed |
| Rohan      |        3 | Completed |
| Rohan      |       10 | Completed |
| Ananya     |       15 | Completed |
| Vivaan     |        6 | Completed |
| Ishaan     |        8 | Completed |
| Saanvi     |        9 | Completed |
| Kabir      |     NULL | NULL      |
| Mia        |       13 | Completed |
| Noah       |     NULL | NULL      |
+------------+----------+-----------+

Now it reads: "keep every customer, and attach only their completed orders". Kabir and Noah stay, with NULLs, because they have no completed orders to attach. Diya's cancelled order is gone, but Diya isn't.

In a LEFT JOIN, a condition on the right table placed in...means
ON"Which right-side rows count as a match?" Left rows always stay.
WHERE"Which result rows do I keep?" Left rows with no match get thrown away.

Conditions on the left table (like WHERE c.country = 'India') belong in WHERE as normal. For an INNER JOIN, ON and WHERE give the same result, so the trap only bites with outer joins.

7RIGHT JOIN and FULL OUTER JOIN

RIGHT JOIN is the mirror of LEFT JOIN: it keeps every row of the right table. These two give exactly the same rows:

SQL
SELECT c.first_name, o.order_id
FROM orders o
RIGHT JOIN customers c ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;
Result
+------------+----------+
| first_name | order_id |
+------------+----------+
| Noah       |     NULL |
+------------+----------+

It's Noah again, found from the other side. In practice, most people only ever write LEFT JOIN, and put the table they want to keep first. Queries are much easier to read when "keep everything" always means "the table on the left". If you meet a RIGHT JOIN, you can always swap the two tables and make it a LEFT JOIN.

A FULL OUTER JOIN keeps unmatched rows from both sides. PostgreSQL and SQL Server have it, but MySQL does not. You build it yourself with a UNION of a left join and a right join. You'll see how in section 12.

JoinKeepsUnmatched columns become
INNER JOIN (or JOIN)only matching pairs(no unmatched rows)
LEFT JOINevery left row, plus matchesNULL on the right
RIGHT JOINevery right row, plus matchesNULL on the left
FULL OUTER JOINevery row from both sidesNULL on whichever side is missing (not in MySQL)
CROSS JOINevery possible pair (section 11)(no matching at all)

8Joins with GROUP BY

This is where joins and Day 6 come together, and where most real reports come from. Join to get the names, then group to summarise.

Revenue in one query

On Day 6 you worked out real revenue in two steps, typing the IDs of the non-completed orders by hand. Now orders and order_items can be joined, so the query can read the status itself:

SQL
SELECT SUM(oi.quantity * oi.unit_price) AS revenue,
       COUNT(DISTINCT o.order_id)       AS completed_orders
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
WHERE o.status = 'Completed';
Result
+----------+------------------+
| revenue  | completed_orders |
+----------+------------------+
| 39969.00 |               11 |
+----------+------------------+

₹39,969 from 11 orders, the same as Day 6. But this version keeps working when tomorrow's orders arrive, because it reads the status instead of a list you typed.

Revenue per category, with names

SQL
SELECT cat.category_name,
       SUM(oi.quantity * oi.unit_price) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id    = o.order_id
JOIN products    p  ON p.product_id   = oi.product_id
JOIN categories  cat ON cat.category_id = p.category_id
WHERE o.status = 'Completed'
GROUP BY cat.category_name
ORDER BY revenue DESC;
Result
+----------------+----------+
| category_name  | revenue  |
+----------------+----------+
| Electronics    | 25491.00 |
| Books          |  4494.00 |
| Clothing       |  4294.00 |
| Home & Kitchen |  3493.00 |
| Sports         |  2197.00 |
+----------------+----------+

Four tables, one clear answer. Electronics brings in more than the other four categories put together, mostly thanks to two sales of the ₹7,999 headphones.

Monthly revenue

Day 6 had to stop at counting orders per month, because the dates and the amounts live in different tables. Not any more:

SQL
SELECT DATE_FORMAT(o.order_date, '%Y-%m')   AS order_month,
       COUNT(DISTINCT o.order_id)           AS orders,
       SUM(oi.quantity * oi.unit_price)     AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
WHERE o.status = 'Completed'
GROUP BY order_month
ORDER BY order_month;
Result
+-------------+--------+----------+
| order_month | orders | revenue  |
+-------------+--------+----------+
| 2024-01     |      2 | 10196.00 |
| 2024-02     |      2 |  7094.00 |
| 2024-03     |      2 |  4991.00 |
| 2024-04     |      2 |  4796.00 |
| 2024-05     |      2 | 10196.00 |
| 2024-06     |      1 |  2696.00 |
+-------------+--------+----------+

This is the first real business report of the series: revenue month by month. It's also exactly the shape of the chart every owner wants to see.

Top customers by spend

SQL
SELECT c.customer_id,
       CONCAT(c.first_name, ' ', c.last_name) AS customer,
       COUNT(DISTINCT o.order_id)             AS orders,
       SUM(oi.quantity * oi.unit_price)       AS total_spent
FROM customers c
JOIN orders o       ON o.customer_id = c.customer_id
JOIN order_items oi ON oi.order_id   = o.order_id
WHERE o.status = 'Completed'
GROUP BY c.customer_id, customer
ORDER BY total_spent DESC
LIMIT 5;
Result
+-------------+--------------+--------+-------------+
| customer_id | customer     | orders | total_spent |
+-------------+--------------+--------+-------------+
|           1 | Aarav Sharma |      3 |    15193.00 |
|           2 | Diya Patel   |      1 |     7999.00 |
|           3 | Rohan Mehta  |      2 |     6594.00 |
|           6 | Ishaan Gupta |      1 |     2794.00 |
|           4 | Ananya Reddy |      1 |     2696.00 |
+-------------+--------------+--------+-------------+

Aarav is the best customer by far: three orders, and almost 40% of all revenue. Notice we grouped by c.customer_id as well as the name. Two different customers can share a name, so always group by the ID, and add the name for display.

Every product, including the ones nobody bought

On Day 6, "units sold per product" left out the Frying Pan, because it had no rows to group. A LEFT JOIN from products keeps it:

SQL
SELECT p.product_name,
       COUNT(oi.order_item_id) AS times_ordered,
       SUM(oi.quantity)        AS units_sold
FROM products p
LEFT JOIN order_items oi ON oi.product_id = p.product_id
GROUP BY p.product_id, p.product_name
ORDER BY times_ordered, p.product_name
LIMIT 4;
Result
+----------------------+---------------+------------+
| product_name         | times_ordered | units_sold |
+----------------------+---------------+------------+
| Non-Stick Frying Pan |             0 |       NULL |
| Ceramic Coffee Mug   |             1 |          4 |
| Hooded Sweatshirt    |             1 |          1 |
| Resistance Bands Set |             1 |          2 |
+----------------------+---------------+------------+

The Frying Pan is back, with 0. Two details are worth a careful look:

  • We wrote COUNT(oi.order_item_id), not COUNT(*). The Frying Pan's group has one row: the product, with NULLs on the right. COUNT(*) would count that row and say 1. COUNT(column) skips the NULL and correctly says 0. Day 6's "COUNT(*) vs COUNT(column)" lesson matters most right here.
  • units_sold is NULL, not 0, because SUM of nothing is NULL (Day 6, section 4). Tomorrow, COALESCE(SUM(oi.quantity), 0) turns it into a proper 0.

9The row-multiplying trap

You saw in section 3 that a join creates one row per matching pair. Join an order to its three lines, and that one order becomes three rows. That's correct, but it quietly breaks some sums and counts.

Say you want each customer's number of orders, and you write it after joining to order_items (maybe because you also need amounts):

SQL
SELECT o.customer_id,
       COUNT(*)                   AS count_star,
       COUNT(DISTINCT o.order_id) AS real_orders
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
GROUP BY o.customer_id
ORDER BY o.customer_id
LIMIT 4;
Result
+-------------+------------+-------------+
| customer_id | count_star | real_orders |
+-------------+------------+-------------+
|           1 |          6 |           3 |
|           2 |          2 |           2 |
|           3 |          4 |           2 |
|           4 |          4 |           2 |
+-------------+------------+-------------+

Aarav doesn't have 6 orders. He has 3, with 6 lines between them. After the join, each row is an order line, so COUNT(*) counts lines. COUNT(DISTINCT o.order_id) gives the true number of orders.

Sums can be inflated the same way. If orders had a delivery_fee column, SUM(o.delivery_fee) after this join would add each order's fee once per line, two or three times over. No error, just a wrong number in a report.

The habit that prevents this: before you aggregate, ask "what does one row mean after my joins?" Here, one row is one order line, not one order and not one customer. Sum values that belong to that level (like quantity * unit_price), and use COUNT(DISTINCT ...) for anything above it. On Day 8 you'll learn a cleaner fix: summarise each table first, then join the summaries.

10Self joins: a table joined to itself

Sometimes the two things you want to compare live in the same table. A self join lists the table twice, with two different aliases, as if it were two copies.

The classic example is an employees table where each row has a manager_id, and the manager is also an employee. You met this table design in Day 3's Interview corner. To show each employee next to their manager's name, you join employees e to employees m on e.manager_id = m.employee_id. Our shop's real employees table arrives on Day 10.

Here's a self join on our own data. The owner asks: "Which customers came back and ordered again within 60 days?" Both orders live in orders, so we pair the table with itself:

SQL
SELECT o1.customer_id,
       o1.order_id   AS earlier_order,
       o1.order_date AS earlier_date,
       o2.order_id   AS later_order,
       o2.order_date AS later_date,
       DATEDIFF(o2.order_date, o1.order_date) AS days_between
FROM orders o1
JOIN orders o2 ON o2.customer_id = o1.customer_id
              AND o2.order_date  > o1.order_date
WHERE DATEDIFF(o2.order_date, o1.order_date) <= 60
ORDER BY o1.customer_id;
Result
+-------------+---------------+--------------+-------------+------------+--------------+
| customer_id | earlier_order | earlier_date | later_order | later_date | days_between |
+-------------+---------------+--------------+-------------+------------+--------------+
|           1 |             1 | 2024-01-10   |           4 | 2024-02-20 |           41 |
|           2 |             2 | 2024-01-15   |           7 | 2024-03-12 |           57 |
+-------------+---------------+--------------+-------------+------------+--------------+
  • o1 and o2 are the same table seen twice: "an earlier order" and "a later order".
  • The ON pairs orders from the same customer where the second comes after the first. Without o2.order_date > o1.order_date, every order would also pair with itself, and every pair would appear twice, once in each direction.
  • DATEDIFF(later, earlier) gives the number of days between two dates. You'll meet many more date functions on Day 12.

Aarav came back after 41 days, and Diya after 57 (though, as you know, that second order was cancelled). Repeat purchase speed is one of the most watched numbers in e-commerce, and you'll analyse it properly on Day 13.

11CROSS JOIN: every combination

A CROSS JOIN has no matching rule at all. It pairs every row of one table with every row of the other. Think of a menu: 3 drinks × 4 snacks = 12 possible combos. 10 customers × 5 categories gives 50 rows:

SQL
SELECT COUNT(*) AS combinations
FROM customers
CROSS JOIN categories;
Result
+--------------+
| combinations |
+--------------+
|           50 |
+--------------+

Why would you want that? To build a complete grid first, and fill it in after. For example, "how much has each customer spent in each category, including the zeros?" A normal join only shows combinations that happened. A cross join makes all 50, and a left join then attaches the spending. You'll use this pattern on Day 12 to make reports that show months with no sales.

The accidental cross join. Older SQL lists tables with a comma: FROM orders, customers WHERE orders.customer_id = customers.customer_id. That works, but forget the WHERE and you get every order paired with every customer: 150 rows of nonsense, or billions on real tables. Write explicit JOIN ... ON, so a missing condition is easy to spot.

12UNION: stacking results

Joins put tables side by side: more columns. UNION puts results one on top of the other: more rows. Think of stapling two printed lists together into one long list.

Here's a timeline of everything Aarav has done: his sign-up from customers and his orders from orders, in one list:

SQL
SELECT signup_date AS event_date, 'Signed up' AS event, NULL AS order_id
FROM customers
WHERE customer_id = 1

UNION ALL

SELECT order_date, CONCAT('Order (', status, ')'), order_id
FROM orders
WHERE customer_id = 1

ORDER BY event_date;
Result
+------------+-------------------+----------+
| event_date | event             | order_id |
+------------+-------------------+----------+
| 2023-01-15 | Signed up         |     NULL |
| 2024-01-10 | Order (Completed) |        1 |
| 2024-02-20 | Order (Completed) |        4 |
| 2024-05-07 | Order (Completed) |       12 |
+------------+-------------------+----------+

The rules for stacking:

  • Both queries must return the same number of columns, in the same order, with types that fit together.
  • The column names come from the first query.
  • One ORDER BY at the very end sorts the whole combined list.

UNION vs UNION ALL

UNION ALL keeps every row. UNION removes duplicate rows, like a DISTINCT over the combined list. Which customers have a completed order or a pending one?

SQL
SELECT customer_id FROM orders WHERE status = 'Completed'
UNION

Building a FULL OUTER JOIN

Since MySQL has no FULL OUTER JOIN, you combine a left join and a right join with UNION, which also removes the matched rows that appear in both halves:

SQL
SELECT c.first_name, o.order_id
FROM customers c LEFT JOIN orders o ON o.customer_id = c.customer_id
UNION
SELECT c.first_name, o.order_id
FROM customers c RIGHT JOIN orders o ON o.customer_id = c.customer_id;

On our data the result is just the left join, because every order has a customer (the foreign key makes sure of that). Full outer joins earn their keep when you compare two lists where either side can have extras, such as this month's customers against last month's.

🎯 Interview corner

Joins are the most tested topic in SQL interviews. Expect at least one join question in every round, often with a NULL or a missing row hidden in it.

Concept questions

Q1What types of joins are there? Explain each in one line.

INNER: only rows that match on both sides. LEFT: every row from the left table, plus matches, with NULLs where there's no match. RIGHT: the mirror of LEFT. FULL OUTER: every row from both sides (not in MySQL, built with UNION). CROSS: every combination of rows. A self join is any of these with a table joined to itself.

Q2What's the difference between INNER JOIN and LEFT JOIN? Give an example where it matters.

An inner join drops rows that have no match. A left join keeps every row of the left table. Example: "orders per customer". With an inner join, a customer who never ordered is missing. With a left join and COUNT(o.order_id), they appear with 0. When you report on "all customers" or "all products", you almost always need a left join.

Q3In a LEFT JOIN, what's the difference between putting a condition in ON and in WHERE?

In ON, it decides which right-side rows count as a match, and every left row is still kept. In WHERE, it filters the joined result, so left rows whose right side is NULL get thrown away, and the left join behaves like an inner join. So conditions on the right table usually go in ON, and conditions on the left table go in WHERE. For inner joins, both give the same result.

Q4How do you find rows in one table that have no match in another?

A LEFT JOIN followed by WHERE right_table.primary_key IS NULL. For example, customers with no orders: customers c LEFT JOIN orders o ON ... WHERE o.order_id IS NULL. On Day 8 you'll see two more ways, NOT EXISTS and NOT IN, and why NOT IN can go wrong when NULLs are involved.

Q5Why might a query return more rows after you add a join?

Because a join returns one row per matching pair. Joining a one-to-many relationship (an order to its lines) repeats the "one" side once for every match. That's correct, but it inflates COUNT(*) and sums of columns from the "one" side. Fix it with COUNT(DISTINCT ...), or by summarising each table before joining. If both sides have duplicate keys, the rows multiply even faster, which is a common cause of shockingly large results.

Q6Do NULLs match each other in a join?

No. NULL = NULL is UNKNOWN, not TRUE, so rows with a NULL key never match anything in an inner join, not even another NULL. In a left join they're kept, but with NULLs on the right.

Q7What is a self join? Give a real use.

A table joined to itself using two aliases. The classic use is an employees table with a manager_id: join employees e to employees m on e.manager_id = m.employee_id to show each employee with their manager. Others: comparing a customer's orders with their own earlier orders, or finding pairs of products in the same category.

Q8What's the difference between UNION and UNION ALL?

Both stack the rows of two queries. UNION removes duplicate rows. UNION ALL keeps them all and is faster, because it skips the duplicate check. Both need the same number of columns with compatible types, and they take column names from the first query.

Q9What's the difference between a JOIN and a UNION?

A join combines tables horizontally: it matches rows and puts their columns side by side. A union combines results vertically: it puts the rows of one query under the rows of another, with the same columns.

Q10MySQL has no FULL OUTER JOIN. How do you get one?

Take a LEFT JOIN and a RIGHT JOIN of the same two tables and combine them with UNION. The left join brings every left row, the right join brings every right row, and UNION removes the matched rows that appear in both.

Practical questions

P1An employees table has employee_id, name, salary and manager_id. Find employees who earn more than their manager.
For an employees table (arrives on Day 10)
SELECT e.name   AS employee,
       e.salary AS employee_salary,
       m.name   AS manager,
       m.salary AS manager_salary
FROM employees e
JOIN employees m ON e.manager_id = m.employee_id
WHERE e.salary > m.salary;

One of the most asked SQL interview questions. The table is joined to itself: e is the employee, m is their manager. An inner join is right here, because the top boss has no manager and can't earn more than one. You'll run this for real on Day 10.

P2Which customers have bought from both Electronics and Books (completed orders only)?
SQL
SELECT c.first_name, c.last_name
FROM customers c
JOIN orders o        ON o.customer_id   = c.customer_id
JOIN order_items oi  ON oi.order_id     = o.order_id
JOIN products p      ON p.product_id    = oi.product_id
JOIN categories cat  ON cat.category_id = p.category_id
WHERE o.status = 'Completed'
  AND cat.category_name IN ('Electronics', 'Books')
GROUP BY c.customer_id, c.first_name, c.last_name
HAVING COUNT(DISTINCT cat.category_name) = 2;
Result
+------------+-----------+
| first_name | last_name |
+------------+-----------+
| Aarav      | Sharma    |
| Ananya     | Reddy     |
+------------+-----------+

The trick: WHERE keeps only purchases from the two categories, then HAVING COUNT(DISTINCT ...) = 2 keeps customers who have both. Writing WHERE category_name = 'Electronics' AND category_name = 'Books' is the classic wrong answer. A single row can't be in two categories at once, so it returns nothing.

P3Show every category with its number of products and its completed revenue, including categories that sold nothing.

       COUNT(DISTINCT p.product_id)     AS products,
       SUM(oi.quantity * oi.unit_price) AS revenue
FROM categories cat
LEFT JOIN products p     ON p.category_id = cat.category_id
LEFT JOIN order_items oi ON oi.product_id = p.product_id
LEFT JOIN orders o       ON o.order_id    = oi.order_id
                        AND o.status = 'Completed'
GROUP BY cat.category_name
ORDER BY revenue DESC;
Result
+----------------+----------+----------+
| category_name  | products | revenue  |
+----------------+----------+----------+
| Electronics    |        4 | 25491.00 |
| Clothing       |        3 |  9391.00 |
| Books          |        3 |  6892.00 |
| Home & Kitchen |        3 |  3493.00 |
| Sports         |        2 |  3196.00 |
+----------------+----------+----------+

Look closely and compare with the revenue-per-category query in section 8. Clothing shows ₹9,391 here but ₹4,294 there, Books ₹6,892 against ₹4,494, Sports ₹3,196 against ₹2,197. This query is wrong, and it's a subtle one worth studying. The status condition sits on the last left join, so a cancelled order simply fails to match. But its order lines are still in the result, and still added to SUM(oi.quantity * oi.unit_price). So cancelled and pending lines are counted as revenue.

The fix is to only count a line's amount when its order matched. Here's an inner join version that's correct (it drops categories with no sales):

SQL
SELECT cat.category_name,
       COUNT(DISTINCT p.product_id)     AS products_sold,
       SUM(oi.quantity * oi.unit_price) AS revenue
FROM categories cat
JOIN products p     ON p.category_id = cat.category_id
JOIN order_items oi ON oi.product_id = p.product_id
JOIN orders o       ON o.order_id    = oi.order_id
WHERE o.status = 'Completed'
GROUP BY cat.category_name
ORDER BY revenue DESC;
Result
+----------------+---------------+----------+
| category_name  | products_sold | revenue  |
+----------------+---------------+----------+
| Electronics    |             4 | 25491.00 |
| Books          |             3 |  4494.00 |
| Clothing       |             2 |  4294.00 |
| Home & Kitchen |             2 |  3493.00 |
| Sports         |             2 |  2197.00 |
+----------------+---------------+----------+

To keep every category and count only completed lines, you need either CASE inside the SUM, or to summarise revenue first and then left join it to categories. Both are tomorrow's tools. If you spotted the problem before reading this, you're thinking like an analyst: always sanity-check a new number against one you already trust.

Quick recap

  • A join puts tables side by side by matching rows, usually a foreign key to a primary key: JOIN table ON a.key = b.key. Use short aliases and prefix every column.
  • A join returns one row per matching pair. One-to-many joins repeat the "one" side.
  • INNER JOIN keeps only matches. LEFT JOIN keeps every left row, with NULLs where nothing matched. Prefer LEFT over RIGHT. MySQL has no FULL OUTER JOIN, so use LEFT + UNION + RIGHT.
  • Anti-join: LEFT JOIN ... WHERE right.primary_key IS NULL finds things with no match.
  • In a LEFT JOIN, conditions on the right table go in ON. In WHERE, they turn it into an inner join.
  • After joins, ask "what does one row mean now?" Use COUNT(DISTINCT ...) and COUNT(column), not COUNT(*), to avoid inflated counts.
  • Self joins compare rows in the same table. CROSS JOIN makes every combination. UNION stacks results and removes duplicates, UNION ALL keeps them.
  • Real revenue in one query: ₹39,969. Electronics leads the categories, Aarav leads the customers.
