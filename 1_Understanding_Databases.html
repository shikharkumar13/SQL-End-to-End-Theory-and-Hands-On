1What is a database?

A database is a collection of data stored in an organized way, so you can easily find it, change it and keep it safe.

Think of a library. Books are not thrown into a pile. They sit on labeled shelves, grouped by subject, and a catalog tells you where each one is. Because of this, you can find any book in a few seconds. A database does the same job for data.

You use databases every day without noticing. Your bank balance, your chat messages and the status of your food order all come from a database.

The important word is organized. A folder full of random spreadsheets holds data, but it is not a database. The organization is what makes a database useful.

2Database vs. DBMS vs. RDBMS

People often mix up these three terms. Here is the difference.

Database

The data itself, stored in an organized way. Think of it as the content.

DBMS

Database Management System. The software you use to create, read, change and manage the data. You never open the raw data files yourself. The DBMS does that for you. It also controls who can see the data, keeps backups and lets many people use the data at the same time.

RDBMS

Relational DBMS. A DBMS that stores data in tables that are linked to each other. SQL is the language we use to talk to an RDBMS. This whole series is about this type.

Short version: the database is the data, the DBMS is the software, and an RDBMS is a DBMS that uses linked tables.

Common RDBMS software: MySQL, PostgreSQL, Microsoft SQL Server, Oracle and SQLite. They have small differences, but they all use SQL, so what you learn here works on all of them. In this series we use MySQL.

Going deeper: ACID properties

Think about sending ₹5,000 from your bank account to a friend. Two things must happen: the money leaves your account, and the money reaches your friend's account. What if the system crashes after the first step? A good RDBMS makes sure this never leaves things half-done. It follows four rules, known as ACID:

AAtomicityAll steps happen, or none of them happen. No half-done work.
CConsistencyAfter any change, the data still follows every rule you set.
IIsolationWhen many people change data at the same time, they don't mess up each other's work.
DDurabilityOnce a change is saved, it stays saved, even if the system crashes right after.

Because of these rules, banks, hospitals and shops trust relational databases with important data. On Day 4 you will use two commands linked to this: COMMIT and ROLLBACK.

3Why should a data analyst or data scientist care?

You may ask: I can already open data in Excel or Python, so why learn databases? Here are the reasons.

🏛️

Real data lives in databases

In most companies, customer details, sales, website activity and product data are stored in databases, not in Excel files. To analyze real company data, you first have to get it out of the database.

📈

Size

An Excel sheet can hold about one million rows at most, and it gets slow long before that. Databases can hold millions or even billions of rows and still answer quickly.

⚡

Speed and accuracy

Instead of filtering and scrolling by hand, you write one query and get exactly the data you asked for. "Total sales per category last quarter, highest first" takes only a few lines of SQL.

🔬

It is the first step of analysis

Before you make a chart, train a model or write a report, you need the right data. Getting it with SQL is usually the first step, which is why SQL appears in almost every analyst and data scientist job post.

In short: SQL is how you get the data. Everything else you do as an analyst depends on it.

4Relational vs. non-relational databases

There are two main families of databases. You will use the first one most of the time, but you should know that both exist.

Relational (SQL)

  • Data is stored in tables (rows and columns)
  • Tables are linked using keys
  • Works best when the data has a fixed, clear structure
  • Good for customers, orders, products and payments
  • Most business data is stored this way
Examples: MySQL, PostgreSQL, SQL Server, Oracle, SQLite

Non-relational (NoSQL)

  • Data is stored as documents, key-value pairs or graphs
  • No fixed table structure
  • Works well when the shape of the data keeps changing
  • Good for social media posts, sensor readings and app data that changes often
  • Built to grow easily for some kinds of workloads
Examples: MongoDB, Redis, Cassandra, DynamoDB

Neither one is better than the other. They are built for different jobs. For data analysis, relational databases and SQL are what you need first. In this series, "database" always means a relational database.

5The core vocabulary you must know

This is the most important part of today. You will see these words in every article from now on. We will use this small customers table to explain each one:

customers example table
🔑 customer_idfirst_namelast_namecity

2DiyaPatelMumbai
3RohanMehtaDelhi

Table

A set of related data arranged in rows and columns. Each table holds one kind of thing, like customers, orders or products. Another name for a table is a relation.

Column also called field or attribute

One type of information that every row has. Each column has a name and a data type (number, text, date and so on). Here, first_name and city are columns. A column tells you what detail is being stored.

Row also called record or tuple

One complete entry in the table. The row 1, Aarav, Sharma, Jaipur holds everything about one customer. A row tells you who or what the entry is about.

Schema

The design of the database: which tables exist, which columns each table has, what type each column is, and how the tables are linked. The schema is the plan, and the rows are the data that fills it. You will see the full schema of our example database on Day 2 and build it with SQL on Day 3.

🔑 Primary key

A column whose value is different for every row, so it can identify each row. Two rows can never have the same primary key, and it can never be empty. Here, customer_id is the primary key. Think of a roll number in a school: two students can have the same name, but never the same roll number. Sometimes two columns together act as the primary key. This is called a composite key.

🔗 Foreign key

A column in one table that points to the primary key of another table. This is how tables get linked. For example, an orders table has a customer_id column that points to the customers table. So each order knows who placed it, without copying the customer's name and city into every order.

Relationship

The link between two tables, made using keys. Because every order has a customer_id, we can combine the two tables and answer questions like "show all orders placed by customers from Jaipur." You will learn how to do this with joins on Day 7.

💡 If you remember only one thing from this section, remember primary key and foreign key. They are what connect tables. Understanding them now will make joins (usually the hardest topic for beginners) much easier later.

One more thing about primary keys. There are two types, and it helps to know the difference.

Natural key

  • A value that already exists in real life
  • Has meaning outside the database (an email address, a book's ISBN number)
  • Problem: it can change, have typos, or sometimes repeat
  • Example: using a customer's email as the primary key

Surrogate key

  • A number created only to identify the row
  • Has no meaning outside the database, just 1, 2, 3 and so on
  • Never needs to change, even if the customer's other details change
  • Example: customer_id, created automatically

Every table in our example database uses a surrogate key (customer_id, product_id, order_id and so on), created automatically by MySQL. You will see how on Day 3, using a feature called AUTO_INCREMENT.

6A first taste of normalization

Normalization means arranging data so the same information is not stored again and again. Repeated data is called redundant data, and it causes problems. The main idea is simple: store each fact once, in one place, and link tables using keys.

Here is an example. Suppose we store orders in one table and repeat the customer's details on every order:

✕ Bad design: repeated data
orders not normalized, avoid this

  • Aarav's name and city are repeated on every row. This wastes space.
  • If Aarav moves to another city, you have to change every one of his rows. Miss one, and your data now says two different things.
  • Someone might type "Jaipur" in one row and "jaipur " (with an extra space) in another. Now the same person looks like two different customers.

The fix is to split this into two tables, one for customers and one for orders, and link them with a key.

💡 That is normalization in one line: split data into focused tables, store each fact once, and link the tables with keys. There are formal rules for this called normal forms (1NF, 2NF, 3NF), which we cover properly on Day 17. For now, just remember that a good database does not repeat the same information. This is why our example database uses several linked tables instead of one big table.

7Putting it all together

Let's connect everything from today.

A database is organized data. We manage it with software called a DBMS. The relational kind, an RDBMS, stores data in tables made of rows and columns, and we talk to it using SQL. The design of these tables is the schema. Each row is identified by a primary key, and tables are linked through foreign keys, which creates relationships. We split data into several linked tables (normalization) so each fact is stored only once.

You will see every one of these words again in the coming days.

🎯 Interview corner

These questions come up often in data analyst and data scientist interviews. Try to answer each one out loud before you open the answer. Keep your answers short and add a small example. Interviewers like that.

Concept questions

Q1What is the difference between a database, a DBMS and an RDBMS?

A database is the organized data itself. A DBMS is the software used to store, read and manage that data. An RDBMS is a type of DBMS that stores data in tables linked by keys, and we use SQL to work with it. Example: MySQL is an RDBMS, and the online_store data inside it is a database.

Q2What is a primary key? Can it be NULL? Can a table have more than one?

A primary key is a column (or a group of columns) that uniquely identifies each row. It can never be NULL and it can never repeat. A table can have only one primary key, but that key can be made of more than one column. That is called a composite key.

Q3What is a foreign key, and why do we need it?

A foreign key is a column in one table that points to the primary key of another table. It links the two tables, and it also blocks bad data. For example, the database will not accept an order for customer_id = 99 if there is no customer 99. This protection is called referential integrity.

Q4What is the difference between a primary key and a unique key?

Both stop duplicate values. But a table can have only one primary key, and it can never be NULL. A table can have many unique keys, and a unique column is allowed to hold NULL (in MySQL, even more than one NULL). Example: customer_id is the primary key and email is a unique key. You will create a UNIQUE column yourself on Day 3.

Q5What is normalization, and why do we do it?

Normalization means splitting data into smaller linked tables so that each fact is stored only once. It saves space, avoids update mistakes (changing a value in one place but not another) and keeps the data consistent. Example: we store a customer's city once in customers instead of repeating it in every order.

Q6Does normalization have any downside?

Yes. Because the data is split into many tables, you need joins to bring it back together, and a lot of joins can make queries slower. That is why reporting databases (data warehouses) sometimes keep some repeated data on purpose. This is called denormalization. We look at this on Day 17.

Q7What are the ACID properties? Give an example.

ACID is a set of four rules that keep data safe. Atomicity: all steps of a change happen, or none do. Consistency: the data always follows the rules. Isolation: changes made at the same time don't disturb each other. Durability: saved changes survive a crash. Example: in a bank transfer, money must either leave one account and reach the other, or not move at all.

Q8SQL vs NoSQL: when would you choose each one?

Choose a relational (SQL) database when the data has a clear, fixed structure and accuracy matters, like orders, payments and stock levels. Choose NoSQL when the shape of the data changes often or doesn't fit into tables well, like social media posts, chat messages or sensor data. Most analyst work happens in SQL databases.

Q9Natural key or surrogate key: which would you use as a primary key?

A natural key is a real-world value like an email. A surrogate key is an ID the database creates, like 1, 2, 3. I would usually pick a surrogate key, because it never changes. If we used email as the key and a customer changed their email, we would have to update it in every table linked to that customer.

Quick recap

  • A database is organized data. A DBMS is the software that manages it. An RDBMS is the kind that uses linked tables and SQL.
  • Analysts need databases because real company data lives there, it is far too big for Excel, and SQL gets exactly the data you ask for.
  • Relational databases use linked tables and SQL. NoSQL databases use flexible formats. This series is about relational databases.
  • Core words: table, column, row, schema, primary key, foreign key, relationship.
  • ACID (Atomicity, Consistency, Isolation, Durability) are the four rules that keep data in an RDBMS safe.
  • A natural key is a real-world value like an email. A surrogate key is an ID the database creates. This series uses surrogate keys.
  • Normalization means splitting data into linked tables so each fact is stored only once.
