On Day 6, GROUP BY turned 15 orders into 3 rows. Very useful, but the details were gone. You could see "11 completed orders", but no longer which orders. Many questions need both at once: each product and its category's average, each month and the change from last month, each customer and their rank. Today's tool, the window function, does exactly that. It's the last big tool of the must-have core, and the end of this lesson is Checkpoint 1.

1Why window functions?

Picture a school marks sheet. Each student has their own row, with their name and mark. Next to it are two more columns: the class average, and the student's rank in the class. Every student still has their own row, but each row also shows something worked out from the whole class.

That's a window function. For each row, it looks through a "window" at a set of related rows, works something out from them, and writes the answer on that row. Nothing gets squashed.

On Day 8 you did this with a correlated subquery: each product compared with its own category's average. It worked, but the query was long and ran a subquery for every row. Here's the same idea as a window function:

SQL
SELECT product_name,
       category_id,
       price,
       ROUND(AVG(price) OVER (PARTITION BY category_id), 2) AS category_avg
FROM products
ORDER BY category_id, price DESC;

2OVER(): a window on the whole table

Empty brackets, OVER (), mean the window is every row. So SUM(x) OVER () puts the grand total on every row. That makes "share of the total" easy.

On Day 6 you typed the total, 15, by hand. On Day 8 you used a subquery. Here's the window function way:

SQL
SELECT status,
       COUNT(*) AS orders,
       SUM(COUNT(*)) OVER () AS all_orders,
       ROUND(COUNT(*) * 100 / SUM(COUNT(*)) OVER (), 1) AS pct
FROM orders
GROUP BY status
ORDER BY orders DESC;
Result
+-----------+--------+------------+------+
| status    | orders | all_orders | pct  |
+-----------+--------+------------+------+
| Completed |     11 |         15 | 73.3 |
| Pending   |      2 |         15 | 13.3 |
| Cancelled |      2 |         15 | 13.3 |
+-----------+--------+------------+------+

SUM(COUNT(*)) OVER () looks strange at first. Read it from the inside out. COUNT(*) is the count per status from the GROUP BY (11, 2, 2). Then SUM(...) OVER () adds up those three counts across all the result rows: 15. Window functions run after GROUP BY, so they can work on the grouped results.

Here's the same idea on single rows: each product's share of the shop's total stock value.

SQL
SELECT product_name,
       price * stock_quantity AS stock_value,
       ROUND(price * stock_quantity * 100
             / SUM(price * stock_quantity) OVER (), 1) AS pct_of_stock_value
FROM products
ORDER BY stock_value DESC
LIMIT 5;
Result
+------------------------------+-------------+--------------------+
| product_name                 | stock_value | pct_of_stock_value |
+------------------------------+-------------+--------------------+
| Noise-Cancelling Headphones  |   319960.00 |               16.2 |
| Mechanical Keyboard          |   199920.00 |               10.1 |
| Denim Jeans                  |   197890.00 |               10.0 |
| Stainless Steel Water Bottle |   174750.00 |                8.9 |
| Cotton T-Shirt               |   149700.00 |                7.6 |
+------------------------------+-------------+--------------------+

The headphones alone are about 16% of all the money sitting on the shelves.

3PARTITION BY: a window per group

PARTITION BY splits the rows into groups, like GROUP BY, but without squashing them. Each row's window is only its own group. You saw it in section 1 with categories. Here it is with customers: each completed order, next to that customer's total and the order's share of it.

SQL
WITH order_totals AS (
    SELECT o.customer_id, o.order_id, SUM(oi.quantity * oi.unit_price) AS order_total
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE o.status = 'Completed'
    GROUP BY o.customer_id, o.order_id
)
SELECT customer_id,
       order_id,
       order_total,
       SUM(order_total) OVER (PARTITION BY customer_id) AS customer_total,
       COUNT(*)         OVER (PARTITION BY customer_id) AS customer_orders
FROM order_totals
WHERE customer_id IN (1, 3)
ORDER BY customer_id, order_id;
Result
+-------------+----------+-------------+----------------+-----------------+
| customer_id | order_id | order_total | customer_total | customer_orders |
+-------------+----------+-------------+----------------+-----------------+
|           1 |        1 |     2197.00 |       15193.00 |               3 |
|           1 |        4 |     3798.00 |       15193.00 |               3 |
|           1 |       12 |     9198.00 |       15193.00 |               3 |
|           3 |        3 |     3296.00 |        6594.00 |               2 |
|           3 |       10 |     3298.00 |        6594.00 |               2 |
+-------------+----------+-------------+----------------+-----------------+

Aarav's three orders all show his total of ₹15,193. Rohan's two show his ₹6,594. Each partition is its own little window. With GROUP BY customer_id, you'd have lost the individual orders.

Where window functions can go. They're worked out near the end of the query, just before ORDER BY. So you can use them in SELECT and ORDER BY, but not in WHERE, GROUP BY or HAVING. Section 5 shows what to do when you want to filter on one.

4Ranking: ROW_NUMBER, RANK, DENSE_RANK

Ranking functions number the rows in the order you choose. They need an ORDER BY inside the OVER, so they know what "first" means. There are three, and the difference is all about ties.

Think of a race where two runners cross the line together in second place:

  • ROW_NUMBER() gives everyone a different number anyway: 1, 2, 3, 4. Someone has to be 3rd, even though it was a tie.
  • RANK() gives both tied runners 2nd, then skips: 1, 2, 2, 4. Like the Olympics, where there's no bronze if two people share silver.
  • DENSE_RANK() gives both 2nd, with no gap: 1, 2, 2, 3.

Our shop has a real tie: SQL Fundamentals and the Resistance Bands Set both cost ₹599. Here are the cheapest products with all three:

SQL
SELECT product_name,
       price,
       ROW_NUMBER() OVER (ORDER BY price) AS row_num,
       RANK()       OVER (ORDER BY price) AS rnk,
       DENSE_RANK() OVER (ORDER BY price) AS dense_rnk
FROM products
ORDER BY price
LIMIT 6;
Result
+------------------------------+--------+---------+-----+-----------+
| product_name                 | price  | row_num | rnk | dense_rnk |
+------------------------------+--------+---------+-----+-----------+
| Ceramic Coffee Mug           | 349.00 |       1 |   1 |         1 |
| Cotton T-Shirt               | 499.00 |       2 |   2 |         2 |
| SQL Fundamentals             | 599.00 |       3 |   3 |         3 |
| Resistance Bands Set         | 599.00 |       4 |   3 |         3 |
| Stainless Steel Water Bottle | 699.00 |       5 |   5 |         4 |
| Wireless Mouse               | 799.00 |       6 |   6 |         5 |
+------------------------------+--------+---------+-----+-----------+

Look at the two ₹599 products. ROW_NUMBER split them into 3 and 4, and which one gets 3 is up to MySQL, just like the LIMIT tie on Day 5. RANK gave both 3, then jumped to 5. DENSE_RANK gave both 3, then carried on with 4.

UseWhen you want
ROW_NUMBERexactly one row per position, like "the single latest order per customer". Add a tie-breaker column to make it stable.
RANKa fair ranking, where ties share a place and the next place is skipped, like a leaderboard.
DENSE_RANK"the Nth highest value", where ties count as one value.

5Top N per group

"The top 2 products in each category." "Each customer's latest order." These "top N per group" questions are among the most common in real work and in interviews. The natural first try is to filter on the rank:

SQL
SELECT product_name, category_id, price
FROM products
WHERE RANK() OVER (PARTITION BY category_id ORDER BY price DESC) <= 2;
MySQL says
ERROR 3593 (HY000): You cannot use the window function 'rank' in this context.'

As section 3 said, window functions are worked out after WHERE runs, so WHERE can't see them. The fix is the Day 8 trick: work out the rank in a CTE, then filter in the outer query.

SQL
WITH ranked AS (
    SELECT category_id,
           product_name,
           price,
           RANK() OVER (PARTITION BY category_id ORDER BY price DESC) AS rnk
    FROM products
)
SELECT category_id, product_name, price, rnk
FROM ranked
WHERE rnk <= 2
ORDER BY category_id, rnk;
Result
+-------------+------------------------------+---------+-----+
| category_id | product_name                 | price   | rnk |
+-------------+------------------------------+---------+-----+
|           1 | Noise-Cancelling Headphones  | 7999.00 |   1 |
|           1 | Mechanical Keyboard          | 2499.00 |   2 |
|           2 | Data Science Handbook        | 1199.00 |   1 |
|           2 | The Pragmatic Programmer     |  899.00 |   2 |
|           3 | Denim Jeans                  | 1799.00 |   1 |
|           3 | Hooded Sweatshirt            | 1499.00 |   2 |
|           4 | Non-Stick Frying Pan         | 1599.00 |   1 |
|           4 | Stainless Steel Water Bottle |  699.00 |   2 |
|           5 | Yoga Mat                     |  999.00 |   1 |
|           5 | Resistance Bands Set         |  599.00 |   2 |
+-------------+------------------------------+---------+-----+

Remember this shape: rank in a CTE, filter outside. You'll use it constantly.

Ties done right

Two questions from earlier days were left hanging because of ties. On Day 6, three months tied for "most orders", and LIMIT 1 would have hidden two of them. RANK keeps them all:

SQL
WITH monthly AS (
    SELECT DATE_FORMAT(order_date, '%Y-%m') AS order_month,
           COUNT(*) AS orders
    FROM orders
    GROUP BY order_month
)
SELECT order_month, orders
FROM (SELECT order_month, orders,
             RANK() OVER (ORDER BY orders DESC) AS rnk
      FROM monthly) AS ranked
WHERE rnk = 1
ORDER BY order_month;
Result
+-------------+--------+
| order_month | orders |
+-------------+--------+
| 2024-02     |      3 |
| 2024-03     |      3 |
| 2024-04     |      3 |
+-------------+--------+

And on Days 5 and 8 you found the second highest price. Here's the general version for the Nth highest, using DENSE_RANK so that tied prices count once:

SQL
WITH price_ranks AS (
    SELECT DISTINCT price,
           DENSE_RANK() OVER (ORDER BY price DESC) AS price_rank
    FROM products
)
SELECT price
FROM price_ranks
WHERE price_rank = 3;
Result
+---------+
| price   |
+---------+
| 1799.00 |
+---------+

Change the 3 to any N. This is the standard answer to the interview classic "find the Nth highest salary".

6NTILE: split into equal groups

NTILE(n) deals the rows out into n groups of (nearly) the same size, in order, like dealing a pack of cards into piles from best to worst. It's how analysts make "top half and bottom half" or "top 25%" groups.

SQL
WITH customer_spend AS (
    SELECT o.customer_id, SUM(oi.quantity * oi.unit_price) AS total_spent
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE o.status = 'Completed'
    GROUP BY o.customer_id
)
SELECT customer_id,
       total_spent,
       NTILE(4) OVER (ORDER BY total_spent DESC) AS spend_quartile
FROM customer_spend
ORDER BY total_spent DESC;
Result
+-------------+-------------+----------------+
| customer_id | total_spent | spend_quartile |
+-------------+-------------+----------------+
|           1 |    15193.00 |              1 |
|           2 |     7999.00 |              1 |
|           3 |     6594.00 |              2 |
|           6 |     2794.00 |              2 |
|           4 |     2696.00 |              3 |
|           5 |     2197.00 |              3 |
|           7 |     1498.00 |              4 |
|           9 |      998.00 |              4 |
+-------------+-------------+----------------+

Eight customers into 4 groups gives 2 per group. Group 1 is the top quarter of spenders. When the rows don't divide evenly, the first groups get one extra row each. On Day 13, NTILE is the engine behind RFM segmentation, where every customer gets a score from 1 to 5 on recency, frequency and spend.

7LAG and LEAD: look at the row before or after

LAG(column) fetches a value from the previous row, and LEAD(column) from the next row, in the order you give. It's like reading a bank statement and comparing each month's balance with the one above it.

Month-over-month change

SQL
WITH monthly AS (
    SELECT DATE_FORMAT(o.order_date, '%Y-%m') AS order_month,
           SUM(oi.quantity * oi.unit_price)   AS revenue
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE o.status = 'Completed'
    GROUP BY order_month
)
SELECT order_month,
       revenue,
       LAG(revenue) OVER (ORDER BY order_month)           AS prev_month,
       revenue - LAG(revenue) OVER (ORDER BY order_month) AS change_amt,
       ROUND((revenue - LAG(revenue) OVER (ORDER BY order_month)) * 100
             / LAG(revenue) OVER (ORDER BY order_month), 1) AS change_pct
FROM monthly
ORDER BY order_month;
Result
+-------------+----------+------------+------------+------------+
| order_month | revenue  | prev_month | change_amt | change_pct |
+-------------+----------+------------+------------+------------+
| 2024-01     | 10196.00 |       NULL |       NULL |       NULL |
| 2024-02     |  7094.00 |   10196.00 |   -3102.00 |      -30.4 |
| 2024-03     |  4991.00 |    7094.00 |   -2103.00 |      -29.6 |
| 2024-04     |  4796.00 |    4991.00 |    -195.00 |       -3.9 |
| 2024-05     | 10196.00 |    4796.00 |    5400.00 |      112.6 |
| 2024-06     |  2696.00 |   10196.00 |   -7500.00 |      -73.6 |
+-------------+----------+------------+------------+------------+

January has no previous month, so LAG gives NULL, and the change is NULL too. That's correct: there's nothing to compare with. February fell about 30%, and May more than doubled. This "change versus last period" column is in nearly every business report.

Gaps in the calendar. LAG looks at the previous row, not the previous month. If a month had no sales, it would be missing from the result, and LAG would quietly compare with two months back. Our data has a sale every month, but real data often doesn't. Day 12 shows how to fill in the missing months first.

Days between a customer's orders

On Day 7, the self join paired every order with every later order, so Aarav got three pairs, including a jump straight from order 1 to order 12. LAG with PARTITION BY pairs each order with just the one before it, from the same customer:

SQL
SELECT customer_id,
       order_id,
       order_date,
       LAG(order_date) OVER (PARTITION BY customer_id ORDER BY order_date) AS previous_order,
       DATEDIFF(order_date,
                LAG(order_date) OVER (PARTITION BY customer_id ORDER BY order_date)) AS days_since_previous
FROM orders
WHERE customer_id IN (1, 2, 3)
ORDER BY customer_id, order_date;
Result
+-------------+----------+------------+----------------+---------------------+
| customer_id | order_id | order_date | previous_order | days_since_previous |
+-------------+----------+------------+----------------+---------------------+
|           1 |        1 | 2024-01-10 | NULL           |                NULL |
|           1 |        4 | 2024-02-20 | 2024-01-10     |                  41 |
|           1 |       12 | 2024-05-07 | 2024-02-20     |                  77 |
|           2 |        2 | 2024-01-15 | NULL           |                NULL |
|           2 |        7 | 2024-03-12 | 2024-01-15     |                  57 |
|           3 |        3 | 2024-02-03 | NULL           |                NULL |
|           3 |       10 | 2024-04-18 | 2024-02-03     |                  75 |
+-------------+----------+------------+----------------+---------------------+

Aarav waited 41 days, then 77. A customer's first order has nothing before it, so it gets NULL. LAG(column, 2) would look two rows back, and LAG(column, 1, 0) gives 0 instead of NULL when there's no earlier row.

8Running totals, moving averages and frames

When you put ORDER BY inside the OVER of an aggregate like SUM, the window changes. Instead of the whole partition, each row's window becomes "everything from the start up to me". That's a running total, like the balance column on a bank statement.

SQL
WITH monthly AS (
    SELECT DATE_FORMAT(o.order_date, '%Y-%m') AS order_month,
           SUM(oi.quantity * oi.unit_price)   AS revenue
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE o.status = 'Completed'
    GROUP BY order_month
)
SELECT order_month,
       revenue,
       SUM(revenue) OVER (ORDER BY order_month) AS revenue_to_date,
       ROUND(AVG(revenue) OVER (ORDER BY order_month
                                ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS moving_avg_3m
FROM monthly
ORDER BY order_month;
Result
+-------------+----------+-----------------+---------------+
| order_month | revenue  | revenue_to_date | moving_avg_3m |
+-------------+----------+-----------------+---------------+
| 2024-01     | 10196.00 |        10196.00 |      10196.00 |
| 2024-02     |  7094.00 |        17290.00 |       8645.00 |
| 2024-03     |  4991.00 |        22281.00 |       7427.00 |
| 2024-04     |  4796.00 |        27077.00 |       5627.00 |
| 2024-05     | 10196.00 |        37273.00 |       6661.00 |
| 2024-06     |  2696.00 |        39969.00 |       5896.00 |
+-------------+----------+-----------------+---------------+
  • revenue_to_date keeps adding: by June the shop has made ₹39,969, the familiar total.
  • moving_avg_3m averages this month and the two before it. Moving averages smooth out jumpy numbers, so you can see the trend. In January and February there aren't two earlier months yet, so it averages what's there.

Frames: choosing exactly which rows

ROWS BETWEEN 2 PRECEDING AND CURRENT ROW is a frame: it says exactly which rows around the current one go into the calculation. The pieces you can use:

PieceMeans
UNBOUNDED PRECEDINGfrom the very first row of the partition
n PRECEDINGn rows before the current one
CURRENT ROWthe current row
n FOLLOWINGn rows after it
UNBOUNDED FOLLOWINGup to the very last row of the partition

Going deeper: the hidden default frame, and why it bites

When you write ORDER BY in OVER without a frame, MySQL uses a default: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. RANGE means rows with the same ORDER BY value are treated as one block. That's harmless when the value is unique, like our months. When it isn't, it gives surprising results. Watch a running total over order lines, sorted by order_id:

SQL
SELECT order_item_id,
       order_id,
       quantity * unit_price AS amount,
       SUM(quantity * unit_price) OVER (ORDER BY order_id) AS running_default,
       SUM(quantity * unit_price) OVER (ORDER BY order_id, order_item_id
                                        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_rows
FROM order_items
ORDER BY order_item_id
LIMIT 6;
Result
+---------------+----------+---------+-----------------+--------------+
| order_item_id | order_id | amount  | running_default | running_rows |
+---------------+----------+---------+-----------------+--------------+
|             1 |        1 | 1598.00 |         2197.00 |      1598.00 |
|             2 |        1 |  599.00 |         2197.00 |      2197.00 |
|             3 |        2 | 7999.00 |        10196.00 |     10196.00 |
|             4 |        3 | 1497.00 |        13492.00 |     11693.00 |
|             5 |        3 | 1799.00 |        13492.00 |     13492.00 |
|             6 |        4 | 2499.00 |        17290.00 |     15991.00 |
+---------------+----------+---------+-----------------+--------------+

Order 1 has two lines with the same order_id. With the default RANGE frame, both lines count as "the current row", so both show 2197 straight away. In the second column we added a tie-breaker (order_item_id) and a ROWS frame, so the total grows one line at a time: 1598, then 2197. Neither is wrong, but only one is what you meant. When the sort column can have ties, add a tie-breaker and write the frame out. (ROWS without a tie-breaker isn't enough: MySQL would still pick the order of the tied lines itself.)

The same default trips up LAST_VALUE. "The last row in the window" is the current row under the default frame, so it just returns itself:

SQL
SELECT product_name,
       price,
       FIRST_VALUE(product_name) OVER (ORDER BY price) AS cheapest,
       LAST_VALUE(product_name)  OVER (ORDER BY price) AS last_default,
       LAST_VALUE(product_name)  OVER (ORDER BY price
                                       ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS dearest
FROM products
WHERE category_id = 1;
Result
+-----------------------------+---------+----------------+-----------------------------+-----------------------------+
| product_name                | price   | cheapest       | last_default                | dearest                     |
+-----------------------------+---------+----------------+-----------------------------+-----------------------------+
| Wireless Mouse              |  799.00 | Wireless Mouse | Wireless Mouse              | Noise-Cancelling Headphones |
| USB-C Hub                   | 1299.00 | Wireless Mouse | USB-C Hub                   | Noise-Cancelling Headphones |
| Mechanical Keyboard         | 2499.00 | Wireless Mouse | Mechanical Keyboard         | Noise-Cancelling Headphones |
| Noise-Cancelling Headphones | 7999.00 | Wireless Mouse | Noise-Cancelling Headphones | Noise-Cancelling Headphones |
+-----------------------------+---------+----------------+-----------------------------+-----------------------------+

FIRST_VALUE works as expected. LAST_VALUE only gives the true last row once the frame reaches UNBOUNDED FOLLOWING. An easier trick: use FIRST_VALUE with the order reversed (ORDER BY price DESC).

Naming a window. When several columns use the same OVER (...), you can name it once with a WINDOW clause after FROM / WHERE / GROUP BY, for example WINDOW w AS (ORDER BY order_month), then write LAG(revenue) OVER w. Shorter, and you can't accidentally make two windows slightly different.

9Views: save a query as a virtual table

By now you've written the same four-table join, filtered to completed orders, many times. A view saves a query under a name, and then you can use it as if it were a table. Think of a saved filter in your email app: "Unread from my team" isn't a separate folder of copied emails, it's a saved way of looking at your inbox. A view is a saved way of looking at your tables.

Create the view (run this once)
CREATE OR REPLACE VIEW completed_sales AS
SELECT o.order_id,
       o.order_date,
       c.customer_id,
       c.first_name,
       c.last_name,
       c.city,
       c.country,
       p.product_id,
       p.product_name,
       cat.category_name,
       oi.quantity,
       oi.unit_price,
       oi.quantity * oi.unit_price AS line_total
FROM orders o
JOIN customers   c   ON c.customer_id   = o.customer_id
JOIN order_items oi  ON oi.order_id     = o.order_id
JOIN products    p   ON p.product_id    = oi.product_id
JOIN categories  cat ON cat.category_id = p.category_id
WHERE o.status = 'Completed';

Now the long join is one word:

SQL
SELECT category_name,
       SUM(line_total) AS revenue
FROM completed_sales
GROUP BY category_name
ORDER BY revenue DESC;
Result
+----------------+----------+
| category_name  | revenue  |
+----------------+----------+
| Electronics    | 25491.00 |
| Books          |  4494.00 |
| Clothing       |  4294.00 |
| Home & Kitchen |  3493.00 |
| Sports         |  2197.00 |

Things to know about views:

  • A view stores the query, not the data. Every time you use it, MySQL runs the query again on the current tables. So it's always up to date, and it takes no extra space.
  • It saves you from repeating mistakes. The definition of "completed sales" lives in one place. If it ever changes, you fix it once, and every report that uses the view follows.
  • It's a good way to share. Companies often give analysts views instead of raw tables: cleaned up, with only the columns they need, and nothing private.
  • CREATE OR REPLACE lets you run the same statement again to change the view. DROP VIEW completed_sales; removes it. Your tables aren't affected either way.

The view stays in your database, and the capstone below uses it. It doesn't change any of your data, so all the numbers from earlier days still match.

10Habits of good queries

You now know enough SQL to answer most business questions. These habits are what make your answers trustworthy. Most of them came up as traps somewhere in Days 5 to 9:

  • Agree the definition first. What counts as revenue, an active customer, a month? Write it down next to the number (Day 6).
  • Know what one row means, before and after every join. It prevents inflated counts and sums (Day 7).
  • Think about NULLs every time: in !=, in NOT IN, in AVG, in COUNT(*) vs COUNT(column), in CASE (Days 5 to 8).
  • Check for ties before using LIMIT or ROW_NUMBER to pick a "top" answer (Days 5, 6, 9).
  • Build big queries in small steps with CTEs, and run each step on its own while you build (Day 8).
  • Sanity-check new numbers against ones you trust, like the ₹39,969 total. If a new report adds up to something else, find out why before you share it (Day 7).
  • Make it readable: keywords in capitals, one column per line, short table aliases on every column, and a -- comment on anything clever.

1. The monthly report

"For each month: revenue, the change from the month before, and the running total for the year."

3. How much do the top customers bring in?

5. How long between orders?

"On average, how many days pass between one order and the next from the same customer? Count every order placed, whatever happened to it."

Show the answer
SQL
WITH gaps AS (
    SELECT customer_id,
           DATEDIFF(order_date,
                    LAG(order_date) OVER (PARTITION BY customer_id ORDER BY order_date)) AS days_gap
    FROM orders
)
SELECT COUNT(days_gap)          AS repeat_orders,
       ROUND(AVG(days_gap), 1)  AS avg_days_between,
       MIN(days_gap)            AS shortest,
       MAX(days_gap)            AS longest
FROM gaps;
Result
+---------------+------------------+----------+---------+
| repeat_orders | avg_days_between | shortest | longest |
+---------------+------------------+----------+---------+
|             6 |             74.3 |       41 |     108 |
+---------------+------------------+----------+---------+

Six orders were someone's second (or third) order. On average, customers came back after about 2½ months. AVG and COUNT(days_gap) skip the NULLs from each customer's first order (Day 6), which is exactly right here: a first order has no gap. We used orders directly, not the view, because the question is about ordering behaviour, cancelled orders included.

7. The win-back list

"Our data runs to 30 June 2024. Which customers haven't placed any order in the last 60 days, including anyone who has never ordered? Marketing wants to send them an offer."

Show the answer
SQL
SELECT c.first_name,
       c.last_name,
       MAX(o.order_date) AS last_order,
       DATEDIFF('2024-06-30', MAX(o.order_date)) AS days_since
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.first_name, c.last_name
HAVING MAX(o.order_date) IS NULL
    OR DATEDIFF('2024-06-30', MAX(o.order_date)) > 60
ORDER BY days_since DESC;

8. Stock alert

"Give me a list of products that need attention: out of stock, never sold, or low on stock (under 60). Most urgent first."

Show the answer
SQL
WITH sold AS (
    SELECT product_id, SUM(quantity) AS units_sold
    FROM completed_sales
    GROUP BY product_id
),
flagged AS (
    SELECT p.product_name,
           p.stock_quantity,
           COALESCE(s.units_sold, 0) AS units_sold,
           CASE
               WHEN p.stock_quantity = 0   THEN 'Out of stock'
               WHEN s.units_sold IS NULL   THEN 'Never sold'
               WHEN p.stock_quantity < 60  THEN 'Low stock'
           END AS alert
    FROM products p
    LEFT JOIN sold s ON s.product_id = p.product_id
)
SELECT product_name, stock_quantity, units_sold, alert
FROM flagged
WHERE alert IS NOT NULL
ORDER BY CASE alert WHEN 'Out of stock' THEN 1
                    WHEN 'Low stock'    THEN 2
                    WHEN 'Never sold'   THEN 3 END;

| product_name                | stock_quantity | units_sold | alert        |

| Hooded Sweatshirt           |             75 |          0 | Never sold   |
| Non-Stick Frying Pan        |             50 |          0 | Never sold   |

Summarise first, then left join (Day 8), so every product is checked. CASE with no ELSE gives NULL for products that are fine, and the outer WHERE drops them. 🎯 Interview corner

Window functions are where interviewers separate beginners from people who've used SQL for real. "Top N per group" and "running total" come up again and again.

Concept questions

Q1What is a window function? How is it different from GROUP BY?

A function that works out a value for each row from a set of related rows (its window), defined with OVER (...). GROUP BY squashes each group into one row. A window function keeps every row and adds the result as a new column. Example: AVG(price) OVER (PARTITION BY category_id) shows each product with its category's average.

Q2What's the difference between ROW_NUMBER, RANK and DENSE_RANK?

They differ only on ties. For values 100, 90, 90, 80: ROW_NUMBER gives 1, 2, 3, 4 (ties broken in no fixed order), RANK gives 1, 2, 2, 4 (ties share a place, then a gap), DENSE_RANK gives 1, 2, 2, 3 (no gap). Use ROW_NUMBER for exactly one row per position, RANK for a fair leaderboard, and DENSE_RANK for "Nth highest value".

Q3What does PARTITION BY do?

It splits the rows into groups, and the window function works separately inside each group. Rankings restart at 1, and sums and averages cover only that group. Unlike GROUP BY, no rows are removed.

Q4Why can't you use a window function in WHERE? How do you filter on one?

Because window functions are worked out after WHERE, GROUP BY and HAVING, so the value doesn't exist yet when WHERE runs. MySQL gives error 3593. Work out the window function in a CTE or derived table, then filter in the outer query: WITH r AS (SELECT ..., RANK() OVER (...) AS rnk FROM t) SELECT * FROM r WHERE rnk <= 3.

Q5What do LAG and LEAD do?

LAG(col) returns the value from the previous row and LEAD(col) from the next row, in the order given inside OVER, optionally within each partition. They're used for period-over-period changes and gaps between events. The first row's LAG is NULL, unless you give a default, as in LAG(col, 1, 0).

Q6How do you calculate a running total?

SUM(amount) OVER (ORDER BY date_col), with PARTITION BY to restart it per group. To be safe, state the frame: ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. Without it, the default RANGE frame lumps together rows with the same sort value.

Q7What is a window frame? What's the default?

The exact set of rows, relative to the current row, that an aggregate window function uses, such as ROWS BETWEEN 2 PRECEDING AND CURRENT ROW for a 3-row moving average. With ORDER BY in OVER and no frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which includes all rows tied with the current one. Without ORDER BY, the frame is the whole partition.

Q8Why does LAST_VALUE often return the current row?

Because of the default frame, which ends at the current row (and its ties), so "the last row in the window" is the current row. Fix it with ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING, or use FIRST_VALUE with the sort order reversed.

Q9What is a view? Does it store data?

A view is a saved query that you can use like a table. It does not store data: each time you use it, the query runs on the current tables. Views keep a definition in one place, hide complicated joins, and can limit which columns or rows people see. (Some databases also have materialised views that do store results, but MySQL doesn't.)

Quick recap

  • A window function (... OVER (...)) works out a value from a set of rows but keeps every row. GROUP BY squashes, windows don't.
  • OVER () is the whole result, which is great for shares of a total. PARTITION BY gives each group its own window.
  • ROW_NUMBER, RANK and DENSE_RANK differ only on ties. NTILE(n) splits rows into n equal groups.
  • Top N per group: rank in a CTE, then filter outside. Windows can't go in WHERE.
  • LAG / LEAD look at the previous or next row, for period-over-period changes and gaps between events.
  • ORDER BY inside OVER makes running totals. Frames (ROWS BETWEEN ...) give moving averages. Spell out the frame when the sort column has ties.
  • A view saves a query under a name, with no data stored. Good habits: agree definitions, know what a row means, think about NULLs and ties, build in steps, sanity-check.
  • Checkpoint 1: you can now answer real business questions on clean data. Next comes real, messy data.
