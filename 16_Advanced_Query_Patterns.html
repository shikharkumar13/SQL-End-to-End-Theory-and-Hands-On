Checkpoint 2 marked the end of the must-haves. Welcome to the good-to-haves. Nothing today is a brand-new kind of tool: everything is built from CASE, window functions and CTEs, which you already know. What's new are five recipes that combine them in clever ways. They're the patterns behind the harder interview questions ("find users who logged in three days in a row") and behind reports that managers love ("which 20% of customers bring in most of our money?").

Before you start. Run USE online_store_full;. Today uses the Day 11 clean layer, Day 13's customer_summary view and the employees table. As always, try to predict each result before you look at it.

1Pivoting in full

Day 8 showed the core trick: one SUM(CASE WHEN ...) per column turns rows into columns. Day 6 added a total row with WITH ROLLUP. A real report usually wants both, plus a total column. Here's revenue by category and quarter for 2024, the way a manager would ask for it:

SQL
SELECT IF(GROUPING(category_name), 'All categories', category_name) AS category,
       ROUND(SUM(CASE WHEN QUARTER(order_date) = 1 THEN line_total ELSE 0 END)) AS q1,
       ROUND(SUM(CASE WHEN QUARTER(order_date) = 2 THEN line_total ELSE 0 END)) AS q2,
       ROUND(SUM(CASE WHEN QUARTER(order_date) = 3 THEN line_total ELSE 0 END)) AS q3,
       ROUND(SUM(CASE WHEN QUARTER(order_date) = 4 THEN line_total ELSE 0 END)) AS q4,
       ROUND(SUM(line_total))                                                   AS total_2024
FROM clean_sales
WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'
GROUP BY category_name WITH ROLLUP;
Result
+----------------+---------+---------+---------+---------+------------+
| category       | q1      | q2      | q3      | q4      | total_2024 |
+----------------+---------+---------+---------+---------+------------+
| Books          |  146853 |  136920 |  188626 |  176392 |     648791 |
| Clothing       |  408242 |  351942 |  392739 |  849245 |    2002168 |
| Electronics    |  449116 |  551705 |  647441 |  960872 |    2609135 |
| Home & Kitchen |  230219 |  251585 |  320986 |  282387 |    1085177 |
| Sports         |  316005 |  419728 |  419711 |  453229 |    1608672 |
| Uncategorised  |       0 |       0 |       0 |   28491 |      28491 |
| All categories | 1550434 | 1711879 | 1969503 | 2750617 |    7982433 |
+----------------+---------+---------+---------+---------+------------+

Three tools in one query. The CASE columns pivot the quarters. The plain SUM(line_total) is the row total. And WITH ROLLUP adds the column totals at the bottom, with GROUPING() giving that row a proper label instead of NULL (Day 6). Check the bottom row against numbers you trust: ₹27,50,617 for Q4 and ₹79,82,433 for the year, exactly Day 12's figures. Reading across, Clothing more than doubled in the festive fourth quarter, and the Smart Fitness Band only appears in Q4.

Subtotals at two levels

With two grouping columns, ROLLUP adds a subtotal for each value of the first column, and then a grand total:

SQL
SELECT IF(GROUPING(yr), 'Both years', yr)                AS yr,
       IF(GROUPING(channel), 'All channels', channel)    AS channel,
       COUNT(DISTINCT order_id)                          AS orders,
       ROUND(SUM(line_total))                            AS revenue
FROM (SELECT YEAR(order_date) AS yr, channel, order_id, line_total
      FROM clean_sales) AS s
GROUP BY yr, channel WITH ROLLUP;
Result
+------------+--------------+--------+----------+
| yr         | channel      | orders | revenue  |
+------------+--------------+--------+----------+
| 2023       | app          |    970 |  2216073 |
| 2023       | web          |   1373 |  2974355 |
| 2023       | All channels |   2343 |  5190428 |
| 2024       | app          |   1664 |  4097976 |
| 2024       | web          |   1655 |  3884457 |
| 2024       | All channels |   3319 |  7982433 |
| Both years | All channels |   5662 | 13172860 |
+------------+--------------+--------+----------+

The year is worked out in a subquery first, so ROLLUP groups by a plain column. (Grouping directly by YEAR(order_date) and then labelling it with GROUPING() runs into error 1055, the GROUP BY rule from Days 6 and 14.) The subtotals tell a story: in 2023, the website took more orders than the app, and in 2024 the app overtook it. That's the kind of shift a two-level summary makes easy to spot.

Unpivoting: columns back into rows

Sometimes you get data the other way round: one column per year, and you need one row per year, because charts and tools like pandas (Day 14) prefer this long shape. That's an unpivot, and in MySQL it's a UNION ALL, one SELECT per column:

SQL
WITH wide AS (
    SELECT category_name,
           SUM(CASE WHEN order_date <  '2024-01-01' THEN line_total ELSE 0 END) AS rev_2023,
           SUM(CASE WHEN order_date >= '2024-01-01' THEN line_total ELSE 0 END) AS rev_2024
    FROM clean_sales
    WHERE category_name IN ('Books', 'Sports')
    GROUP BY category_name
)
SELECT category_name, 2023 AS yr, ROUND(rev_2023) AS revenue FROM wide
UNION ALL
SELECT category_name, 2024,       ROUND(rev_2024)            FROM wide
ORDER BY category_name, yr;
Result
+---------------+------+---------+
| category_name | yr   | revenue |
+---------------+------+---------+
| Books         | 2023 |  595738 |
| Books         | 2024 |  648791 |
| Sports        | 2023 |  624728 |
| Sports        | 2024 | 1608672 |
+---------------+------+---------+

The wide CTE plays the part of a wide table someone sent you. Each SELECT in the union takes one of its columns, and labels it with the year it came from. Wide to long, long to wide: once you can do both, the shape of the data never blocks you.

A truly dynamic pivot

Every pivot so far has one weakness: you type each column yourself. Day 14 solved that in Python. Can SQL do it alone? In MySQL, yes, in two stages: first, a query writes the pivot query as text, and then MySQL runs that text. This is called dynamic SQL:

SQL
SET SESSION group_concat_max_len = 10000;

-- Stage 1: build one SUM(CASE ...) column for every category that exists
SELECT GROUP_CONCAT(DISTINCT
           CONCAT('ROUND(SUM(CASE WHEN category_name = ''', category_name,
                  ''' THEN line_total ELSE 0 END)) AS `', category_name, '`')
           ORDER BY category_name SEPARATOR ',\n       ')
INTO @cols
FROM clean_sales;

SET @sql = CONCAT('SELECT channel,\n       ', @cols,
                  '\nFROM clean_sales\nGROUP BY channel\nORDER BY channel');

-- Stage 2: turn the text into a statement, and run it
PREPARE pivot_stmt FROM @sql;
EXECUTE pivot_stmt;
DEALLOCATE PREPARE pivot_stmt;
Result
+---------+--------+----------+-------------+----------------+---------+---------------+
| channel | Books  | Clothing | Electronics | Home & Kitchen | Sports  | Uncategorised |
+---------+--------+----------+-------------+----------------+---------+---------------+
| app     | 557097 |  1684217 |     2067949 |         913433 | 1074259 |         17094 |
| web     | 687433 |  1728291 |     2225517 |        1047033 | 1159141 |         11396 |
+---------+--------+----------+-------------+----------------+---------+---------------+

Stage 1 uses GROUP_CONCAT (Day 6) to glue one column definition per category into a single piece of text, and stores it in a variable, @cols. ('' inside a text value means one quote mark.) Here's the query it wrote, printed with SELECT @sql:

What @sql contains
SELECT channel,
       ROUND(SUM(CASE WHEN category_name = 'Books' THEN line_total ELSE 0 END)) AS `Books`,
       ROUND(SUM(CASE WHEN category_name = 'Clothing' THEN line_total ELSE 0 END)) AS `Clothing`,
       ROUND(SUM(CASE WHEN category_name = 'Electronics' THEN line_total ELSE 0 END)) AS `Electronics`,
       ROUND(SUM(CASE WHEN category_name = 'Home & Kitchen' THEN line_total ELSE 0 END)) AS `Home & Kitchen`,
       ROUND(SUM(CASE WHEN category_name = 'Sports' THEN line_total ELSE 0 END)) AS `Sports`,
       ROUND(SUM(CASE WHEN category_name = 'Uncategorised' THEN line_total ELSE 0 END)) AS `Uncategorised`
FROM clean_sales
GROUP BY channel
ORDER BY channel

Stage 2: PREPARE turns the text into a statement, EXECUTE runs it, and DEALLOCATE tidies up. Add a category tomorrow, and the pivot grows a column without anyone editing the SQL.

Three warnings before you use this. First, GROUP_CONCAT stops at 1,024 characters by default and cuts off the rest. All you get is a warning (1260, "Row ... was cut by GROUP_CONCAT()") that's easy to miss, and the query it builds then breaks or loses columns. That's why the first line raises the limit. Second, never build dynamic SQL from values a user typed: that's SQL injection again (Day 14). Here, the values come from our own table. Third, dynamic SQL is hard to read, test and debug. In real work, most teams pivot in Python or the BI tool instead, and keep SQL for the summarising. It's worth knowing for interviews, and for the occasional job where SQL is all you have.

2Medians and percentiles

Ten people are in a café, and each earns about ₹50,000 a month. A billionaire walks in. The average income in the room is now in the crores, but nobody else got any richer. The median, the income of the person in the middle when everyone is lined up from lowest to highest, barely moves. When a few very large values exist, the median tells you what's typical, and the average doesn't.

Order values are exactly like that: most orders are modest, and a few are very large. MySQL has no MEDIAN() function, so we build one. Line the orders up with ROW_NUMBER, count them, and take the middle:

SQL
WITH order_totals AS (
    SELECT order_id, SUM(line_total) AS order_total
    FROM clean_sales
    GROUP BY order_id
),
lined_up AS (
    SELECT order_total,
           ROW_NUMBER() OVER (ORDER BY order_total) AS position,
           COUNT(*)     OVER ()                     AS how_many,
           AVG(order_total) OVER ()                 AS mean_value
    FROM order_totals
)
SELECT MAX(how_many)           AS orders,
       ROUND(MAX(mean_value))  AS mean_order_value,
       ROUND(AVG(order_total)) AS median_order_value
FROM lined_up
WHERE position IN (FLOOR((how_many + 1) / 2), CEIL((how_many + 1) / 2));
Result
+--------+------------------+--------------------+
| orders | mean_order_value | median_order_value |
+--------+------------------+--------------------+
|   5662 |             2327 |               1796 |
+--------+------------------+--------------------+

The WHERE keeps the middle row, or the middle two rows. With 5 orders, (5 + 1) / 2 is 3, and FLOOR and CEIL both give 3: one middle row. With 5,662 orders, it's 2,831.5, so FLOOR gives 2,831 and CEIL gives 2,832, and AVG averages the two middle values. That's the standard definition of a median.

The result: the average order is ₹2,327, but the median is ₹1,796. Half of all orders are below ₹1,796. The average is pulled up by a smaller number of big orders. If the owner asks "what does a typical customer spend per order?", the honest answer is about ₹1,800, not ₹2,300.

Percentiles: the whole picture

The median is the 50th percentile: 50% of values are at or below it. Other percentiles describe the rest of the spread. The 90th percentile is the value that 90% of orders don't exceed. The window function CUME_DIST() gives each row the share of rows at or below its value, so the first value whose share reaches 0.9 is the 90th percentile:

SQL
WITH order_totals AS (
    SELECT order_id, SUM(line_total) AS order_total
    FROM clean_sales
    GROUP BY order_id
),
shares AS (
    SELECT order_total,
           CUME_DIST() OVER (ORDER BY order_total) AS share_at_or_below
    FROM order_totals
)
SELECT MIN(CASE WHEN share_at_or_below >= 0.25 THEN order_total END) AS p25,
       MIN(CASE WHEN share_at_or_below >= 0.50 THEN order_total END) AS p50_median,
       MIN(CASE WHEN share_at_or_below >= 0.75 THEN order_total END) AS p75,
       MIN(CASE WHEN share_at_or_below >= 0.90 THEN order_total END) AS p90,
       MIN(CASE WHEN share_at_or_below >= 0.99 THEN order_total END) AS p99
FROM shares;
Result
+--------+------------+---------+---------+---------+
| p25    | p50_median | p75     | p90     | p99     |
+--------+------------+---------+---------+---------+
| 998.00 |    1796.40 | 3014.95 | 4765.50 | 9898.00 |
+--------+------------+---------+---------+---------+

Read it as a sentence: a quarter of orders are under about ₹1,000, half under ₹1,800, three-quarters under ₹3,000, and only 1 order in 100 is above ₹9,900. That's far more useful than any single average. For example, if free delivery started at ₹3,000, about three-quarters of orders would still pay for delivery. (PERCENT_RANK() is a close cousin: it gives the share of rows below each value, from 0 to 1.)

In other databases. PostgreSQL, SQL Server and Oracle have percentile functions built in: PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY order_total) for the median. We checked these exact orders in PostgreSQL. PERCENTILE_DISC ("pick a real value") gives exactly the numbers above, and PERCENTILE_CONT ("blend between values") gives the same median and slightly different others, such as 3,012.04 instead of 3,014.95 for the 75th percentile. Either is fine. Just say which one you used.

The median for each group

Add PARTITION BY, and every group gets its own lineup. Do app shoppers spend more than website shoppers?

SQL
WITH order_totals AS (
    SELECT order_id, channel, SUM(line_total) AS order_total
    FROM clean_sales
    GROUP BY order_id, channel
),
lined_up AS (
    SELECT channel,
           order_total,
           ROW_NUMBER()     OVER (PARTITION BY channel ORDER BY order_total) AS position,
           COUNT(*)         OVER (PARTITION BY channel)                      AS how_many,
           AVG(order_total) OVER (PARTITION BY channel)                      AS mean_value
    FROM order_totals
)
SELECT channel,
       MAX(how_many)           AS orders,
       ROUND(MAX(mean_value))  AS mean_order_value,
       ROUND(AVG(order_total)) AS median_order_value
FROM lined_up
WHERE position IN (FLOOR((how_many + 1) / 2), CEIL((how_many + 1) / 2))
GROUP BY channel;
Result
+---------+--------+------------------+--------------------+
| channel | orders | mean_order_value | median_order_value |
+---------+--------+------------------+--------------------+
| app     |   2634 |             2397 |               1799 |
| web     |   3028 |             2265 |               1698 |
+---------+--------+------------------+--------------------+

Same recipe, with each channel lined up separately. App orders are a little bigger by both measures. And in both channels the mean is well above the median, so the big-order effect isn't caused by one channel. Whenever you report an "average" of money, it's worth checking the median beside it.

3The 80/20 rule

The Pareto principle, or 80/20 rule, says that in many situations, roughly 80% of the results come from 20% of the causes: most of the revenue from a minority of customers, most of the complaints from a few products. Day 9 saw a hint of it in the tiny shop. Let's test it properly. Split the customers into five equal groups by how much they've spent, with Day 9's NTILE:

SQL
SELECT spend_group,
       COUNT(*)                AS customers,
       ROUND(SUM(revenue))     AS revenue,
       ROUND(SUM(revenue) * 100 / SUM(SUM(revenue)) OVER (), 1) AS pct_of_revenue
FROM (
    SELECT revenue,
           NTILE(5) OVER (ORDER BY revenue DESC, customer_id) AS spend_group
    FROM customer_summary
) AS grouped
GROUP BY spend_group
ORDER BY spend_group;
Result
+-------------+-----------+---------+----------------+
| spend_group | customers | revenue | pct_of_revenue |
+-------------+-----------+---------+----------------+
|           1 |       423 | 8244925 |           62.6 |
|           2 |       423 | 2641076 |           20.0 |
|           3 |       423 | 1318236 |           10.0 |
|           4 |       423 |  683798 |            5.2 |
|           5 |       423 |  284825 |            2.2 |
+-------------+-----------+---------+----------------+

The top 20% of customers (group 1) bring in 62.6% of all revenue, more than the other 80% put together. It's not exactly 80/20 (real data rarely is), but the shape is clear. Group 5, the bottom fifth, brings in just 2.2%. (NTILE works well here, because spending amounts are spread out. Day 13 showed where it doesn't.)

The other way to ask it: how many customers does it take to reach 80% of revenue? That needs a running total of revenue, as a share of the whole, from the biggest customer down:

SQL
WITH running AS (
    SELECT ROW_NUMBER() OVER (ORDER BY revenue DESC, customer_id) AS position,
           SUM(revenue) OVER (ORDER BY revenue DESC, customer_id
                              ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
             / SUM(revenue) OVER ()                               AS share_so_far,
           COUNT(*) OVER ()                                       AS all_customers
    FROM customer_summary
)
SELECT MIN(position)                              AS customers_for_80_pct,
       MAX(all_customers)                         AS all_customers,
       ROUND(MIN(position) * 100 / MAX(all_customers), 1) AS pct_of_customers
FROM running
WHERE share_so_far >= 0.80;
Result
+----------------------+---------------+------------------+
| customers_for_80_pct | all_customers | pct_of_customers |
+----------------------+---------------+------------------+
|                  769 |          2115 |             36.4 |
+----------------------+---------------+------------------+

The first customer at whom the running share reaches 80% is number 769: 36% of customers bring in 80% of the revenue. The explicit ROWS frame and the customer_id tie-breaker keep the running total exact, even when two customers spent the same amount (Day 9's frame lesson).

ABC classification

Shops use the same idea to sort their products into three classes. A: the products that together make the first 80% of revenue, the ones to never run out of. B: the next 15%. C: the last 5%, the ones to review. The trick is to look at the running share before each product, so the product that crosses the 80% line still counts as an A:

SQL
WITH product_revenue AS (
    SELECT product_id, product_name, SUM(line_total) AS revenue
    FROM clean_sales
    GROUP BY product_id, product_name
),
running AS (
    SELECT product_id,
           product_name,
           revenue,
           SUM(revenue) OVER (ORDER BY revenue DESC, product_id
                              ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING)
             / SUM(revenue) OVER () AS share_before
    FROM product_revenue
),
classified AS (
    SELECT product_name,
           revenue,
           CASE
               WHEN COALESCE(share_before, 0) < 0.80 THEN 'A'
               WHEN share_before < 0.95             THEN 'B'
               ELSE 'C'
           END AS abc_class
    FROM running
)
SELECT abc_class,
       COUNT(*)               AS products,
       ROUND(SUM(revenue))    AS revenue,
       ROUND(SUM(revenue) * 100 / SUM(SUM(revenue)) OVER (), 1) AS pct_of_revenue
FROM classified
GROUP BY abc_class
ORDER BY abc_class;
Result
+-----------+----------+----------+----------------+
| abc_class | products | revenue  | pct_of_revenue |
+-----------+----------+----------+----------------+
| A         |       34 | 10578550 |           80.3 |
| B         |       16 |  1941409 |           14.7 |
| C         |       11 |   652901 |            5.0 |
+-----------+----------+----------+----------------+

The new piece is the frame ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING: "all the rows before this one, but not this one". For the top product there are no rows before it, so the sum is NULL, and COALESCE turns that into 0 (Day 8). Products are less concentrated than customers: it takes 34 of the 61 products to make 80% of revenue. The 11 C products are worth a look, and Try this does that.

4Gaps and islands: finding streaks

Picture a string of fairy lights where some bulbs have gone out. The runs of lit bulbs are islands, and the dark stretches between them are gaps. In data: the months in a row when a customer ordered, the days in a row a user logged in, or the missing numbers in a sequence of invoices. "Find users who logged in three days in a row" is one of the most famous SQL interview questions, and it has a beautiful trick.

Take Kavya (customer 1, from Day 11) and the months in which she ordered. Number the months in order, then subtract that number of months from each date:

SQL
WITH months AS (
    SELECT DISTINCT CAST(DATE_FORMAT(order_date, '%Y-%m-01') AS DATE) AS month_start
    FROM clean_sales
    WHERE customer_id = 1
),
numbered AS (
    SELECT month_start,
           ROW_NUMBER() OVER (ORDER BY month_start) AS rn
    FROM months
)
SELECT month_start,
       rn,
       month_start - INTERVAL rn MONTH AS island_key
FROM numbered
ORDER BY month_start;
Result
+-------------+----+------------+
| month_start | rn | island_key |
+-------------+----+------------+
| 2023-11-01  |  1 | 2023-10-01 |
| 2024-04-01  |  2 | 2024-02-01 |
| 2024-05-01  |  3 | 2024-02-01 |
| 2024-08-01  |  4 | 2024-04-01 |
| 2024-10-01  |  5 | 2024-05-01 |
+-------------+----+------------+

Look at April and May 2024. They're consecutive months, and their row numbers are also consecutive (2 and 3), so subtracting gives the same answer for both: 2024-02-01. When the dates go up by one month and the row numbers go up by one, the difference stays the same. As soon as there's a gap (May to August), the dates jump by more than the row numbers, and the difference changes. So every island gets its own key, and GROUP BY on that key gives one row per streak. The key itself means nothing. It's just a label that's shared by the members of one island.

Now use it on every customer, and find the longest streaks of ordering in consecutive months:

SQL
WITH months AS (
    SELECT DISTINCT customer_id,
           CAST(DATE_FORMAT(order_date, '%Y-%m-01') AS DATE) AS month_start
    FROM clean_sales
),
islands AS (
    SELECT customer_id,
           month_start,
           month_start - INTERVAL ROW_NUMBER() OVER (PARTITION BY customer_id
                                                     ORDER BY month_start) MONTH AS island_key
    FROM months
),
streaks AS (
    SELECT customer_id,
           MIN(month_start) AS streak_start,
           MAX(month_start) AS streak_end,
           COUNT(*)         AS months_in_a_row
    FROM islands
    GROUP BY customer_id, island_key
)
SELECT s.customer_id,
       c.first_name,
       c.last_name,
       DATE_FORMAT(s.streak_start, '%b %Y') AS from_month,
       DATE_FORMAT(s.streak_end, '%b %Y')   AS to_month,
       s.months_in_a_row
FROM streaks s
JOIN clean_customers c ON c.customer_id = s.customer_id
ORDER BY s.months_in_a_row DESC, s.streak_start
LIMIT 5;
Result
+-------------+------------+-----------+------------+----------+-----------------+
| customer_id | first_name | last_name | from_month | to_month | months_in_a_row |
+-------------+------------+-----------+------------+----------+-----------------+
|        1750 | Amit       | Singh     | Jan 2023   | Jan 2024 |              13 |
|        1800 | Pranav     | Chopra    | Dec 2023   | Dec 2024 |              13 |
|        2463 | Tarun      | Kulkarni  | Mar 2023   | Dec 2023 |              10 |
|        2493 | Sneha      | Desai     | Mar 2023   | Dec 2023 |              10 |
|        1191 | Akash      | Reddy     | Jul 2023   | Apr 2024 |              10 |
+-------------+------------+-----------+------------+----------+-----------------+

Three steps: one row per customer per month (DISTINCT, because several orders in one month should count once), the island key with PARTITION BY customer_id so each customer is numbered separately, then GROUP BY customer and key. Two customers ordered every single month for over a year. Pranav's streak is still running at the end of the data. He's the same Pranav who topped Day 15's "spent more in 2024" list.

The same trick for days, numbers and more. For "logged in on consecutive days", subtract INTERVAL rn DAY from each date. For invoice numbers or IDs, subtract rn itself. Two rules make it work: remove duplicates first (two logins on the same day must count once), and make sure the values move in the same steps as the row numbers (one day, one month, one number).

5Recursive CTEs: hierarchies and sequences

Day 12 used a recursive CTE as a recipe to build the calendar, and promised to explain it. Here's how it works. Think of tracing a family tree: start with one grandparent, then find their children, then their children, and keep going until a generation has no children at all. A recursive CTE does the same, in rounds:

SQL
WITH RECURSIVE counter AS (
    SELECT 1 AS n                -- the anchor: the starting row(s)
    UNION ALL
    SELECT n + 1                 -- the recursive part: builds on the previous round
    FROM counter                 -- ...by reading the CTE itself
    WHERE n < 5                  -- the stop condition
)
SELECT n FROM counter;
Result
+------+
| n    |
+------+
|    1 |
|    2 |
|    3 |
|    4 |
|    5 |
+------+
  1. The anchor runs once: one row, n = 1.
  2. The recursive part runs on the rows from the previous round only: from 1, it makes 2. Then from 2, it makes 3, and so on.
  3. When a round produces no new rows (from 5, n < 5 is false), it stops. All the rounds together are the result.

Day 12's calendar was exactly this, with dates instead of numbers. Without a stop condition, it would run forever, which is why MySQL stops it after 1,000 rounds (error 3636, Day 12).

Walking down a hierarchy

Day 15 left a question open: "list everyone under the Head of Technology, at every level." A self join (Day 7) goes down one level. A recursive CTE goes down as many levels as there are:

SQL
WITH RECURSIVE team AS (
    SELECT employee_id,
           CONCAT(first_name, ' ', last_name) AS name,
           job_title,
           1                                  AS level,
           CAST(first_name AS CHAR(200))      AS path
    FROM employees
    WHERE employee_id = 5                     -- the anchor: Ananya, Head of Technology

    UNION ALL

    SELECT e.employee_id,
           CONCAT(e.first_name, ' ', e.last_name),
           e.job_title,
           t.level + 1,
           CONCAT(t.path, ' > ', e.first_name)
    FROM employees e
    JOIN team t ON e.manager_id = t.employee_id   -- people whose manager is already in the team
)
SELECT CONCAT(REPEAT('    ', level - 1), name) AS org_chart,
       job_title,
       level,
       path
FROM team
ORDER BY path;
Result
+----------------------+--------------------------+-------+------------------------+
| org_chart            | job_title                | level | path                   |

Round 1 is Ananya. Round 2 finds everyone whose manager is Ananya (Meera and Priya). Round 3 finds everyone whose manager is Meera or Priya. Round 4 finds nobody, so it stops. Change the anchor to the CEO, and you get the whole company: 1 person at level 1, then 5, 10 and 14.

Why the CAST(first_name AS CHAR(200))? MySQL decides each column's type from the anchor. If the first row's text is short, longer text in later rounds doesn't fit:

SQL
WITH RECURSIVE r AS (
    SELECT 1 AS n, 'x' AS dots
    UNION ALL
    SELECT n + 1, CONCAT(dots, 'x') FROM r WHERE n < 4
)
SELECT * FROM r;
MySQL says
ERROR 1406 (22001): Data too long for column 'dots' at row 1

The anchor's 'x' made dots one character wide, so 'xx' doesn't fit (error 1406). Casting the anchor's value to a wider type, like CHAR(200), gives later rounds room to grow.

Walking up, and adding up

Reverse the join, and the CTE climbs instead: from one employee up to the CEO, their chain of command:

SQL
WITH RECURSIVE chain AS (
    SELECT employee_id, first_name, job_title, manager_id, 0 AS steps_up
    FROM employees
    WHERE employee_id = 27                         -- Zara, a data analyst

    UNION ALL

    SELECT m.employee_id, m.first_name, m.job_title, m.manager_id, c.steps_up + 1
    FROM employees m
    JOIN chain c ON m.employee_id = c.manager_id   -- the manager of the previous person
)
SELECT employee_id, first_name, job_title, steps_up
FROM chain;
Result
+-------------+------------+-------------------------+----------+
| employee_id | first_name | job_title               | steps_up |
+-------------+------------+-------------------------+----------+
|          27 | Zara       | Data Analyst            |        0 |
|          24 | Priya      | Data Analytics Lead     |        1 |
|           5 | Ananya     | Head of Technology      |        2 |
|           1 | Ritu       | Chief Executive Officer |        3 |
+-------------+------------+-------------------------+----------+

The only change is the join: m.employee_id = c.manager_id finds each person's manager, where the team query found each person's reports. It stops at the CEO, whose manager_id is NULL and matches nobody.

And a question that's hard any other way: how many people, and how much salary, sit under each department head? Start the anchor with all the heads at once, and carry the head's ID down every branch:

SQL
WITH RECURSIVE tree AS (
    SELECT employee_id AS head_id, employee_id, salary
    FROM employees
    WHERE manager_id = 1                       -- everyone reporting to the CEO

    UNION ALL

    SELECT t.head_id, e.employee_id, e.salary
    FROM employees e
    JOIN tree t ON e.manager_id = t.employee_id
)
SELECT h.first_name       AS head,
       h.department,
       COUNT(*)           AS people_incl_head,
       SUM(t.salary)      AS total_salary
FROM tree t
JOIN employees h ON h.employee_id = t.head_id
GROUP BY h.employee_id, h.first_name, h.department
ORDER BY total_salary DESC;
Result
+--------+------------------+------------------+--------------+
| head   | department       | people_incl_head | total_salary |
+--------+------------------+------------------+--------------+
| Ananya | Technology       |                9 |  18050000.00 |
| Farah  | Marketing        |                5 |   7950000.00 |
| Sanjay | Operations       |                5 |   6260000.00 |
| Vikram | Customer Support |                7 |   5680000.00 |
| Rohit  | Finance          |                3 |   3900000.00 |
+--------+------------------+------------------+--------------+

Every row in tree keeps the head_id it started from, so after the recursion, a normal GROUP BY adds up each head's whole branch. Technology is the biggest and most expensive team. This "roll up a tree" pattern also works for product categories with subcategories, or for parts lists in manufacturing.

Watch out for loops. If the data ever said "A's manager is B" and "B's manager is A", the recursion would go round and round until MySQL's 1,000-round limit stopped it with an error. With data you don't fully trust, add a safety stop to the recursive part, like AND t.level < 20, or check that the path doesn't already contain the next person.

🎯 Interview corner

These patterns are favourites for "hard" SQL rounds. The trick questions here test whether you know the recipe, and whether you can explain why it works.

Concept questions

Q1What's the difference between pivoting and unpivoting?

Pivoting turns values in rows into columns (one column per quarter), usually with SUM(CASE WHEN ...). Unpivoting turns columns back into rows (one row per quarter), in MySQL with a UNION ALL of one SELECT per column. Reports like wide tables. Charts and analysis tools usually prefer long ones.

Q2How do you calculate a median in MySQL?

MySQL has no median function. Number the rows in order with ROW_NUMBER(), count them with COUNT(*) OVER (), and average the middle one or two: WHERE rn IN (FLOOR((n + 1) / 2), CEIL((n + 1) / 2)). Add PARTITION BY for a median per group. Databases like PostgreSQL have PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY x).

Q3When would you report a median instead of an average?

When the data is skewed by a few very large (or small) values, as order values, incomes, house prices and session lengths usually are. The median shows the typical value. The average is pulled towards the extremes. Here, the average order was ₹2,327 but the median ₹1,796. Reporting both, with the difference explained, is often best.

Q4What's the difference between PERCENTILE_CONT and PERCENTILE_DISC?

PERCENTILE_DISC returns an actual value from the data: the first value whose cumulative share reaches the percentile. PERCENTILE_CONT blends (interpolates) between the two nearest values, so it can return a number that isn't in the data. For a median with an even number of rows, CONT averages the two middle values.

Q5Explain the gaps-and-islands trick.

Remove duplicates, then number the values in order with ROW_NUMBER(). For consecutive values, value minus row number stays constant, because both go up by one step at a time. A gap breaks that, and the difference changes. So the difference is a group key: GROUP BY it to get one row per island, with MIN, MAX and COUNT for the start, end and length. For dates, subtract an INTERVAL of rn days or months.

Q6How does a recursive CTE work, and how does it stop?

It has an anchor query, which runs once, and a recursive query joined with UNION ALL, which refers to the CTE itself. The recursive part runs repeatedly, each time on the rows produced in the previous round, and stops when a round produces no new rows. The result is all rounds together. A stop condition (like WHERE n < 5, or simply running out of children in a hierarchy) is essential. MySQL also stops at cte_max_recursion_depth (1,000 by default).

Q7What can go wrong with recursive CTEs?

Infinite loops if the data has a cycle (A manages B, B manages A), which hit the recursion limit. Column types fixed by the anchor, so text built up in later rounds can be too long (error 1406). The fix is to CAST in the anchor. And performance on very large or deep trees. Guard against cycles with a level limit or a path check.

Q8What is dynamic SQL, and what are its risks?

SQL built as text at run time and then executed, in MySQL with PREPARE and EXECUTE. It allows things like pivots whose columns aren't known in advance. Risks: SQL injection if any part comes from user input, text cut off by group_concat_max_len with only an easy-to-miss warning, and code that's hard to read and debug. Often a reporting tool or Python is the better place for it.

P3Show each category's share of total revenue, with a running total from the biggest category down.
SQL
SELECT category_name,
       ROUND(SUM(line_total)) AS revenue,
       ROUND(SUM(line_total) * 100 / SUM(SUM(line_total)) OVER (), 1) AS pct,
       ROUND(SUM(SUM(line_total)) OVER (ORDER BY SUM(line_total) DESC
                                        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
             * 100 / SUM(SUM(line_total)) OVER (), 1) AS cumulative_pct
FROM clean_sales
GROUP BY category_name
ORDER BY revenue DESC;
Result
+----------------+---------+------+----------------+
| category_name  | revenue | pct  | cumulative_pct |
+----------------+---------+------+----------------+
| Electronics    | 4293466 | 32.6 |           32.6 |
| Clothing       | 3412509 | 25.9 |           58.5 |
| Sports         | 2233400 | 17.0 |           75.5 |
| Home & Kitchen | 1960466 | 14.9 |           90.3 |
| Books          | 1244529 |  9.4 |           99.8 |

Quick recap

  • Pivots: SUM(CASE ...) columns, a plain SUM for the row total, WITH ROLLUP with GROUPING() labels for the total rows. Unpivot with UNION ALL. Dynamic pivots need PREPARE and EXECUTE, and are usually better done in Python.
  • Medians: MySQL has no MEDIAN(). Number the rows, count them, and average the middle one or two. CUME_DIST() gives any percentile. Report the median beside the average when values are skewed.
  • 80/20: NTILE for groups, or a running share with SUM() OVER (ORDER BY ... ROWS ...). Here, 20% of customers bring 62.6% of revenue. ABC classes use the running share before each item.
  • Gaps and islands: remove duplicates, subtract ROW_NUMBER() (as days, months or numbers), and GROUP BY the result: one row per streak.
  • Recursive CTEs: an anchor, UNION ALL, and a recursive part that reads the CTE until no new rows appear. Use them to walk down or up hierarchies, roll up whole branches, and generate sequences. CAST text in the anchor, and guard against loops.
