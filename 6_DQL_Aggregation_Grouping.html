Yesterday every query gave back rows: customers from India, products over ₹1,000, the three latest orders. That's useful, but it isn't what the shop owner usually asks. The owner asks "how many orders did we get?", "what's our total revenue?", "which category has the most products?" Those questions need one number, or one number per group, worked out from many rows. Today you learn how.

Same data as always. Every result below comes from online_store exactly as you loaded it on Day 4. Like yesterday, these queries only read, so nothing can break.

1From rows to answers

Think of your bank statement. The top of the page lists every single payment, one line each. The bottom shows a few summary lines: total spent, total received, the closing balance. Nobody reads all 200 lines to find out how much they spent. They look at the summary.

SQL's aggregate functions produce that summary. Each one takes many rows and squeezes them into one value:

FunctionGives youExample question
COUNT()how manyHow many orders do we have?
SUM()the totalHow many items are in stock altogether?
AVG()the averageWhat's the average product price?
MIN()the smallestWhat's our cheapest product?
MAX()the largestWhen was the most recent order?

Here's the simplest one:

SQL
SELECT COUNT(*) AS total_orders
FROM orders;
Result
+--------------+
| total_orders |
+--------------+
|           15 |
+--------------+

Fifteen rows went in, one row came out. That is what "aggregate" means: gather many things into one.

2COUNT: three ways to count

Picture a birthday party with 10 guests. You could count three different things:

  • How many guests came? (count the people)
  • How many guests wrote their city in the guest book? (count the filled-in boxes)
  • How many different cities did guests come from? (count the different values)

SQL has a version of COUNT for each:

SQL
SELECT COUNT(*)                AS all_customers,
       COUNT(city)             AS with_a_city,
       COUNT(DISTINCT country) AS countries
FROM customers;
Result
+---------------+-------------+-----------+
| all_customers | with_a_city | countries |
+---------------+-------------+-----------+
|            10 |           9 |         4 |
+---------------+-------------+-----------+
FormWhat it countsHere
COUNT(*)Every row, no matter what's in it10 customers
COUNT(column)Rows where that column is not NULL9, because Noah's city is NULL
COUNT(DISTINCT column)Different non-NULL values4 countries: India, Pakistan, UK, USA

The difference between the first two is a favourite interview question, and it matters in real work. If you want "how many customers", use COUNT(*). If you use COUNT(city) by mistake, Noah silently disappears.

A useful one: how many customers have ordered?

Every order has a customer_id. Counting the different ones tells you how many customers have bought something:

SQL
SELECT COUNT(*)                    AS orders,
       COUNT(DISTINCT customer_id) AS customers_who_ordered
FROM orders;
Result
+--------+-----------------------+
| orders | customers_who_ordered |
+--------+-----------------------+
|     15 |                     9 |
+--------+-----------------------+

15 orders came from 9 different customers. We have 10 customers, so one has never ordered. That's Noah again. Analysts use this all the time: "active customers" is just COUNT(DISTINCT customer_id) over some period.

3SUM, AVG, MIN and MAX

These four work on a column of values:

SQL
SELECT SUM(stock_quantity) AS items_in_stock,
       AVG(price)          AS avg_price,
       MIN(price)          AS cheapest,
       MAX(price)          AS dearest
FROM products;
Result
+----------------+-------------+----------+---------+
| items_in_stock | avg_price   | cheapest | dearest |
+----------------+-------------+----------+---------+
|           1835 | 1555.666667 |   349.00 | 7999.00 |
+----------------+-------------+----------+---------+

There are 1,835 items on the shelves. The cheapest product costs ₹349 and the dearest ₹7,999. The average price has a long tail of decimals, so tidy it up with ROUND(value, decimals):

SQL
SELECT ROUND(AVG(price), 2) AS avg_price
FROM products;
Result
+-----------+
| avg_price |
+-----------+
|   1555.67 |
+-----------+

MIN and MAX aren't only for numbers

On dates, MIN is the earliest and MAX the latest. On text, they go by alphabetical order:

SQL
SELECT MIN(signup_date)  AS first_signup,
       MAX(signup_date)  AS latest_signup,
       MIN(first_name)   AS first_alphabetically
FROM customers;
Result
+--------------+---------------+----------------------+
| first_signup | latest_signup | first_alphabetically |
+--------------+---------------+----------------------+
| 2023-01-15   | 2024-02-14    | Aarav                |
+--------------+---------------+----------------------+

SUM and AVG only make sense for numbers. You can't add up names.

Aggregating a calculation

You can put a whole calculation inside an aggregate. On Day 5 you worked out each product's stock value. Here is the total for the whole shop:

SQL
SELECT SUM(price * stock_quantity) AS total_stock_value
FROM products;
Result
+-------------------+
| total_stock_value |
+-------------------+
|        1969665.00 |
+-------------------+

MySQL works out price * stock_quantity for every row first, then adds up the results. About ₹19.7 lakh is sitting on the shelves.

WHERE still works. An aggregate only sees the rows that got past WHERE. SELECT COUNT(*) FROM orders WHERE status = 'Completed'; counts only completed orders. Filter first, then summarise.

4NULLs and empty results

Two rules decide how aggregates behave in tricky cases.

Rule 1: aggregates skip NULLs

You already saw COUNT(city) skip Noah. SUM, AVG, MIN and MAX do the same: they act as if NULL rows weren't there. This matters most for AVG, because it changes what you are averaging.

Say the owner asks: "What's the average stock of the products we actually have?" The Resistance Bands Set has 0 in stock. Compare these two averages:

SQL
SELECT AVG(stock_quantity)              AS avg_all_products,
       AVG(NULLIF(stock_quantity, 0))   AS avg_in_stock_only
FROM products;
Result
+------------------+-------------------+
| avg_all_products | avg_in_stock_only |
+------------------+-------------------+
|         122.3333 |          131.0714 |
+------------------+-------------------+

NULLIF(stock_quantity, 0) (which you met on Day 4) turns the 0 into a NULL, so AVG skips that product. The first average divides by 15 products, the second by 14. Neither is wrong. They answer different questions, and you have to know which one you're asking.

The same thing happens by accident in real data. If a discount column is NULL for "no discount", AVG(discount) gives the average discount among products that have one, which is much higher than the average across all products. When NULL really means zero, say so with COALESCE(discount, 0) (Day 8).

Rule 2: on no rows, COUNT gives 0, the rest give NULL

What if WHERE filters out every row? Nothing costs over ₹1,00,000:

SQL
SELECT COUNT(*)   AS how_many,
       SUM(price) AS total,
       AVG(price) AS average,
       MAX(price) AS dearest
FROM products
WHERE price > 100000;
Result
+----------+-------+---------+---------+
| how_many | total | average | dearest |
+----------+-------+---------+---------+
|        0 |  NULL |    NULL |    NULL |
+----------+-------+---------+---------+

Counting nothing gives 0, which makes sense. But the total of nothing is NULL, not 0, because there was nothing to add. This catches people out when a report shows a blank instead of ₹0. You'll fix it with COALESCE(SUM(price), 0) on Day 8.

5The shop's real revenue

On Day 4 you added up every order line and got ₹48,463. Back then we said that's not the shop's real revenue. Let's work out the real number, because this is exactly the kind of thing analysts get asked on their first day.

First, decide what "revenue" means

This is a business question before it's an SQL question. Our orders have three statuses:

  • Completed: the customer paid and got the goods. This is clearly revenue.
  • Cancelled: the sale didn't happen. Clearly not revenue.
  • Pending: not finished yet. Most shops don't count it until it completes.

So we count Completed orders only. In real work, always agree the definition with whoever asked, and write it down next to the number. Two analysts who define revenue differently will both be "right" and still give the boss two different numbers.

Step 1: which orders are not completed?

The amounts live in order_items, but the status lives in orders. Joining the two comes tomorrow, so for now we'll do it in two simple steps, the way you'd do it with two spreadsheets:

SQL
SELECT order_id, status
FROM orders
WHERE status != 'Completed';
Result
+----------+-----------+
| order_id | status    |
+----------+-----------+
|        5 | Pending   |
|        7 | Cancelled |
|       11 | Pending   |
|       14 | Cancelled |
+----------+-----------+

Step 2: add up everything else

SQL
SELECT SUM(quantity * unit_price)  AS revenue,
       COUNT(DISTINCT order_id)    AS completed_orders
FROM order_items
WHERE order_id NOT IN (5, 7, 11, 14);
Result
+----------+------------------+
| revenue  | completed_orders |
+----------+------------------+
| 39969.00 |               11 |
+----------+------------------+

The shop's real revenue is ₹39,969 from 11 completed orders. That's about ₹8,500 less than the raw total. Reporting ₹48,463 as revenue would overstate it by more than 20%.

Average order value

One of the most watched numbers in any online shop is the average order value (AOV): revenue divided by the number of orders.

SQL
SELECT ROUND(SUM(quantity * unit_price) / COUNT(DISTINCT order_id), 2) AS avg_order_value
FROM order_items
WHERE order_id NOT IN (5, 7, 11, 14);
Result
+-----------------+
| avg_order_value |
+-----------------+
|         3633.55 |
+-----------------+

Notice we divided by COUNT(DISTINCT order_id), not COUNT(*). Here COUNT(*) would count order lines, and many orders have two or three lines. Dividing by lines would give "average line value", a different and much smaller number. Always ask: "What does one row in this table mean?" On order_items, one row is one line on a bill, not one order.

Typing IDs by hand is fragile. If a new order is cancelled tomorrow, step 2 won't know about it. On Day 7 you'll write this as one query that reads the status directly, and that version keeps working however the data changes.

6GROUP BY: one answer per group

So far, every aggregate gave one number for the whole table. But owners rarely want just one number. They want it per something: orders per status, customers per country, products per category.

Think about sorting laundry. First you make piles: whites, colours, darks. Then you count each pile. GROUP BY does exactly that: it sorts the rows into piles that share a value, then runs the aggregate on each pile separately.

SQL
SELECT status,
       COUNT(*) AS orders
FROM orders
GROUP BY status;
Result
+-----------+--------+
| status    | orders |
+-----------+--------+
| Completed |     11 |
| Pending   |      2 |
| Cancelled |      2 |
+-----------+--------+

This is the query from the top of the page. MySQL put the 15 orders into three piles by status, then counted each pile. One row per group.

Sorting the groups

Groups come back in no fixed order, so add ORDER BY. You can sort by the aggregate itself. Customers per country, biggest first:

SQL
SELECT country,
       COUNT(*) AS customers
FROM customers
GROUP BY country
ORDER BY customers DESC;
Result
+----------+-----------+
| country  | customers |
+----------+-----------+
| India    |         7 |
| Pakistan |         1 |
| UK       |         1 |
| USA      |         1 |
+----------+-----------+

Several aggregates per group

You can work out as many summaries per group as you like. A quick profile of each category:

SQL
SELECT category_id,
       COUNT(*)             AS products,
       MIN(price)           AS cheapest,
       MAX(price)           AS dearest,
       ROUND(AVG(price), 2) AS avg_price,
       SUM(stock_quantity)  AS units_in_stock
FROM products
GROUP BY category_id
ORDER BY category_id;
Result
+-------------+----------+----------+---------+-----------+----------------+
| category_id | products | cheapest | dearest | avg_price | units_in_stock |
+-------------+----------+----------+---------+-----------+----------------+
|           1 |        4 |   799.00 | 7999.00 |   3149.00 |            330 |
|           2 |        3 |   599.00 | 1199.00 |    899.00 |            410 |
|           3 |        3 |   499.00 | 1799.00 |   1265.67 |            485 |
|           4 |        3 |   349.00 | 1599.00 |    882.33 |            480 |
|           5 |        2 |   599.00 |  999.00 |    799.00 |            130 |
+-------------+----------+----------+---------+-----------+----------------+

Electronics (category 1) has the highest average price, pulled up by the ₹7,999 headphones. Sports (5) has the least stock, because the Resistance Bands Set is sold out. Annoyingly, we only see category numbers. Turning 1 into "Electronics" means looking it up in another table, and that's what joins do. You'll fix it tomorrow.

Totals per order

Grouping order_items by order_id turns order lines back into whole orders, with their totals. These are the five biggest orders:

SQL
SELECT order_id,
       COUNT(*)                   AS line_count,
       SUM(quantity)              AS items,
       SUM(quantity * unit_price) AS order_total
FROM order_items
GROUP BY order_id
ORDER BY order_total DESC
LIMIT 5;
Result
+----------+------------+-------+-------------+
| order_id | line_count | items | order_total |
+----------+------------+-------+-------------+
|       12 |          2 |     2 |     9198.00 |
|        2 |          1 |     1 |     7999.00 |
|        4 |          2 |     2 |     3798.00 |
|       11 |          1 |     2 |     3598.00 |
|       10 |          2 |     2 |     3298.00 |
+----------+------------+-------+-------------+

Order 4 should look familiar: 2 lines, 2 items, ₹3,798. It's the order you traced by hand in Day 2's Try this.

Why line_count and not just lines? LINES is a reserved word in MySQL. It already means something (you saw it in LOAD DATA on Day 4), so using it as an alias gives a confusing syntax error 1064. ROWS, ORDER, GROUP and RANK are other common traps. If an alias gives a strange error, try renaming it first.

Going deeper: the average of averages trap

From the category profile above, you could average the five avg_price values: (3149 + 899 + 1265.67 + 882.33 + 799) ÷ 5 = ₹1,399. But the real average price of all products is:

SQL
SELECT ROUND(AVG(price), 2) AS true_avg_price
FROM products;
Result
+----------------+
| true_avg_price |
+----------------+
|        1555.67 |
+----------------+

Why the difference? Averaging the averages treats every category as equal, even though Electronics has 4 products and Sports has only 2. It's like a class where one section has 40 students and another has 4. The average of the two section averages is not the class average.

This mistake shows up in real dashboards all the time, for example averaging daily averages to get a monthly average. The fix: go back to the raw rows and do the AVG once, or compute it yourself as SUM(...) / COUNT(...) over all rows.

7The GROUP BY rule

Try this. You want each customer's number of orders, and you also add order_date:

SQL
SELECT customer_id,
       order_date,
       COUNT(*) AS orders
FROM orders
GROUP BY customer_id;
MySQL says
ERROR 1055 (42000): Expression #2 of SELECT list is not in GROUP BY clause and contains nonaggregated column 'online_store.orders.order_date' which is not functionally dependent on columns in GROUP BY clause; this is incompatible with sql_mode=only_full_group_by

Think about what you asked for. Aarav (customer 1) has three orders, on three different dates. His group becomes one row. Which of the three dates should go in that one row? MySQL can't guess, so it refuses.

That gives us the GROUP BY rule: every column in SELECT must either be

  1. listed in GROUP BY, so it has one value per group, or
  2. inside an aggregate like COUNT, MAX or SUM, so it gets squeezed into one value.

So the fix depends on what you meant. "The date of each customer's latest order" is MAX(order_date):

SQL
SELECT customer_id,
       COUNT(*)        AS orders,
       MIN(order_date) AS first_order,
       MAX(order_date) AS latest_order
FROM orders
GROUP BY customer_id
ORDER BY orders DESC, customer_id;
Result
+-------------+--------+-------------+--------------+
| customer_id | orders | first_order | latest_order |
+-------------+--------+-------------+--------------+
|           1 |      3 | 2024-01-10  | 2024-05-07   |
|           2 |      2 | 2024-01-15  | 2024-03-12   |
|           3 |      2 | 2024-02-03  | 2024-04-18   |
|           4 |      2 | 2024-02-28  | 2024-06-15   |
|           5 |      2 | 2024-03-05  | 2024-06-01   |
|           6 |      1 | 2024-03-25  | 2024-03-25   |
|           7 |      1 | 2024-04-02  | 2024-04-02   |
|           8 |      1 | 2024-04-30  | 2024-04-30   |
|           9 |      1 | 2024-05-19  | 2024-05-19   |
+-------------+--------+-------------+--------------+

Now every column has exactly one value per customer. And you've built something useful: each customer's first and latest order date. Analysts use exactly this to spot customers who haven't come back in a while.

Older MySQL didn't stop you. Before version 5.7, MySQL quietly picked any date from the group and showed it, with no warning. Many old tutorials and old company queries still rely on that. Today the setting ONLY_FULL_GROUP_BY is on by default, and you should leave it on. A query that guesses is a query that's sometimes wrong.

8Grouping by more than one thing

Two columns

List two columns in GROUP BY, and each different pair becomes a group. Think of laundry sorted by colour and by fabric. How many orders does each customer have in each status?

SQL
SELECT customer_id,
       status,
       COUNT(*) AS orders
FROM orders
WHERE customer_id IN (1, 2, 4, 5)
GROUP BY customer_id, status
ORDER BY customer_id, status;
Result
+-------------+-----------+--------+
| customer_id | status    | orders |
+-------------+-----------+--------+
|           1 | Completed |      3 |
|           2 | Cancelled |      1 |
|           2 | Completed |      1 |
|           4 | Completed |      1 |
|           4 | Pending   |      1 |
|           5 | Cancelled |      1 |
|           5 | Completed |      1 |
+-------------+-----------+--------+

Aarav has one group (all Completed). Diya, Ananya and Vivaan each have two, because their orders have two different statuses.

A calculation: grouping by month or year

You can group by a calculation, not just a column. This is how every "per month" report is made. DATE_FORMAT(order_date, '%Y-%m') turns a date like 2024-03-12 into the text 2024-03, so all March orders land in the same pile:

SQL
SELECT DATE_FORMAT(order_date, '%Y-%m') AS order_month,
       COUNT(*)                         AS orders
FROM orders
GROUP BY order_month
ORDER BY order_month;
Result
+-------------+--------+
| order_month | orders |
+-------------+--------+
| 2024-01     |      2 |
| 2024-02     |      3 |
| 2024-03     |      3 |
| 2024-04     |      3 |
| 2024-05     |      2 |
| 2024-06     |      2 |
+-------------+--------+

And sign-ups per year, with YEAR():

SQL
SELECT YEAR(signup_date) AS signup_year,
       COUNT(*)          AS customers
FROM customers
GROUP BY signup_year;
Result
+-------------+-----------+
| signup_year | customers |
+-------------+-----------+
|        2023 |         8 |
|        2024 |         2 |
+-------------+-----------+

Monthly revenue would need the date from orders and the amounts from order_items together. That's a join again, so it waits for tomorrow. Day 12 then goes much deeper into dates: weeks, quarters, and months with no orders at all.

A MySQL shortcut. Notice we wrote GROUP BY order_month, using the alias. MySQL allows that, but many databases don't, and there you'd repeat the whole DATE_FORMAT(...) in GROUP BY. If you'll ever move your SQL to another database, repeating the expression is the safer habit.

9HAVING: filtering groups

"Which customers have placed more than one order?" Your first try might be to put the count in WHERE:

SQL
SELECT customer_id, COUNT(*) AS orders
FROM orders
WHERE COUNT(*) > 1
GROUP BY customer_id;
MySQL says
ERROR 1111 (HY000): Invalid use of group function

Remember the order MySQL runs a query in from Day 5. WHERE looks at single rows before any groups exist. At that point there's no count to check yet. To filter groups, after they've been counted, you need HAVING:

SQL
SELECT customer_id,
       COUNT(*) AS orders
FROM orders
GROUP BY customer_id
HAVING COUNT(*) > 1
ORDER BY orders DESC, customer_id;
Result
+-------------+--------+
| customer_id | orders |
+-------------+--------+
|           1 |      3 |
|           2 |      2 |
|           3 |      2 |
|           4 |      2 |
|           5 |      2 |
+-------------+--------+

Five repeat customers. Think of a school deciding which classes get a prize for having an average mark above 80. You can't decide that by looking at one student. You first need each class's average, then you keep the classes that pass. WHERE judges students. HAVING judges classes.

WHERE and HAVING together

They're not either/or. Each does its own job, at its own step. "Which customers have two or more orders that weren't cancelled?"

SQL
SELECT customer_id,
       COUNT(*) AS orders
FROM orders
WHERE status != 'Cancelled'      -- 1. throw away cancelled orders (rows)
GROUP BY customer_id             -- 2. make one pile per customer
HAVING COUNT(*) >= 2             -- 3. keep piles with 2 or more (groups)
ORDER BY orders DESC, customer_id;
Result
+-------------+--------+
| customer_id | orders |
+-------------+--------+
|           1 |      3 |
|           3 |      2 |
|           4 |      2 |
+-------------+--------+

Diya and Vivaan dropped out. Each had two orders, but one of them was cancelled. Here's the difference in one table:

WHEREHAVING
Filterssingle rowswhole groups
Runsbefore groupingafter grouping
Can use aggregates?NoYes, that's its job
ExampleWHERE status != 'Cancelled'HAVING COUNT(*) >= 2

A speed habit. If a condition is about single rows, put it in WHERE, even though HAVING would sometimes accept it. WHERE throws rows away before the grouping work, so there's less to group. On a table with millions of rows, that can make a big difference.

Big orders

One more. Which orders are worth more than ₹3,000?

SQL
SELECT order_id,
       SUM(quantity * unit_price) AS order_total
FROM order_items
GROUP BY order_id
HAVING order_total > 3000
ORDER BY order_total DESC;
Result
+----------+-------------+
| order_id | order_total |
+----------+-------------+
|       12 |     9198.00 |
|        2 |     7999.00 |
|        4 |     3798.00 |
|       11 |     3598.00 |
|       10 |     3298.00 |
|        3 |     3296.00 |
+----------+-------------+

This time HAVING used the alias order_total. MySQL allows that. Like the GROUP BY alias, other databases may not, so HAVING SUM(quantity * unit_price) > 3000 is the version that works everywhere.

The full running order

On Day 5 the running order had five steps. GROUP BY and HAVING slot in after WHERE:

  1. 1FROM

    Find the table

  2. 2WHERE

    Filter rows

  3. 3GROUP BY

    Make piles

  4. 4HAVING

    Filter piles

  5. 5SELECT

    Work out columns

  6. 6ORDER BY

    Sort

  7. 7LIMIT

    Cut short

This is the full order for a single-table query. It explains every rule today: WHERE can't see counts (they don't exist until step 3), and HAVING can.

10Handy extras

GROUP_CONCAT: list the values in each group

Sometimes you want to see what's in each group, not just count it. GROUP_CONCAT joins the group's values into one piece of text:

SQL
SELECT order_id,
       GROUP_CONCAT(product_id ORDER BY product_id SEPARATOR ', ') AS products
FROM order_items
GROUP BY order_id
ORDER BY order_id
LIMIT 5;
Result
+----------+----------+
| order_id | products |
+----------+----------+
|        1 | 1, 5     |
|        2 | 4        |
|        3 | 8, 9     |
|        4 | 2, 3     |
|        5 | 6        |
+----------+----------+

It's handy for a quick look, for example "which products are in each order?". Keep it for display, though. Text like "1, 5" is hard to calculate with afterwards. (By default, MySQL cuts the result off after 1,024 characters without any error, so very large groups get trimmed.)

WITH ROLLUP: add a grand total

Reports usually want a "Total" line at the bottom. WITH ROLLUP adds it for you:

SQL
SELECT status,
       COUNT(*) AS orders
FROM orders
GROUP BY status WITH ROLLUP;
Result
+-----------+--------+
| status    | orders |
+-----------+--------+
| Cancelled |      2 |
| Completed |     11 |
| Pending   |      2 |
| NULL      |     15 |
+-----------+--------+

The extra row with NULL is the grand total: 15. A NULL label is confusing, though. GROUPING(status) is 1 on the total row and 0 elsewhere, so you can give that row a proper name:

SQL
SELECT IF(GROUPING(status), 'All orders', status) AS status,
       COUNT(*) AS orders
FROM orders
GROUP BY status WITH ROLLUP;
Result
+------------+--------+
| status     | orders |
+------------+--------+
| Cancelled  |      2 |
| Completed  |     11 |
| Pending    |      2 |
| All orders |     15 |
+------------+--------+

IF(condition, a, b) gives a when the condition is true and b when it isn't. You'll meet its bigger brother, CASE, on Day 8.

Counting with a condition

What share of orders were cancelled? In MySQL, a comparison like status = 'Cancelled' gives 1 when true and 0 when false. So SUM of a comparison counts the rows where it's true:

SQL
SELECT COUNT(*)                                       AS all_orders,
       SUM(status = 'Cancelled')                      AS cancelled,
       ROUND(SUM(status = 'Cancelled') / COUNT(*) * 100, 1) AS cancel_rate_pct
FROM orders;
Result
+------------+-----------+-----------------+
| all_orders | cancelled | cancel_rate_pct |
+------------+-----------+-----------------+
|         15 |         2 |            13.3 |
+------------+-----------+-----------------+

13.3% of orders were cancelled. This trick lets you count several things in one pass over the table. It's MySQL-only, though. On Day 8 you'll learn the version that works in every database, SUM(CASE WHEN ... THEN 1 ELSE 0 END).

3. First order in 2024 and more than one order.

SQL
SELECT customer_id,
       COUNT(*)        AS orders,
       MIN(order_date) AS first_order
FROM orders
GROUP BY customer_id
HAVING MIN(order_date) >= '2024-01-01'
   AND COUNT(*) > 1
ORDER BY customer_id;
Result
+-------------+--------+-------------+
| customer_id | orders | first_order |
+-------------+--------+-------------+
|           1 |      3 | 2024-01-10  |
|           2 |      2 | 2024-01-15  |
|           3 |      2 | 2024-02-03  |
|           4 |      2 | 2024-02-28  |
|           5 |      2 | 2024-03-05  |
+-------------+--------+-------------+

Every order in our data is from 2024, so this keeps all five repeat customers. The key idea: "first order in 2024" is about the group (its earliest date), not about single rows, so it belongs in HAVING. If you'd put WHERE order_date >= '2024-01-01', you'd be asking a different question: "orders placed in 2024".

       COUNT(*) AS orders,

🎯 Interview corner

Aggregation questions are in nearly every analyst interview, usually as "WHERE vs HAVING" and "COUNT(*) vs COUNT(column)". Answer out loud, with an example, before you open each one.

Concept questions

Q1What's the difference between COUNT(*), COUNT(column) and COUNT(DISTINCT column)?

COUNT(*) counts every row. COUNT(column) counts rows where that column isn't NULL. COUNT(DISTINCT column) counts the different non-NULL values. In our shop: 10 customers, 9 with a city, 4 different countries.

Q2What's the difference between WHERE and HAVING?

WHERE filters single rows before grouping, and can't use aggregates. HAVING filters groups after grouping, and is where aggregate conditions go. Example: WHERE status != 'Cancelled' removes cancelled orders, then HAVING COUNT(*) >= 2 keeps customers with at least two of the remaining orders. Put row conditions in WHERE, because filtering early is faster.

Q3Why do you get "not in GROUP BY clause" errors?

Because a column in SELECT isn't in GROUP BY and isn't inside an aggregate, so it could have several values in one group and MySQL can't pick one. Every selected column must be grouped or aggregated. The fix depends on intent, for example MAX(order_date) for the latest date. MySQL enforces this with ONLY_FULL_GROUP_BY, which is on by default since 5.7.

Q4How do aggregate functions treat NULL?

They ignore it. SUM, AVG, MIN, MAX and COUNT(column) skip NULL rows (only COUNT(*) counts them). The dangerous one is AVG: with NULLs it divides by fewer rows, so it can be much higher than if NULLs were treated as 0. If NULL means zero, use AVG(COALESCE(col, 0)).

Q5What does SUM return when no rows match?

NULL, not 0. So do AVG, MIN and MAX. Only COUNT returns 0. If a report should show 0, wrap it: COALESCE(SUM(amount), 0).

Q6What's the difference between GROUP BY and DISTINCT?

Both give one row per different value, so SELECT DISTINCT status FROM orders and SELECT status FROM orders GROUP BY status return the same rows. But GROUP BY lets you calculate something for each group, like COUNT(*) or SUM(amount). Use DISTINCT to list unique values, and GROUP BY to summarise them.

Q7Can you use a column alias in GROUP BY or HAVING?

In MySQL, yes, as an extension to standard SQL. In others, like SQL Server, no, because those clauses run before SELECT creates the alias. The portable habit is to repeat the expression. In WHERE, aliases never work, in any database.

Q8In what order does a query with GROUP BY run?

FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT. That explains why WHERE can't use aggregates (no groups yet), why HAVING can, and why ORDER BY can sort by an aggregate's alias.

Q9Why is "average of averages" usually wrong?

Because it gives every group the same weight, whatever its size. Averaging five category averages treats a category with 2 products the same as one with 4. Our shop's true average price is ₹1,555.67, but the average of the category averages is ₹1,399. Average the raw rows once, or compute SUM / COUNT over all rows.

Q10What does WITH ROLLUP do?

It adds summary rows to a GROUP BY: a grand total, and with several grouping columns, subtotals for each level. The total rows show NULL in the grouped columns. GROUPING(col) returns 1 on those rows, so you can label them, for example IF(GROUPING(status), 'All', status).

Practical questions

P1Find any email address used by more than one customer.
SQL
SELECT email,
       COUNT(*) AS times_used
FROM customers
GROUP BY email
HAVING COUNT(*) > 1;
Result
(no rows)

No rows, because email has a UNIQUE rule (Day 3), so duplicates can't exist. But this is the classic way to find duplicates in any column without such a rule, and you'll use it for real on the messy data on Day 11. A good interview answer adds: "In real data I'd also check for near-duplicates, like different capital letters or extra spaces, with GROUP BY LOWER(TRIM(email))."

P2Which month had the most orders?
SQL
SELECT DATE_FORMAT(order_date, '%Y-%m') AS order_month,
       COUNT(*)                         AS orders
FROM orders
GROUP BY order_month
ORDER BY orders DESC, order_month;
Result
+-------------+--------+
| order_month | orders |
+-------------+--------+
| 2024-02     |      3 |
| 2024-03     |      3 |
| 2024-04     |      3 |
| 2024-01     |      2 |
| 2024-05     |      2 |
| 2024-06     |      2 |
+-------------+--------+

The tempting answer is to add LIMIT 1 and say "February". But February, March and April tie on 3 orders each. LIMIT 1 would hide that and give a misleading answer. Always look at the ties before cutting the list. On Day 9, RANK() returns every month that shares first place.

P3For each customer, show how many orders they've completed and how many they've cancelled, in one row each.
SQL
SELECT customer_id,
       SUM(status = 'Completed') AS completed,
       SUM(status = 'Cancelled') AS cancelled
FROM orders
GROUP BY customer_id
ORDER BY customer_id;
Result
+-------------+-----------+-----------+
| customer_id | completed | cancelled |
+-------------+-----------+-----------+
|           1 |         3 |         0 |
|           2 |         1 |         1 |
|           3 |         2 |         0 |
|           4 |         1 |         0 |
|           5 |         1 |         1 |
|           6 |         1 |         0 |
|           7 |         1 |         0 |
|           8 |         0 |         0 |
|           9 |         1 |         0 |
+-------------+-----------+-----------+

This turns status values into columns, which is called pivoting. Each SUM(condition) counts the rows where the condition is true, inside each customer's group. The version that works in every database uses CASE (Day 8), and Day 16 covers pivoting in full.

Quick recap

  • Aggregate functions squeeze many rows into one value: COUNT, SUM, AVG, MIN, MAX. Tidy decimals with ROUND.
  • COUNT(*) counts rows, COUNT(col) counts non-NULL values, COUNT(DISTINCT col) counts different values.
  • Aggregates skip NULLs, which changes what AVG means. On no rows, COUNT gives 0 and the others give NULL.
  • Agree what a metric means before you calculate it. The shop's real revenue (Completed orders only) is ₹39,969 from 11 orders, an average order value of ₹3,633.55.
  • GROUP BY makes one row per group. Every selected column must be grouped or aggregated.
  • You can group by several columns, or by a calculation like DATE_FORMAT(order_date, '%Y-%m').
  • WHERE filters rows before grouping. HAVING filters groups after. Run order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
  • Watch for the average of averages, ties when picking a "top" group, and groups that are missing because they have no rows.
