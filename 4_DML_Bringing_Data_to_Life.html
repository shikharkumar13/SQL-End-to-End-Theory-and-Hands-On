1What DML does

On Day 3 we said DDL builds the house and DML moves the furniture in. DML stands for Data Manipulation Language. It works on the rows inside tables, never on the tables themselves.

There are three commands. Back in our shop:

CommandWhat it doesIn the shop
INSERTAdds new rowsPut new products on the shelf
UPDATEChanges rows that are already thereChange a price tag
DELETERemoves rowsTake an item off the shelf

You may hear people say CRUD: Create, Read, Update, Delete. These are the four basic things you can do with data. In SQL they are INSERT, SELECT, UPDATE and DELETE. Today covers three of them. Reading gets the whole of Days 5 to 9.

One warning before we start. UPDATE and DELETE change every row you don't filter out. Forget the filter, and you change the whole table. Section 8 is all about this, and section 6 gives you an undo button before you touch anything.

2INSERT: your first rows

Think of filling in a register at a hotel's front desk. You write one line per guest, and you fill in the columns the register asks for: name, phone, room. INSERT is the same. You name the table, list the columns you are filling in, then give the values in the same order:

The shape of an INSERT
INSERT INTO table_name (column1, column2, ...)
VALUES (value1, value2, ...);

Make sure you are inside the database first, then add the first category:

Add one row
USE online_store;

INSERT INTO categories (category_name)
VALUES ('Electronics');
MySQL says
Query OK, 1 row affected

"1 row affected" is MySQL telling you how many rows the command touched. Get used to reading this line. It is the quickest way to spot a mistake. (In MySQL Workbench, you'll find it in the Output panel at the bottom.)

We never gave a category_id. That column is AUTO_INCREMENT (Day 3), so MySQL handed out number 1 by itself, like the token machine.

Many rows in one go

Writing one INSERT per row works, but it is slow for you and for the database. Instead, put several rows after VALUES, each in its own brackets, separated by commas:

Add the other four categories
INSERT INTO categories (category_name) VALUES
('Books'),
('Clothing'),
('Home & Kitchen'),
('Sports');
MySQL says
Query OK, 4 rows affected
Records: 4  Duplicates: 0  Warnings: 0

Let's look at what is in the table. SELECT * FROM table means "show me every column of every row". You'll learn SELECT properly tomorrow, but you can already use this simple form to check your work:

SQL
SELECT * FROM categories;
Result
+-------------+----------------+
| category_id | category_name  |
+-------------+----------------+
|           2 | Books          |
|           3 | Clothing       |
|           1 | Electronics    |
|           4 | Home & Kitchen |
|           5 | Sports         |
+-------------+----------------+

Electronics got ID 1 and the others got 2 to 5, in the order we inserted them. But look at the order of the rows: alphabetical by name, not by ID. That is not a mistake. A table has no built-in order, and MySQL hands rows back in whatever order is quickest for it. Here it read them from the UNIQUE index on category_name. If the order matters to you, you must ask for it with ORDER BY, which is coming on Day 5.

Three habits for every INSERT

  • Always list the columns. You can leave out the column list, but then you must give a value for every column, in the exact order of the table. If someone adds a column later, your old INSERT breaks or, worse, puts values in the wrong columns.
  • Leave out the ID. Let AUTO_INCREMENT do its job.
  • Quote text and dates, not numbers. 'Books' and '2024-01-10' go in single quotes. 799 does not.

Things to notice:

  • Dates are written as 'YYYY-MM-DD' in single quotes, as you learned on Day 2.
  • The values follow the column list. The fourth value in each row goes into the fourth column, city. MySQL doesn't read the values' meaning. If you swap city and country in one row, MySQL happily stores "India" as the city.
  • Lining up the values with spaces, like a table, is only for humans. MySQL ignores extra spaces, but you will spot a mistake much faster.
  • Noah Brown has NULL for his city. We write the word NULL with no quotes to mean "no value". This only works because city has no NOT NULL rule (Day 3).

The 'NULL' trap

Put quotes around it, and 'NULL' is no longer missing. It is a piece of text, four letters long, like a name. Here is what goes wrong (this row is added and then undone, so just read it):

Read only: don't run
INSERT INTO customers (first_name, last_name, email, city, country, signup_date)
VALUES ('Riya', 'Kapoor', 'riya.kapoor@email.com', 'NULL', 'India', '2024-06-25');

SELECT first_name, city, city IS NULL AS is_missing
FROM customers WHERE email = 'riya.kapoor@email.com';
Result
+------------+------+------------+
| first_name | city | is_missing |
+------------+------+------------+
| Riya       | NULL |          0 |
+------------+------+------------+

The city looks like NULL, but IS NULL says no (0 means false). Riya now lives in a city called "NULL", and every query that looks for missing cities will skip her. This kind of fake NULL shows up a lot in real data, and you'll clean it up on Day 11. For now, the rule: no quotes around NULL.

6Transactions: your undo button

Your data is now perfect, and the rest of the series depends on it staying that way. So before you change a single row, let's learn how to undo a change.

Normally, every change is saved at once

By default, MySQL saves each statement the moment it finishes. This is called autocommit, and it is switched on:

SQL
SELECT @@autocommit;
Result
+--------------+
| @@autocommit |
+--------------+
|            1 |
+--------------+

1 means on. So far that has been fine. But once you start changing and deleting rows, you want a chance to look before you save.

A transaction is like a trial room

In a clothes shop, you take a few things into the trial room. You try them on and look in the mirror. Then you either buy them all, or you put them all back. Nothing is final until you reach the counter.

A transaction works the same way:

CommandWhat it doesIn the trial room
START TRANSACTIONStarts a group of changes. Nothing is saved yet.Walk into the trial room
COMMITSaves every change in the group for goodPay at the counter
ROLLBACKThrows away every change in the groupPut everything back on the rack

Try it: a sale that never happened

On Day 2 we said that when a customer buys 2 mice, several things must happen together: the stock goes down, and the sale is recorded. Let's do exactly that inside a transaction. Rohan (customer 3) buys 2 Wireless Mice:

Step 1: make the changes inside a transaction
START TRANSACTION;

UPDATE products SET stock_quantity = stock_quantity - 2
WHERE product_id = 1;

INSERT INTO orders (customer_id, order_date)
VALUES (3, '2024-06-20');
SET @new_order = LAST_INSERT_ID();

INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (@new_order, 1, 2, 799.00);

Two new things here:

  • We left out status, so the DEFAULT gives this new order 'Pending'.
  • LAST_INSERT_ID() means "the ID MySQL just gave out". The new order got an ID from AUTO_INCREMENT, and we need that same number for the order line. Instead of guessing it, we ask for it. Real apps do this all the time.
  • SET @new_order = ... saves that ID in a user variable. Think of it as a sticky note: MySQL keeps it for you until you disconnect, and you can use @new_order anywhere you'd type a value.

Now look in the mirror. Inside your transaction, you can see your own changes:

Step 2: check
SELECT product_name, stock_quantity FROM products WHERE product_id = 1;
SELECT * FROM orders WHERE order_id = @new_order;
Result
+----------------+----------------+
| product_name   | stock_quantity |
+----------------+----------------+
| Wireless Mouse |            148 |
+----------------+----------------+
+----------+-------------+------------+---------+
| order_id | customer_id | order_date | status  |
+----------+-------------+------------+---------+
|       16 |           3 | 2024-06-20 | Pending |
+----------+-------------+------------+---------+

Stock went from 150 to 148, and there is a new order 16, marked Pending. In a real shop, you would now run COMMIT. We want to keep our data unchanged, so put it all back:

Step 3: undo everything
ROLLBACK;

SELECT product_name, stock_quantity FROM products WHERE product_id = 1;
SELECT COUNT(*) FROM orders;
Result
+----------------+----------------+
| product_name   | stock_quantity |
+----------------+----------------+
| Wireless Mouse |            150 |
+----------------+----------------+
+----------+
| COUNT(*) |
+----------+
|       15 |
+----------+

Back to 150 mice and 15 orders, as if nothing happened. All three changes were undone together. This is the atomicity from Day 1's ACID: a group of changes either all happens, or none of it does. If the power went off halfway through, MySQL would also throw the half-done group away, so you never end up with stock taken but no sale recorded.

Going deeper: a few things worth knowing about transactions

  • Your changes are private until you commit. While your transaction is open, other people using the database still see the old data. Only after COMMIT do they see the new rows. (How private exactly is a setting called the isolation level. Day 19 covers it.)
  • Closing the connection without COMMIT rolls back. If your laptop dies mid-transaction, nothing half-done is saved.
  • Starting a new transaction saves the open one. If you run START TRANSACTION while a transaction is still open, MySQL quietly commits the open one first. So always finish one transaction with COMMIT or ROLLBACK before starting the next.
  • DDL ends a transaction. As you saw on Day 3, commands like CREATE, ALTER and DROP save everything first. So don't mix them into a transaction you might want to undo.
  • A ROLLBACK doesn't give back AUTO_INCREMENT numbers. Order 16 was handed out and thrown away, so the next new order will get 17. That's one more reason for the gaps you met on Day 3.
  • SAVEPOINT lets you undo part of a transaction. It's like a checkpoint in a video game. SAVEPOINT before_prices; marks the spot, and ROLLBACK TO SAVEPOINT before_prices; undoes only what came after it, while keeping the transaction open.

The rule for the rest of today: every change starts with START TRANSACTION; and ends with ROLLBACK;. That way you can run every example and your data stays exactly as loaded. If you ever forget, re-run the two checks in section 5. If they don't match, reset with complete_setup.sql.

7UPDATE: changing rows

UPDATE changes values in rows that already exist. It has three parts:

The shape of an UPDATE
UPDATE table_name
SET column = new_value
WHERE which_rows;

Read it as: "in this table, set this column to this value, but only for these rows." The WHERE part is the filter. It is the most important part of the whole statement, as you'll see in section 8.

Change one row

Order 5 (Ananya's) is Pending. The parcel has arrived, so mark it Completed:

SQL
START TRANSACTION;

UPDATE orders
SET status = 'Completed'
WHERE order_id = 5;
MySQL says
Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0

For an UPDATE, MySQL tells you two numbers. Rows matched is how many rows passed the WHERE filter. Changed is how many actually got a new value. Run the same UPDATE again, and you'll see the difference:

MySQL says, the second time
Query OK, 0 rows affected
Rows matched: 1  Changed: 0  Warnings: 0

The row matched, but it was already Completed, so nothing changed.

Change several columns at once

Separate them with commas after SET. Say the headphones get a price cut, and 20 more arrive in stock:

SQL
UPDATE products
SET price = 6999.00,
    stock_quantity = stock_quantity + 20
WHERE product_id = 4;

Notice stock_quantity = stock_quantity + 20. The new value can be worked out from the old one: "take what is there now and add 20". You don't need to know the current stock to write this.

Change many rows at once

The WHERE doesn't have to point to just one row. To raise the price of every book (category 2) by 10%:

SQL
UPDATE products
SET price = price * 1.10
WHERE category_id = 2;

SELECT product_name, price FROM products WHERE category_id = 2;
Result
+--------------------------+---------+
| product_name             | price   |
+--------------------------+---------+
| SQL Fundamentals         |  658.90 |
| Data Science Handbook    | 1318.90 |
| The Pragmatic Programmer |  988.90 |
+--------------------------+---------+

Three books, three new prices. Multiplying by 1.10 is the same as "add 10%".

The guard checks updates too

Every rule from Day 3 still applies. Try to set a negative price, or move a product into a category that doesn't exist:

SQL
UPDATE products SET price = -1 WHERE product_id = 1;
MySQL says
ERROR 3819 (HY000): Check constraint 'products_chk_1' is violated.
SQL
UPDATE products SET category_id = 9 WHERE product_id = 1;
MySQL says
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`online_store`.`products`, CONSTRAINT `products_ibfk_1` FOREIGN KEY (`category_id`) REFERENCES `categories` (`category_id`))

Both refused. Now undo this section's changes:

SQL
ROLLBACK;

Order 5 is Pending again, and every price is back to normal.

8The missing WHERE

Here is the single most common accident in SQL. Someone means to change one product's price, and forgets the WHERE:

SQL
START TRANSACTION;

UPDATE products SET price = 0;
MySQL says
Query OK, 15 rows affected
Rows matched: 15  Changed: 15  Warnings: 0

Every product in the shop is now free. No error, no warning, no "are you sure?". MySQL did exactly what it was told. (In Workbench you may get error 1175 instead. That's a safety lock, explained at the end of this section.) The same goes for DELETE FROM order_items;, which would wipe out every order line in the shop.

Luckily, you are inside a transaction:

SQL
ROLLBACK;

Without one, the only way back would be a backup. At work, this is how people end up having a very bad day.

Habits that save you

A carpenter's rule: measure twice, cut once. For SQL it looks like this:

  1. Write the WHERE first. Then go back and fill in the SET.
  2. Preview with SELECT. Before changing anything, run a SELECT with the same WHERE. The rows you see are the rows you'll change.
  3. Use a transaction for anything bigger than a one-row fix, and check the "rows affected" number before you commit. If you expected 1 and see 15, roll back.
Preview first, then change
-- 1. Preview: which rows will change?
SELECT product_id, product_name, price
FROM products
WHERE product_id = 14;

-- 2. Happy with what you see? Then change exactly those rows.
START TRANSACTION;
UPDATE products SET price = 899.00 WHERE product_id = 14;
ROLLBACK;   -- at work, COMMIT here

Safe update mode

MySQL Workbench switches on a safety lock called safe update mode by default. With it on, MySQL refuses an UPDATE or DELETE unless the WHERE uses a key column, like an ID:

MySQL says
ERROR 1175 (HY000): You are using safe update mode and you tried to update a table without a WHERE that uses a KEY column.

If you see this in Workbench, the lock is doing its job. Rewrite your WHERE to use the ID. If you really must, you can switch the lock off for your session with SET SQL_SAFE_UPDATES = 0;, but it is there to protect you, so think twice.

9DELETE: removing rows

DELETE removes whole rows. Its shape is the shortest of all, which is exactly why it is dangerous:

The shape of a DELETE
DELETE FROM table_name
WHERE which_rows;

There is no column list. You can't delete half a row. To empty one value, use UPDATE ... SET column = NULL instead.

The guard checks deletes too

Say the owner wants to remove Aarav from the customer list:

SQL
START TRANSACTION;

DELETE FROM customers WHERE customer_id = 1;
MySQL says
ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`online_store`.`orders`, CONSTRAINT `orders_ibfk_1` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`customer_id`))

Refused. Aarav has three orders, and deleting him would leave them pointing at nobody. This is the default foreign key behaviour from Day 3 (it works like RESTRICT) doing its job. Notice the words "parent row": customers is the parent, and orders is the child that depends on it.

Noah has no orders, so nothing depends on him:

SQL
DELETE FROM customers WHERE customer_id = 10;
MySQL says
Query OK, 1 row affected

Children first, then the parent

Now say order 7 (Diya's cancelled order) should be removed completely. The order has a line in order_items, so you have to remove the line first, then the order. It's the same reverse order you used for DROP on Day 3:

SQL
DELETE FROM order_items WHERE order_id = 7;
DELETE FROM orders      WHERE order_id = 7;
MySQL says
Query OK, 1 row affected
Query OK, 1 row affected

Put Noah and order 7 back:

SQL
ROLLBACK;

Going deeper: soft deletes

Many companies almost never delete important rows. Think of how an email app works: "delete" moves a message to the Bin, and you can still bring it back. A soft delete does the same thing in a database. The table gets an extra column, such as is_active or deleted_at, and "deleting" a row just means updating that column:

Read only: our tables don't have this column
UPDATE customers
SET is_active = FALSE
WHERE customer_id = 10;

The row stays, and so do all its orders, reviews and history. Why bother?

  • A real delete can't be undone once it is committed. A soft delete can.
  • Old reports stay correct. If you really deleted a customer, last year's sales would change.
  • There is a record of who was removed and when, which banks and hospitals are often required to keep.

The price: every query must now remember to skip the "deleted" rows, usually with WHERE is_active = TRUE. Forget it, and removed customers quietly show up in your reports. As an analyst, this is the part that matters to you. When you start on a new database, always ask: "Are there soft-deleted rows I should filter out?"

DELETE or TRUNCATE? You met TRUNCATE on Day 3. Use DELETE ... WHERE to remove chosen rows, inside a transaction if you want an undo button. Use TRUNCATE only to empty a whole table fast, knowing it can't be rolled back.

10Upserts: insert or update in one step

Think about saving a contact on your phone. If the number is new, the phone adds a new contact. If the number is already saved, it updates the existing contact. You don't have to check first.

Databases need the same thing all the time. Every night, the shop might receive a file of customer details from its website. Some customers are new and some already exist. A plain INSERT fails on the existing ones, because email is UNIQUE. What you want is: "insert this row, or if it already exists, update it." This is called an upsert (update + insert). MySQL writes it with ON DUPLICATE KEY UPDATE.

Aarav has moved from Jaipur to Bengaluru:

SQL
START TRANSACTION;

INSERT INTO customers (first_name, last_name, email, city, country, signup_date)
VALUES ('Aarav', 'Sharma', 'aarav.sharma@email.com', 'Bengaluru', 'India', '2023-01-15') AS new
ON DUPLICATE KEY UPDATE city = new.city;
MySQL says
Query OK, 2 rows affected

Read it in two halves:

  • The first half is a normal INSERT. AS new gives the incoming row a name, so we can point to its values.
  • ON DUPLICATE KEY UPDATE city = new.city says: "if this would break a UNIQUE or primary key rule, don't fail. Update the existing row's city to the new row's city instead."

Aarav's email already exists, so his row was updated, and he keeps his ID of 1. The odd "2 rows affected" is MySQL's usual way of saying "an existing row was updated". It reports 1 when a new row is added, and 0 when the row already had exactly these values. Run it a second time and you'll get 0.

The best part: you can run an upsert once or a hundred times and never get duplicates or errors. That's why most data import jobs are written this way.

An older form you'll see online. Before MySQL 8.0.19, upserts were written with city = VALUES(city) instead of AS new and new.city. It still works, but MySQL now gives a warning that it will be removed one day. Use the AS new form in new code.

11Loading data from files

Typing INSERT statements was fine for our 70 rows. Real data doesn't arrive that way. It arrives as a CSV file with 3 lakh rows, exported from some other system. You won't type that, and you shouldn't send it in as 3 lakh separate INSERTs either. You load the file.

LOAD DATA INFILE

Say you have a file called new_customers.csv that looks like this:

new_customers.csv
first_name,last_name,email,city,country,signup_date
Riya,Kapoor,riya.kapoor@email.com,Kolkata,India,2024-06-25
Arjun,Nair,arjun.nair@email.com,"Kochi, Kerala",India,2024-06-28
Lena,Fischer,lena.fischer@email.com,,Germany,2024-07-02

This one statement loads the whole file:

Read only: you don't have this file
LOAD DATA LOCAL INFILE 'new_customers.csv'
INTO TABLE customers
FIELDS TERMINATED BY ',' ENCLOSED BY '"'
LINES TERMINATED BY '\n'
IGNORE 1 ROWS
(first_name, last_name, email, @city, country, signup_date)
SET city = NULLIF(@city, '');
MySQL says
Query OK, 3 rows affected
Records: 3  Deleted: 0  Skipped: 0  Warnings: 0
LineWhat it means
LOCAL INFILE 'new_customers.csv'The file is on your computer, not on the database server
FIELDS TERMINATED BY ','Values are separated by commas
ENCLOSED BY '"'Some values are wrapped in quotes, like "Kochi, Kerala", which has a comma inside it
LINES TERMINATED BY '\n'Each row ends with a new line. (Files saved on Windows often use '\r\n' instead.)
IGNORE 1 ROWSSkip the first line, because it holds column names, not data

SET city = NULLIF(@city, '')Lena's city is empty in the file. This turns an empty value into a real NULL.

That last line deserves a second look. @city holds the city from the file for a moment. NULLIF(@city, '') means "if it is empty, use NULL, otherwise use the value". Without it, Lena would get an empty piece of text instead of a real NULL. That's the same kind of fake missing value as the 'NULL' trap in section 3.

On a big file, this is many times faster than one INSERT per row.

If you get an error. For safety, MySQL 8 switches off loading local files by default. You'll see this:

MySQL says
ERROR 3948 (42000): Loading local data is disabled; this must be enabled on both the client and server sides

The fix needs a setting on the server (local_infile) and one in your tool. That is usually set up by whoever runs the database, so on your own computer the easier path is below.

Easier ways you'll actually use

  • MySQL Workbench: right-click a table and choose Table Data Import Wizard. Pick the CSV, match the columns, and click through. No SQL needed.
  • Python: read the file with pandas and send it to MySQL in a few lines. You'll do this on Day 14.

Whichever way you load a file, run the same two checks as in section 5 afterwards: count the rows, and add up a number column. Files go wrong more often than you'd think.

Part A: a new customer's first order. Riya Kapoor from Kolkata, India signs up on 25 June 2024. On the same day she orders 1 Yoga Mat (product 14, ₹999) and 2 Ceramic Coffee Mugs (product 12, ₹349 each). Write the statements to:

  1. add Riya as a customer,
  2. add her order (leave the status to the default),
  3. add the two order lines,
  4. reduce the stock of both products.

Hint: you'll need Riya's new ID for the order, and the order's new ID for the lines. Save each one on a sticky note, the way section 6 did with SET @new_order = LAST_INSERT_ID();.

Part B: the owner's messages. Write one statement for each message, and say how many rows it should affect.

  1. "Kabir's order (order 11) has been delivered."
  2. "The Ceramic Coffee Mug is now ₹299."
  3. "50 more Resistance Bands Sets just arrived."
  4. "We've stopped selling the Non-Stick Frying Pan (product 13). Remove it."
  5. "Remove the Hooded Sweatshirt (product 10) too."
Show a sample answer

Part A.

SQL
START TRANSACTION;

-- 1. The customer
INSERT INTO customers (first_name, last_name, email, city, country, signup_date)
VALUES ('Riya', 'Kapoor', 'riya.kapoor@email.com', 'Kolkata', 'India', '2024-06-25');
SET @riya_id = LAST_INSERT_ID();

-- 2. The order (status will default to 'Pending')
INSERT INTO orders (customer_id, order_date)
VALUES (@riya_id, '2024-06-25');
SET @order_id = LAST_INSERT_ID();

-- 3. The two order lines
INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES
(@order_id, 14, 1, 999.00),
(@order_id, 12, 2, 349.00);

-- 4. The stock
UPDATE products SET stock_quantity = stock_quantity - 1 WHERE product_id = 14;
UPDATE products SET stock_quantity = stock_quantity - 2 WHERE product_id = 12;

-- Check
SELECT * FROM order_items WHERE order_id = @order_id;
SELECT product_name, stock_quantity FROM products WHERE product_id IN (12, 14);

ROLLBACK;
  • The order must come before its lines, and the customer before the order. It's the same parent-before-child order as always.
  • Stock should end at 129 Yoga Mats and 178 Mugs. Your ID numbers may be higher than you expect, because earlier rolled-back examples used some up. That's fine.
  • This is exactly the kind of change that belongs in one transaction. If any step fails, you don't want a customer with half an order, or stock taken for an order that doesn't exist.

Part B.

SQL
START TRANSACTION;

UPDATE orders SET status = 'Completed' WHERE order_id = 11;                      -- 1 row
UPDATE products SET price = 299 WHERE product_id = 12;                           -- 1 row
UPDATE products SET stock_quantity = stock_quantity + 50 WHERE product_id = 15;  -- 1 row
DELETE FROM products WHERE product_id = 13;                                      -- 1 row
DELETE FROM products WHERE product_id = 10;                                      -- fails!

ROLLBACK;

The first four work. The fifth fails with ERROR 1451, because the Hooded Sweatshirt appears in order 7, and order lines point to it. The Frying Pan was never ordered, so nothing stopped its delete.

What should you do about message 5? Not delete the order line, because that would change the shop's sales history. The better answer is to ask what the owner really means. They probably mean "stop selling it", and that is a soft delete: keep the product, and mark it as no longer for sale. Our table doesn't have a column for that yet, so this would be a good reason to add one with ALTER TABLE (Day 3). 🎯 Interview corner

DML questions often test whether you would be safe to trust with real data. Answer each one out loud before you open it, and add a small example when you can.

Concept questions

Q1What is DML? What does CRUD stand for?

DML (Data Manipulation Language) is the set of commands that work with the rows inside tables: INSERT adds rows, UPDATE changes them and DELETE removes them. CRUD stands for Create, Read, Update, Delete, the four basic actions on data. In SQL they map to INSERT, SELECT, UPDATE and DELETE.

Q2What happens if you run an UPDATE or DELETE without a WHERE clause? How do you protect yourself?

It affects every row in the table. UPDATE products SET price = 0; makes every product free, and DELETE FROM order_items; removes every order line in the shop. To protect yourself: write the WHERE first, preview the rows with a SELECT using the same WHERE, run the change inside a transaction and check the "rows affected" count before committing, and keep safe update mode on.

Q3What is a transaction? What do COMMIT and ROLLBACK do?

A transaction is a group of statements that is treated as one unit: either all of them are saved, or none are. START TRANSACTION begins it, COMMIT saves every change for good, and ROLLBACK throws them all away. The classic example is a bank transfer: taking money from one account and adding it to another must happen together, or not at all.

Q4What are the ACID properties?

Atomicity: all or nothing. Consistency: a transaction moves the database from one valid state to another, so no rules are broken. Isolation: transactions running at the same time don't see each other's half-finished work. Durability: once committed, the change survives a crash or power cut. In MySQL, the InnoDB engine provides all four.

Q5What is autocommit?

A setting that makes MySQL save every statement as soon as it finishes, as if each one were its own small transaction. It is on by default (SELECT @@autocommit; returns 1). START TRANSACTION pauses it until the next COMMIT or ROLLBACK.

Q6What is a SAVEPOINT?

A named checkpoint inside a transaction. ROLLBACK TO SAVEPOINT name undoes only the changes made after that point, and the transaction stays open. It is useful in a long transaction where you want to retry one step without throwing away the earlier work.

Q7What is an upsert? How do you write one in MySQL?

A single statement that inserts a row if it is new, or updates it if it already exists, based on a primary key or UNIQUE column. In MySQL: INSERT INTO t (...) VALUES (...) AS new ON DUPLICATE KEY UPDATE col = new.col;. It can be run again and again safely, which is why import jobs use it. (In PostgreSQL the same idea is written ON CONFLICT ... DO UPDATE, and many databases also have MERGE.)

Q8What is the difference between INSERT IGNORE, REPLACE and ON DUPLICATE KEY UPDATE?

When a row would break a unique rule: INSERT IGNORE skips it with a warning, REPLACE deletes the old row and inserts the new one, and ON DUPLICATE KEY UPDATE updates the existing row in place. REPLACE is the riskiest. Because it really deletes, it can be blocked by foreign keys, it fires delete triggers, and any column you don't supply goes back to its default.

Q9What is a soft delete? When would you use one?

Instead of removing a row, you mark it as deleted with a column like is_active or deleted_at. The row and everything linked to it stay, so you can undo the delete, old reports stay correct, and there is a record of what was removed. Use it for important records like customers, products and payments. The cost is that every query must filter out the "deleted" rows.

Q10Why might DELETE FROM customers WHERE customer_id = 1 fail?

Because other rows depend on it. If orders has a foreign key to customers and customer 1 has orders, MySQL refuses with error 1451 ("cannot delete or update a parent row"), to keep referential integrity. To remove the customer, you'd first deal with the child rows, or use ON DELETE CASCADE if that's really what the business wants. Often the right answer is a soft delete instead.

Q11How would you load a large CSV file into a MySQL table?

With LOAD DATA [LOCAL] INFILE, which reads the whole file in one statement and is much faster than many INSERTs. You tell it the separator, the quote character, to skip the header row, and which columns the values go into. Other options are the Table Data Import Wizard in Workbench, or pandas in Python. Either way, check row counts and totals after loading.

Practical questions

P1Raise the price of every Electronics product (category 1) that costs less than ₹2,000 by 5%.
SQL
START TRANSACTION;

UPDATE products
SET price = price * 1.05
WHERE category_id = 1
  AND price < 2000;

ROLLBACK;
MySQL says
Query OK, 2 rows affected
Rows matched: 2  Changed: 2  Warnings: 0

The Wireless Mouse becomes ₹838.95 and the USB-C Hub ₹1,363.95. The keyboard and headphones cost more than ₹2,000, so they don't change. AND means both conditions must be true. You'll learn it properly tomorrow.

P2Remove both cancelled orders (orders 7 and 14) completely.
SQL
START TRANSACTION;

DELETE FROM order_items WHERE order_id IN (7, 14);   -- children first: 2 rows
DELETE FROM orders      WHERE order_id IN (7, 14);   -- then the parents: 2 rows

ROLLBACK;   -- or COMMIT if you really mean it

IN (7, 14) means "order_id is 7 or 14". The order lines have to go first, or the foreign key blocks the second delete. A strong answer also asks: "Should we really delete cancelled orders? The cancellation rate is useful data. Maybe we keep them and filter them out in reports instead."

P3Write the SQL to move ₹5,000 from account 101 to account 202, so that it can never half-happen.
SQL
START TRANSACTION;

UPDATE accounts SET balance = balance - 5000 WHERE account_id = 101;
UPDATE accounts SET balance = balance + 5000 WHERE account_id = 202;

COMMIT;

Both updates sit in one transaction, so either both happen or neither does. If anything goes wrong between them, a ROLLBACK (or a crash) undoes the first one. A good follow-up point: check that account 101 has at least ₹5,000 first, for example with a CHECK (balance >= 0) rule on the table, so the first update fails if the money isn't there.

Quick recap

  • DML works on rows: INSERT adds, UPDATE changes, DELETE removes. With SELECT, they make up CRUD.
  • INSERT: list the columns, leave out the ID, quote text and dates, write NULL without quotes. Add many rows in one statement.
  • Fill tables parent first, child last, the same order you built them in.
  • Check every load: count the rows (5, 10, 15, 15, 25) and add up a number column (₹48,463).
  • A transaction groups changes: START TRANSACTION, then COMMIT to save or ROLLBACK to undo. Autocommit saves everything else at once.
  • UPDATE ... SET ... WHERE and DELETE FROM ... WHERE. A missing WHERE hits every row. Preview with SELECT first.
  • Foreign keys block deletes that would leave orphans. Delete children before parents, or use a soft delete.
  • An upsert (ON DUPLICATE KEY UPDATE) inserts or updates in one safe step. LOAD DATA INFILE loads files fast.
